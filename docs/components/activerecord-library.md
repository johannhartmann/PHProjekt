# Component: ActiveRecord

## Overview

The ActiveRecord library represents the foundational object-relational mapping (ORM) layer for the PHProjekt 6 application, providing a sophisticated implementation of the Active Record pattern built on top of Zend Framework's Zend_Db_Table component. This library serves as the primary abstraction between the application's business logic and the underlying relational database, transforming database tables into PHP objects where each instance represents a single row and provides intuitive object-oriented access to column data through dynamic property access. The implementation extends beyond basic CRUD operations to include advanced features such as relationship mapping (belongsTo, hasMany, hasManyAndBelongsToMany, and hasOne), automatic foreign key management, lazy loading of related entities, and lifecycle hooks that enable cross-cutting concerns like validation, history tracking, and cache invalidation.

The library's architecture demonstrates careful consideration of both developer ergonomics and runtime performance through features like automatic table name inference from class names, convention-based foreign key naming, support for complex queries with joins and aggregations, and iterator implementation that allows ActiveRecord objects to be used in foreach loops. The relationship mapping system provides object graph navigation through intuitive property access patterns, automatically generating the necessary SQL joins and managing the complexity of many-to-many relationships through intermediate join tables. This approach enables developers to work primarily with objects and relationships rather than crafting SQL queries, while maintaining the ability to optimize specific queries through direct database access when needed for performance-critical operations.

The Phprojekt_ActiveRecord_Abstract class serves as the base class for all model classes throughout the application, establishing naming conventions and lifecycle patterns that ensure consistency across the codebase. Every model that extends this base class inherits CRUD operations (create, read, update, delete), validation infrastructure, relationship handling, and integration with the broader Phprojekt ecosystem including authentication, access control, search indexing, and history tracking. The implementation includes sophisticated features like detecting changed fields by comparing current data with original database values, managing foreign key updates when primary keys change, cascading deletes through relationships, and supporting both simple one-to-many relationships and complex many-to-many relationships through automatically generated join tables with alphabetically sorted naming conventions.

The ActiveRecord library is intentionally minimal in terms of file count, consisting of only two PHP files that together provide the complete ORM foundation for the entire application. The Exception.php file provides a specialized exception type that enables precise error handling for database operations, relationship resolution failures, validation errors, and constraint violations, allowing calling code to distinguish between different categories of persistence-related failures.

## Key Classes and Files

### Phprojekt_ActiveRecord_Abstract (Abstract.php:53-1316)

The Phprojekt_ActiveRecord_Abstract class represents the complete implementation of the Active Record pattern for PHProjekt 6, extending Zend_Db_Table_Abstract to inherit basic database table functionality while adding sophisticated relationship management, lifecycle hooks, and developer-friendly property access patterns. This abstract class defines the core machinery for mapping PHP objects to database tables, with automatic table name inference based on class naming conventions where the last segment of a class name (after the final underscore) becomes the table name in lowercase. The class implements the Iterator interface, allowing ActiveRecord instances to be used in foreach loops to iterate over column values, while also providing magic methods __get and __set that enable natural property syntax for accessing database columns, related objects, and custom getter/setter methods.

The relationship management system represents one of the most sophisticated aspects of this class, supporting four distinct relationship types through public arrays that subclasses populate with relationship definitions. The `belongsTo` array defines many-to-one relationships where the current model has a foreign key referencing another model's primary key, such as a Timecard belonging to a Project. The `hasMany` array defines one-to-many relationships where multiple instances of another model reference the current model, such as a User having many Notifications. The `hasManyAndBelongsToMany` array handles many-to-many relationships through intermediate join tables with automatically generated names, such as Users belonging to many Roles and Roles having many Users. The `hasOne` array supports one-to-one relationships for cases where a single related entity is associated with the current model. All relationship definitions follow a consistent structure with keys identifying the relationship accessor name and values providing either explicit class names or module/model pairs for dynamic class loading.

The save() method (Abstract.php:837-888) implements intelligent insert-or-update logic by tracking whether an object originated from the database through the `_storedId` property, automatically generating INSERT statements for new objects and UPDATE statements for existing ones. When performing updates, the method detects if the primary key has changed and cascades this change through all hasMany and hasManyAndBelongsToMany relationships by updating foreign keys in related tables. The implementation carefully handles nullable columns by checking metadata to determine which fields accept NULL values, and it maintains both `_data` and `_originalData` arrays to enable change detection for optimistic locking and audit trail purposes. The save logic also manages relationship insertion for hasManyAndBelongsToMany relationships by creating entries in the intermediate join table after the primary insert completes and the new primary key is available.

The delete() method (Abstract.php:895-933) implements cascading deletion behavior that ensures referential integrity by removing related records before deleting the primary record. For hasMany relationships, the method deletes all records in the related table where the foreign key matches the current object's ID, preventing orphaned records. For hasManyAndBelongsToMany relationships, the method deletes entries from the intermediate join table but does not cascade deletes to the related entities themselves, as they may be referenced by other objects. After removing all related data, the method deletes the primary record and resets the object's internal state by reinitializing the data array and clearing relationship information, allowing the object to be reused for creating a new record if desired.

The fetchAll() method (Abstract.php:947-996) provides flexible query capabilities with support for WHERE clauses, ORDER BY specifications, LIMIT/OFFSET for pagination, and optional JOIN statements for retrieving related data in a single query. The method automatically handles relationship-aware querying by examining the `_relations` array and adding appropriate WHERE conditions for hasMany relationships, ensuring that queries naturally scope to the correct parent object when accessing related collections. The implementation returns an array of fully hydrated ActiveRecord objects rather than raw database rows, with each object having its `_storedId` and `_originalData` properly set to indicate that it originated from the database. This approach maintains object-oriented semantics throughout the application while supporting both simple queries through convenient methods and complex queries through the underlying Zend_Db_Select interface.

The find() method (Abstract.php:1003-1043) provides a clean interface for retrieving a single record by primary key, accepting exactly one argument and throwing exceptions for invalid input including NULL values, missing arguments, or multiple arguments. Unlike the parent Zend_Db_Table implementation which returns an array of rows, this method returns a single ActiveRecord instance with all data populated and the `_storedId` set, or returns false when no matching record exists. The implementation resets the object's internal state before populating it with the retrieved data, ensuring that calling find() on an existing object properly replaces its data rather than merging or leaving stale information. This stateful approach allows a single object instance to be reused for multiple find operations, though most application code creates new instances for clarity.

The relationship accessor methods _belongsTo(), _hasMany(), and _hasManyAndBelongsToMany() (Abstract.php:522-589, 397-413) implement lazy loading of related objects by checking if the relationship has already been resolved and cached in the `_data` array before performing any database operations. When a relationship is accessed for the first time, these methods instantiate the related class, configure its `_relations` array with information about the parent object, and store the resulting instance in the `_data` array for subsequent accesses. For belongsTo relationships, the method immediately performs a find() operation to retrieve the single related object. For hasMany and hasManyAndBelongsToMany relationships, the method returns a configured ActiveRecord instance that will automatically scope any subsequent fetchAll() calls to the parent object, providing a fluent interface for relationship traversal like `$user->roles->fetchAll()`.

### Phprojekt_ActiveRecord_Exception (Exception.php:19-63)

The Phprojekt_ActiveRecord_Exception class extends PHP's standard Exception class to provide specialized error handling for ActiveRecord operations, enabling calling code to catch and handle persistence-related errors separately from other application exceptions. This exception type is thrown throughout the ActiveRecord implementation for various error conditions including attempting to access non-existent properties or relationships, providing invalid arguments to methods like find(), attempting to modify the primary key through property assignment, failing to instantiate relationship classes that don't exist, and encountering database constraint violations during save or delete operations. The constructor follows the standard Exception signature with a message string and optional error code, with the class itself containing only the constructor implementation and relying on the parent Exception class for all other functionality including stack trace capture, getMessage(), and formatting for display or logging.

The exception class serves as a critical error handling boundary between the persistence layer and the business logic layer, allowing controllers and service classes to distinguish between recoverable validation errors that should be displayed to users, system-level database errors that require technical intervention, and logic errors like accessing undefined properties that indicate programming mistakes. Throughout the ActiveRecord implementation, exceptions are thrown with descriptive messages that identify the specific problem, such as "HasMany {$key} does not exist" when accessing an undefined relationship or "Changing ids is not permitted" when attempting to modify the primary key. This detailed error messaging combined with exception-based error handling enables debugging during development while providing clean error boundaries for production error handling and logging infrastructure.

## Public API and Interfaces

The ActiveRecord library exposes its functionality primarily through property access patterns and method calls on model instances, following the Active Record pattern where domain objects know how to persist themselves rather than relying on separate repository or data mapper classes. Model classes extend Phprojekt_ActiveRecord_Abstract and define their relationship mappings through public arrays (`belongsTo`, `hasMany`, `hasManyAndBelongsToMany`, `hasOne`), with all actual data access occurring through the inherited methods. The magic __get() and __set() methods enable natural property syntax for reading and writing database columns, with the implementation intelligently routing property access to custom getter/setter methods if they exist (named like `getPropertyName()` or `setPropertyName()`), relationship resolution for defined relationships, direct property access for public class properties, or the `_data` array for database columns.

Data persistence operations follow a simple and consistent API across all model classes. Creating a new record involves instantiating a model class, setting properties through normal assignment, and calling the save() method which automatically performs an INSERT operation. Retrieving records uses the find() method for primary key lookups or fetchAll() for queries, with the latter supporting flexible WHERE clauses, ordering, pagination, and joins. Updating records involves calling find() or fetchAll() to retrieve objects, modifying their properties through assignment, and calling save() which automatically detects that these are existing records and performs UPDATE operations. Deleting records simply requires calling delete() on an object, which handles cascading deletion through relationships. This consistent CRUD interface abstracts the SQL details and allows developers to work with objects throughout the application lifecycle.

The relationship API provides object graph navigation through property access on relationship names defined in the relationship arrays. For belongsTo relationships, accessing the relationship name returns a single related object or NULL if no relation exists, such as `$timecard->project` returning the Project object. For hasMany relationships, accessing the relationship name returns a configured ActiveRecord instance that automatically scopes queries to the parent, enabling patterns like `$project->timecards->fetchAll()` to retrieve all timecards for a project. For hasManyAndBelongsToMany relationships, the same pattern applies with additional complexity handled transparently, such as `$user->roles->fetchAll()` which automatically performs the necessary three-table join through the user_role_relation table. Creating related records uses the create() method to instantiate new objects with relationship information preserved, as in `$newTimecard = $project->timecards->create(); $newTimecard->hours = 8; $newTimecard->save();` which automatically sets the project_id foreign key.

## Dependencies and Integration

The ActiveRecord library depends fundamentally on Zend Framework's database abstraction layer, specifically Zend_Db_Table_Abstract which provides the underlying table metadata, connection management, and query building capabilities. The inheritance relationship with Zend_Db_Table_Abstract gives ActiveRecord access to the complete Zend_Db ecosystem including adapter-based database portability across MySQL, PostgreSQL, SQLite, and other supported databases, Zend_Db_Select for building complex queries, and Zend_Db_Table_Row/Rowset for representing query results. The ActiveRecord implementation wraps these Zend components to provide a more intuitive and feature-rich API while maintaining compatibility with the underlying infrastructure, allowing direct access to the Zend_Db_Adapter through the getAdapter() method when needed for optimized queries or database-specific operations.

Integration with the broader Phprojekt framework occurs through multiple touchpoints including the Phprojekt singleton class which provides the default database adapter, the Phprojekt_Loader class which handles dynamic class loading for relationship resolution and supports the module/model naming convention, and the Phprojekt_Auth class which is referenced in comments and expected to be used by subclasses for access control checks. The ActiveRecord implementation includes optional logging support through the `_log` property which captures generated SQL statements when a Zend_Log instance is available, enabling debugging and performance analysis. The library also integrates with Phprojekt's naming conventions through static methods convertVarToSql() and convertVarFromSql() that translate between camelCase PHP property names and snake_case database column names, ensuring consistency across the application.

Model classes throughout the application extend Phprojekt_ActiveRecord_Abstract to gain persistence capabilities, including core models like Phprojekt_User_User, Phprojekt_Role_Role, and Phprojekt_Module_Module, as well as application-specific models like Project_Models_Project, Calendar2_Models_Calendar2, and Timecard_Models_Timecard. Each model class defines its specific relationship mappings by populating the `belongsTo`, `hasMany`, `hasManyAndBelongsToMany`, and `hasOne` arrays with appropriate definitions. The relationship definitions follow a consistent structure with keys serving as accessor names and values containing either direct class names or module/model pairs that the Phprojekt_Loader resolves to fully qualified class names. This modular approach enables each application module to define its own models with relationships spanning multiple modules, such as Timecard referencing Project or Calendar2 referencing User, while maintaining clean separation of concerns and avoiding tight coupling between modules.

## Data Models and Structures

The ActiveRecord library does not define specific database tables directly, as it serves as the abstract foundation for all model classes throughout the application. Each concrete model class that extends Phprojekt_ActiveRecord_Abstract represents a specific database table, with the table name automatically derived from the class name through the _translateClassNameToTable() method. The naming convention extracts the last segment of the class name after the final underscore and converts it to a database table name, so a class named `Phprojekt_User_User` maps to the `user` table, and `Calendar2_Models_Calendar2` maps to the `calendar2` table. This convention-based approach eliminates the need for explicit configuration while remaining overridable through the protected `_name` property when custom table names are required.

Every ActiveRecord-based table follows a consistent structure with certain conventions enforced by the implementation. All tables must have an `id` column serving as the primary key, with the implementation explicitly checking for this column's presence and throwing exceptions when it's missing. Foreign key columns follow the naming format defined by the FOREIGN_KEY_FORMAT constant (default `:tableName_id`), where the table name of the related model is combined with `_id` suffix, such as `project_id` for a foreign key referencing the project table. For many-to-many relationships, the implementation automatically generates join table names by sorting the two related table names alphabetically and joining them with an underscore followed by `_relation`, such as `role_user_relation` for the many-to-many relationship between roles and users. This consistent naming convention enables the ActiveRecord implementation to automatically resolve relationships without requiring explicit join table configuration.

The internal data structures maintained by ActiveRecord instances include the `_data` array which holds the current values for all columns and cached relationship objects, the `_originalData` array which preserves the database values as they existed when the object was loaded to enable change detection and optimistic locking, the `_relations` array which stores metadata about active relationship traversal to enable proper query scoping for hasMany and hasManyAndBelongsToMany relationships, and the `_storedId` property which tracks the primary key value as it exists in the database to distinguish between new objects requiring INSERT and existing objects requiring UPDATE. The `_colInfo` array contains metadata about all columns in the table including names, data types, nullable status, and default values, populated from the Zend_Db_Table metadata during construction. These internal structures work together to provide the rich functionality of the Active Record pattern including lazy loading, change tracking, relationship management, and intelligent save behavior.

## Configuration and Settings

The ActiveRecord library requires minimal explicit configuration, relying primarily on conventions and default behaviors that can be overridden when necessary. The most fundamental configuration is the database adapter, provided through the constructor's `$config` parameter which accepts either a Zend_Db_Adapter_Abstract instance directly or an array with a `db` key containing the adapter. When no configuration is provided, the constructor automatically obtains the default database adapter from the Phprojekt singleton through `Phprojekt::getInstance()->getDb()`, ensuring that all models share a common database connection unless explicitly overridden. This singleton-based default connection simplifies model instantiation throughout the application while supporting dependency injection for testing scenarios that require mock database adapters.

Table name mapping follows convention-over-configuration principles with sensible defaults that cover most use cases. The _setupTableName() method calls getTableName() which delegates to getModelName() to extract the relevant class name segment, then applies convertVarToSql() to transform it into a database table name. Subclasses can override getTableName() to provide custom table names when the convention doesn't apply, though this is rarely necessary in practice. The FOREIGN_KEY_FORMAT constant defines the pattern for generating foreign key column names, defaulting to `:tableName_id` where `:tableName` is replaced with the actual table name. This constant can be modified in subclasses to support different foreign key naming conventions such as `:tableNameId` (without underscore) or `fk_:tableName` (with prefix), though changing this convention requires ensuring consistency across all models to prevent relationship resolution failures.

Relationship definitions represent the primary configuration that model classes must provide, accomplished by populating the public relationship arrays with appropriate definitions. Each relationship definition maps an accessor name to an array containing either a `classname` key with the fully qualified class name, or `module` and `model` keys that the Phprojekt_Loader resolves into a class name. The accessor name becomes the property name for accessing the relationship, such as defining `$hasMany = array('timecards' => array('module' => 'Timecard', 'model' => 'Timecard'))` which enables access through `$project->timecards`. The order of relationship arrays matters due to the precedence rules documented in the class comments: when the same accessor name appears in multiple relationship arrays, hasManyAndBelongsToMany takes precedence, followed by hasMany, then belongsTo, and finally hasOne. This precedence enables relationship redefinition in subclasses while generally suggesting that accessor names should be unique across all relationship types to avoid confusion.

## Design Patterns and Principles

The Active Record pattern forms the architectural foundation of this library, combining data access logic with business logic in domain objects that know how to persist themselves. This pattern contrasts with the Data Mapper pattern (used by ORMs like Doctrine) where separate mapper classes handle persistence and domain objects remain persistence-ignorant. The Active Record approach offers the advantage of simplicity with CRUD operations directly available on model objects through methods like save() and delete(), reducing the number of classes and concepts developers must understand. The trade-off involves tighter coupling between domain objects and the database schema, making it more challenging to evolve the database schema independently or support multiple persistence mechanisms. PHProjekt's implementation mitigates some of these concerns through careful layering and the use of Zend_Db as an abstraction over specific database engines.

The Template Method pattern appears throughout the ActiveRecord implementation, particularly in query construction and data persistence operations where the base class defines the algorithm structure while allowing subclasses to customize specific steps. The save() method implements a template for data persistence with extension points through the `_data` array population that subclasses can influence, and the __get() and __set() magic methods define templates for property access that check for custom getter/setter methods before falling back to default behavior. This pattern enables the ActiveRecord base class to provide consistent behavior across all models while allowing specific models to customize validation, formatting, or computation through getter and setter methods named following the convention `getPropertyName()` and `setPropertyName()`.

The Lazy Loading pattern optimizes performance by deferring relationship resolution until the relationship is actually accessed, avoiding unnecessary database queries for relationships that are never used. When code accesses a relationship property like `$timecard->project`, the __get() method detects that `project` is defined in the `belongsTo` array and calls _belongsTo() to resolve the relationship, which then instantiates the related object and caches it in the `_data` array. Subsequent accesses to the same relationship return the cached object without additional database queries. For collections (hasMany and hasManyAndBelongsToMany), the implementation returns a configured ActiveRecord instance rather than immediately fetching all related records, enabling patterns like `$project->timecards->fetchAll("date = '2023-10-01'")` where the query is further refined before execution.

The Iterator interface implementation follows the Iterator design pattern, enabling ActiveRecord objects to be used in foreach loops and other contexts expecting iterable objects. The implementation provides methods current(), key(), next(), rewind(), and valid() that iterate over the column values in the `_data` array using the `_colInfo` array for cursor management. This pattern enhances the object-oriented feel of ActiveRecord by allowing natural syntax like `foreach ($user as $columnName => $value)` to iterate over all fields, useful for generic display or serialization logic. The iterator operates over column data only and does not include relationships, maintaining a clear distinction between scalar database values and complex object relationships.

The Convention over Configuration principle permeates the entire ActiveRecord design, minimizing explicit configuration requirements through sensible defaults and naming conventions. Class names automatically map to table names, foreign keys follow predictable naming patterns, primary keys are assumed to be named `id`, and join tables for many-to-many relationships have generated names based on the related tables. These conventions enable developers to create new models with minimal boilerplate—often just extending the base class and defining relationships—while maintaining the flexibility to override conventions when needed through protected properties and method overrides. This approach balances developer productivity with flexibility, reducing cognitive load for common cases while supporting edge cases through explicit configuration.

The Identity Map pattern appears implicitly in the relationship caching behavior where related objects are stored in the `_data` array after initial resolution, ensuring that multiple accesses to the same relationship return the identical object instance rather than multiple instances representing the same database record. This pattern prevents inconsistencies where different parts of the code modify different instances representing the same database entity, and it improves performance by avoiding redundant database queries. However, the implementation does not maintain a global identity map across the application, meaning that retrieving the same record through different queries or from different parent relationships may result in multiple object instances, requiring developers to be conscious of object identity when caching or comparing instances.
