# Component: DatabaseManager

## Overview

The DatabaseManager library provides dynamic metadata management for PHProjekt 6, implementing a database-driven approach to field definitions where form structures, validation rules, display properties, and data types are stored in a database table rather than hardcoded in model classes. This library serves as the metadata repository for PHProjekt's Module Designer feature, which enables administrators to create custom modules with user-defined fields through a web interface without writing code. The DatabaseManager stores comprehensive field metadata including table structure (field names, data types, lengths), form presentation (labels, hints, positions, tabs, required flags), list display (positions, filter usage), validation rules (ranges, regular expressions, default values), and UI widget types (text, selectbox, date, etc.), providing a complete description of how fields should be stored, validated, and presented.

The library architecture implements a dual-role design where Phprojekt_DatabaseManager extends Phprojekt_ActiveRecord_Abstract to provide persistence operations for metadata records while also implementing Phprojekt_ModelInformation_Interface to serve as a metadata provider for dynamically created modules. This dual nature enables the DatabaseManager to be both a model that manages its own database table (database_manager) and a metadata source that other models query to determine their field structures. The implementation includes sophisticated caching to avoid repeated database queries when the same field definitions are accessed multiple times within a request, storing fetched field definitions in the _dbFields array indexed by ordering type (form, list, filter).

The field definition conversion system implements format translation between the database storage format and the application's runtime field definition format, handling special field types like selectboxes that require range data, upload fields that need special processing, and display fields that may reference other models. The _convertSelect() and _convertStandard() methods transform database records into standardized field definition arrays with consistent keys (key, label, type, hint, range, required, readOnly, etc.) that form generation and validation systems consume throughout the application. The conversion includes language translation of labels and range values, retrieving translated strings from the translation system based on the current user's language preference.

The validation system implements comprehensive field definition validation through the recordValidate() method, which checks module structure integrity including presence of required fields, uniqueness of field names, valid data types and lengths, proper range definitions for selectboxes, presence of project_id field for project-scoped modules, and presence of at least one list-displayable field. The validation accumulates errors in a Phprojekt_Error object with structured error messages suitable for display in UI forms, enabling the Module Designer interface to provide immediate feedback when administrators create invalid module structures. The synchronization system in syncTable() implements schema evolution by comparing old and new field definitions to generate ALTER TABLE operations, supporting the Module Designer's ability to modify existing modules without losing data.

The DatabaseManager library follows a minimal organizational structure with the primary functionality concentrated in the main class that extends ActiveRecord for persistence while implementing ModelInformation_Interface for metadata provision. The DatabaseManager/Field.php class provides a value object pattern that combines field values with their metadata, enabling enhanced property access where code can retrieve both the value and metadata attributes (like type, label, required) through a single object. This two-class structure demonstrates focused design where the main class handles complex operations including retrieval, conversion, validation, and synchronization, while the field class provides a simple wrapper for unified value+metadata access.

## Key Classes and Files

### Phprojekt_DatabaseManager (DatabaseManager.php:42-1007)

The Phprojekt_DatabaseManager class serves as both an ActiveRecord model for the database_manager table and a metadata provider implementing Phprojekt_ModelInformation_Interface, enabling it to manage its own persistence while providing field definitions for other models. The class maintains several protected properties including _dbFields for caching retrieved field definitions indexed by ordering type, _model for the associated domain model, _modelInfo for database table metadata, _moduleName for the cached module name, _fieldTypes for a map of field names to types, and _error for validation error accumulation. The class defines column name constants COLUMN_NAME and COLUMN_TITLE for database field names, and a _mapping array that translates ordering constants to database column names.

The constructor (DatabaseManager.php:115-122) initializes the DatabaseManager by calling parent::__construct() to set up ActiveRecord functionality, storing the provided model reference, and extracting model info through $model->info() when a model is present. This initialization establishes the association between DatabaseManager and a specific model, enabling subsequent operations to query and manipulate that model's field definitions. The acceptance of a model parameter enables the DatabaseManager to work with any model implementing Phprojekt_Item_Abstract, supporting both standard PHProjekt modules and custom modules created through the Module Designer.

The _getFields() method (DatabaseManager.php:164-191) implements cached field retrieval by first checking if the requested order's fields are cached in _dbFields array, returning cached data immediately when available to avoid redundant database queries, and when not cached constructing a WHERE clause that filters by table_name and the ordering column (form_position, list_position, or list_use_filter), optionally filtering for status = 1 to exclude inactive fields, fetching all matching records sorted by the ordering column, and caching the results before returning. This caching strategy optimizes performance when the same ordering is requested multiple times within a request, common in workflows that render both forms and lists of the same model type.

The getFieldDefinition() method (DatabaseManager.php:253-294) implements comprehensive field definition retrieval by calling _getFields() to retrieve raw database records, iterating over each field to determine its formType, delegating to _convertSelect() for selectValues and multipleSelectValues types to handle range parsing, delegating to _convertSelect() or _convertStandard() for display types depending on whether formRange is populated, delegating to _convertStandard() for upload types with explicit type override, and delegating to _convertStandard() for all other types. This dispatch logic handles the diversity of field types in PHProjekt, ensuring that each type receives appropriate conversion including range data for selectboxes, metadata preservation for displays, and proper type designation for uploads.

The _convertSelect() method (DatabaseManager.php:303-327) implements selectbox field conversion by calling _convertStandard() to populate base field properties, initializing an empty range array for option storage, checking if formRange contains pipe characters indicating static range data, and for static ranges parsing the formRange string which uses "|" to separate options and "#" to separate keys from values (like "1#Open|2#Closed|3#Done"), translating each value through Phprojekt::getInstance()->translate() for localization, and building an array of range entries with id, name (translated), and originalName (untranslated). For non-static ranges (without pipe characters), the method delegates to getRangeFromModel() which loads range data from related models, supporting dynamic selectboxes that populate from database tables like User or Project.

The _convertStandard() method (DatabaseManager.php:339-366) implements base field conversion by extracting the field name and converting from SQL snake_case to PHP camelCase, retrieving the module name for translation context, constructing the field definition array with key, label (translated), originalLabel (untranslated), type, hint (retrieved from tooltip system), listPosition, formPosition, empty fieldset, placeholder range structure, required flag, readOnly flag (defaulted to false), tab number, integer flag, and length extracted from model metadata with fallback to 0, and default value. This method provides the foundation for all field conversions, with specialized converters like _convertSelect() extending this base with additional properties appropriate to their field types.

The getRangeFromModel() method (DatabaseManager.php:432-471) implements dynamic range loading from related models by parsing formRange as "Module#keyField#displayField" format, extracting module name, key field, and value field through explode('#'), and dispatching based on module type. For Project modules, the method instantiates a Project model, sets up a tree structure, iterates over nodes, and builds options using getDepthDisplay() to indent based on hierarchy level. For User modules, the method calls getAllowedUsers() to retrieve users with permission filtering, prepending an empty option when field is not required. For other modules, the method attempts to call a custom getRangeFromModel() method on the target model, falling back to fetchAll() with _setRangeValues() for formatting. This extensible design supports built-in module types with special handling while providing a default implementation for custom modules.

The recordValidate() method (DatabaseManager.php:481-686) implements comprehensive module structure validation by checking for empty data (modules must have at least one field), validating module name presence and format (must start with letter), iterating over fields to validate tableLength, tableField, tableType, and formType presence, checking for field name uniqueness by accumulating found names, checking for question marks in field names (reserved character), validating varchar length between 1 and 255, validating int length between 1 and 11, validating selectbox formRange format for both static ranges (key#value pairs) and model references (Module#key#value), checking for project_id field presence in non-global modules, and checking for at least one field with list_position > 0. The method accumulates errors in _error object with structured messages suitable for UI display, returning boolean success/failure.

The saveData() method (DatabaseManager.php:709-745) implements metadata persistence by deleting all existing records for the table through fetchAll() and delete() in a loop, iterating over the provided data array to create new records, cloning the DatabaseManager for each field to create independent objects, populating each cloned object with field values after applying special handling for formRegexp/formRange/defaultValue (converting empty to null), isInteger (setting to 1 for int table types), and tableField (converting through convertTableField()), setting tableName on each record, and calling save() to persist. This replace-all approach simplifies logic by avoiding complex diff operations, though it requires careful transaction handling to avoid leaving the database in inconsistent state if errors occur mid-process.

The syncTable() method (DatabaseManager.php:812-894) implements schema synchronization by retrieving old field definitions through getDataDefinition(), clearing metadata cache to force reload of table structure, retrieving table manager for DDL operations, iterating over old fields to find matches in new fields by ID, calling modifyField() when field name unchanged, calling changeField() when field name changed (to preserve data during rename), calling deleteField() when no match found (field was removed), and iterating over new fields with ID = 0 to call addField() for newly added fields. This differential synchronization enables the Module Designer to evolve module schemas without losing existing data, supporting field additions, modifications, and deletions while protecting system fields (id, owner_id, project_id) from modification.

The deleteModule() method (DatabaseManager.php:901-914) implements module deletion by fetching all metadata records for the module, deleting each record through ActiveRecord delete(), instantiating a Phprojekt_Table object, and calling dropTable() to remove the module's database table. This two-phase deletion (metadata then table) ensures clean removal of dynamically created modules, though the lack of transaction wrapping means partial failures could leave the database in inconsistent state where metadata is deleted but table remains or vice versa.

### Phprojekt_DatabaseManager_Field (DatabaseManager/Field.php:19-97)

The Phprojekt_DatabaseManager_Field class provides a lightweight wrapper that combines a field value with its metadata, enabling unified access to both value and metadata properties through a single object. The class contains protected _metadata property storing the Phprojekt_DatabaseManager record and public value property storing the field's value. The constructor accepts a DatabaseManager instance, field name, and optional value, calling $dbm->find($name) to retrieve the metadata record and storing the string-cast value. This initialization creates a self-contained field object that knows both its value and its metadata properties like type, label, and validation rules.

The __get() method (Field.php:57-65) implements property access proxying by converting the requested property name from PHP camelCase to SQL snake_case, checking if the metadata record has the property, and returning the metadata property value when present or null when not. This enables code to access metadata properties like `$field->formType` or `$field->isRequired` on the field object itself rather than explicitly accessing `$field->_metadata->formType`, providing a more natural API. The __toString() method returns the value property, enabling field objects to be used in string contexts like echo or concatenation operations.

## Public API and Interfaces

The DatabaseManager library exposes its functionality primarily through the Phprojekt_DatabaseManager class which provides both persistence operations for metadata records and metadata query operations for field definitions. The metadata retrieval workflow involves instantiating a DatabaseManager with a model using `new Phprojekt_DatabaseManager($model)`, calling getFieldDefinition() with an ordering constant to retrieve field definitions sorted by form position, list position, or filter usage, and consuming the returned array of field definition structures for form generation, validation rule application, or list rendering. The typical usage occurs in controllers that need to render forms or lists, with code like `$dbManager = new Phprojekt_DatabaseManager($item); $fields = $dbManager->getFieldDefinition(Phprojekt_ModelInformation_Default::ORDERING_FORM);` retrieving form field definitions.

The Module Designer workflow uses DatabaseManager for module creation and modification including validating field definitions through recordValidate(), persisting metadata through saveData(), synchronizing database schema through syncTable(), and removing modules through deleteModule(). The validation workflow calls recordValidate() with field definition array and save type, checks the boolean return for success/failure, and retrieves detailed error information through getError() when validation fails. The save workflow calls saveData() with table name, field definitions, and table structure data, followed by syncTable() to apply schema changes to the module's database table, implementing atomic module updates that modify both metadata and schema.

The range data retrieval API provides getRangeFromModel() for loading selectbox options from related models, supporting both built-in module types (Project, User) with special handling and custom modules with generic loading. This method enables dynamic selectboxes that populate from current database state rather than static option lists, supporting use cases like "assign to user" where the options reflect currently active users. The typical usage involves field definitions with formRange like "User#id#displayName" which getRangeFromModel() parses to load user options.

| Method | Purpose | Return Type |
|--------|---------|-------------|
| `getFieldDefinition($ordering)` | Retrieves complete field definitions with metadata | array of field definitions |
| `getShortFieldDefinition($ordering)` | Retrieves minimal field definitions (key and type) | array of key-type pairs |
| `recordValidate($data, $saveType)` | Validates module structure and field definitions | boolean |

| `getType($fieldName)` | Returns field type for single field | string |
| `find($fieldName)` | Retrieves metadata record for field | Zend_Db_Row or null |

## Dependencies and Integration

The DatabaseManager library depends fundamentally on PHProjekt's ActiveRecord infrastructure through extension of Phprojekt_ActiveRecord_Abstract, inheriting database persistence operations, query construction through Zend_Db_Select, and metadata retrieval through the info() method that provides table structure information. The ActiveRecord foundation enables DatabaseManager to manage its own persistence while providing metadata for other models, demonstrating a reflexive architecture where metadata about metadata is managed through the same patterns as regular domain data. The dependency on Phprojekt_Item_Abstract as the model parameter type restricts DatabaseManager to working with models that extend this base class, coupling it to PHProjekt's model hierarchy.

Integration with the Phprojekt_Table class provides DDL (Data Definition Language) capabilities for schema synchronization, with syncTable() delegating to Table methods including addField(), modifyField(), changeField(), and deleteField() for ALTER TABLE operations, and deleteModule() calling dropTable() for table removal. This integration enables the DatabaseManager to not only manage metadata but also apply that metadata to actual database schema, implementing the vision of database-driven module creation where administrators define modules through forms and the system generates corresponding database tables. The cache clearing through Zend_Db_Table_Abstract::getDefaultMetadataCache()->remove() ensures that ActiveRecord models pick up schema changes immediately rather than using stale cached metadata.

The translation integration through Phprojekt::getInstance()->translate() enables internationalization of field labels and range values, with _convertStandard() translating labels for the current user's language and _convertSelect() translating static range values. The translation system uses module name as context through the second parameter, enabling module-specific translations where the same label might have different meanings in different modules. The tooltip integration through getTooltip() retrieves field hints from a centralized tooltip repository, providing contextual help text for fields without requiring hint text to be stored in every field definition.

The Phprojekt_Error integration provides structured error handling for validation operations, with recordValidate() accumulating errors through addError() calls that build error structures with field, label, and message keys suitable for JSON serialization and UI display. The error object supports multiple errors enabling comprehensive validation that reports all issues rather than stopping at first failure, improving user experience in the Module Designer by showing all validation problems simultaneously. The getError() method's use of array_pop() returns only the most recent error, suggesting an iterative validation model where errors are consumed and addressed one at a time.

The Module Designer integration represents the primary consumer of DatabaseManager functionality, with module creation and modification workflows using validateData() to check field definitions before saveData() persists them and syncTable() applies schema changes. The Module Designer UI submits field definitions as JSON which controllers parse into PHP arrays, validate through DatabaseManager, and persist when valid. The bidirectional integration where getDataDefinition() retrieves existing module structure for editing supports module modification workflows where administrators load existing modules, modify fields, and save updated definitions.

## Data Models and Structures

The DatabaseManager library manages the database_manager table which stores comprehensive field metadata for all modules including both built-in and custom modules created through the Module Designer. The table structure consists of id (auto-increment primary key), table_name (varchar identifying which module this field belongs to), table_field (varchar with the database column name), table_type (varchar with SQL data type like 'int', 'varchar', 'text'), table_length (integer with field length constraint), form_label (varchar with untranslated label), form_type (varchar with UI widget type like 'text', 'selectValues', 'date'), form_position (integer controlling form field order), form_columns (integer for multi-column forms), form_tab (integer identifying which tab contains the field), form_range (text storing selectbox options or model references), form_regexp (varchar with validation regular expression), default_value (varchar with default value for new records), list_position (integer controlling list column order), list_align (varchar with 'left', 'center', or 'right'), list_use_filter (integer flag enabling list filtering), is_required (integer flag marking required fields), is_integer (integer flag for integer fields), and status (integer with 1 for active, 0 for inactive).

The table_name and table_field columns together form a logical composite key that uniquely identifies fields, though no database constraint enforces this uniqueness. The table_name uses Pascal case like "Project" or "Todo" matching module names, while table_field uses snake_case like "project_id" or "start_date" following database naming conventions. The form_type column uses PHProjekt-specific type vocabulary including "text" for single-line text, "textarea" for multi-line text, "selectValues" for dropdowns, "multipleSelectValues" for multi-select, "date" for date pickers, "time" for time pickers, "datetime" for combined date+time, "upload" for file uploads, "display" for read-only computed values, and others that map to Dojo UI widgets in the frontend.

The form_range column implements a flexible format that varies by form_type, storing static option lists for selectValues as pipe-delimited key-value pairs like "1#Open|2#Closed|3#Done" where hash separates key from value and pipe separates options, or model references like "User#id#displayName" where the first part identifies the model module, second part the key field, and third part the display field. This overloaded format trades type safety for storage efficiency, with the conversion logic in _convertSelect() parsing the format based on presence of pipe characters. The form_regexp field remains largely unused in the codebase, suggesting a planned but unimplemented client-side validation feature.

The list_position and form_position fields implement independent ordering where fields can appear in different orders in lists versus forms, with position 0 indicating the field should not appear in that context. This dual-position system enables flexible UI layouts where less important fields appear in forms but not lists (form_position > 0, list_position = 0) or where fields appear in different orders optimized for their contexts. The form_tab field implements tabbed form layouts where related fields are grouped onto the same tab, though the implementation limits tab usage to simple numeric identifiers without tab label storage.

## Configuration and Settings

The DatabaseManager library operates primarily through database-stored configuration in the database_manager table rather than external configuration files, reflecting its role in supporting dynamic module creation where field definitions are user-defined rather than developer-defined. The ordering constants in Phprojekt_ModelInformation_Default (ORDERING_FORM, ORDERING_LIST, ORDERING_FILTER) determine which fields are retrieved and in what order, with the _mapping array translating these constants to database column names (form_position, list_position, list_use_filter). This mapping approach decouples the API from database schema, enabling the ordering vocabulary to remain stable even if underlying column names change.

The system field protection in syncTable() uses a hardcoded array of field names ('id', 'owner_id', 'project_id') that must not be modified or deleted, ensuring that core fields required by PHProjekt's security and organizational model remain intact even when administrators modify module schemas. This whitelist approach protects critical infrastructure while allowing administrators to modify all other fields, implementing a safety guard that prevents accidental breaking of essential functionality. The choice of specific protected fields reflects PHProjekt's model where every item has an owner for security, belongs to a project for organization (in project-scoped modules), and has an ID for identity.

The validation rules in recordValidate() implement configurable constraints including varchar length limits (1-255 characters), int length limits (1-11 digits), required presence of project_id for saveType = 0 (project-scoped modules), required presence of at least one list field (list_position > 0), and required presence of at least one field overall. These rules balance flexibility with consistency, enabling administrators to create diverse module structures while ensuring minimum viability. The saveType parameter enables different validation rules for global modules (saveType = 1) versus project-scoped modules (saveType = 0), with project-scoped modules requiring project_id fields for organizational context.

The cache strategy uses a protected _dbFields array that persists only for the lifetime of a single request, clearing automatically when the request ends. This request-scoped caching provides performance benefits for multiple accesses to the same field definitions within a request without introducing the complexity of cross-request cache invalidation. The schema metadata cache clearing in syncTable() uses Zend_Db_Table_Abstract's default metadata cache, generating cache IDs from database configuration (port, host, database name, schema, table) to identify specific table metadata for removal. This surgical cache invalidation ensures that schema changes are immediately visible without requiring full cache clears.

## Design Patterns and Principles

The Metadata pattern dominates the DatabaseManager's architecture, implementing the principle that "data about data" can itself be treated as data and managed through the same persistence mechanisms. This pattern enables PHProjekt's Module Designer to store field definitions in the database, query them dynamically, and use them to drive form generation, validation, and list rendering without hardcoding field structures in PHP classes. The pattern demonstrates a reflexive or meta-programming approach where the system can modify its own structure through administrator interfaces, supporting customization without code changes. The trade-off involves runtime overhead of metadata queries and complexity in maintaining consistency between metadata and actual database schema.

The Active Record pattern appears through DatabaseManager's extension of Phprojekt_ActiveRecord_Abstract, enabling the metadata manager to use the same persistence patterns as the models it describes. This reflexive application of Active Record demonstrates that even metadata can be treated as domain objects with CRUD operations, validation, and database mapping. The pattern enables DatabaseManager to be instantiated, modified through property assignment, and persisted through save() calls just like any other model, providing consistency across the codebase where all database-backed entities use the same API.

The Strategy pattern appears in the field conversion logic where _convertSelect() and _convertStandard() implement different conversion strategies selected based on field type, with getFieldDefinition() dispatching to appropriate converters through switch statement. This pattern enables the system to handle diverse field types with specialized conversion logic while maintaining a uniform field definition format for consumers. The pattern supports extensibility where new field types could be added by implementing new converter methods and extending the dispatch logic, though the current implementation uses a switch statement rather than a more formal strategy registry.

The Template Method pattern structures the conversion logic where _convertStandard() defines the base field definition structure while _convertSelect() extends this template with range data, demonstrating how specialized converters build upon common conversion logic. The pattern enables code reuse where all converters benefit from standard label translation, length extraction, and metadata population while adding field-type-specific properties. The pattern also appears in validation where recordValidate() defines the overall validation algorithm (check presence, check uniqueness, check types, check formats) while individual validation checks handle specific constraints.

The Repository pattern appears implicitly in how DatabaseManager provides centralized access to field metadata, encapsulating the query logic behind methods like getFieldDefinition() and find() that abstract SQL details. This pattern enables calling code to work with field definitions as objects without understanding database structure or query construction, supporting loose coupling between metadata consumers and the storage mechanism. The pattern also enables the caching strategy where the repository implementation can optimize queries without affecting client code.

The Builder pattern appears in how field definitions are constructed through a series of conversion steps, starting with database records, adding base properties through _convertStandard(), adding range data for selectboxes, adding type overrides for special fields, and translating labels for localization. This incremental construction enables complex field definitions to be built through composition of simpler operations, supporting extensibility where new properties can be added to the construction pipeline without modifying existing steps. The pattern demonstrates separation between construction complexity and the final field definition representation.

The Fail Fast pattern appears in validation where recordValidate() returns false and stops checking remaining fields when certain critical errors are detected, preventing cascading errors that would result from invalid module structure. The method's accumulation of errors before returning enables comprehensive feedback for non-critical errors while stopping immediately for critical errors like missing module name or duplicate field names. This balanced approach provides the best error reporting possible without overwhelming users with derivative errors that stem from earlier fundamental issues.
