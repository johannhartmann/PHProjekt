# Component: Converter

## Overview

The Converter library provides a comprehensive suite of data transformation utilities that handle the conversion of PHProjekt models and values between different formats and representations. This library serves as a critical bridge between the internal data structures of PHProjekt and the external interfaces used by clients, including JSON APIs, CSV exports, and human-readable text displays. The converter system is designed to maintain data integrity while transforming information across multiple contexts, including database storage, API responses, user interface displays, and export formats.

The Converter library is built around the principle of format-specific transformation, with each converter class specializing in a particular output format or conversion use case. The library handles complex transformations such as timezone conversions, field type-specific formatting, internationalization concerns, and security considerations like HTML sanitization. By centralizing these transformation responsibilities, the Converter library ensures consistency across the application and simplifies the process of adding new output formats or modifying existing conversion logic.

At its core, the Converter library operates on the Phprojekt_Model_Interface abstraction, allowing it to work with any model object in the system. The converters understand the metadata associated with model fields, including data types, validation rules, and display options, and use this information to perform intelligent transformations. This metadata-driven approach means that converters can handle new field types and models without requiring changes to the conversion logic itself.

The library is particularly important for maintaining the separation of concerns between the business logic layer, which works with strongly-typed domain objects, and the presentation layer, which requires data in various serialized formats. By providing well-defined conversion interfaces, the Converter library enables controllers and other application components to easily transform model data for different consumption contexts without embedding format-specific logic throughout the codebase.

## Component Structure

| Path | Purpose |
|------|---------|
| `library/Phprojekt/Converter/` | Root directory containing all converter implementations |
| `Converter/Json.php` | Converts models and data structures to JSON format for API responses |
| `Converter/Csv.php` | Converts models and arrays to CSV format for export functionality |
| `Converter/Value.php` | Bidirectional converter for database storage and retrieval of typed values |
| `Converter/Text.php` | Converts model field values to human-readable text representations |
| `Converter/Time.php` | Handles timezone conversions and time formatting operations |
| `Converter/String.php` | Provides string manipulation utilities for search indexing |

The Converter library is organized as a collection of independent, specialized converter classes, each focused on a specific type of transformation. This structure reflects a functional decomposition based on output format rather than an object-oriented hierarchy, which is appropriate given that the converters perform stateless transformations rather than maintaining internal state. The classes are all located in the same namespace directory, making them easy to discover and use through a consistent naming convention.

The organization follows a pattern where each converter provides static methods for performing transformations, making them simple to invoke without requiring instantiation or dependency injection. This design choice prioritizes ease of use in controllers and other application components that need to perform quick conversions. The static method approach also reinforces the stateless nature of these transformations and makes it clear that converters are utility classes rather than domain objects.

## Key Classes and Files

### Phprojekt_Converter_Json

The JSON converter is the most complex and feature-rich component in the Converter library, responsible for transforming PHProjekt models into JSON format suitable for consumption by Dojo-based JavaScript clients. Located in `Converter/Json.php`, this class handles multiple conversion scenarios through its polymorphic `convert()` method, which accepts various input types including individual models, arrays of models, tree structures, and raw data arrays. The converter produces JSON objects that conform to the Dojo data store specification, including metadata sections that describe field definitions and data sections containing the actual record values.

The JSON converter integrates deeply with PHProjekt's security and access control systems. When converting model objects, it automatically retrieves and includes rights information for the current user, calling `Phprojekt_Right::getRightsForItems()` to fetch permission bitmasks and converting them to arrays using `Phprojekt_Acl::convertBitmaskToArray()`. This ensures that client-side code has the information needed to enable or disable user interface elements based on permissions. The converter also handles the special case of tree structures through the `_convertTree()` method, which transforms hierarchical project data into a format compatible with Dojo tree widgets, including proper parent-child references and path information.

Key methods include `convert()` which dispatches to specialized private methods based on input type, `echoConvert()` which sets appropriate HTTP headers and outputs JSON directly to the response, `_convertModel()` which transforms model objects and arrays with full metadata, `_convertTree()` which handles hierarchical node structures, and `_convertModelValue()` which performs type-specific value conversions including integer coercion for numeric fields. The JSON converter also handles field definitions from the model information system, ensuring that client-side code receives complete metadata about field types, labels, validation rules, and display options.

### Phprojekt_Converter_Csv

The CSV converter in `Converter/Csv.php` provides export functionality for generating comma-separated value files suitable for use in spreadsheet applications and data analysis tools. Like the JSON converter, it provides a polymorphic `convert()` method that accepts either arrays of model objects or raw data arrays, automatically detecting the input type and routing to the appropriate conversion method. The converter produces standards-compliant CSV output with proper quoting and escaping of special characters, ensuring that fields containing commas, quotes, or newlines are handled correctly.

When converting model objects, the CSV converter leverages the model information system to determine which fields should be included in the export and in what order, respecting the ordering specification passed to the conversion method. The `_convertModel()` method generates a header row containing field labels, followed by data rows with the actual field values. For each field, the converter calls `Phprojekt_Converter_Text::convert()` to transform the model value into a human-readable representation, ensuring that select boxes show display names rather than IDs, percentages are properly formatted, and upload fields show file names rather than internal identifiers.

The `echoConvert()` method handles the complete HTTP response cycle for CSV downloads, setting appropriate cache control headers to prevent browsers from caching the download, setting the Content-Disposition header to trigger a file download with the filename "export.csv", and ensuring UTF-8 encoding through `mb_convert_encoding()`. The `_writeFile()` method performs the actual CSV formatting, iterating through rows and columns and escaping double quotes by doubling them according to CSV standards. This converter is particularly important for users who need to analyze PHProjekt data in external tools or create backups in a portable format.

### Phprojekt_Converter_Value

The Value converter in `Converter/Value.php` provides bidirectional transformation between user-facing value representations and database storage formats. Unlike the other converters which are primarily concerned with output, the Value converter handles both input (the `set()` method) and output (the `get()` method) transformations, making it essential for the data persistence layer. This converter is invoked automatically by the `Phprojekt_Item_Abstract` class in its `__set()` and `__get()` magic methods, ensuring that all property assignments and retrievals pass through appropriate type conversions.

The `set()` method prepares values for database storage by applying type-specific sanitization and formatting. For integer fields, it uses the Cleaner sanitization library to ensure the value is a valid integer. For float fields, it applies both sanitization and locale-aware formatting through `Zend_Locale_Format::getFloat()`. For time and datetime fields, the converter performs timezone conversions using `Phprojekt_Converter_Time::userToUtc()` to ensure all temporal values are stored in UTC format in the database, regardless of the user's timezone setting. For text fields, the method detects HTML content through regular expression matching and applies either HTML sanitization or simple string sanitization depending on the content.

The `get()` method reverses these transformations when retrieving values from the database. It converts float values using locale-aware formatting, converts time and datetime values from UTC back to the user's timezone using `Phprojekt_Converter_Time::utcToUser()`, and strips slashes from HTML content to prepare it for display. This bidirectional conversion system ensures that the application layer can work with values in user-friendly formats while the database maintains consistency through standardized storage formats. The converter's integration with the ActiveRecord magic methods means that developers can assign and retrieve values naturally without explicitly invoking conversion methods.

### Phprojekt_Converter_Text

The Text converter in `Converter/Text.php` specializes in transforming model field values into human-readable strings suitable for display in user interfaces and CSV exports. This converter is particularly important for handling field types that store internal representations that differ from their display representations, such as select boxes that store numeric IDs but need to display textual labels. The single public method, `convert()`, accepts a model object and a field definition array, and returns a formatted string based on the field type.

The converter implements type-specific formatting logic through a switch statement that handles selectbox and multipleselectbox fields by looking up display values in the field's range array, percentage fields by formatting as two-decimal-place numbers, upload fields by parsing the pipe-delimited file format and extracting filenames, time fields by stripping seconds from the timestamp, display fields by checking for range-based translations, and textarea fields by stripping HTML tags and converting newlines to spaces. This comprehensive type handling ensures that exported and displayed data is always presented in a format that makes sense to end users.

The Text converter is invoked by the CSV converter when generating export files, by the search indexing system when preparing text for full-text search, and by various controllers when preparing data for display. Its role as a central point for text transformation ensures consistency in how field values are presented across different parts of the application. The converter's reliance on field metadata means that new field types can be added by extending the switch statement, and changes to display formatting can be centralized in this single class rather than scattered throughout the application.

### Phprojekt_Converter_Time

The Time converter in `Converter/Time.php` handles all timezone-related conversions in the PHProjekt system, providing methods for converting between user local time and UTC storage format. The converter implements the critical requirement that all temporal values be stored in UTC in the database while being displayed to users in their configured timezone. This approach ensures that users in different timezones can collaborate on time-sensitive data without confusion about when events occur.

The converter provides three main methods: `userToUtc()` which converts a user's local time to UTC timestamp, `utcToUser()` which converts a UTC timestamp to the user's local time, and `convert()` which implements the actual conversion logic used by both direction-specific methods. The `convert()` method retrieves the effective user's timezone setting through `Phprojekt_Auth_Proxy::getEffectiveUser()->getSetting("timeZone")`, parses the timezone offset (which may include both hours and minutes separated by an underscore), and uses PHP's `mktime()` function to perform the timezone adjustment by adding or subtracting the appropriate offset.

Additional utility methods include `convertMinutesToHours()` which transforms a minute count into HH:mm format for time duration displays, and `getTimeZones()` which returns a comprehensive array of timezone offsets mapped to human-readable names suitable for use in configuration interfaces. The timezone array includes entries for all major world timezones with GMT offsets and location names. This converter is essential for maintaining data consistency in multi-timezone deployments and ensuring that temporal data is correctly interpreted regardless of where users are located.

### Phprojekt_Converter_String

The String converter in `Converter/String.php` provides specialized string manipulation functions used primarily by the search indexing system. This lightweight converter includes two methods: `cleanupString()` which prepares text for indexing by stripping HTML tags and converting to lowercase, and `stripLengthWords()` which filters out words that are too short or too long to be useful search terms. The converter uses multibyte-aware string functions throughout to properly handle UTF-8 encoded text containing international characters.

The `cleanupString()` method is designed to normalize text before it is tokenized and indexed for full-text search. By stripping HTML tags, the method ensures that markup doesn't interfere with search results and that users searching for content find matches based on actual text rather than tag names or attributes. The lowercase conversion ensures case-insensitive matching, allowing searches to find content regardless of capitalization. The `stripLengthWords()` method implements a common information retrieval technique of filtering out words between 3 and 256 characters, eliminating common articles and conjunctions (which are typically 1-2 characters) as well as extremely long strings that are unlikely to be meaningful search terms.

This converter plays a supporting role in the search subsystem, being invoked by the search indexing process when model content is analyzed and tokenized. By centralizing string normalization logic in this converter, the system ensures consistent text handling across all indexed content. The use of multibyte string functions (`mb_strtolower()` and `mb_strlen()`) demonstrates awareness of internationalization concerns and ensures that the search system works correctly for users working with non-Latin scripts.

## Public API and Interfaces

The Converter library exposes a public API consisting primarily of static methods on each converter class, designed for straightforward invocation from controllers and other application components. The API design prioritizes simplicity and discoverability, with method names that clearly indicate the conversion being performed. Most converters provide a `convert()` method that performs the transformation and returns the result as a string or array, along with an `echoConvert()` method that performs the conversion and also handles the HTTP response, setting appropriate headers and outputting the result directly.

The JSON and CSV converters follow an identical interface pattern where `convert()` accepts polymorphic parameters (either models, arrays of models, or raw data) and an optional ordering parameter, and returns a string in the appropriate format. The `echoConvert()` methods provide a convenient shorthand for the common use case of converting model data and immediately sending it to the client. These methods handle all HTTP header manipulation internally, including content type, caching directives, and content disposition, allowing controllers to perform conversions with a single method call. This design reduces boilerplate in controller actions and ensures consistent header handling across all API endpoints.

The Value converter presents a different interface pattern with separate `set()` and `get()` methods that accept a type string and a value, returning the transformed value. These methods are typically not invoked directly by application code but rather are called automatically by the `Phprojekt_Item_Abstract` magic methods. The Text converter similarly provides a single `convert()` method that accepts a model and field definition, returning a formatted string. The Time converter offers both direction-specific convenience methods (`userToUtc()` and `utcToUser()`) and a generalized `convert()` method that accepts a direction parameter. This variety in interface design reflects the different use cases each converter addresses, with the API shape optimized for the typical usage pattern of each converter type.

## Dependencies and Integration

The Converter library integrates extensively with other PHProjekt subsystems and external libraries to accomplish its transformation tasks. The most fundamental dependency is on the model system, particularly the `Phprojekt_Model_Interface` which all models implement, and the `Phprojekt_ModelInformation_Default` class which provides field metadata including types, labels, and validation rules. The converters rely on this metadata to understand how to transform field values, what ordering to use for output, and what validation constraints apply. This tight integration with the model information system means that changes to field definitions automatically flow through to the converters without requiring updates to conversion logic.

The Converter library makes extensive use of the Zend Framework components, particularly `Zend_Json::encode()` for JSON serialization, `Zend_Locale_Format` for locale-aware number formatting, and `Zend_Controller_Front` for accessing the HTTP response object. The dependency on Zend_Json is particularly important as it provides robust, secure JSON encoding that handles edge cases like circular references and special characters. The use of Zend_Locale_Format ensures that numeric values are formatted according to the user's locale settings, displaying decimal separators and thousands separators in the format familiar to the user.

Security integration is provided through the Cleaner sanitization library, which is invoked by `Phprojekt_Converter_Value::set()` to sanitize all input values before database storage. The converters also integrate with the authentication and authorization system through `Phprojekt_Auth_Proxy`, which provides access to the current user's settings including timezone preferences. The JSON converter integrates with the rights management system through `Phprojekt_Right::getRightsForItems()` and `Phprojekt_Acl::convertBitmaskToArray()`, ensuring that permission information is included in API responses. Additional integration points include the `Phprojekt_CompressedSender` utility used by the JSON converter to support gzip compression of responses, reducing bandwidth usage for large data transfers.

## Data Models and Structures

The Converter library operates on abstract data structures rather than concrete models, working with the `Phprojekt_Model_Interface` abstraction to support any model in the system. The primary data structure is the field definition array provided by the model information system, which contains metadata entries for each field including keys like 'key' (the field name), 'type' (the field type such as 'text', 'int', 'date', 'selectbox'), 'label' (the human-readable display name), 'range' (for select boxes, the available options), 'integer' (a boolean indicating numeric fields), and 'default' (the default value). This metadata-driven approach allows converters to handle any model without hard-coded knowledge of specific model structures.

The JSON converter produces a standardized data structure consisting of three main sections: a 'metadata' array containing field definitions from the model information system, a 'data' array containing the actual record values with type-converted fields, and a 'numRows' integer indicating the number of records returned. Each record in the data array includes an 'id' field, type-specific converted values for each model field, and a 'rights' object containing permission information for the current user. For tree structures, the converter produces objects with 'name', 'id', 'parent', 'path', and optional 'children' arrays containing references to child nodes.

The CSV converter produces a simpler structure consisting of a two-dimensional array where the first row contains field labels and subsequent rows contain string-converted field values. The internal representation uses PHP arrays that are then serialized to CSV format through the `_writeFile()` method. The Time converter works with Unix timestamps internally, accepting and returning integer timestamp values that represent seconds since the Unix epoch. The timezone offset data structure uses string keys (like "-5", "5_30") to represent hours and optional minutes of offset from UTC, with the underscore separator indicating a fractional hour offset. This structure supports timezones like India (UTC+5:30) and Nepal (UTC+5:45) that don't align to whole-hour boundaries.

## Configuration and Settings

The Converter library relies primarily on runtime configuration rather than static configuration files, obtaining most of its settings from user preferences and model metadata. The Time converter retrieves timezone settings from user preferences through `Phprojekt_Auth_Proxy::getEffectiveUser()->getSetting("timeZone")`, allowing each user to configure their preferred timezone independently. The timezone setting accepts special string formats like "5_30" to represent offsets with both hour and minute components, providing flexibility for regions with non-standard timezone offsets.

The model information system provides configuration to the converters through field definitions that specify ordering, types, labels, and ranges. The ordering parameter passed to conversion methods (typically `Phprojekt_ModelInformation_Default::ORDERING_DEFAULT`) determines which fields are included in the output and in what sequence they appear, allowing different views of the same model. The JSON converter's behavior is influenced by whether models implement specific interfaces or extend particular base classes, with special handling for `Phprojekt_Tree_Node_Database` instances and `Project_Models_Project` objects that require different conversion approaches.

## Design Patterns and Principles

The Converter library extensively employs the Strategy pattern, with each converter class representing a different transformation strategy that can be selected based on the desired output format. This pattern allows the application to vary the conversion algorithm independently from the models being converted, supporting multiple output formats without modifying model classes. The static method interface reinforces the stateless nature of these strategies and makes them easy to invoke without complex instantiation or configuration.

The library also demonstrates the Facade pattern, particularly in the JSON and CSV converters' `echoConvert()` methods which provide a simplified interface that hides the complexity of HTTP header manipulation, encoding, and output. These facade methods encapsulate multiple operations (conversion, header setting, encoding detection, content output) behind a single method call, reducing the coupling between controllers and the underlying conversion and HTTP response systems. This pattern makes it easier for developers to add new controllers or modify existing ones without deep knowledge of HTTP protocol details or conversion internals.

The Converter library follows the Single Responsibility Principle by separating different types of conversions into distinct classes, with each class focused on a specific transformation concern. The JSON converter handles JSON serialization, the CSV converter handles CSV generation, the Value converter handles database persistence transformations, the Text converter handles human-readable formatting, and so on. This separation makes the codebase easier to understand, test, and modify, as changes to one conversion type don't affect others.

The design also reflects the Template Method pattern in the polymorphic `convert()` methods of the JSON and CSV converters. These methods define the overall conversion algorithm structure (type detection, dispatch to specialized method, result formatting) while delegating the specific conversion logic to private methods like `_convertModel()`, `_convertTree()`, and `_convertValue()`. This pattern allows the converters to handle multiple input types through a single public interface while maintaining clean separation of the type-specific logic.

The Dependency Inversion Principle is evident in the converters' reliance on the `Phprojekt_Model_Interface` abstraction rather than concrete model classes. By programming to the interface, the converters can work with any model implementation without modification, supporting extensibility and allowing new models to be added to the system without updating conversion code. The reliance on model metadata rather than hard-coded field knowledge further reinforces this principle, creating a flexible system where models control their own representation through the information they provide about their fields.
