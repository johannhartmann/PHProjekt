# Component: User

## Overview

The User library provides the complete user account management infrastructure for PHProjekt 6, serving as the central domain model for user entities with comprehensive functionality for user creation, retrieval, validation, profile management, and integration with authentication, authorization, and localization systems. This library implements the core Phprojekt_User_User model class that extends the ActiveRecord ORM foundation to represent user accounts stored in the database, providing both data persistence operations and business logic methods that handle user-specific concerns like username uniqueness validation, display name formatting based on configurable preferences, timezone handling for internationalization, and integration with the settings system for user preferences. The User model serves as a critical integration point throughout the application, referenced by virtually every module that needs to track ownership, authorship, assignment, or access control relationships.

The library architecture follows the separation of concerns principle by dividing user functionality across three specialized classes that each handle distinct responsibilities. The Phprojekt_User_User class implements the primary domain model with persistence operations, validation logic, and relationship management including a hasMany relationship to Phprojekt_Setting for user-specific configuration storage. The Phprojekt_User_Information class provides metadata about the user model's structure, defining field definitions with labels, types, validation rules, and display properties used by form generation and UI rendering components throughout the application. The Phprojekt_User_Exception class implements specialized exception handling for user-specific error conditions, most notably enforcing the business rule that user accounts cannot be deleted but only deactivated, ensuring data integrity for historical records and audit trails that reference user IDs.

The User library demonstrates sophisticated integration with PHProjekt's broader infrastructure including collaboration with the Auth library for authentication where User objects are loaded after credential validation, integration with the Phprojekt_Setting system for storing user preferences including password hashes, language preferences, timezone configurations, and holiday region identifiers, participation in the access control system through Phprojekt_Item_Rights which creates default permission records when new users are created, and support for the display name formatting system that allows administrators to configure how user names appear throughout the application. The model includes specialized methods for common query patterns like finding users by username (findIdByUsername, findByUsername), retrieving users by ID with proper error handling (findUserById), and fetching all active users with appropriate permissions for a given project context (getAllowedUsers).

The implementation includes several sophisticated features that demonstrate enterprise-ready user management including configurable display name formatting with four different styles (lastname/firstname, username/lastname/firstname, username only, firstname/lastname) controlled through configuration, timezone handling that converts user timezone preferences into PHP DateTimeZone objects for proper date/time localization, holiday calculator integration that retrieves region-specific holiday calculation objects based on user settings for vacation management, validation logic that enforces username uniqueness across the system, and a soft-delete pattern where users are marked inactive rather than removed from the database to preserve referential integrity. The validation system integrates with Phprojekt_Model_Validate to provide comprehensive field-level validation with user-friendly error messages suitable for display in UI forms.

The User library follows PHProjekt's standard pattern for domain models by separating the model class (User.php) from its metadata descriptor (Information.php), enabling the framework to introspect model structure for form generation, validation, and serialization without hardcoding field knowledge throughout the application. This metadata-driven approach allows UI components to dynamically render appropriate form controls based on field types (text, password, selectbox, checkbox), apply validation rules (required, length constraints, uniqueness), and provide localized labels without coupling presentation code to domain models. The Exception.php file provides a dedicated exception type that enables precise error handling for user-specific failure scenarios, allowing calling code to distinguish between general ActiveRecord errors and user domain logic violations.

## Key Classes and Files

### Phprojekt_User_User (User.php:19-447)

The Phprojekt_User_User class serves as the primary domain model for user accounts, extending Phprojekt_ActiveRecord_Abstract to inherit ORM functionality while implementing the Phprojekt_Model_Interface to provide metadata access through the getInformation() method. The class defines a hasMany relationship to Phprojekt_Setting through the `$hasMany` array (User.php:26-28), enabling access to user-specific settings via the `$user->settings` property which returns a configured ActiveRecord instance for querying related settings records. The constructor initializes the model with database adapter injection following the standard ActiveRecord pattern, while also instantiating Phprojekt_Model_Validate for validation operations and Phprojekt_User_Information for metadata access, establishing the core dependencies needed for model operations.

The findIdByUsername() method (User.php:117-134) implements a common query pattern for authentication workflows where a username string must be resolved to a numeric user ID, executing a database query with proper SQL injection protection through quoted parameters, limiting results to a single record for efficiency, and returning either the integer user ID or boolean false when no matching user exists. This method handles exceptions from the ActiveRecord layer gracefully by logging warnings through the Phprojekt logging system and returning false, ensuring that database errors during authentication don't propagate as unhandled exceptions. The complementary findByUsername() method (User.php:143-154) returns a full User object instead of just the ID, providing richer information for contexts that need user details beyond the ID, with a return type of Phprojekt_User_User or NULL to support null-safe calling patterns.

The findUserById() method (User.php:164-175) implements a factory-like pattern for loading user objects by ID, cloning the current instance to create a new User object, calling the ActiveRecord find() method to load data, and returning the populated clone while leaving the original object unmodified. This approach enables code like `$otherUser = $currentUser->findUserById($targetId)` without mutating the `$currentUser` instance, supporting cleaner object-oriented patterns. The method throws RuntimeException when the requested user ID doesn't exist, providing explicit failure signaling rather than returning NULL or false, ensuring that calling code can distinguish between "user with ID 0" (invalid) and "user not found" scenarios. The validation `if ($id > 0)` ensures that invalid IDs are rejected immediately, with the else branch returning the current instance when ID is zero or negative.

The isActive() method (User.php:101-108) implements a simple but critical business rule check that determines whether a user account is active by examining the status field for the value 'A' (active) versus 'I' (inactive), using case-insensitive comparison through strtoupper() to ensure robustness against mixed-case storage. This method is called by authentication workflows to ensure that inactive users cannot log in even with valid credentials, implementing a soft-delete or account suspension pattern that preserves user data while preventing access. The binary active/inactive model simplifies access control logic compared to more complex status schemes with multiple states, though it limits flexibility for scenarios requiring fine-grained account states like "pending activation" or "password reset required".

The save() method (User.php:182-194) extends the ActiveRecord save() implementation to add user-specific behavior for new user creation, checking if `$this->id == 0` to distinguish between insert and update operations, and for inserts calling Phprojekt_Item_Rights::saveDefaultRights() to establish initial permission records that grant the new user appropriate access to system resources. This lifecycle hook ensures that every new user receives proper default permissions without requiring calling code to manually create permission records, implementing the principle that domain objects know how to properly initialize themselves. The method returns boolean true on successful creation with permissions or delegates to the parent save() for updates, maintaining consistency with the ActiveRecord API contract.

The delete() method (User.php:203-206) implements a critical business rule by unconditionally throwing Phprojekt_User_Exception with the message "Users can't be deleted", enforcing a hard constraint that user accounts must never be removed from the database. This design decision ensures referential integrity for historical records including audit trails (history table), notification recipients (frontend_message table), ownership tracking (owner_id fields), and permission assignments (role_user_permissions table) that all reference user IDs. The soft-delete pattern implemented through the status field provides the functional equivalent of deletion (preventing login and hiding from active user lists) while preserving data integrity. This exception-based approach makes the constraint explicit and impossible to bypass, superior to documentation-based conventions that developers might accidentally violate.

The recordValidate() method (User.php:234-255) implements comprehensive validation logic by delegating to Phprojekt_Model_Validate for standard field validation (required, length, type checks) based on metadata from the Information class, then adding custom validation logic to enforce username uniqueness across the system. The uniqueness check constructs a WHERE clause that excludes the current user's ID (to allow updates without triggering false positives), queries for any other users with the same username, and adds a validation error to the error collection when duplicates exist. The error object structure includes field name, label, and message fields suitable for display in UI forms, with messages retrieved through the translation system to support internationalization. The method returns boolean indicating overall validation success or failure, enabling calling code to check validity before attempting persistence operations.

The getSetting() method (User.php:275-288) provides convenient access to user-specific settings stored in the Phprojekt_Setting system, implementing lazy initialization of the `$_setting` property to avoid repeated object instantiation, configuring the setting object for the 'User' module context, and retrieving the requested setting value with support for default values when settings don't exist. This method encapsulates the complexity of the settings system behind a simple API like `$user->getSetting('timezone', '0')`, eliminating the need for calling code to understand the Setting model's structure. The caching of the `$_setting` object within the User instance improves performance when multiple settings are accessed on the same user object during a request, avoiding repeated initialization overhead.

The getDisplay() static method (User.php:318-339) implements the configurable display name formatting system by reading the userDisplayFormat configuration value and returning an array of field names that should be concatenated to form display names. The method supports four format options: format 0 returns lastname then firstname, format 1 returns username then lastname then firstname, format 2 returns only username, and format 3 returns firstname then lastname. This array-based approach decouples the formatting logic from string concatenation, enabling the applyDisplay() method (User.php:349-359) to iterate over field names, extract values from user objects, and join them with comma-space delimiters. The getDisplayName() method (User.php:366-373) combines these two methods with static format caching to provide a convenient instance method that returns the formatted display name for a user object.

The getUserDateTimeZone() static method (User.php:296-311) implements timezone handling for internationalization by retrieving the effective user's timezone setting through Phprojekt_Auth_Proxy::getEffectiveUser(), parsing the timezone value which uses an underscore-separated format like "5_30" for +5:30 or "-8_00" for -8:00, constructing a time offset string in the format "+HH:MM" or "-HH:MM", and creating a DateTime object to extract its DateTimeZone. This sophisticated parsing handles both positive and negative offsets with optional minute components, supporting fractional hour timezones like India Standard Time (+5:30). The use of getEffectiveUser() instead of getUserId() ensures proper timezone handling during proxy authentication when administrators are impersonating other users.

The getAllowedUsers() method (User.php:382-392) implements a query for retrieving all active users that have appropriate permissions for the current project context, filtering by status = 'A' to exclude inactive accounts and returning an array of dictionaries with 'id' and 'name' keys suitable for dropdown controls in UI forms. The method relies on Phprojekt::setCurrentProjectId() being called beforehand to establish project context, though the actual permission filtering logic appears to be missing from the implementation (the WHERE clause only checks status, not permissions). The return format with 'name' using the displayName property ensures consistent formatting across the application according to the configured display format preference.

The getHolidayCalculator() method (User.php:427-446) integrates with the Mayflower Holiday library to provide region-specific holiday calculation for vacation management, retrieving the holidayIdentifier setting which specifies the user's region (like 'de_DE:by' for Bavaria or 'de_DE' for Germany), throwing Phprojekt_Exception_HolidayRegionNotSet when no identifier is configured, and instantiating the appropriate Holiday calculator class based on the identifier. This integration enables vacation planning features to automatically account for regional holidays when calculating working days, with support for different German states that observe different holidays. The method uses a switch statement for region selection, requiring code changes to support additional regions rather than using a registry or factory pattern.

### Phprojekt_User_Information (Information.php:21-116)

The Phprojekt_User_Information class extends Phprojekt_ModelInformation_Default to provide metadata definitions for the User model, implementing the setFields() method that defines each field with its label, type, validation rules, and display properties. This metadata-driven approach enables PHProjekt's form generation system to automatically create appropriate UI controls, validation systems to enforce constraints without hardcoded logic, and serialization systems to transform between database representations and JSON/XML formats for API responses. The class represents a declarative configuration of the user data structure that serves as the single source of truth for user entity structure throughout the application.

The setFields() method (Information.php:52-115) defines ten fields for the user entity using the fillField() helper method inherited from the parent class. The username field (line 55-57) is configured as required text with 255 character maximum, displayed in both list and form views (indicated by the '1' tab value), and enforced with required validation. The password and confirmValue fields (lines 60-65) are password type fields not displayed in lists (tab value '0'), providing password entry with confirmation for change operations. The firstname and lastname fields (lines 68-75) are required text fields with list display, ensuring that every user has identifiable name information. The email field (line 78-79) is optional text without list display, supporting email notifications when configured but not requiring email addresses for all users.

The language field (lines 82-90) uses selectbox type with dynamically populated options from Phprojekt_LanguageAdapter::getLanguageList(), marked as required with a default value of 'en' (English), enabling per-user interface localization. The timeZone field (lines 93-101) similarly uses selectbox with options from Phprojekt_Converter_Time::getTimeZones(), defaulting to '000' which represents UTC, supporting proper datetime display and manipulation according to user preferences. The status field (lines 104-107) is a selectbox with two options ('A' for Active, 'I' for Inactive) displayed in lists (tab value '4'), implementing the soft-delete pattern where users are deactivated rather than removed. The admin field (lines 110-114) is a checkbox type with 0/1 values marking as integer, displayed in lists (tab value '5'), controlling whether the user has administrator privileges throughout the system.

### Phprojekt_User_Exception (Exception.php:19-63)

The Phprojekt_User_Exception class extends PHP's standard Exception class to provide specialized error handling for user-specific operations, following the same pattern as other domain-specific exception classes throughout PHProjekt. The class contains only a constructor that delegates to the parent Exception constructor with message and optional code parameters, serving primarily as a type marker that enables calling code to catch user-specific exceptions separately from other exception types. The most common use of this exception is in the User model's delete() method which throws it with the message "Users can't be deleted" to enforce the business rule against user deletion, providing a clear and unambiguous signal that the operation is not supported rather than failing silently or returning an error code.

The exception type enables sophisticated error handling patterns where code can catch Phprojekt_User_Exception specifically to handle user domain violations differently from Phprojekt_ActiveRecord_Exception (ORM errors) or general PHP exceptions (system errors). This type-based error handling supports better user experience by enabling controllers to provide appropriate error messages based on exception type, distinguishing between recoverable validation errors (show in form), business logic violations (show as alerts), and system errors (log and show generic error page). The numbered error code support (though the User library primarily uses code 1 for deletion attempts) enables programmatic error handling where different error conditions within the user domain require different handling logic.

## Public API and Interfaces

The User library exposes its functionality primarily through the Phprojekt_User_User model class which provides both standard ActiveRecord operations inherited from Phprojekt_ActiveRecord_Abstract and user-specific methods for common operations. The standard CRUD workflow involves instantiating a User object with `new Phprojekt_User_User()`, setting properties through direct assignment like `$user->username = 'jdoe'`, calling save() to persist, using find($id) for primary key retrieval, and using fetchAll($where, $order) for queries. The User model extends this basic API with specialized methods that handle user-specific concerns, providing a richer domain model than a generic ActiveRecord would offer.

The username-based lookup methods provide critical functionality for authentication workflows where usernames are known but user IDs must be determined. The findIdByUsername($username) method returns an integer ID or false, suitable for authentication checks where only the ID is needed. The findByUsername($username) method returns a full User object or NULL, appropriate when additional user information will be needed after lookup. The findUserById($id) method provides a safe way to load users by ID with proper error handling, throwing exceptions for invalid IDs rather than returning NULL or false. These three methods cover the common patterns for user retrieval and serve as the foundation for authentication and authorization operations throughout the application.

The validation API centers on the recordValidate() method which returns boolean success/failure and populates an internal error collection accessible through getError(), enabling calling code to validate before attempting save operations and display appropriate error messages when validation fails. The validation automatically enforces username uniqueness, required field presence, and length constraints based on the Information metadata, providing comprehensive validation without requiring calling code to implement validation logic. The pattern of checking validation before save supports better user experience by catching errors before database operations fail, and enables transaction-like semantics where multiple validations can occur before committing changes.

The settings integration API provides access to user-specific configuration through getSetting($settingName, $defaultValue) which retrieves values from the Phprojekt_Setting system, supporting preference storage for language, timezone, password (stored as setting rather than user field), and custom application-specific settings. The getUserDateTimeZone() static method converts the timezone setting into a DateTimeZone object suitable for DateTime operations, encapsulating the complexity of timezone parsing. The getHolidayCalculator() method retrieves region-specific holiday calculators based on user settings, supporting vacation management features. These setting-related methods provide high-level APIs that hide the underlying Setting system's complexity.

## Dependencies and Integration

The User library depends fundamentally on the ActiveRecord ORM infrastructure through its extension of Phprojekt_ActiveRecord_Abstract, inheriting all database abstraction capabilities including query construction via Zend_Db_Select, result hydration into object form, relationship management through hasMany declarations, and lifecycle hook support. The direct dependency on Phprojekt_ActiveRecord_Abstract couples the User model to the Active Record pattern, making it challenging to use dependency injection or repository patterns that might be preferred in more modern architectures. The dependency on Zend_Db through the ActiveRecord layer provides database portability across MySQL, PostgreSQL, and other Zend_Db-supported databases, though the application primarily targets MySQL.

Integration with the Phprojekt core infrastructure occurs through multiple touchpoints including the Phprojekt singleton which provides database adapter access via `Phprojekt::getInstance()->getDb()` and logging facilities via `getLog()`, the translation system accessed through `Phprojekt::getInstance()->translate()` for internationalized error messages, and the configuration system accessed through `Phprojekt::getInstance()->getConfig()` for display format and other settings. The model implements Phprojekt_Model_Interface which requires implementing getInformation() and related methods, establishing a contract that form generation and serialization systems depend upon. This interface-based design enables generic code to work with any model implementing the interface without knowing the specific model type.

The validation infrastructure integrates with Phprojekt_Model_Validate which provides field-level validation based on metadata from the Information class, supporting required field checks, length constraints, regular expression matching, and type validation. The validate object maintains an error collection that accumulates validation failures across multiple fields, enabling comprehensive validation that reports all issues rather than failing on the first error. The User model extends standard validation with custom logic for username uniqueness, demonstrating how models can add domain-specific validation beyond the metadata-driven standard validation. The error reporting structure with field name, label, and message keys integrates with form rendering systems that display validation errors inline with form controls.

The Settings integration through the hasMany relationship to Phprojekt_Setting and the getSetting() convenience method enables user-specific configuration storage without adding columns to the user table for every possible preference. This normalized approach stores settings as key-value pairs in a separate table, supporting extensibility where modules can add new user settings without schema changes. The password storage as a setting rather than a user field demonstrates this pattern, keeping sensitive credentials separate from the main user entity. The relationship also enables bulk loading of all user settings through `$user->settings->fetchAll()` for scenarios that need multiple settings, with the getSetting() method providing convenient single-value access.

The authentication integration occurs through the Auth library which instantiates User objects during login with `new Phprojekt_User_User()` followed by `findIdByUsername($username)` to resolve the username, then `find($userId)` to load the full user object, and finally accessing properties like admin flag and calling isActive() to enforce account status requirements. The proxy authentication system through Phprojekt_Auth_Proxy uses `findUserById()` to load impersonated users, with getUserDateTimeZone() respecting the effective user via `Phprojekt_Auth_Proxy::getEffectiveUser()`. This bidirectional integration where Auth uses User for data access and User uses Auth for proxy awareness demonstrates the tight coupling between these two domain models.

The permission system integration through Phprojekt_Item_Rights occurs in the save() method's lifecycle hook which calls `saveDefaultRights($userId)` for newly created users, establishing initial permission grants that enable the user to access the system. The getAllowedUsers() method is intended to integrate with project-based permissions to filter users based on access rights, though the implementation appears incomplete. The User model also participates in the access control system as the subject of permissions checks throughout the application, with code like `if ($item->ownerId == Phprojekt_Auth::getUserId())` comparing user IDs to determine authorization.

## Data Models and Structures

The User library centers on the user database table defined in Core/Sql/Db.json which specifies the schema for user account storage. The table structure consists of id (auto-increment primary key), username (varchar, required, unique constraint ensuring no duplicates), firstname (varchar, nullable), lastname (varchar, nullable), status (varchar length 1, default 'A' for active), and admin (integer length 1, default 0 for non-admin). This lean schema stores only core identity and status information in the user table itself, delegating preferences and sensitive data like passwords to the setting table through the hasMany relationship. The unique constraint on username is enforced at the database level providing defense-in-depth alongside the application-level uniqueness validation in recordValidate().

The status field implements the soft-delete pattern using a single-character code where 'A' indicates active and 'I' indicates inactive, with inactive users unable to authenticate but preserved in the database for referential integrity. This approach maintains historical accuracy for audit trails, ownership tracking, and relationships while preventing account reuse and enforcing business rules against deletion. The admin field uses integer rather than boolean type (common in MySQL which lacks native boolean), with 0 indicating regular user and 1 indicating administrator privileges that grant access to system administration functions like user management, module configuration, and system settings. This binary permission model lacks role-based access control granularity, with the separate Role model providing finer-grained permissions through project-user-role associations.

The setting table provides extensible key-value storage for user preferences through the hasMany relationship, with the schema including user_id (foreign key to user.id), module_id (integer indicating which module owns the setting), key_value (varchar identifying the setting name), value (text for the setting value), and identifier (varchar grouping related settings). This normalized design enables unlimited user preferences without schema changes, though it trades query performance (requires joins) for flexibility. Common settings stored include password (hashed password for authentication), timezone (timezone offset in hours_minutes format like "5_30"), language (language code like "en" or "de"), holidayIdentifier (region code for holiday calculations like "de_DE:by"), and keepLoggedToken_hash and keepLoggedToken_expires for persistent authentication cookies.

The relationship between User and Setting is one-to-many with the User as parent, configured through the hasMany declaration in the User model (`'settings' => array('classname' => 'Phprojekt_Setting', 'module' => 'Setting', 'model' => 'Setting')`). This relationship enables both navigation patterns including accessing settings via `$user->settings->fetchAll()` to retrieve all settings for a user, and querying specific settings via `$user->getSetting('timezone', '0')` which uses the relationship behind the scenes. The module_id and identifier fields in the setting table enable filtering settings by context, with the User module (module_id 0) typically used for core user preferences while other modules can store their own user-specific settings with different module IDs.

The user_proxy table referenced by the Auth library establishes many-to-many relationships between users for impersonation authorization, but the User model itself doesn't define this relationship in its hasMany or hasManyAndBelongsToMany arrays. This asymmetric relationship definition where ProxyTable manages the relationship without User model participation demonstrates that not all relationships need to be defined in both directions, particularly for relationships managed by specialized subsystems. The absence of a direct User-to-User relationship for proxying keeps the User model focused on core user management without coupling it to the proxy authentication feature.

## Configuration and Settings

The User library's behavior is controlled through several configuration settings in configuration.php that affect how users are displayed and managed throughout the application. The userDisplayFormat configuration setting controls how user names are formatted for display across the application, accepting integer values 0 through 3 that determine field ordering and selection. Format 0 (default) displays "lastname, firstname", format 1 displays "username, lastname, firstname", format 2 displays only "username", and format 3 displays "firstname, lastname". This configuration enables organizations to choose formatting conventions that match their culture and naming practices, with Western organizations typically preferring lastname-first (format 0) while some Asian cultures might prefer firstname-last (format 3).

The language configuration setting provides a system-wide default language used when creating new users during LDAP integration, with individual users able to override this through their personal language setting stored in the setting table. The supported languages are defined by Phprojekt_LanguageAdapter::getLanguageList() which returns available translation files, with the system supporting multiple languages including English (en), German (de), and others depending on installed translation files. The language preference affects UI labels, error messages, date formatting, and other localized content, with the translation system using the current user's language setting (or effective user's setting during proxy authentication) to determine which translations to load.

The timezone handling uses a custom format stored in user settings rather than standard timezone identifiers, representing offsets as "hours_minutes" like "5_30" for +5:30 or "-8_00" for -8:00 offset from UTC. This format supports fractional hour timezones like India Standard Time and Nepal Time, though it lacks the sophisticated daylight saving time handling that standard timezone identifiers provide. The default timezone of '000' or '0' represents UTC, with users able to configure their timezone through the settings interface which populates options from Phprojekt_Converter_Time::getTimeZones(). The getUserDateTimeZone() method converts this custom format into standard PHP DateTimeZone objects for use with DateTime operations throughout the application.

The holiday region configuration uses the holidayIdentifier setting to specify which regional holiday calculator to use, with supported values including 'de_DE' for Germany and 'de_DE:by' for Bavaria. This configuration enables vacation planning features to account for regional holidays that vary by German state, with the getHolidayCalculator() method using a switch statement to instantiate the appropriate Holiday calculator class from the Mayflower Holiday library. The configuration is per-user rather than system-wide, supporting organizations with users in different regions who observe different holiday schedules. The lack of a default value means users must explicitly configure their holiday region before using vacation features that depend on holiday calculations.

## Design Patterns and Principles

The Active Record pattern dominates the User library's design through extension of Phprojekt_ActiveRecord_Abstract, embodying the pattern's core principle that domain objects know how to persist themselves and encapsulate both data and database access logic. This pattern simplifies the API by providing methods like save() and delete() directly on domain objects rather than requiring separate repository or data mapper classes, making the code more intuitive for developers familiar with the pattern. The trade-off involves tighter coupling between domain logic and persistence mechanisms, making it more challenging to test domain logic in isolation or swap persistence implementations. The User model demonstrates both the benefits (simple API) and costs (difficulty testing, tight coupling) of the Active Record pattern.

The Information Object pattern (also called Metadata or Descriptor pattern) separates the definition of model structure from the model itself through the Phprojekt_User_Information class, enabling introspection of field definitions without hardcoding structure knowledge throughout the application. This pattern enables generic form generation that reads field definitions to determine which UI controls to render, generic validation that applies rules defined in metadata rather than hardcoded logic, and generic serialization that transforms between different representations based on field types. The separation of concerns between model (User.php) and metadata (Information.php) supports maintainability by keeping structure definitions in one location that can be updated without modifying multiple files throughout the codebase.

The Template Method pattern appears in the save() method which extends the parent ActiveRecord save() to add user-specific behavior, specifically calling saveDefaultRights() for new user creation. This pattern defines the skeleton of an algorithm in a parent class while allowing subclasses to override specific steps, with the User model adding a before-save hook for new users while delegating the actual persistence to the parent implementation. The pattern enables the framework to provide standard save behavior while allowing models to inject domain-specific logic at appropriate lifecycle points, supporting the Open-Closed Principle where the base behavior is closed to modification but open to extension through subclass overrides.

The Soft Delete pattern (also called Logical Delete) implements the business rule that users cannot be removed from the database, instead marking them as inactive through the status field. The delete() method enforces this pattern by unconditionally throwing an exception, preventing any code from accidentally removing user records. This pattern preserves referential integrity for historical records while providing the functional equivalent of deletion through status checks like isActive() in authentication and user lists that filter inactive users. The pattern supports audit trail requirements common in enterprise applications where all historical records must remain queryable, and enables account recovery if an inactive user needs to be reactivated.

The Factory Method pattern appears in getHolidayCalculator() which creates appropriate Holiday calculator instances based on the user's holidayIdentifier setting, encapsulating the instantiation logic and shielding calling code from knowing which concrete Holiday class to instantiate. While the current implementation uses a simple switch statement rather than a more sophisticated factory registry, the pattern's intent is clear: providing an interface for creating objects while letting the method decide which class to instantiate. This pattern supports extensibility where new holiday regions could be added by extending the switch statement, though a more robust implementation might use a registry or strategy pattern to avoid requiring code changes for new regions.

The Display Strategy pattern (though not implemented with formal Strategy pattern classes) appears in the getDisplay() and applyDisplay() methods which separate the determination of display format from the application of that format, enabling multiple formatting strategies selected through configuration. The getDisplay() method returns an array of field names representing the strategy, while applyDisplay() executes the strategy by extracting those fields and concatenating them. This separation enables adding new display formats by extending getDisplay() without modifying applyDisplay(), supporting the Open-Closed Principle. A more formal Strategy implementation might define DisplayStrategy classes with a common interface, though the current array-based approach provides simplicity at the cost of type safety and extensibility.

The Lazy Initialization pattern appears in the getSetting() method which instantiates the `$_setting` property only when first accessed, avoiding unnecessary object creation when settings are never retrieved for a particular user instance. This pattern improves performance by deferring expensive initialization until actually needed, and may avoid it entirely if code paths don't require settings access. The static caching in getDisplayName() implements a related optimization by initializing the display format array once and reusing it across multiple calls, avoiding repeated configuration lookups. These performance optimizations demonstrate attention to efficiency in an era when PHP performance was more constrained than modern PHP 7+ environments.
