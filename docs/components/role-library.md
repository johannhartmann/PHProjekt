# Component: Role

## Overview

The Role library provides the role-based access control (RBAC) foundation for PHProjekt 6, implementing a hierarchical permission system that governs module-level access rights for users throughout the application. This library defines roles as named collections of permissions that can be assigned to users within project contexts, enabling flexible authorization policies where different users receive different levels of access to system modules based on their assigned roles. The Role model works in conjunction with the Phprojekt_Acl component to integrate with Zend Framework's ACL infrastructure, translating role-module permission mappings stored in the database into Zend_Acl rules that the application enforces during request processing and business logic execution.

The library architecture centers on two primary model classes that work together to implement the RBAC pattern. The Phprojekt_Role_Role class represents individual roles with their names and optional parent roles for hierarchical inheritance, providing lifecycle management operations including creation, update, and deletion with special protection for the administrative role. The Phprojekt_Role_RoleModulePermissions class manages the many-to-many relationship between roles and modules, storing permission bitmasks that encode multiple access rights (read, write, create, delete, admin, etc.) in a single integer value for storage efficiency. These two classes collaborate with the Project_Models_ProjectRoleUserPermissions class (defined in the Project module) to complete the three-way association between projects, roles, and users that implements PHProjekt's project-aware RBAC model.

The permission system uses a bitmask encoding scheme where eight distinct access rights are represented as bit flags within an integer value, enabling multiple permissions to be stored and checked efficiently. The permission types include READ (view records), WRITE (modify records), ACCESS (access the module), CREATE (create new records), COPY (duplicate records), DELETE (remove records), DOWNLOAD (download files), and ADMIN (administrative functions), with each right corresponding to a power of two (1, 2, 4, 8, 16, 32, 64, 128). This bitmask approach allows a single integer field to encode any combination of permissions through bitwise OR operations, while permission checks use bitwise AND operations to test for specific rights. The Phprojekt_Acl class provides convertBitmaskToArray() and convertArrayToBitmask() utility methods that translate between integer bitmasks and boolean arrays for UI presentation and manipulation.

The hierarchical role model supports permission inheritance where roles can have parent roles, automatically inheriting all parent permissions while potentially adding additional permissions of their own. This inheritance enables organizations to create role hierarchies like "Manager" extending "Developer" extending "User", with each level adding more permissions without requiring redundant permission grants at each level. The special administrative role (ID 1) receives universal permissions to all modules including any newly installed modules through the addModuleToAdminRole() method, ensuring that system administrators maintain access to all functionality regardless of permission configuration. The Role library enforces a hard constraint preventing deletion of this administrative role, protecting the system from accidentally removing administrative access and creating unrecoverable permission states.

The Role library follows PHProjekt's standard domain model organization pattern by separating the primary model class (Role.php) from its relationship manager (RoleModulePermissions.php) and metadata descriptor (Information.php), enabling clean separation of concerns and supporting the framework's metadata-driven form generation and validation systems. The Role class focuses on role lifecycle management including creation, modification, and deletion with appropriate business rule enforcement, while delegating the complexity of permission management to the RoleModulePermissions class which handles the many-to-many relationship with modules. The Information class provides declarative metadata about role structure that form generation systems consume to render appropriate UI controls without hardcoding knowledge of role fields.

## Key Classes and Files

### Phprojekt_Role_Role (Role.php:19-175)

The Phprojekt_Role_Role class serves as the primary domain model for roles in the access control system, extending Phprojekt_ActiveRecord_Abstract to inherit ORM functionality while implementing Phprojekt_Model_Interface to provide metadata access for form generation and validation. The class defines a hasMany relationship to Phprojekt_Role_RoleModulePermissions through the `$hasMany` array declaration (Role.php:26), enabling navigation from roles to their module permissions via the `$role->modulePermissions` property which returns a configured ActiveRecord instance for querying related permission records. The class includes protected properties for user ID tracking (`$_user`), a private cache for project roles (`$_projectRoles`), and the standard validation and information manager dependencies that all PHProjekt models maintain.

The constructor initializes the model following the standard ActiveRecord pattern by calling the parent constructor with optional database adapter injection, then instantiating Phprojekt_Model_Validate for validation operations and Phprojekt_Role_Information for metadata access (Role.php:63-69). This initialization establishes the dependencies needed for model operations including persistence, validation, and form generation. The __clone() method (Role.php:76-81) overrides the parent clone implementation to ensure that validation and information manager instances are not shared between cloned objects, preventing state pollution when multiple role instances are created through cloning operations common in query result processing.

The saveRights() method (Role.php:102-114) implements the primary API for managing role permissions by accepting an array where keys are module IDs and values are access bitmasks, first deleting all existing module permissions for the role to ensure a clean slate, then iterating over the provided permissions to create new RoleModulePermissions records with the appropriate roleId, moduleId, and access values. This replace-all approach simplifies permission management by avoiding complex add/remove operations and ensuring that the database state matches exactly what was submitted, though it requires transactional handling to prevent inconsistent states if creation fails midway. The method uses the hasMany relationship's create() method to instantiate new permission objects that automatically have the role association configured, then calls save() on each to persist the permissions.

The recordValidate() method (Role.php:121-127) implements validation logic by delegating to Phprojekt_Model_Validate which applies metadata-driven validation rules from the Information class, checking that required fields are present, length constraints are satisfied, and field types are appropriate. The Role model's validation is relatively simple compared to models like User, as the primary business rule is that the name field must be populated and cannot exceed 255 characters. The getError() method (Role.php:134-137) provides access to validation errors through the validate object's error collection, returning an array of error structures suitable for display in UI forms with field names, labels, and messages.

The delete() method (Role.php:169-174) implements a critical business rule by checking if the role ID is greater than 1 before allowing deletion, silently ignoring deletion attempts for the administrative role (ID 1) rather than throwing an exception. This protective logic ensures that the administrative role cannot be accidentally removed from the system, which would leave the system without administrator access and potentially create unrecoverable states. The silent failure approach differs from the User model's exception-throwing delete() method, representing a different design choice where the operation appears to succeed but performs no action. The parent delete() implementation handles cascading deletion of related RoleModulePermissions records through the ActiveRecord relationship management, ensuring referential integrity when roles are removed.

The getInformation() method (Role.php:90-93) implements the Phprojekt_Model_Interface contract by returning the information manager instance that provides metadata about the role model's structure, enabling form generation systems to introspect field definitions and render appropriate UI controls. This metadata-driven approach separates presentation concerns from domain logic, allowing UI code to work generically with any model implementing the interface without hardcoding knowledge of specific model structures.

### Phprojekt_Role_RoleModulePermissions (RoleModulePermissions.php:20-115)

The Phprojekt_Role_RoleModulePermissions class manages the many-to-many association between roles and modules, extending Phprojekt_ActiveRecord_Abstract to represent records in the role_module_permissions database table. Each instance represents a single role-module permission grant, with fields for roleId (foreign key to role.id), moduleId (foreign key to module.id), and access (integer bitmask encoding multiple permission types). The class provides high-level query and manipulation methods that operate on collections of permissions rather than requiring calling code to work with individual permission records, abstracting the relational complexity behind a domain-focused API.

The getRoleModulePermissionsById() method (RoleModulePermissions.php:29-53) implements a comprehensive query operation that returns all modules in the system along with their permission status for a specified role, building a data structure suitable for permission management UIs. The method first queries all modules with save_type values of 0 or 2 (normal and system modules that support permissions), initializing each module in the result array with basic information (id, name, translated label) and a default permission array with all rights set to false via Phprojekt_Acl::convertBitmaskToArray(0). The method then queries the role_module_permissions table for the specified role, merging the actual permission bitmasks into the result structure using convertBitmaskToArray() to transform integer bitmasks into boolean arrays. This approach ensures that all modules appear in the result even if no permissions have been granted, simplifying UI implementation by providing a complete picture rather than requiring the UI to merge data from multiple sources.

The addModuleToAdminRole() method (RoleModulePermissions.php:63-69) implements a specialized operation for maintaining administrative access when new modules are installed, creating a permission record that grants role ID 1 (the administrative role) full access to the specified module. The hardcoded access value of 139 represents the bitmask for READ (1) + WRITE (2) + ACCESS (4) + CREATE (8) + ADMIN (128), providing comprehensive access without COPY (16), DELETE (32), or DOWNLOAD (64). This asymmetric permission grant reflects that administrators need core CRUD and administrative capabilities but perhaps not all specialized operations, though the exclusion of DELETE seems inconsistent with administrative intent. The method is called during module installation workflows to ensure that administrators can immediately access new functionality without requiring manual permission configuration.

The deleteModuleRelation() method (RoleModulePermissions.php:108-114) implements cleanup operations when modules are removed from the system, querying all role_module_permissions records for the specified module and deleting each one individually. This cascading deletion prevents orphaned permission records that reference non-existent modules, maintaining referential integrity without requiring database foreign key constraints with ON DELETE CASCADE. The method uses fetchAll() with a WHERE clause to retrieve all affected records, then iterates calling delete() on each, an approach that triggers ActiveRecord lifecycle hooks and maintains audit trails compared to bulk DELETE statements that bypass application logic.

### Phprojekt_Role_Information (Information.php:21-56)

The Phprojekt_Role_Information class extends Phprojekt_ModelInformation_Default to provide metadata definitions for the Role model, implementing the setFields() method that declares the structure of role entities. Unlike more complex models like User that define numerous fields with various types and validation rules, the Role model has a remarkably simple structure consisting of only a single user-facing field. The setFields() method (Information.php:49-55) defines the name field as required text with a maximum length of 255 characters, displayed in both list and form views (tab value 1), and positioned first in form rendering (position 1). This minimal structure reflects the design principle that roles are simply named collections of permissions, with the complexity residing in the permission relationships rather than role attributes themselves.

The simplicity of the Role model's structure demonstrates a focused domain model design where each class has a single clear responsibility. Rather than embedding permission data directly in the Role model through complex nested structures, the design separates permission management into the RoleModulePermissions relationship, keeping the Role model clean and maintainable. The parent field referenced in the role database table is notably absent from the Information metadata, suggesting either that hierarchical role relationships are managed through administrative interfaces that bypass standard form generation, or that parent role selection is handled through custom UI logic rather than metadata-driven form controls.

## Public API and Interfaces

The Role library exposes its functionality primarily through the Phprojekt_Role_Role and Phprojekt_Role_RoleModulePermissions model classes, providing both standard ActiveRecord operations for role lifecycle management and specialized methods for permission manipulation. The basic role management workflow involves instantiating a Role object with `new Phprojekt_Role_Role()`, setting the name property through direct assignment, calling save() to persist, and using find($id) or fetchAll() for retrieval. Roles can be modified by loading them via find(), changing properties, and calling save() again, though deletion requires care due to the protection of the administrative role.

The permission management API centers on the saveRights() method which accepts an associative array mapping module IDs to permission bitmasks, providing an atomic operation that replaces all permissions for a role. This high-level API simplifies permission management by allowing UI code to submit the complete desired state without tracking which permissions were added, removed, or modified. The typical workflow involves loading a role with find(), calling getRoleModulePermissionsById() to retrieve current permissions in UI-friendly format, displaying a permission matrix in the UI where users can check/uncheck permission boxes, converting the boolean checkboxes back to bitmasks using Phprojekt_Acl::convertArrayToBitmask(), and calling saveRights() with the resulting module-to-bitmask array.

The query API provides methods for retrieving role and permission information in various formats suitable for different use cases. The standard fetchAll($where, $order) inherited from ActiveRecord enables querying roles with flexible filtering and sorting, commonly used to populate role selection dropdowns in user management interfaces. The getRoleModulePermissionsById($roleId) method returns a comprehensive data structure with all modules and their permission status for a specific role, formatted for permission management UIs with nested arrays containing module metadata and boolean permission flags. The Project_Models_ProjectRoleUserPermissions::fetchUserRole($userId, $projectId) method (while not part of the Role library itself) completes the query API by determining which role a user has in a specific project, integrating the Role library with project-based access control.

The integration API includes specialized methods for system-level operations including addModuleToAdminRole($moduleId) which grants full access to newly installed modules for the administrative role, and deleteModuleRelation($moduleId) which removes all permission records when modules are uninstalled. These methods support the module lifecycle by ensuring that permission state remains consistent as modules are added and removed from the system, automating permission maintenance that would otherwise require manual administrative intervention.

## Dependencies and Integration

The Role library depends fundamentally on the ActiveRecord ORM infrastructure through extension of Phprojekt_ActiveRecord_Abstract, inheriting database abstraction, query construction, and relationship management capabilities. The hasMany relationship to RoleModulePermissions demonstrates the ActiveRecord relationship system where the Role model declares the association and the framework handles query construction, foreign key management, and object graph navigation. The dependency on Zend_Db through the ActiveRecord layer provides database portability and query building capabilities, with both Role and RoleModulePermissions leveraging Zend_Db_Select for complex queries that join across multiple tables.

Integration with the Phprojekt_Acl component provides the critical link between role definitions in the database and runtime access control enforcement. The Phprojekt_Acl constructor calls `new Phprojekt_Role_Role()` and iterates over fetchAll() results to register roles with Zend_Acl through addRole() calls, building the role hierarchy by passing parent role IDs. The ACL constructor also instantiates Phprojekt_Role_RoleModulePermissions and queries all permission records, converting bitmasks to permission arrays via convertBitmaskToArray(), and registering permissions with Zend_Acl through allow() calls that grant specific roles specific access types (read, write, create, etc.) to specific module resources. This initialization occurs once per request during application bootstrap, with the resulting Zend_Acl instance cached and reused for all authorization checks during request processing.

The Module system integration occurs through the role_module_permissions.module_id foreign key relationship and the Phprojekt_Module_Module class that RoleModulePermissions queries to retrieve module lists. The getRoleModulePermissionsById() method filters modules by save_type to include only those that support permission management (save_type 0 for normal modules and 2 for system modules), excluding meta-modules that don't have independent permission requirements. The addModuleToAdminRole() method is called during module installation by the module management system, ensuring that newly installed modules are immediately accessible to administrators without manual configuration. The deleteModuleRelation() method is invoked during module uninstallation, removing obsolete permission records as part of cleanup operations.

The Project module integration through Project_Models_ProjectRoleUserPermissions completes the RBAC model by associating users with roles within project contexts. While the Role library defines what permissions each role has, the ProjectRoleUserPermissions model determines which users have which roles in which projects, implementing project-scoped role assignments rather than global role assignments. The fetchUserRole() method in ProjectRoleUserPermissions queries the project_role_user_permissions table to determine a user's role for a specific project, returning a role ID that can be used with Phprojekt_Acl to check permissions. This three-way association (user-role-project) enables different users to have different roles in different projects, supporting organizational structures where the same person might be a developer in one project and a manager in another.

The validation integration through Phprojekt_Model_Validate provides field-level validation based on metadata from the Information class, ensuring that role names meet length and required constraints before persistence. The validate object maintains error collections that accumulate validation failures, supporting comprehensive error reporting that lists all validation issues rather than failing fast on the first error. The Role model's relatively simple validation requirements (just name presence and length) contrast with more complex models like User that add custom validation logic beyond metadata-driven validation.

## Data Models and Structures

The Role library manages two primary database tables that together implement the role-based access control model. The role table defined in Core/Sql/Db.json contains id (auto-increment primary key), name (varchar required for role identification), and parent (integer nullable foreign key to role.id for hierarchical inheritance). This structure supports hierarchical role organization where roles can inherit from parent roles, though the hierarchy implementation in PHProjekt appears limited compared to full RBAC systems that support multiple inheritance or complex role graphs. The name field provides human-readable identification for roles displayed in user interfaces and administrative tools, while the parent field enables simple single-inheritance hierarchies where child roles automatically inherit all parent permissions through Zend_Acl's role inheritance mechanisms.

The role_module_permissions table implements the many-to-many relationship between roles and modules with permission bitmask storage, containing id (auto-increment primary key), role_id (integer foreign key to role.id), module_id (integer foreign key to module.id), and access (integer storing permission bitmask). The access field uses integer encoding where each bit represents a different permission type: bit 0 (value 1) for READ, bit 1 (value 2) for WRITE, bit 2 (value 4) for ACCESS, bit 3 (value 8) for CREATE, bit 4 (value 16) for COPY, bit 5 (value 32) for DELETE, bit 6 (value 64) for DOWNLOAD, and bit 7 (value 128) for ADMIN. This bitmask encoding allows any combination of permissions to be stored in a single integer field through bitwise OR operations, with permission checks using bitwise AND operations to test for specific rights.

The bitmask encoding scheme provides storage efficiency and computational performance advantages over alternative designs like storing separate boolean columns for each permission type or using a join table with one row per permission grant. A single integer comparison with bitwise AND can check multiple permissions simultaneously, and the compact representation reduces storage requirements and index sizes. However, the bitmask approach has limitations including a fixed maximum number of permission types (8 in this implementation, limited by using bits 0-7 of an integer), less intuitive SQL queries that require bitwise operations rather than simple equality checks, and potential confusion for developers unfamiliar with bit manipulation. The Phprojekt_Acl utility methods convertBitmaskToArray() and convertArrayToBitmask() abstract the bitwise operations behind array interfaces, mitigating some of the complexity.

The project_role_user_permissions table (managed by Project_Models_ProjectRoleUserPermissions rather than the Role library itself) completes the RBAC model by associating users with roles within project contexts, containing id (auto-increment primary key), project_id (foreign key to project.id), user_id (foreign key to user.id), and role_id (foreign key to role.id). This three-way association enables project-scoped role assignments where a user's role varies by project, implementing a contextual RBAC model rather than global role assignments. The table structure supports one role per user per project, preventing conflicting role assignments but potentially requiring multiple records if the same user participates in multiple projects with different roles.

The relationship between these tables implements a hierarchical permission model where User entities have Roles within Project contexts, and Roles have Permissions on Modules. Authorization queries traverse this structure by first determining the user's role in the current project (via project_role_user_permissions), then checking if that role has the required permission on the requested module (via role_module_permissions), with permission checks potentially considering parent role permissions through Zend_Acl's inheritance support. The special administrative role (ID 1) has universal permissions to all modules and cannot be deleted, serving as a failsafe that ensures administrative access regardless of permission configuration issues.

## Configuration and Settings

The Role library operates primarily through database configuration stored in the role and role_module_permissions tables rather than through external configuration files, following the principle that access control policies are dynamic data managed through administrative interfaces rather than static configuration deployed with application code. The only hardcoded configuration in the Role library is the special status of role ID 1 as the administrative role, with the delete() method explicitly checking `if ($this->id > 1)` before allowing deletion and the addModuleToAdminRole() method hardcoding `$this->roleId = 1` when granting permissions to the administrative role. This hardcoded reference to role ID 1 couples the code to the initial data seeding that creates the administrative role during installation, requiring that the administrative role always have ID 1 to maintain proper behavior.

The permission bitmask values are defined as class constants in Phprojekt_Acl rather than configuration values, establishing a fixed permission vocabulary across the entire application. The constants define NONE = 0, READ = 1, WRITE = 2, ACCESS = 4, CREATE = 8, COPY = 16, DELETE = 32, DOWNLOAD = 64, ADMIN = 128, and ALL = 255, with each value representing a specific bit position in the bitmask encoding. These constants provide semantic meaning to bit positions and enable code like `$access | Phprojekt_Acl::READ` to set read permission or `$access & Phprojekt_Acl::WRITE` to check for write permission. The constants are referenced throughout the application for permission checks and grants, making them a critical part of the access control vocabulary that cannot be changed without application-wide refactoring.

The module filtering in getRoleModulePermissionsById() uses save_type values to determine which modules support permission management, with the query including `save_type = 0 OR save_type = 2` to include normal modules and system modules while excluding other module types. This configuration is stored in the module table's save_type field rather than in external configuration, following PHProjekt's pattern of storing system configuration in the database. The save_type values represent a module taxonomy where 0 indicates normal user-created modules, 1 indicates global modules without project association, and 2 indicates system modules that are project-aware but system-defined, with only types 0 and 2 requiring role-based permission management.

The session caching in Project_Models_ProjectRoleUserPermissions::fetchUserRole() uses session namespaces named like `Project_Models_ProjectRoleUserPermissions-fetchUserRole-{projectId}-{userId}` to cache role lookups for performance, reducing database queries for repeated permission checks within a request. This caching strategy trades memory for performance by storing role IDs in session storage, with cache invalidation occurring explicitly in the saveRelation() method through `$roleNamespace->unsetAll()` calls when role assignments change. The session-based caching approach requires careful invalidation management to prevent stale permission data from causing security issues, with the current implementation handling invalidation during save operations but potentially missing invalidation scenarios like role deletion or permission changes.

## Design Patterns and Principles

The Role-Based Access Control (RBAC) pattern forms the architectural foundation of the Role library, implementing the standard RBAC model where Users are assigned Roles, Roles are granted Permissions, and authorization checks evaluate whether the user's assigned role has the required permission for the requested operation. This pattern decouples users from permissions through the role abstraction, enabling permission management at the role level rather than requiring per-user permission grants. The RBAC pattern supports organizational permission policies where multiple users share the same role and receive the same permissions, simplifying administration compared to user-level permission management while maintaining flexibility through role assignments that can vary by user and context.

The Active Record pattern dominates the implementation through extension of Phprojekt_ActiveRecord_Abstract by both Role and RoleModulePermissions classes, embodying the pattern's principle that domain objects know how to persist themselves and encapsulate both data and database access logic. This pattern simplifies the API by providing save() and delete() methods directly on domain objects rather than requiring separate repository classes, making role management code more intuitive for developers familiar with Active Record. The trade-off involves tighter coupling between domain logic and persistence mechanisms, making it more challenging to test domain logic in isolation or swap persistence implementations, though PHProjekt consistently applies Active Record throughout the codebase.

The Information Object pattern (also called Metadata or Descriptor pattern) separates the definition of model structure from the model itself through the Phprojekt_Role_Information class, enabling introspection of field definitions without hardcoding structure knowledge throughout the application. This pattern enables generic form generation that reads field definitions to determine UI controls, generic validation that applies rules defined in metadata, and generic serialization that transforms between representations based on field types. The separation between model and metadata supports maintainability by keeping structure definitions in one location that can be updated without modifying multiple files, though the Role model's simple structure with a single field makes the benefits less apparent than in more complex models.

The Bitmask pattern implements efficient storage and checking of multiple boolean permissions through integer encoding where each bit represents a different permission flag. This pattern enables operations like granting multiple permissions through a single integer value, checking for specific permissions with bitwise AND operations, and combining permissions with bitwise OR operations, all with performance superior to alternative designs involving multiple columns or join tables. The pattern's use in the access field of role_module_permissions demonstrates space-efficient permission storage that scales to eight distinct permission types (limited by using an 8-bit portion of the integer), though extending beyond eight permissions would require additional storage fields or a different encoding scheme.

The Protected Variation pattern appears in the delete() method's protection of the administrative role, encapsulating the variation point of "which roles can be deleted" behind a conditional check that prevents deletion of role ID 1. This pattern protects the system from variation in administrative intent (users might accidentally attempt to delete critical roles) by making the business rule explicit in code rather than relying on external documentation or user training. The silent failure approach where delete() simply doesn't execute for the administrative role (rather than throwing an exception) represents a specific design choice that prioritizes robustness over explicit error signaling, though it may surprise developers expecting delete() to either succeed completely or throw an exception.

The Replace-All pattern appears in saveRights() which deletes all existing permissions before creating new ones, implementing an atomic replacement operation that ensures the database state exactly matches what was submitted. This pattern simplifies permission management by avoiding complex diff operations to determine which permissions were added, removed, or modified, instead treating each save as a complete replacement of the permission set. The trade-off involves potentially higher database overhead (deleting and recreating unchanged permissions) compared to incremental updates, though the simplicity and correctness benefits typically outweigh performance concerns for permission management operations that occur infrequently.

The Session Caching pattern in ProjectRoleUserPermissions::fetchUserRole() implements performance optimization by storing frequently accessed role lookups in session storage, avoiding repeated database queries for the same user-project combination within a request or across requests in the same session. This pattern trades memory for performance by caching query results, with explicit cache invalidation in saveRelation() ensuring that permission changes are reflected in subsequent queries. The session-scoped caching (rather than request-scoped or application-scoped) balances performance with memory constraints, though it requires careful invalidation management to prevent security issues from stale cached permissions.

The Hierarchical Role pattern supports role inheritance through the parent field in the role table, enabling child roles to automatically inherit all parent permissions while potentially adding additional permissions. This pattern reduces permission grant redundancy by defining permissions at parent role levels and having child roles inherit them, supporting organizational hierarchies like "Manager extends Developer extends User" where each level adds permissions without duplicating grants from parent levels. The implementation through Zend_Acl's addRole() with parent parameter leverages the framework's built-in inheritance support, though PHProjekt's usage appears limited compared to full RBAC systems that extensively leverage role hierarchies.
