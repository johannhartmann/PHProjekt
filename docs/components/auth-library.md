# Component: Auth

## Overview

The Auth library provides the complete authentication and authorization infrastructure for PHProjekt 6, managing user identity verification, session persistence, remember-me functionality through cookies, and user impersonation capabilities for proxy access. This library extends Zend Framework's Zend_Auth component to integrate authentication seamlessly with PHProjekt's user management system, supporting both traditional database-backed authentication and enterprise LDAP directory service integration for single sign-on scenarios. The authentication system operates primarily through stateless static methods that interact with Zend_Session for session management and the Phprojekt_Setting system for persistent token storage, providing a clean API that controllers and business logic can invoke without managing complex state or configuration details.

The library implements a sophisticated "remember me" feature that allows users to maintain authenticated sessions across browser restarts through secure token-based cookie authentication. When users opt to remain logged in, the system generates a random hash token stored both in the database (via Phprojekt_Setting) and in browser cookies, with an expiration timestamp set one week in the future. On subsequent visits, if no active session exists, the isLoggedIn() method automatically validates the cookie token against the database, regenerates the token for enhanced security, and restores the user session without requiring credential re-entry. This approach balances security with user convenience by limiting token lifetime, rotating tokens on each use, and storing them separately from user credentials.

The proxy authentication feature enables designated users to impersonate other users for administrative support, workflow delegation, and temporary access scenarios common in enterprise environments. The Phprojekt_Auth_Proxy class manages proxy relationships through the user_proxy database table, enforcing access control rules that determine which users can impersonate whom. The Phprojekt_Auth_ProxyTable class provides database abstraction for proxy relationship management, supporting bidirectional queries to retrieve both the users a person can impersonate and the users who can impersonate a given person. This proxy system integrates with the broader access control infrastructure to ensure that proxied sessions respect the impersonated user's permissions while maintaining audit trail capabilities for security and compliance requirements.

The authentication modes supported by the library include a default mode using database-stored credentials with MD5-based password hashing, and an LDAP mode that authenticates against directory services like Active Directory or OpenLDAP while synchronizing user profile information back to the PHProjekt database. The LDAP integration supports multi-server configurations where users can authenticate against different LDAP domains, with automatic user provisioning that creates PHProjekt user accounts on first login and updates profile information (firstname, lastname, email) from LDAP attributes on subsequent logins. The flexible configuration allows system administrators to designate LDAP users as PHProjekt administrators based on username matching or default role assignments, enabling seamless integration with existing enterprise identity management infrastructure.

## Component Structure

| File/Directory | Purpose |
|----------------|---------|
| `Auth.php` | Main authentication class extending Zend_Auth with login, logout, session management, cookie-based remember-me, LDAP integration, and credential verification (719 lines) |
| `Auth/Exception.php` | Specialized exception class for authentication errors including invalid credentials, inactive users, LDAP failures, and configuration issues |
| `Auth/Proxy.php` | Proxy authentication manager enabling user impersonation with access control enforcement and effective user tracking (140 lines) |
| `Auth/ProxyTable.php` | Database abstraction layer for user_proxy table operations including relationship queries and validation (239 lines) |

The Auth library follows a clear organizational structure with the main Phprojekt_Auth class at the root level and specialized supporting classes in the Auth subdirectory. This structure separates the core authentication logic from the proxy impersonation feature, making the codebase easier to navigate and maintain. The Phprojekt_Auth class provides all fundamental authentication operations through static methods, making it accessible from any part of the application without requiring instantiation or dependency injection. The supporting classes (Proxy, ProxyTable, Exception) encapsulate specific functionality domains, with Proxy handling the business logic of user impersonation and ProxyTable providing clean database access patterns that abstract SQL queries behind an object-oriented interface.

## Key Classes and Files

### Phprojekt_Auth (Auth.php:19-718)

The Phprojekt_Auth class serves as the central authentication authority for the entire application, extending Zend_Auth to leverage its adapter-based authentication architecture while adding PHProjekt-specific features like persistent login cookies, LDAP integration with user synchronization, and integration with the application's user and settings infrastructure. The class operates entirely through static methods, providing a functional API that controllers and business logic can invoke without managing object lifecycle or state. The design choice to use static methods reflects the singleton nature of authentication in web applications where a single authenticated user exists per request, though this approach trades testability for convenience in a pre-dependency-injection era codebase.

The isLoggedIn() method (Auth.php:42-94) implements the primary authentication check used throughout the application, examining both active session state and persistent cookie tokens to determine user authentication status. The method first checks the Zend_Session_Namespace('Phprojekt_Auth-login') for userId and admin properties that indicate an active authenticated session. If no session exists, the method examines browser cookies for the remember-me token, reading both the hash and user ID cookies with names derived from the COOKIES_PREFIX constant. When valid cookies exist, the method retrieves the corresponding token hash and expiration timestamp from the database via Phprojekt_Setting, validates that the token has not expired, compares the cookie hash with the database hash, and if all checks pass, loads the user object and populates the session namespace with user information. This two-tier authentication approach (session then cookies) optimizes performance by avoiding database queries when sessions are active while providing seamless authentication restoration when users return after session expiration.

The login() method (Auth.php:118-148) orchestrates the authentication process by first determining the authentication mode from configuration (default or ldap), delegating to mode-specific authentication logic (_defaultLogin or _ldapLogin), regenerating the session ID on successful authentication to prevent session fixation attacks, and throwing Phprojekt_Auth_Exception with appropriate error codes and messages on authentication failures. The method accepts a username and password as required parameters, plus an optional loginOptions array that can specify keepLogged (boolean for remember-me functionality) and loginServer (string identifying the LDAP server for authentication). The error handling uses numbered exception codes (2-11) that distinguish between different failure scenarios including invalid credentials (code 2-4), inactive user accounts (code 5), LDAP configuration errors (code 7-9), and user provisioning failures (code 10-11), enabling calling code to provide specific user feedback or take different actions based on failure type.

The _defaultLogin() method (Auth.php:150-192) implements database-backed authentication by querying the Phprojekt_User_User model to find the user by username, validating that the user account is active through the isActive() check, retrieving the stored password hash from Phprojekt_Setting, comparing the provided password with the stored hash using _compareStringWithPassword(), and on success populating the Zend_Session_Namespace with userId and admin flag. The method handles the keepLogged option by calling _saveLoginData() to generate and store authentication tokens when users opt to remain logged in. The password comparison uses a custom cryptographic scheme that prepends "phprojektmd5" to the password before hashing with MD5, a scheme that provides minimal security by modern standards but was common in the era of this application's development. The method explicitly throws exceptions for various failure conditions including user not found, inactive account, and password mismatch, with all exceptions providing the generic "Invalid user or password" message to prevent username enumeration attacks.

The _ldapLogin() method (Auth.php:194-230) implements LDAP authentication by first checking that the LDAP PHP extension is loaded, retrieving LDAP configuration from Phprojekt configuration, creating a Zend_Auth_Adapter_Ldap with the configuration and credentials, attempting authentication through the Zend_Auth_Adapter_Ldap adapter which handles the LDAP bind operation and searches multiple configured LDAP servers, and on successful LDAP authentication calling _ldapIntegration() to synchronize user information with the PHProjekt database. The method explicitly excludes the system administrator account (userId 1) from LDAP authentication, always requiring default authentication for this account to ensure administrative access even when LDAP services are unavailable. After LDAP authentication succeeds and integration completes, the method delegates to _defaultLogin() to establish the session, ensuring that LDAP-authenticated users follow the same session lifecycle as locally-authenticated users. The error handling distinguishes between authentication failures (wrong username/password) which are expected and should cascade to local authentication, and system errors (LDAP server unavailable, configuration issues) which are logged and result in exception throws with administrator-facing error messages.

The _ldapIntegration() method (Auth.php:232-390) implements sophisticated user provisioning and synchronization by establishing a direct LDAP connection to search for the authenticated user's attributes, extracting profile information (givenname, sn, mail) from LDAP attributes, determining whether the user exists in PHProjekt by checking the provided userId parameter, and either updating an existing user or creating a new user with information from LDAP combined with configuration-driven defaults. The LDAP search uses a filter that matches both posixAccount and Person object classes with either uid or samAccountName attributes, providing compatibility with both Unix-style LDAP schemas and Active Directory. For new users, the method applies defaults from configuration including admin status (determined by checking if username appears in the systemAdmins configuration list), account status (Active or Inactive), language preference, and timezone, allowing administrators to define standard settings for auto-provisioned users. The method includes a security-questionable but pragmatic hack where it temporarily sets the session to admin user (userId 1) to gain permissions for user creation operations, then clears the session, demonstrating the challenges of implementing cross-cutting features in systems with pervasive permission checking.

The logout() method (Auth.php:493-512) implements secure logout by retrieving the user ID from either the active session or remember-me cookies, calling _deleteDbAndCookies() to remove persistent authentication tokens and expire cookies, and destroying the entire session through Zend_Session::destroy() to ensure all session data is cleared. This comprehensive logout prevents session hijacking or token replay attacks by ensuring that all authentication artifacts are removed from both client and server. The method handles cases where logout is invoked without an active session by attempting to read the user ID from cookies, ensuring that the cleanup can proceed even when the session has already expired or been invalidated.

The getUserId() method (Auth.php:450-460) and isAdminUser() method (Auth.php:477-486) provide the primary API for authorization checks throughout the application, reading from the Zend_Session_Namespace('Phprojekt_Auth-login') to retrieve the currently authenticated user's ID and admin status. These methods return 0 or false when no user is authenticated, enabling calling code to use simple truthiness checks like `if (Phprojekt_Auth::getUserId())` to verify authentication. The getRealUser() method (Auth.php:462-470) implements a static cache pattern to avoid repeatedly querying the database for user information, loading the Phprojekt_User_User object once and returning the same instance on subsequent calls within a request.

The cookie management methods _saveLoginData() (Auth.php:619-660) and _deleteDbAndCookies() (Auth.php:590-610) handle the persistent authentication token lifecycle by generating random MD5 hashes based on time and random numbers, storing these hashes along with expiration timestamps in the Phprojekt_Setting system under the User module with keys keepLoggedToken_hash and keepLoggedToken_expires, and setting browser cookies with matching values and expiration times. The token generation on each use (rather than generating once and reusing) implements a token rotation strategy that limits the window of vulnerability if tokens are compromised. The _setCookies() method (Auth.php:707-717) handles the technical details of cookie setting including path extraction from configuration (to support installations in subdirectories), cookie naming with the COOKIES_PREFIX constant, and expiration time management, with conditional execution that skips cookie operations when headers have already been sent (supporting unit test execution).

### Phprojekt_Auth_Proxy (Auth/Proxy.php:21-139)

The Phprojekt_Auth_Proxy class manages user impersonation functionality that enables designated users to act on behalf of other users for administrative support, troubleshooting, and delegation scenarios. The class maintains a static $_effectiveUser property that tracks the currently impersonated user separate from the authenticated user stored in the session, enabling the application to distinguish between who is logged in (the real user) and who is being impersonated (the effective user). This separation allows the application to maintain proper audit trails showing both the actor and the identity being assumed, critical for compliance and security investigations. The class operates entirely through static methods following the same pattern as Phprojekt_Auth, providing a simple API that controllers and business logic can use without managing object state.

The switchToUserById() method (Proxy.php:40-51) implements the core impersonation functionality by accepting a target user ID (or NULL to switch back to the real user), validating that the authenticated user has proxy rights to impersonate the target through hasProxyRightForUserById(), and if authorized calling _setEffectiveUserById() to update the effective user. The method throws Phprojekt_Auth_Exception when the user lacks permission to impersonate the target, providing a clear security boundary that prevents unauthorized impersonation attempts. The design allows switching back to the real user by passing NULL, implementing a stack-like behavior where users can "push" into impersonation and "pop" back out, though the current implementation only supports one level deep rather than nested impersonation chains.

The hasProxyRightForUserById() method (Proxy.php:58-65) determines whether the authenticated user can impersonate a target user by first checking if the target is the current effective user (always allowed, supporting the switch-back-to-real-user case), and if not delegating to the ProxyTable's hasProxyRights() method which queries the user_proxy table. This method provides the authorization check used both by switchToUserById() and by UI code that needs to determine whether to display impersonation controls. The getEffectiveUser() method (Proxy.php:72-80) and getEffectiveUserId() method (Proxy.php:87-90) provide the primary API for retrieving the currently effective user, implementing lazy initialization that loads from the session if no explicit impersonation is active. The isAdminUser() method (Proxy.php:97-100) checks whether the effective user (not the real user) has administrator privileges, ensuring that impersonation extends to permission checking and enabling administrators to impersonate non-admin users with correctly limited privileges.

### Phprojekt_Auth_ProxyTable (Auth/ProxyTable.php:21-238)

The Phprojekt_Auth_ProxyTable class provides database abstraction for the user_proxy table, implementing create, read, and query operations for proxy relationships while enforcing validation rules and providing convenient high-level methods. The class wraps Zend_Db_Table functionality through a private $_proxyTable property initialized in the constructor, following the Table Data Gateway pattern where a single class provides all database operations for a specific table. The constructor accepts an optional Zend_Db_Adapter_Abstract parameter with a default of NULL, automatically obtaining the application's default database adapter from the Phprojekt singleton when no adapter is provided, supporting both production use and test scenarios that require isolated databases.

The setProxyIdsForUserId() method (ProxyTable.php:49-66) implements atomic proxy relationship management by accepting an array of user IDs that should be allowed to impersonate the specified user, clearing all existing proxy relationships for that user through _clearProxiesForUserId(), validating each provided user ID through _isValidUserId(), building an array of row data with proxying_id and proxyed_id columns, and inserting all rows through _insertRowsIntoProxyTable(). This replace-all approach simplifies UI implementation by allowing forms to submit the complete list of proxy users without requiring complex add/remove operations, though it requires care with concurrent modifications since the clear-then-insert sequence is not wrapped in an explicit transaction. The method defaults the target user ID to the currently authenticated user when NULL is provided, supporting the common case where users manage their own proxy list.

The getProxyableUserIdsForUserId() method (ProxyTable.php:76-93) implements the forward direction query that retrieves user IDs the specified user can impersonate, executing a SELECT with WHERE proxying_id = ? to find all relationships where the user is the impersonator. The getProxyableUsersForUserId() method (ProxyTable.php:103-115) builds on this by loading full Phprojekt_User_User objects for each ID, providing a higher-level API that returns complete user objects rather than just IDs. The getProxyIdsForUserId() method (ProxyTable.php:125-143) implements the inverse direction query that retrieves user IDs who can impersonate the specified user, executing a SELECT with WHERE proxyed_id = ? to find all relationships where the user is being impersonated. These bidirectional query methods enable different UI scenarios including showing a user who they can impersonate, and showing an administrator which users have been granted proxy access to a specific account.

The hasProxyRights() method (ProxyTable.php:153-165) implements the authorization check used by Phprojekt_Auth_Proxy, accepting both source user ID (the impersonator) and target user ID (the impersonated), executing a SELECT with both WHERE proxyed_id = ? AND proxying_id = ? conditions, and returning boolean true when a matching row exists or false when no relationship exists. This method encapsulates the security-critical query that determines impersonation authorization, with the two-parameter design making the authorization semantics explicit and preventing confusion about direction. The validation helper methods _isValidUserId() (ProxyTable.php:183-198) and _throwOnInvalidUserId() (ProxyTable.php:176-181) enforce that user IDs are numeric, positive, and correspond to existing users in the database by attempting to find the user and checking success, preventing foreign key violations and improving error messages by catching invalid IDs before database operations.

### Phprojekt_Auth_Exception (Auth/Exception.php:19-63)

The Phprojekt_Auth_Exception class extends PHP's standard Exception class to provide specialized error handling for authentication and authorization failures, enabling calling code to catch and handle authentication errors separately from other application exceptions. The exception type is thrown throughout the Auth library for various error conditions including invalid credentials during login, inactive user accounts, missing LDAP extension, LDAP server connectivity failures, LDAP configuration errors, LDAP user provisioning failures, and unauthorized impersonation attempts. The constructor follows the standard Exception signature with a message string and optional error code, allowing the throwing code to provide both human-readable error messages and numeric error codes that enable programmatic error handling.

The error code scheme used by the Auth library provides semantic categorization of failure types, with codes 2-4 representing various credential validation failures that should be presented to users with the same generic message to prevent username enumeration, code 5 indicating inactive account status that may warrant specific messaging, code 7 indicating LDAP extension not loaded (configuration/deployment issue), codes 8-9 representing LDAP configuration or connectivity issues that require administrator intervention, and codes 10-11 representing user provisioning failures during LDAP integration. This error code scheme enables login controllers to distinguish between user-facing errors (wrong password) and system-facing errors (LDAP server down) to provide appropriate feedback and logging.

## Public API and Interfaces

The Auth library exposes its functionality primarily through static methods on the Phprojekt_Auth and Phprojekt_Auth_Proxy classes, following a functional programming style that reflects the singleton nature of authentication in web request processing. The primary authentication workflow involves calling Phprojekt_Auth::isLoggedIn() to check authentication status (typically in a front controller or base controller preDispatch() hook), redirecting to login when not authenticated, accepting credentials from the login form and calling Phprojekt_Auth::login($username, $password, $options), handling Phprojekt_Auth_Exception for credential validation failures, and on successful authentication proceeding with request processing. Throughout request handling, code retrieves the authenticated user's ID with Phprojekt_Auth::getUserId() and checks administrator status with Phprojekt_Auth::isAdminUser() to enforce authorization policies.

The proxy authentication workflow extends the basic authentication with impersonation capabilities, enabling users to switch contexts to act on behalf of others. The typical flow involves checking if the user has proxy rights with Phprojekt_Auth_Proxy::hasProxyRightForUserById($targetUserId), calling Phprojekt_Auth_Proxy::switchToUserById($targetUserId) to initiate impersonation when authorized, using Phprojekt_Auth_Proxy::getEffectiveUserId() instead of Phprojekt_Auth::getUserId() in business logic that should respect impersonation, and calling Phprojekt_Auth_Proxy::switchToUserById(NULL) or switchToUserById(Phprojekt_Auth::getUserId()) to end impersonation. This dual-API approach (Auth for real user, Proxy for effective user) requires careful attention in authorization checks to use the appropriate API depending on whether impersonation should be respected or explicitly checked against the real authenticated user.

The cookie-based remember-me feature operates transparently without explicit API calls, activated by passing keepLogged => true in the login options array. When enabled, the system automatically manages token generation, storage, and validation on subsequent requests through isLoggedIn(). Application code need not interact with cookie management directly, with all token handling encapsulated within the Auth class. The logout process requires only calling Phprojekt_Auth::logout() which handles cleanup of both session and persistent tokens. This design provides a high-level API that handles the security-sensitive details of persistent authentication while requiring minimal integration effort from application developers.

## Dependencies and Integration

The Auth library depends fundamentally on Zend Framework's authentication and session management components, specifically Zend_Auth which provides the adapter-based authentication architecture, Zend_Session and Zend_Session_Namespace for session state management across requests, Zend_Auth_Adapter_Ldap for LDAP directory service authentication, Zend_Ldap for direct LDAP server communication during user synchronization, and Zend_Db_Table for database operations in ProxyTable. The extension of Zend_Auth by Phprojekt_Auth enables the library to leverage Zend's authentication adapters while adding PHProjekt-specific features like cookie-based token authentication, LDAP user provisioning, and integration with the application's user management system. The use of Zend_Session_Namespace with the identifier 'Phprojekt_Auth-login' ensures isolation from other session data while maintaining consistent access patterns throughout the application.

Integration with the PHProjekt ecosystem occurs through multiple touchpoints including the Phprojekt_User_User model which provides user CRUD operations and username lookup via findIdByUsername(), the Phprojekt_Setting system which stores user-specific configuration including password hashes and persistent authentication tokens, the Phprojekt singleton which provides configuration access for authentication mode and LDAP settings, the Cleaner utility class which sanitizes user input in login controllers, and the Phprojekt_Loader which handles dynamic class loading for user creation during LDAP provisioning. The authentication system serves as a critical security boundary referenced throughout the application, with controllers checking isLoggedIn() in preDispatch() hooks, base classes like Default_Controllers_IndexController enforcing authentication requirements, and business logic using getUserId() and isAdminUser() for authorization decisions.

The LDAP integration demonstrates sophisticated external system integration by supporting multi-server LDAP configurations defined in the configuration.php file, attribute mapping between LDAP schemas (Active Directory and Unix/POSIX) and PHProjekt user properties, automatic user provisioning that creates local accounts on first LDAP login, synchronization of profile information from LDAP to PHProjekt on each login, and configuration-driven role assignment for auto-provisioned users. This integration enables PHProjekt to participate in enterprise single sign-on infrastructure while maintaining local user records for authorization, preferences, and application-specific data. The fallback behavior where LDAP authentication failure cascades to local authentication provides resilience against directory service outages while maintaining security by requiring correct credentials against one of the authentication sources.

## Data Models and Structures

The Auth library directly manages the user_proxy database table which implements the many-to-many relationship between users for impersonation authorization. The table structure consists of proxying_id (integer foreign key to user.id representing the user who can impersonate), proxyed_id (integer foreign key to user.id representing the user being impersonated), and likely a primary key combining these fields to ensure uniqueness though the code doesn't explicitly reference it. This simple two-column junction table enables bidirectional queries to answer both "who can user A impersonate" and "who can impersonate user A", critical for different UI and administrative scenarios. The table name user_proxy follows PHProjekt's naming convention of lowercase with underscores separating words.

The Auth library interacts with but does not directly manage several other database tables and data structures including the user table (managed by Phprojekt_User_User) which stores user credentials, profile information, and status, the setting table (managed by Phprojekt_Setting) which stores user-specific configuration including password hashes and persistent authentication tokens, and the session storage mechanism (managed by Zend_Session) which may be database-backed or file-based depending on configuration. The keepLoggedToken_hash and keepLoggedToken_expires settings stored in the setting table implement the persistent authentication token system, with the hash storing an MD5 value that must match the cookie value and the expires storing a Unix timestamp beyond which the token is invalid.

The session structure maintained in Zend_Session_Namespace('Phprojekt_Auth-login') contains userId (integer ID of the authenticated user) and admin (boolean flag indicating administrator status), representing the minimal authentication state required by the application. This lean session structure avoids storing large user objects in sessions, instead loading user details on demand through getUserId() lookups. The Phprojekt_Auth_Proxy class extends this with a static $_effectiveUser property that caches the impersonated user object when proxy authentication is active, though this caching occurs in PHP memory rather than session storage and is therefore request-scoped. The separation of authenticated user (in session) and effective user (in static property) enables the application to maintain proper audit trails showing both the actor and the assumed identity.

## Configuration and Settings

The Auth library's behavior is controlled primarily through the configuration.php file which defines authentication mode, LDAP server settings, and integration parameters. The authentication.mode configuration setting determines whether to use 'default' database authentication or 'ldap' directory service authentication, with the system defaulting to 'default' if the setting is missing or invalid. The LDAP mode requires extensive additional configuration under authentication.ldap including arrays for each LDAP server (supporting multi-domain environments) with settings for host, port, baseDn, accountDomainName, accountCanonicalForm, username, password, bindRequiresDn, and other Zend_Ldap options. Each LDAP server configuration represents a separate directory service that users might authenticate against, with the loginServer parameter during login specifying which server to use for a particular authentication attempt.

The authentication.integration configuration section controls behavior during LDAP user provisioning including systemAdmins (comma-separated list of usernames that should be granted administrator privileges), admin (default value 0 or 1 for the admin flag on auto-provisioned users), status (default value 'A' or 'I' for the status field), language (default language code like 'en' or 'de'), and timeZone (default timezone identifier). These integration settings enable administrators to define standard defaults for LDAP-authenticated users without requiring manual account creation, critical for large organizations where users expect immediate access after LDAP authentication succeeds. The systemAdmins list provides explicit control over which LDAP users receive elevated privileges, implementing a whitelist approach that prevents privilege escalation through LDAP attribute manipulation.

The cookie configuration draws from the webpath setting in the main configuration, using this to extract the path component for cookie scope. The COOKIES_PREFIX constant defined in the Auth class ('p6.') provides a namespace for PHProjekt cookies to avoid conflicts with other applications on the same domain. The cookie naming scheme combines this prefix with the token type (LOGGED_TOKEN) and value type (hash or user), resulting in cookie names like 'p6_keepLoggedToken_hash' and 'p6_keepLoggedToken_user' (with dots converted to underscores per PHP's cookie naming rules). The token expiration of one week (strtotime('+1 week')) balances security with user convenience, requiring re-authentication if users don't access the application for a week while avoiding daily login prompts.

## Design Patterns and Principles

The Static Method pattern dominates the Auth library's design, with both Phprojekt_Auth and Phprojekt_Auth_Proxy providing their entire API through static methods rather than instance methods. This design choice reflects the singleton nature of authentication in web applications where exactly one authenticated user exists per request, eliminating the need for object instantiation or dependency injection. The approach simplifies calling code by removing the need to pass authentication objects through call chains, though it creates challenges for unit testing by introducing global state and making mock injection difficult. This pattern was common in PHP frameworks from the mid-2000s before dependency injection containers became standard practice, representing the architectural style of that era.

The Strategy pattern appears in the authentication mode selection where the login() method determines at runtime whether to delegate to _defaultLogin() or _ldapLogin() based on configuration. This pattern enables runtime selection between authentication algorithms without requiring calling code to understand implementation details, supporting both local development with database authentication and production deployment with enterprise directory services. The mode selection creates a plugin-like architecture where additional authentication strategies could be added by extending the mode detection logic and implementing new strategy methods, though the current implementation hard-codes the two supported modes rather than implementing a fully pluggable strategy system.

The Template Method pattern structures the authentication workflows where high-level methods like login() define the overall algorithm (determine mode, authenticate, regenerate session, return result) while delegating specific steps to protected methods like _defaultLogin() and _ldapLogin(). This pattern enables the high-level workflow to enforce consistent security practices like session regeneration and exception handling while allowing variation in the credential validation logic. The _ldapLogin() method further applies this pattern by handling LDAP-specific operations (directory service authentication, user provisioning) before delegating to _defaultLogin() for session establishment, demonstrating how template methods can compose to build layered algorithms.

The Facade pattern characterizes the ProxyTable class which provides a simplified object-oriented interface over complex SQL operations against the user_proxy table. Rather than requiring calling code to construct Zend_Db_Select objects with appropriate WHERE clauses, the ProxyTable exposes high-level methods like getProxyableUserIdsForUserId() and hasProxyRights() that encapsulate query construction and result processing. This pattern reduces code duplication where multiple parts of the application need to query proxy relationships, centralizes SQL in one location for easier maintenance and optimization, and provides a natural place to add caching or additional business logic if needed in the future.

The Token-Based Authentication pattern implements the remember-me feature through rotating tokens stored in both cookies and the database. Each time a user authenticates via token, the system generates a new random token rather than reusing the same token for the entire validity period. This rotation strategy limits the window of vulnerability if tokens are intercepted, as the captured token becomes invalid after the legitimate user's next request regenerates it. The dual storage (cookie for client-side presentation, database for server-side validation) prevents token forgery by requiring an attacker to compromise both the client and server to generate valid tokens. The one-week expiration with timestamp-based validation enforces maximum token lifetime regardless of rotation, ensuring periodic re-authentication even for frequently used tokens.

The Proxy pattern (in the design patterns sense, not the user impersonation feature) appears in how Phprojekt_Auth_Proxy wraps authorization checks and user retrieval with impersonation-aware logic. Methods like getEffectiveUserId() and isAdminUser() delegate to either the session-based authentication (real user) or the static property (impersonated user) depending on whether impersonation is active, providing a consistent API that automatically accounts for impersonation context. This pattern enables business logic to use Proxy methods throughout without explicit impersonation checks, as the proxy handles the complexity of determining which user identity to use. The hasProxyRightForUserById() check implements the protection proxy variant by enforcing access control rules before allowing operations to proceed.
