# Component: Migration

## Overview

The Migration library provides database schema evolution and data migration capabilities for PHProjekt 6, implementing a version-aware upgrade system that enables modules to define upgrade procedures executed automatically when code versions exceed database versions. This library manages the complete migration lifecycle including discovering modules requiring upgrades through version comparison, coordinating upgrade execution across multiple modules, tracking database schema versions in the module table, and providing a framework for module-specific migration implementations through abstract base classes. The migration system ensures that PHProjekt installations can be upgraded smoothly from older versions to newer versions without manual SQL execution or data loss, supporting both schema changes (adding tables, modifying columns) and data transformations (converting formats, populating new fields).

The library architecture follows a coordinator-worker pattern where the Phprojekt_Migration class serves as the coordinator that discovers which modules need upgrading and orchestrates the upgrade process, while module-specific Phprojekt_Migration_Abstract subclasses act as workers that implement the actual upgrade logic for their respective modules. The coordinator discovers migration workers through the Phprojekt_Extensions system which enables modules to register migration implementations, queries the database to determine current installed versions, compares installed versions with code versions using semantic version comparison, and builds a list of modules requiring upgrades. The worker implementations extend Phprojekt_Migration_Abstract to define their current version through getCurrentModuleVersion() and implement upgrade logic through the upgrade() method that receives the current database version and performs necessary transformations.

The version comparison system uses semantic versioning where versions are compared as dotted-decimal strings like "1.2.3", with the comparison logic implemented in Phprojekt::compareVersion() returning negative when database version is older than code version (upgrade needed), zero when versions match (no upgrade needed), and positive when database version is newer than code version (downgrade scenario). The comparison enables fine-grained upgrade control where modules can define migrations that handle multiple version jumps (like upgrading from 1.0 to 1.3) or single-step migrations that chain together through multiple upgrade calls. The version tracking in the module table's version column provides persistent storage of installed versions that survives application restarts and enables incremental upgrades where administrators can upgrade modules one at a time rather than requiring all-or-nothing upgrades.

The error handling system implements a three-tier approach where recoverable errors are handled through standard exceptions that enable transaction rollback and retry, unrecoverable errors that leave the database in inconsistent state are signaled through Phprojekt_Migration_IKilledTheDatabaseException requiring manual intervention, and success results in cache clearing through Zend_Cache::CLEANING_MODE_ALL to ensure that cached metadata reflects the upgraded schema. The detailed documentation in the abstract class emphasizes the importance of transactions for atomicity, providing guidance on how to handle DDL operations that can't be rolled back in MySQL, and establishing clear error handling contracts that enable calling code to distinguish between fixable problems and critical failures requiring administrative intervention.

This three-class structure demonstrates clear separation between coordination logic, migration contracts, and error signaling.

## Key Classes and Files

### Phprojekt_Migration (Migration.php:19-225)

The Phprojekt_Migration class serves as the central coordinator for database migrations, managing the discovery of modules requiring upgrades and orchestrating the execution of their migration procedures. The class maintains a protected _migrations array that maps module names to Phprojekt_Migration_Abstract instances, and a private _modulesNeedingUpgrade property that caches the upgrade analysis results to avoid repeated database queries. The constructor accepts a Phprojekt_Extensions object and iterates over registered extensions, calling getMigration() on each to retrieve migration implementations and storing them through registerMigration(). This initialization builds a registry of all available migrations that can be queried and executed as needed.

The getModulesNeedingUpgrade() method (Migration.php:74-119) implements the core upgrade detection logic by first checking if results are cached in _modulesNeedingUpgrade and returning immediately when available, querying the module table through a SELECT of name and version columns with results indexed by lowercase module name, iterating over registered migrations to compare versions, calling getCurrentModuleVersion() on each migration to determine code version, checking if the module exists in database results indicating prior installation, and for installed modules calling Phprojekt::compareVersion() to determine version relationship. When the database version is lower than code version (compare < 0), the method adds the module to the return array with from (database version), to (code version), and migration (migration object) keys. For modules not in the database (new installations), the method adds them with from = null, to = code version, and the migration object. The method caches results in _modulesNeedingUpgrade before returning, implementing request-scoped memoization.

The needsUpgrade() method (Migration.php:128-137) provides a convenient boolean check by calling getModulesNeedingUpgrade() to retrieve the full analysis, returning true if any modules need upgrading when no specific module is specified, or checking if the specified module exists in the results when a module name is provided. This method enables simple conditionals like `if ($migration->needsUpgrade())` without requiring calling code to understand the complex upgrade analysis structure, demonstrating the facade pattern where simple interfaces hide complex implementation details.

The performAllUpgrades() method (Migration.php:147-152) implements batch upgrade execution by calling getModulesNeedingUpgrade() to retrieve all modules requiring upgrades, iterating over the array keys (module names), and calling performUpgrade() for each module. This simple iteration delegates all complexity to performUpgrade(), implementing a template where the batch operation is just repeated single operations. The method's documentation warns that it can throw both regular exceptions (recoverable errors) and IKilledTheDatabaseException (unrecoverable errors), establishing clear exception contracts that calling code must handle appropriately.

The performUpgrade() method (Migration.php:201-224) implements single-module upgrade execution by first validating that a migration object exists for the specified module throwing standard Exception if not found, checking that the module needs upgrading through needsUpgrade() throwing Exception if already current, retrieving the database adapter and module upgrade data, calling the migration object's upgrade() method with the current version and database adapter, updating the module table's version column to the new version through a SQL UPDATE, and clearing all application cache through Zend_Cache::CLEANING_MODE_ALL. The version update uses Zend_Db_Adapter's update() method with quoteInto() for SQL injection protection, ensuring that only the specific module's version is updated. The cache clearing ensures that any cached metadata reflecting old schema is invalidated, forcing reload from the upgraded database structure.

The registerMigration() method (Migration.php:50-55) provides manual migration registration by storing migration objects in the _migrations array indexed by module name, supporting scenarios where migrations are created outside the Extensions system or where multiple migration sources need to be combined. This method demonstrates the Open-Closed Principle where the migration system is open to extension through registration while closed to modification of core logic.

### Phprojekt_Migration_Abstract (Migration/Abstract.php:27-127)

The Phprojekt_Migration_Abstract class provides the abstract base that all module-specific migrations must extend, defining the contract that migration implementations must fulfill while providing helper methods for common operations. The class declares two abstract methods that subclasses must implement: getCurrentModuleVersion() which returns the current code version as a string, and upgrade() which performs the actual migration logic. The class uses the Template Method pattern where the abstract class defines the interface while concrete subclasses provide implementation.

The getCurrentModuleVersion() abstract method (Abstract.php:35) requires subclasses to return a version string that should be hardcoded and updated whenever the module's database schema changes. The documentation emphasizes that this should be hardcoded rather than dynamic, ensuring that version comparison is deterministic and matches the actual schema defined in the codebase. The return type of "string" with the note "A valid Phprojekt version string" establishes the contract that values must be semantic version strings like "1.2.3" compatible with Phprojekt::compareVersion().

The upgrade() abstract method (Abstract.php:109) requires subclasses to implement the migration logic that transforms the database from currentVersion to getCurrentModuleVersion(). The method receives the current database version (or null for new installations) and the database adapter enabling direct SQL execution. The extensive documentation provides critical guidance including the admonition to "Use transactions!" for atomicity, instructions to throw standard exceptions for recoverable errors with transaction rollback, warnings about Zend_Controller_Action_Exception visibility concerns that might expose sensitive data to users, guidance on handling non-transactional DDL operations in MySQL by attempting recovery before throwing exceptions, and instructions to log extensively and throw IKilledTheDatabaseException when recovery is impossible. This documentation serves as both API contract and implementation guide, demonstrating the abstract class's role in establishing best practices.

The parseDbFile() protected final method (Abstract.php:119-126) provides a helper that parses the module's Sql/Db.json file and applies the schema definitions to the database through Phprojekt_DbParser. The method accepts a module name parameter, instantiates DbParser with useExtraData = false to skip test data, retrieves the database adapter from the Phprojekt singleton, and calls parseSingleModuleData() to process the module's schema definition. The final modifier prevents subclasses from overriding this helper, ensuring consistent behavior across all migrations. This helper enables simple migrations that only need to update schema to latest definition without complex data transformations, supporting cases where the Db.json file fully describes the target schema.

### Phprojekt_Migration_IKilledTheDatabaseException (Migration/IKilledTheDatabaseException.php:43-45)

The Phprojekt_Migration_IKilledTheDatabaseException class extends PHP's standard Exception class to provide a specialized exception type signaling unrecoverable migration failures where the database is left in an inconsistent state requiring manual recovery. The class contains only the class declaration with no additional methods or properties, serving purely as a type marker that enables exception handling code to distinguish critical failures from recoverable errors. The intentionally alarming class name (with comment "I Killed The Database") communicates the severity of this exception type, using humor to ensure developers understand the gravity of throwing or catching this exception.

The exception's documentation emphasizes that it should be thrown "after a failed upgrade when the original state cannot be recovered", establishing a clear use case of irrecoverable errors rather than ordinary failures. The pattern enables calling code to implement differentiated error handling where standard exceptions trigger retry or graceful degradation while IKilledTheDatabaseException triggers administrative alerts, backup restoration prompts, or application lockdown until manual recovery completes. This exception demonstrates the use of type systems for semantic signaling where exception type alone conveys rich information about error severity and required response.

## Public API and Interfaces

The Migration library exposes its functionality primarily through the Phprojekt_Migration coordinator class which provides methods for discovering upgrade needs and executing migrations. The typical usage pattern for application initialization involves instantiating a migration coordinator with `$migration = new Phprojekt_Migration($extensions)` where $extensions provides access to module migration implementations, checking if upgrades are needed through `$migration->needsUpgrade()`, and executing upgrades through `$migration->performAllUpgrades()` or `$migration->performUpgrade($moduleName)` for selective upgrade. The typical deployment scenario runs migration checks during application bootstrap, preventing application access when upgrades are pending to ensure users only interact with correctly upgraded schemas.

The module development workflow for creating migrations involves extending Phprojekt_Migration_Abstract in a module-specific migration class, implementing getCurrentModuleVersion() to return the current code version, implementing upgrade() to handle migration logic including version checking to determine which transformations are needed and transaction management for atomicity, registering the migration through the module's extension by implementing getMigration() in the extension class to return the migration instance, and updating getCurrentModuleVersion() whenever schema changes are made. The upgrade implementation typically uses switch or if statements on $currentVersion to handle different upgrade paths, enabling migrations that work from multiple starting versions like supporting both 1.0→2.0 and 1.5→2.0 upgrades through a single implementation.

The error handling workflow requires migration implementations to distinguish between recoverable and unrecoverable errors, using try-catch blocks around database operations to catch SQL errors, calling transaction rollback on recoverable errors before throwing standard exceptions, logging extensive diagnostic information through Phprojekt::getInstance()->getLog()->debug() when recovery fails, and throwing IKilledTheDatabaseException only when the database is truly in an unrecoverable state. The calling code must handle both exception types appropriately, presenting user-friendly error messages for standard exceptions while triggering administrative alerts and preventing further application access for IKilledTheDatabaseException.

## Dependencies and Integration

The Migration library depends fundamentally on the Phprojekt_Extensions system which provides the mechanism for modules to register migration implementations, with the Migration constructor accepting a Phprojekt_Extensions object and calling getExtensions() to retrieve available extensions and getMigration() on each to retrieve migration objects. This integration couples the migration system to the extension architecture, requiring modules to implement extension classes that provide migration instances. The dependency enables a plugin-like architecture where modules can optionally provide migrations without requiring modifications to core migration code.

Integration with the database layer occurs through Zend_Db_Adapter_Abstract which migration implementations receive as a parameter to the upgrade() method, enabling direct SQL execution through query(), update(), insert(), and delete() methods. The migration system uses the adapter's transaction support through beginTransaction(), commit(), and rollBack() to ensure atomicity of multi-statement migrations. The Phprojekt singleton provides database adapter access through getInstance()->getDb(), centralizing database connection management and configuration. The module table serves as the version tracking store with migrations querying SELECT name, version FROM module to determine installed versions and calling UPDATE module SET version = ? WHERE name = ? to record successful upgrades.

The Phprojekt_DbParser integration through the parseDbFile() helper enables simple migrations that delegate schema definition to JSON files, with DbParser reading module Sql/Db.json files and generating CREATE TABLE and ALTER TABLE statements. This integration provides a declarative migration approach where modules define target schema in JSON format and DbParser handles the transformation logic, avoiding hand-written SQL in simple cases. The useExtraData parameter in DbParser instantiation controls whether test data is loaded, with migrations setting it to false to skip test data loading during production upgrades.

The cache integration through Zend_Cache demonstrates awareness that migrations modify database schema which invalidates cached metadata, with performUpgrade() calling getInstance()->getCache()->clean(Zend_Cache::CLEANING_MODE_ALL) to clear all cached data. This aggressive cache invalidation ensures that no stale metadata remains after schema changes, forcing reload of table metadata, field definitions, and other database-derived information. The cache clearing occurs after version update and outside any transactions, ensuring it executes only on successful upgrades.

The Phprojekt::compareVersion() integration provides version comparison logic that the migration system depends on for upgrade detection, with getModulesNeedingUpgrade() calling compareVersion($moduleVersion, $codeVersion) to determine version relationships. This centralized version comparison ensures consistent versioning semantics across the application, with the method implementing semantic version comparison that handles dotted-decimal version strings. The negative return (database older), zero return (versions equal), and positive return (database newer) provide clear semantics that migration code uses to determine upgrade needs.

## Data Models and Structures

The Migration library interacts with but does not directly manage the module table which stores version information for installed modules. The table structure includes id (primary key), name (varchar with module name), label (varchar with display name), active (integer flag), and version (varchar storing semantic version string like "1.2.3"). The version column serves as the persistent version tracking store that enables the migration system to determine which modules need upgrading, with migrations updating this column after successful upgrade to record the new installed version. The lowercase name storage matches the migration system's use of strtolower() when comparing module names, ensuring case-insensitive module matching.

The migration detection algorithm compares database versions from the module table with code versions from getCurrentModuleVersion() implementations, building upgrade plans that include from (database version), to (code version), and migration (migration object) for each module needing upgrade. The null value for from indicates a new installation where the module is not yet in the database, triggering initial schema creation rather than incremental migration. The migration object reference enables the coordinator to call upgrade() without re-discovering or re-instantiating migration implementations, demonstrating efficient object reuse.

The version comparison semantics follow semantic versioning principles where "1.2.3" represents major.minor.patch format, with comparison examining components left-to-right to determine ordering. The Phprojekt::compareVersion() implementation compares version strings component by component, returning negative when the first argument is older (1.2.3 < 2.0.0), zero when equal (1.2.3 == 1.2.3), and positive when newer (2.0.0 > 1.2.3). This comparison logic enables the migration system to detect when code has been updated to newer versions than installed database schemas, triggering upgrade execution.

The upgrade() method receives currentVersion parameter that contains either the database version string for existing installations or null for new installations, enabling migration implementations to use conditional logic like `if (is_null($currentVersion))` for initial installation versus `if (version_compare($currentVersion, '2.0.0', '<'))` for incremental upgrades. This dual-mode operation supports both fresh installs and upgrades through a single migration implementation, reducing code duplication. The version string parameter enables fine-grained migration paths where implementations can handle multiple starting versions with different transformation logic for each path.

## Configuration and Settings

The Migration library operates with minimal external configuration, using the module table's version column as the primary configuration store that tracks installed versions. The version strings are freeform text stored as varchar without validation, trusting migration implementations to use valid semantic version formats that Phprojekt::compareVersion() can process. The lack of strict version format validation trades type safety for flexibility, enabling custom versioning schemes if needed though the documentation strongly encourages semantic versioning for consistency.

The TODO comment in getModulesNeedingUpgrade() (line 98) noting "Handle this" for the scenario where database version is higher than code version suggests an unimplemented configuration for handling downgrades or version mismatches. The current implementation silently ignores this case without adding the module to upgrade list, effectively treating newer database versions as compatible with older code versions. A production implementation might add warnings, prevent application startup, or provide downgrade migration support, though the current simplified approach assumes that version mismatches result from development environments or deployment errors rather than intentional downgrades.

The cache clearing in performUpgrade() uses Zend_Cache::CLEANING_MODE_ALL which clears all cached data across the entire application, implementing an aggressive invalidation strategy that ensures no stale metadata remains after schema changes. This configuration choice trades cache performance for correctness, accepting that successful upgrades will cause cache misses and reload overhead across the application. Alternative configurations might use CLEANING_MODE_MATCHING_TAG or CLEANING_MODE_MATCHING_ANY_TAG with schema-related tags, though the current approach's simplicity avoids the complexity of tracking which cache entries depend on database schema.

The parseDbFile() helper's useExtraData parameter defaults to false, configuring DbParser to skip test data loading during migrations. This configuration ensures that production upgrades only apply schema changes without inserting development or test data, maintaining data integrity. The hardcoded false value prevents accidental test data insertion in production, though it means migrations requiring data population must implement custom INSERT logic rather than relying on Db.json extra data.

## Design Patterns and Principles

The Template Method pattern dominates the Migration library's design through Phprojekt_Migration_Abstract which defines the migration contract while delegating implementation to subclasses through abstract methods getCurrentModuleVersion() and upgrade(). This pattern establishes the interface that all migrations must implement while enabling each module to provide custom migration logic appropriate to its schema evolution needs. The pattern demonstrates inversion of control where the framework defines the structure (abstract class) while plugins define behavior (concrete implementations), enabling extensibility without framework modification.

The Coordinator pattern appears in the Phprojekt_Migration class which orchestrates the complex multi-step process of discovering modules needing upgrade, determining upgrade order, executing individual migrations, updating version tracking, and clearing caches. This pattern centralizes coordination logic in one class rather than distributing it across migrations, enabling migrations to focus solely on transformation logic while the coordinator handles orchestration concerns. The pattern demonstrates separation of concerns where strategic decisions (which modules to upgrade, in what order) are separated from tactical operations (how to upgrade each module).

The Registry pattern appears in the _migrations array which stores module-to-migration mappings, providing centralized registration and lookup of migration implementations. The registerMigration() method enables explicit registration while the constructor's iteration over extensions provides automatic registration from the extension system. This pattern demonstrates the Open-Closed Principle where new migrations can be registered without modifying the coordinator class, supporting extensibility through registration rather than inheritance or modification.

The Memoization pattern appears in getModulesNeedingUpgrade() which caches analysis results in _modulesNeedingUpgrade to avoid repeated database queries and version comparisons. The method checks if results are cached before performing analysis, returning cached results immediately when available. This pattern optimizes performance for repeated calls within a request, common in scenarios where multiple components check upgrade status or where the same upgrade list is used for both detection and execution. The request-scoped caching avoids the complexity of cache invalidation since the cache is automatically cleared when the request ends.

The Exception Hierarchy pattern implements differentiated error handling where standard Exception signals recoverable errors while IKilledTheDatabaseException signals unrecoverable errors, enabling catch blocks to handle errors differently based on exception type. This pattern demonstrates the use of exception inheritance to create semantic categories where exception type alone conveys information about error severity and required response. The pattern enables sophisticated error handling like `catch (IKilledTheDatabaseException $e) { alertAdmin($e); shutdownApp(); } catch (Exception $e) { rollback(); retry(); }` that matches response to error severity.

The Helper Method pattern appears in parseDbFile() which encapsulates the common operation of parsing Db.json files and applying schema definitions, enabling migrations to avoid boilerplate code for this frequent operation. The final modifier prevents overriding, ensuring all migrations use the same parseDbFile() implementation for consistency. This pattern demonstrates code reuse where common operations are extracted to shared helpers rather than duplicated across implementations, improving maintainability by centralizing logic that might need updates.

The Fail Fast pattern appears in performUpgrade() which validates preconditions (migration exists, upgrade needed) before attempting operations, throwing exceptions immediately when preconditions aren't met rather than proceeding with invalid state. This pattern prevents wasted work and provides clear error messages at the point of failure rather than allowing operations to fail later with less context. The pattern demonstrates defensive programming where invalid inputs are rejected explicitly rather than causing subtle failures downstream.
