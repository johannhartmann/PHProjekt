# Component: Phprojekt Core Library

## Overview

The Phprojekt core library serves as the foundational infrastructure layer of the entire PHProjekt application, providing essential services, abstractions, and utilities that all modules and components build upon. This library implements the architectural patterns, data access layer, authentication system, configuration management, and cross-cutting concerns that create consistency across the application while enabling rapid module development. The core library bridges between Zend Framework's generic capabilities and PHProjekt's specific business requirements, translating Zend's flexible components into opinionated patterns that enforce consistency while reducing boilerplate code. The singleton Phprojekt class acts as the application kernel, coordinating initialization of all major subsystems including database connections, caching, logging, translation, and configuration loading.

The architectural role of the Phprojekt core extends beyond mere utility provision to establish the conventions and patterns that define "the PHProjekt way" of building modules. The Active Record abstraction (Phprojekt_ActiveRecord_Abstract) implements a domain-driven ORM that combines data persistence with business logic, relationship management, and validation capabilities. The authentication system (Phprojekt_Auth) provides session-based identity management with cookie-based persistence and multiple authentication adapter support including database, LDAP, and proxy authentication. The configuration system (Phprojekt_Configuration) implements hierarchical key-value storage where system defaults can be overridden by module-specific settings which can be overridden by user-specific preferences, creating flexible customization without requiring code changes.

The Phprojekt core library implements numerous cross-cutting concerns through dedicated subsystems including search indexing (Phprojekt_Search) that tokenizes content across all modules, history tracking (Phprojekt_History) that records all data changes for audit trails, notification delivery (Phprojekt_Notification) that sends email alerts and frontend messages, and tag management (Phprojekt_Tags) that enables informal categorization across module boundaries. These infrastructure services operate transparently through model lifecycle hooks, requiring minimal explicit invocation from business logic code. The tree structure support (Phprojekt_Tree_Node_Database) implements nested set patterns for hierarchical data like project structures, while the database management system (Phprojekt_DatabaseManager) provides schema introspection, migration execution, and dynamic table creation capabilities that power the Module Designer feature.

The technological foundation of the Phprojekt core includes PHP 5.3+ with extensive use of static methods for framework-wide services, Zend Framework 1.10.7 components wrapped and extended through PHProjekt-specific classes, and dependency injection through the singleton pattern where the Phprojekt instance serves as a service locator providing access to database, cache, configuration, and logging services. The library implements numerous design patterns including Active Record for data persistence, Singleton for global state management, Registry for service location, Template Method for customizable workflows, Strategy for pluggable algorithms, and Observer for event-driven behavior. The core's separation into focused subdirectories (ActiveRecord, Auth, CalDAV, Converter, etc.) creates clear boundaries between different concerns, enabling developers to navigate the codebase by following directory structure rather than scanning through monolithic files.

The Phprojekt core library's organization reflects careful separation of concerns where each major subsystem occupies its own file or directory, creating navigable structure that scales from dozens to hundreds of classes without becoming unwieldy. The root-level Phprojekt.php file contains the singleton kernel that most code interacts with, providing getInstance() method for service access and static helpers for common operations like translation. The subdirectories group related classes by functional area, with directories like ActiveRecord containing the complete ORM implementation, Auth containing all authentication components, and User containing all user management classes.

The library's naming conventions enforce consistency where base classes use names like Abstract or Interface, implementation variants use descriptive names like Database or Json, and the Default suffix indicates standard implementations that modules typically extend. The parallel structure between directories (e.g., Auth directory and Auth.php file) indicates that the root file contains the facade or primary interface while the directory contains supporting implementations. This organizational pattern enables developers to quickly locate relevant code—permission-related code lives in Right.php and RoleRights.php, search-related code lives in Search.php and Search directory, authentication code lives in Auth.php and Auth directory—without requiring IDE search features or grep commands.

## Key Classes and Files

### Phprojekt.php (Singleton Kernel)

The Phprojekt class implements the singleton pattern serving as the application kernel that coordinates initialization of all major subsystems and provides centralized access to infrastructure services. The getInstance static method returns the single application instance, lazily initializing it on first invocation and returning the cached instance on subsequent calls. This singleton pattern ensures consistent state throughout request processing, avoiding the complexities of passing service objects through every method parameter while maintaining global accessibility for core infrastructure. The class stores references to Zend_Config_Ini for configuration, Zend_Db for database connections, Phprojekt_Log for logging, Zend_Cache for caching, and Zend_View for templating, acting as a service locator that provides these services to calling code through getter methods.

The initialization sequence orchestrated by the Phprojekt constructor includes loading configuration from INI files, establishing database connections through Zend_Db factory methods, initializing the Zend_Translate adapter with language files from the configured locale, setting up caching backends (APC, file, or memory depending on configuration), configuring the PHP error handler to route errors through Phprojekt_Log, and registering the autoloader to enable class discovery through naming conventions. This bootstrap process transforms bare PHP environment into a fully configured application runtime with all services ready for use. The constructor accepts optional parameters for testing scenarios where different configurations or database connections should be used, demonstrating testability through dependency injection even within singleton pattern implementation.

The translate method provides the primary interface for internationalization, accepting message keys and optional parameters for string interpolation, then delegating to Zend_Translate to retrieve localized strings based on the current user's language preference. This centralized translation system ensures that all user-facing text flows through the same mechanism, enabling consistent localization without requiring modules to directly manage language files or locale detection. The method supports placeholder substitution where %s markers in translation strings are replaced with provided parameters, enabling dynamic message construction like "Deleted {count} items" where count varies by operation. The translation integration with Zend_Translate's message format enables use of standard Gettext workflows where translation teams can use industry-standard tools for localization without requiring programming knowledge.

The setCurrentProjectId and getCurrentProjectId methods manage the crucial project context that flows through request processing, determining which project's data should be displayed and which permissions should be checked. These methods store the current project ID in Zend_Registry under a constant key, making it accessible throughout the request without explicit parameter passing. The project context affects nearly every query in the application, with list views filtering by current project, permission checks scoping to current project, and navigation showing project-relevant modules. This context pattern creates the user experience where selecting a project in the interface causes the entire application to reconfigure itself to show that project's data, without requiring page reloads or URL parameter juggling.

### ActiveRecord/Abstract.php (ORM Foundation)

The Phprojekt_ActiveRecord_Abstract class extends Zend_Db_Table_Abstract to implement a sophisticated ORM that combines Zend's database abstraction with PHProjekt-specific features including relationship mapping, lifecycle hooks, and automatic timestamp management. This class serves as the base for all data models in PHProjekt, providing standard persistence methods (save, delete, find, fetchAll) while enabling models to customize behavior through method overrides and property declarations. The relationship mapping system uses declarative arrays (hasMany, belongsTo, hasManyAndBelongsToMany) where models specify their associations, then the base class automatically handles join queries, foreign key resolution, and collection management when these relationships are accessed.

The save method implements the Unit of Work pattern where the model tracks which properties have changed since loading from the database, then generates UPDATE statements touching only modified columns rather than overwriting the entire record. This change tracking improves performance by reducing database I/O and avoids race conditions where concurrent updates to different fields would overwrite each other if full-record updates were used. The method distinguishes between INSERT and UPDATE operations by checking whether the record has a primary key value, with empty keys triggering INSERTs and populated keys triggering UPDATEs. The automatic primary key detection eliminates the need for separate create and update methods in calling code, simplifying controllers that can use the same save workflow for both operations.

The lifecycle hook system enables models to inject custom logic at critical points in the persistence cycle through methods like _preSave (before database write), _postSave (after successful write), _preDelete (before removal), and _postDelete (after removal). These hooks enable cross-cutting concerns to be implemented declaratively—search indexing happens in _postSave hooks, history recording happens through _preSave hooks that capture pre-modification state, cache invalidation happens through _postDelete hooks. The hook pattern demonstrates the Template Method design pattern where the base class defines the overall workflow while subclasses customize specific steps, maintaining consistent orchestration logic while enabling diverse customization.

The relationship loading mechanism uses lazy loading where related records are only queried when accessed, avoiding the N+1 query problem through intelligent caching of loaded relationships. When code accesses a hasMany relationship, the base class generates and executes a query for related records, caches the results, and returns a collection that behaves like an array. Subsequent accesses to the same relationship return the cached collection without additional database queries. The eager loading capability allows optimization where models can pre-load known relationships through explicit method calls, trading single-query simplicity for multi-query efficiency in scenarios where relationship access patterns are predictable.

### Auth.php (Authentication System)

The Phprojekt_Auth class extends Zend_Auth to implement PHProjekt's authentication system including session management, cookie-based persistence, multiple authentication backend support, and proxy authentication for administrative operations. The isLoggedIn static method serves as the primary authentication check throughout the application, examining session state to determine whether the current request has valid authentication credentials. The method implements sophisticated logic that first checks session storage, then falls back to examining cookies for remember-me tokens, querying the database to validate these tokens, and establishing new sessions if valid tokens are found. This multi-tier checking creates seamless user experience where authentication persists across browser sessions without requiring repeated logins.

The login static method coordinates credential validation by instantiating appropriate authentication adapters based on configuration (Phprojekt_Auth_Adapter_Database for local accounts, Phprojekt_Auth_Adapter_Ldap for directory service authentication, Phprojekt_Auth_Adapter_Proxy for admin-as-user scenarios), passing credentials to these adapters for verification, creating session records on successful authentication, and setting cookie tokens if remember-me functionality is requested. The adapter pattern enables multiple authentication mechanisms to coexist within single deployment, with authentication mode determined by configuration rather than requiring code changes. This flexibility supports scenarios like development environments using database authentication while production uses LDAP, or administrative interfaces using proxy authentication while normal users use standard credentials.

The cookie-based persistence mechanism generates cryptographically random tokens on successful login, stores these tokens in the database associated with user accounts and expiration times, sets corresponding cookies in the browser, and validates these tokens on subsequent requests without sessions. The token validation checks that cookie tokens match database tokens and that expiration times haven't passed, establishing new sessions when validation succeeds. This persistent authentication implements remember-me functionality that balances security (tokens expire, tokens are random, database holds authoritative token value) with convenience (users don't re-login on every browser launch). The logout method properly cleans up both session state and cookie state, preventing reuse of authentication tokens after explicit logout.

The isAdminUser static method provides the primary authorization check for administrative functionality, examining session state to determine whether the authenticated user possesses administrative privileges. This method appears throughout controllers and views to conditionally display or enable administrative features, creating the permission boundary between regular users and administrators. The proxy authentication system builds on this foundation by enabling administrators to temporarily assume other user identities for troubleshooting purposes, with special session markers indicating proxy mode and audit logging recording all actions taken while impersonating.

### Configuration.php (Settings Management)

The Phprojekt_Configuration class implements hierarchical key-value configuration storage where system-wide defaults can be overridden by module-specific settings which can be overridden by user-specific preferences, creating three-tier flexibility that balances standardization with customization. The class extends Phprojekt_ActiveRecord_Abstract to gain standard persistence capabilities while adding configuration-specific methods for querying and updating settings. The storage model uses a single configuration table with columns for module_id (scope), key_value (setting name), and value (setting content), enabling arbitrary settings without requiring schema changes when new configuration options are added.

The getConfiguration method retrieves setting values with automatic fallback through the configuration hierarchy, first checking for user-specific settings, then module-specific settings, finally falling back to system-wide defaults. This fallback logic ensures that configuration queries always return meaningful values even when specific overrides aren't defined, avoiding null checks throughout calling code. The method signature accepts setting key and optional user_id, with null user_id indicating system or module scope queries. The transparent fallback creates intuitive behavior where users see system defaults until they customize settings, at which point their personal values take precedence without affecting other users.

The setConfiguration method persists setting changes by determining appropriate scope (system, module, or user) from provided parameters, querying for existing setting records, updating these records if found or creating new records if not found, and returning success status. The method implements upsert semantics where the same interface serves both initial setting creation and subsequent updates, simplifying calling code that doesn't need separate create/update logic. The transaction wrapping ensures atomicity where multi-setting updates either all succeed or all fail, preventing partial configuration states that could leave the system in inconsistent condition.

The getModules method discovers which modules provide configuration interfaces by scanning the application directory for modules containing Configuration model classes, instantiating these classes to verify they work, and returning an array of module names with translated labels. This discovery mechanism enables the configuration interface to automatically adapt as modules are added or removed, without requiring manual registration of configuration providers. The discovery respects exclusion lists (Default and Core modules are typically excluded) to focus on business modules rather than infrastructure modules, creating cleaner configuration interfaces.

### Search.php (Full-Text Search Engine)

The Phprojekt_Search class implements full-text search capabilities across all modules through inverted index architecture where textual content is tokenized into words, words are stored with references to the items containing them, and queries match these word indexes to locate relevant items. The indexWords method accepts module ID, item ID, and text content, tokenizing the content through Phprojekt_Filter to extract searchable words, removing common words (stop words) that would pollute indexes, stemming words to root forms (enabling "running" to match "run"), and storing word-item associations in the search_words and search_word_module tables. This indexing happens automatically through model lifecycle hooks where _postSave callbacks invoke indexing, requiring no explicit invocation from business logic.

The search method processes queries by tokenizing query strings through the same filter applied during indexing (ensuring consistent tokenization), looking up word IDs from the search_words table, joining to search_word_module to find items containing these words, ranking results by relevance (items containing more query words rank higher), filtering results through permission checks to exclude items the user shouldn't access, and returning item references with enough context to display meaningful results. The permission filtering happens through joins to item_rights table that determines whether current user has read access to each result item, ensuring search never leaks information about items the user shouldn't know about.

The deleteObjectIndex method removes search index entries for deleted items, accepting module ID and item ID to identify the target, then removing corresponding rows from search_word_module junction table. This cleanup happens through _preDelete hooks in models, ensuring that deleted items don't continue appearing in search results. The orphaned word cleanup process (removing words that no longer reference any items) runs periodically rather than on every deletion, balancing index cleanliness with deletion performance. The search system's architecture as cross-cutting concern that operates through lifecycle hooks demonstrates the Observer pattern where models don't directly invoke search operations but rather fire events that search subsystem responds to.

The getDisplay method formats search results for presentation by querying search_display table that contains cached display strings (title, summary) for each indexed item, joining this display data with search results, and returning structured arrays suitable for frontend rendering. The display caching avoids expensive joins to original tables during search result rendering, trading storage space for query performance. The display strings are updated during indexing operations, ensuring cached data remains synchronized with actual item content. The search infrastructure's separation into indexing (write path) and querying (read path) enables optimizations specific to each path without forcing compromises that would make both paths suboptimal.

### History.php (Audit Trail)

The Phprojekt_History class maintains comprehensive audit trails by recording all modifications to data including which user made the change, when the change occurred, which field changed, the previous value, and the new value. The saveFields method accepts model instances before and after modification, computes differences between the two states, and creates history records for each changed field. This comparison-based approach captures exactly what changed without requiring models to explicitly track modifications, implementing audit capabilities transparently to business logic. The method iterates over model properties, comparing old and new values, skipping unchanged fields to avoid noise in audit logs, and creating history records for actual modifications.

The history storage model uses a single history table with columns for module_id and item_id (identifying the modified item), user_id (who made the change), field (which property changed), old_value and new_value (before and after states), action (add, edit, delete), and datetime (when change occurred). This generic schema enables history tracking across all modules without requiring module-specific history tables, with the trade-off that field names are stored as strings rather than foreign keys. The action column distinguishes between creation (add), modification (edit), and deletion (delete) operations, enabling historical queries like "when was this item created" or "who deleted this item" that require understanding operation type.

The getHistory method retrieves audit trails for specific items by querying the history table filtered by module_id and item_id, ordering results chronologically to show change progression over time, and formatting results for display including translating field names and action types. The method supports pagination through count and offset parameters, preventing memory exhaustion when querying items with extensive change histories. The history display includes user information through joins to the user table, showing who made each change rather than just user IDs. The permission integration ensures users only access history for items they have read access to, preventing information leakage through audit trails.

The integration with model lifecycle happens through consistent invocation patterns where controllers or base classes capture pre-modification state, perform the modification, then pass both old and new states to History::saveFields. This two-snapshot approach enables accurate difference calculation without requiring models to track their own changes. The history system's design as observer of model changes rather than participant in change logic maintains clean separation where models handle business rules while history handles audit requirements, enabling audit capabilities to be added or removed without modifying business logic.

### Notification.php (Multi-Channel Notifications)

The Phprojekt_Notification class implements multi-channel notification delivery including email messages sent through SMTP and frontend messages displayed as banner notifications or popup dialogs. The send method accepts recipient lists, message content, and delivery preferences, determining appropriate channels based on user settings, formatting messages for each channel (HTML for email, JSON for frontend), queueing messages for asynchronous delivery, and tracking delivery status. The multi-channel approach ensures important information reaches users through their preferred mechanisms rather than forcing single notification channel on all users.

The email notification channel integrates with Phprojekt_Mail which wraps Zend_Mail to provide email composition and sending capabilities. The notification system uses template-based message formatting where templates contain placeholders for dynamic content (recipient name, item title, action description), and the system substitutes actual values during rendering. This template approach maintains consistent message formatting while enabling customization per message type. The email configuration includes SMTP server settings, authentication credentials, sender addresses, and retry policies, with the notification system reading these settings from application configuration. The asynchronous delivery queue ensures that slow mail servers don't block request processing, with background workers processing queued messages independently of web request cycles.

The frontend notification channel stores messages in the frontend_message table with columns for recipient_id (who should see message), module_id and item_id (what item the message concerns), description (message text), valid_from and valid_until (message lifetime), and delivered (whether message has been displayed). The frontend polls this table periodically through AJAX requests, retrieving undelivered messages for the current user, marking them as delivered, and displaying them in notification widgets. This database-backed approach enables notifications to persist across page reloads and browser sessions, ensuring users see important messages even if they're not actively viewing the application when notifications are generated.

The notification system's integration with calendar events, participant status changes, and other business events happens through explicit invocation from business logic where meaningful events trigger notification creation. The system supports conditional notification based on user preferences, with settings controlling which event types trigger notifications and which channels should be used. The notification templates support internationalization through the translation system, ensuring messages appear in each recipient's preferred language rather than the sender's language. The delivery tracking and retry logic handles failures gracefully, re-attempting delivery for transient errors while abandoning delivery for permanent errors.

## Public API and Interfaces

The Phprojekt core library exposes its functionality primarily through the singleton Phprojekt instance which serves as the service locator for infrastructure components. Calling code obtains the instance through Phprojekt::getInstance(), then invokes getter methods like getDb() for database access, getConfig() for configuration, getLog() for logging, and translate() for internationalization. This service locator pattern creates consistent access patterns throughout the application where any code can reach infrastructure services without requiring dependency injection through constructors or method parameters. The static method pattern appears frequently for framework-level operations like Phprojekt_Auth::isLoggedIn() and Phprojekt_Auth::login(), enabling authentication checks without requiring instance management.

The Active Record pattern establishes the primary interface for data persistence where models extend Phprojekt_ActiveRecord_Abstract to gain persistence capabilities. Calling code creates model instances through new operators, populates properties through direct assignment, invokes save() for persistence, invokes delete() for removal, and uses find() or fetchAll() for retrieval. The relationship mapping enables dot-notation navigation like $project->modulePermissions which automatically loads related records through lazy loading. This object-oriented interface abstracts SQL operations, enabling business logic to work with objects rather than query builders, improving code readability while maintaining performance through intelligent query generation.

The configuration interface through Phprojekt_Configuration enables setting queries through getConfiguration($key, $userId) and setting updates through setConfiguration($key, $value, $userId, $moduleId). The hierarchical fallback happens transparently with calling code simply requesting settings and receiving appropriately scoped values. The search interface through Phprojekt_Search::search($words) accepts query strings and returns arrays of result objects, with permission filtering and relevance ranking handled internally. These high-level interfaces encapsulate complex implementation details, enabling calling code to focus on business logic rather than infrastructure concerns.

## Dependencies and Integration

The Phprojekt core library depends heavily on Zend Framework 1.10.7 components including Zend_Db for database abstraction, Zend_Config for configuration file parsing, Zend_Auth for authentication foundation, Zend_Acl for access control framework, Zend_Translate for internationalization, Zend_Mail for email sending, Zend_Cache for caching backends, Zend_Log for logging infrastructure, and Zend_View for templating. These Zend components provide solid foundations that Phprojekt wraps with domain-specific extensions and opinionated patterns. The wrapping creates consistent interfaces where PHProjekt-specific concerns like project context and permission checking are integrated into Zend's generic capabilities.

Integration patterns throughout the core library emphasize composition over inheritance where classes contain Zend components as private members rather than extending Zend base classes directly. The Phprojekt class holds Zend_Db and Zend_Config instances, delegating to them for database and configuration operations while adding PHProjekt-specific initialization and convenience methods. The Phprojekt_Auth class extends Zend_Auth to inherit authentication framework while adding cookie persistence, admin checking, and proxy authentication capabilities. This selective inheritance maintains compatibility with Zend interfaces while enabling substantial behavioral extensions.

The core library's data flows follow request-response patterns where HTTP requests enter through index.php bootstrapper, flow to Phprojekt::getInstance() for initialization, proceed to Phprojekt_Dispatcher for routing, reach module controllers for business logic execution, invoke models for data access, and return responses through view rendering or JSON serialization. The initialization sequence establishes database connections, loads configuration, initializes translation, sets up caching, and configures error handling, transforming raw PHP environment into fully operational application runtime. The request processing uses Zend's MVC components orchestrated through PHProjekt-specific dispatcher that adds module discovery and permission checking.

## Data Models and Structures

The Phprojekt core library's data model centers on several cross-cutting tables that support infrastructure concerns across all modules. The configuration table stores key-value settings with columns for module_id (scope), key_value (setting name), and value (setting content as text), enabling arbitrary configuration without schema changes. The history table records audit trails with columns for module_id and item_id (identifying changed item), user_id (who changed it), field (what changed), old_value and new_value (before and after), action (add/edit/delete), and datetime (when changed). The search_words table stores unique words with occurrence counts, while search_word_module creates junction between words and items containing them.

The user table defines identity records with columns for username (login identifier), firstname and lastname (display name), status (active/inactive), admin (administrative privilege flag), and relationships to setting (user preferences), role (permission templates), and project (access grants). The role table defines permission templates with columns for name (role description) and parent (hierarchical relationships), while role_module_permissions creates junction between roles and modules specifying access levels. The module table tracks installed modules with columns for name (internal identifier), label (display name), save_type (global/project scope), version (schema version), and active (enabled status).

The item_rights table implements fine-grained permissions with columns for module_id, item_id, user_id, and access (bit flags encoding read/write/delete privileges), creating the many-to-many relationship between users and items with associated permission levels. The frontend_message table queues frontend notifications with columns for recipient_id, module_id, item_id, description, valid_from, valid_until, and delivered. The tags table stores tag vocabulary while module-specific junction tables associate tags with items. These infrastructure tables create the foundation for cross-cutting concerns that operate consistently across all business modules.

## Configuration and Settings

The Phprojekt core library's configuration encompasses both deployment configuration stored in INI files and runtime configuration stored in database tables. The configuration.ini file contains deployment-specific settings including database connection parameters (host, username, password, database name), cache backend selection (APC, file, memory), logging configuration (file path, severity level), email server settings (SMTP host, authentication), file upload limits, and timezone defaults. These settings are loaded during bootstrap and remain constant throughout request processing, with changes requiring application restart to take effect.

Runtime configuration stored through Phprojekt_Configuration enables modification without application restart or file editing, supporting scenarios like changing notification preferences, adjusting UI behaviors, or enabling/disabling features. The hierarchical configuration with system, module, and user scopes creates flexibility where system administrators establish organizational standards through system settings, module developers provide sensible defaults through module settings, and individual users customize their experience through user settings. The configuration system supports arbitrary key-value pairs without requiring schema changes, enabling modules to define their own configuration needs through convention rather than central registration.

## Design Patterns and Principles

The Phprojekt core library extensively applies the Singleton pattern through the Phprojekt class that coordinates application-wide state and services, ensuring consistent access to infrastructure throughout request processing while avoiding the complexity of passing service objects through every method parameter. The Service Locator pattern manifests in how Phprojekt instance provides getDb(), getConfig(), getLog(), and other getter methods that return infrastructure services, enabling any code to access these services through the singleton instance. While some modern architectures prefer dependency injection over service location for testability, the singleton+locator pattern provides pragmatic balance between global accessibility and maintainability for the PHP 5.3 era when PHProjekt was designed.

The Active Record pattern combines data persistence with business logic in model classes, enabling models to save themselves to databases, validate their own data, manage their own relationships, and implement domain-specific methods. This pattern trades some architectural purity (separation of persistence from domain logic) for developer productivity where simple CRUD operations require minimal code. The Template Method pattern appears throughout lifecycle hooks where base classes define workflows (_preSave, save, _postSave) while allowing subclasses to customize specific steps through hook method overrides. The Strategy pattern enables pluggable algorithms through authentication adapters, cache backends, and log writers that conform to interfaces enabling runtime selection without conditional logic throughout calling code.

The Observer pattern underlies cross-cutting concerns like search indexing, history tracking, and cache invalidation that respond to model lifecycle events through hooks rather than requiring explicit invocation. Models don't know about search indexing or audit logging, instead they fire lifecycle events through hook method invocations, and infrastructure code registered as observers performs appropriate operations. This decoupling enables cross-cutting concerns to be added or removed without modifying business logic, supporting the Open-Closed Principle where the system is open to extension but closed to modification. The Phprojekt core's architectural patterns create consistent conventions that reduce cognitive load for developers familiar with these patterns while maintaining flexibility for scenarios requiring customization beyond standard patterns.
