# Component: CalDAV

## Overview

The CalDAV library provides Calendar Distributed Authoring and Versioning (CalDAV) protocol support for PHProjekt 6, implementing RFC 4791 calendar access functionality through integration with the SabreDAV library to enable synchronization between PHProjekt's internal calendar data and external calendar clients like Apple Calendar, Mozilla Thunderbird, and mobile devices. This library acts as a bridge between PHProjekt's Calendar2 and Timecard modules and the standard CalDAV protocol, translating between PHProjekt's database-centric calendar storage and the iCalendar format (RFC 5545) expected by CalDAV clients. The implementation enables users to access PHProjekt calendar events through native calendar applications without requiring web browser access, supporting workflows where calendar data is consumed across multiple devices and applications with automatic synchronization.

The library architecture implements the adapter pattern where PHProjekt-specific classes adapt PHProjekt's data models and authentication systems to interfaces defined by SabreDAV, the third-party CalDAV server library that handles the complexity of HTTP request parsing, WebDAV protocol semantics, and iCalendar serialization. The Phprojekt_CalDAV_PrincipalBackend class implements Sabre_DAVACL_IPrincipalBackend to provide user identity information to SabreDAV, translating between PHProjekt's user management system and CalDAV's principal concept. The module-specific Calendar2_CalDAV_CalendarBackend and Timecard_CalDAV_CalendarBackend classes extend Sabre_CalDAV_Backend_Abstract to provide calendar data access, implementing methods like getCalendarsForUser() and getCalendarObjects() that query PHProjekt's database and transform results into the iCalendar format that CalDAV clients expect.

The authentication integration implements HTTP Basic Authentication through custom authentication backends (Calendar2_Helper_Auth) that validate credentials against PHProjekt's authentication system, with special handling in controllers to bypass PHProjekt's session-based authentication in favor of per-request HTTP authentication required by CalDAV clients. The controller classes (Calendar2_CaldavController, Timecard_CaldavController) override standard PHProjekt controller behavior to disable view rendering and implement HTTP authentication, then instantiate and configure a SabreDAV server with appropriate backends and plugins before delegating request handling to SabreDAV through $server->exec(). This delegation approach leverages SabreDAV's comprehensive CalDAV implementation while maintaining control over authentication and data access through custom backends.

The simplified implementation takes pragmatic shortcuts appropriate to PHProjekt's use case including one calendar per user (avoiding multi-calendar complexity), read-only calendar operations in some contexts (users can view but not modify through CalDAV in certain configurations), URI-based event grouping to handle recurring events where multiple database records represent occurrences of the same logical event, and delegation to PHProjekt model classes for iCalendar serialization through methods like asVObject() that encapsulate format conversion logic. These simplifications reduce implementation complexity while providing functional CalDAV access that meets the common use case of viewing PHProjekt calendar data in external calendar applications.

The CalDAV library follows a hybrid organizational structure where shared infrastructure lives in the Phprojekt/CalDAV directory while module-specific implementations reside within their respective modules (Calendar2, Timecard), reflecting the library's role as both reusable component and integration point for module-specific calendar functionality. The PrincipalBackend in the shared directory provides user identity services that any module can use, implementing the SabreDAV principal interface with PHProjekt user lookups. The module-specific CalendarBackend and Controller classes customize the CalDAV implementation for each module's data model and business logic, with Calendar2 providing full event management and Timecard providing vacation/holiday calendar access. This structure demonstrates the Open-Closed Principle where the shared library is closed to modification while modules extend it through backend implementations and controllers.

## Key Classes and Files

### Phprojekt_CalDAV_PrincipalBackend (CalDAV/PrincipalBackend.php:21-101)

The Phprojekt_CalDAV_PrincipalBackend class implements the Sabre_DAVACL_IPrincipalBackend interface to provide user identity information to the SabreDAV server, translating between PHProjekt's user management system and CalDAV's principal concept where principals represent authenticated users or groups with access rights. The class implements the interface methods required by SabreDAV for principal operations including lookup by path, group membership queries, and principal searches, though several methods throw exceptions indicating incomplete implementation suitable for PHProjekt's simplified single-user-per-calendar model.

The getPrincipalByPath() method (PrincipalBackend.php:30-44) implements the primary principal lookup operation by accepting a principal path like "principals/username", extracting the username through regex pattern matching with preg_filter() using pattern '|.*principals/([^/]+)$|' to capture the username portion, instantiating Phprojekt_User_User and calling findByUsername() to retrieve the user object, throwing an exception when no user is found, and returning an array with id (user ID), uri (principal URI like "principals/username"), {DAV:}displayname (username), and {http://sabredav.org/ns}email-address (email from user settings). This method enables SabreDAV to resolve principal references to user information, supporting authentication and authorization checks throughout the CalDAV protocol implementation. The namespace-qualified keys like {DAV:}displayname follow WebDAV conventions where property names are qualified with XML namespaces to avoid collisions.

The getPrincipalsByPrefix() method (PrincipalBackend.php:23-28) is marked as unimplemented with a TODO comment and throws an exception, indicating this functionality isn't required for PHProjekt's use case. This method would typically enumerate all principals under a given prefix, supporting discovery of available users or groups. The incomplete implementation reflects pragmatic engineering where non-essential functionality is deferred or omitted, with the exception providing clear error messaging if calling code unexpectedly invokes this method.

The getGroupMemberSet() and setGroupMemberSet() methods (PrincipalBackend.php:46-59) throw exceptions indicating group membership management is not implemented, while getGroupMembership() (PrincipalBackend.php:51-54) returns an empty array indicating no group memberships. These stubs satisfy the interface contract while indicating that PHProjekt's CalDAV implementation doesn't support group-based access control, instead relying on per-user calendars without group sharing. This simplification aligns with PHProjekt's architecture where calendar access is user-specific rather than group-based.

The updatePrincipal() method (PrincipalBackend.php:71-74) returns false indicating principal updates are not supported, while searchPrincipals() (PrincipalBackend.php:97-100) returns empty array indicating principal search is not implemented. These limitations reflect PHProjekt's model where user management occurs through PHProjekt's administrative interface rather than through CalDAV protocol operations, with CalDAV providing read-only access to user information rather than full user lifecycle management.

### Calendar2_CalDAV_CalendarBackend (Calendar2/CalDAV/CalendarBackend.php:21-...)

The Calendar2_CalDAV_CalendarBackend class extends Sabre_CalDAV_Backend_Abstract to provide calendar data access for the Calendar2 module, implementing the methods that SabreDAV calls to retrieve calendar metadata and event data. The class implements PHProjekt's one-calendar-per-user model where each user has exactly one calendar named "default" rather than supporting multiple calendars with user-defined names, simplifying both implementation and user experience at the cost of organizational flexibility.

The getCalendarsForUser() method (CalendarBackend.php:33-54) implements calendar discovery by accepting a principal URI, extracting the username through regex pattern matching, finding the user through Phprojekt_User_User::findByUsername(), throwing an exception when user not found, and returning a single-element array describing the user's calendar with properties including id (user ID), uri ('default'), principaluri (the provided principal URI), {DAV:}displayname ('default'), {http://apple.com/ns/ical/}calendar-color ('blue'), {http://apple.com/ns/ical/}calendar-order (0), {NS_CALENDARSERVER}getctag (current timestamp for change tracking), and {NS_CALDAV}supported-calendar-component-set (VEVENT only). The hardcoded 'default' name and single-calendar approach simplifies implementation while meeting common use cases where users work with a single unified calendar.

The createCalendar(), updateCalendar(), and deleteCalendar() methods (CalendarBackend.php:59-82) all throw Sabre_DAV_Exception_NotImplemented indicating that calendar lifecycle operations are not supported, with error messages stating "Creation of new calendars is not supported by PHProjekt", "Altering calendars is not supported", and "Deleting calendars is not supported". These restrictions enforce the one-calendar-per-user model where calendars are created automatically for users rather than through explicit CalDAV operations.

The getCalendarObjects() method (CalendarBackend.php:94-124) implements event retrieval by accepting a calendar ID (which is the user ID), querying the calendar2 table joined with calendar2_user_relation to find events associated with the user, grouping events by URI to handle recurring events where multiple database records share the same URI, calling getCalendarObjectsGroup() for each group to generate iCalendar representation, and returning an array of calendar object descriptors. The grouping logic iterates through sorted events accumulating those with the same URI into groups, then calling the helper method to convert each group to iCalendar format. This approach handles PHProjekt's storage model where recurring event instances are stored as separate database records linked by a common URI.

The getCalendarObjectsGroup() helper method (CalendarBackend.php:134-150) converts a group of events with common URI to iCalendar format by creating a Sabre_VObject_Component representing a VCALENDAR, adding version and prodid properties, iterating over the event group calling asVObject() on each to convert to VEVENT components, tracking the latest lastModified timestamp, and returning a descriptor array with id (UID), uri, lastmodified timestamp, calendarid, and calendardata (serialized iCalendar). The delegation to event.asVObject() encapsulates format conversion logic in the domain model rather than backend, following the principle that models know how to serialize themselves.

### Calendar2_CaldavController (Calendar2/Controllers/CaldavController.php:19-89)

The Calendar2_CaldavController class provides the HTTP endpoint for CalDAV protocol requests, extending IndexController to inherit PHProjekt's controller infrastructure while overriding authentication and view rendering to accommodate CalDAV's requirements. The controller serves as the integration point between PHProjekt's MVC architecture and SabreDAV's request processing, configuring and delegating to a SabreDAV server instance that handles protocol details.

The preDispatch() method (CaldavController.php:25-29) overrides the parent implementation to call parent::preDispatch() for standard initialization then disable view rendering through $this->_helper->viewRenderer->setNoRender(true), preventing PHProjekt from attempting to render HTML views for CalDAV requests that should return iCalendar data or HTTP status codes rather than HTML. This override demonstrates adaptation of web application infrastructure to support non-HTML protocols.

The checkAuthentication() method (CaldavController.php:35-47) overrides authentication to implement HTTP Basic Authentication instead of session-based authentication, checking for PHP_AUTH_USER in $_SERVER indicating HTTP authentication credentials, calling Phprojekt_Auth::login() with username and password from HTTP headers, normalizing the username to lowercase through Phprojekt_Auth::getRealUser()->username, catching Phprojekt_Auth_Exception and rethrowing without stack trace to avoid logging passwords. The password logging concern demonstrates security consciousness where error handling must balance debugging information with credential protection, with the rethrow creating a new exception without the stack trace that might contain the password parameter from the login() call.

The indexAction() method (CaldavController.php:54-88) implements the CalDAV server setup by instantiating backend objects (Calendar2_Helper_Auth for authentication, Phprojekt_CalDAV_PrincipalBackend for principals, Calendar2_CalDAV_CalendarBackend for calendar data), creating a directory tree with Sabre_DAVACL_PrincipalCollection for principal access and Sabre_CalDAV_CalendarRootNode for calendar access, instantiating Sabre_DAV_Server with the tree, setting base URI to match the controller route, adding plugins including Sabre_DAV_Auth_Plugin for authentication, Sabre_CalDAV_Plugin for CalDAV protocol support, Sabre_DAVACL_Plugin for access control, and Sabre_DAV_Browser_Plugin for HTML debugging interface, and calling $server->exec() to process the current HTTP request. This configuration demonstrates SabreDAV's plugin architecture where functionality is composed through plugin registration.

## Public API and Interfaces

The CalDAV library's public API is accessed primarily through HTTP endpoints rather than PHP function calls, with CalDAV clients making HTTP requests to URLs like `/index.php/Calendar2/caldav/index` that route to the CaldavController. The typical client workflow involves discovery through CalDAV-specific HTTP requests that query available calendars, authentication through HTTP Basic Auth providing username and password with each request, calendar data retrieval through GET requests that return iCalendar-formatted event data, and optional event modifications through PUT/DELETE requests (though PHProjekt may restrict modifications). External calendar applications like Apple Calendar or Thunderbird Lightning perform these HTTP operations automatically when users add PHProjekt calendars, making the protocol transparent to end users.

The HTTP interface follows CalDAV protocol semantics defined in RFC 4791 including PROPFIND requests for discovering calendars and retrieving metadata, GET requests with Accept: text/calendar for retrieving event data in iCalendar format, PUT requests with Content-Type: text/calendar for creating or updating events (if supported), DELETE requests for removing events (if supported), and REPORT requests with calendar-query XML payloads for filtered event retrieval. The SabreDAV library handles parsing these requests and dispatching to appropriate backend methods, with PHProjekt backends providing data access while SabreDAV manages protocol details.

The programmatic API for extending CalDAV functionality in new modules involves implementing a CalendarBackend class extending Sabre_CalDAV_Backend_Abstract with methods like getCalendarsForUser() to define available calendars, getCalendarObjects() to retrieve events, and optionally createCalendarObject(), updateCalendarObject(), deleteCalendarObject() for writable calendars, implementing a Controller extending IndexController with preDispatch() disabling view rendering, checkAuthentication() implementing HTTP auth, and indexAction() configuring SabreDAV server, and implementing model methods like asVObject() that convert domain objects to Sabre_VObject_Component representing iCalendar elements. This extensibility enables any PHProjekt module with time-based data to expose it through CalDAV.

## Dependencies and Integration

The CalDAV library depends fundamentally on the SabreDAV library (version 1.6.2 as documented in Calendar2 module documentation) which provides the complete CalDAV protocol implementation including HTTP request parsing, WebDAV semantics, iCalendar serialization through Sabre_VObject, and authentication framework. The dependency on SabreDAV enables PHProjekt to support CalDAV without implementing the complex protocol from scratch, leveraging a well-tested open-source implementation that handles protocol edge cases and client compatibility issues. The integration uses SabreDAV's backend interfaces where PHProjekt provides data access while SabreDAV handles protocol operations, demonstrating a clear separation between business logic and protocol implementation.

Integration with PHProjekt's user management system occurs through the Phprojekt_User_User model which PrincipalBackend uses to resolve usernames to user objects, retrieve user settings like email addresses, and validate user existence. The findByUsername() method provides the lookup mechanism while getSetting() retrieves email addresses for principal properties. The authentication integration through Phprojekt_Auth::login() validates credentials using PHProjekt's authentication system (supporting both database and LDAP authentication), with successful authentication establishing user context for subsequent authorization checks. This reuse of existing authentication infrastructure ensures consistent security policies across HTTP and CalDAV access.

The Calendar2 and Timecard module integration demonstrates the CalDAV library's role as infrastructure that modules extend for protocol support. Calendar2_Models_Calendar2 and related models provide the domain objects that CalendarBackend queries, with models implementing asVObject() methods that convert to iCalendar format through Sabre_VObject_Component construction. The calendar2 table and calendar2_user_relation join table provide the data store that CalendarBackend queries, with URI-based grouping handling recurring events stored as multiple records. This integration maintains separation where calendar business logic resides in the module while CalDAV integration lives in the CalDAV-specific classes.

The controller integration with PHProjekt's MVC framework demonstrates adaptation where IndexController's infrastructure (routing, request parsing, authentication hooks) is reused while view rendering and session management are disabled for CalDAV. The preDispatch() override that disables rendering and checkAuthentication() override that implements HTTP auth show how CalDAV requirements are accommodated within PHProjekt's controller architecture. The routing through index.php/Calendar2/caldav/index demonstrates how CalDAV endpoints coexist with HTML endpoints in a unified URL space.

## Data Models and Structures

The CalDAV library works with iCalendar format (RFC 5545) as the primary data representation for client communication, with iCalendar defining a text-based format for representing calendar data including VCALENDAR components containing metadata, VEVENT components representing individual events with properties like DTSTART, DTEND, SUMMARY, RRULE for recurrence, VTODO components for tasks (not used in PHProjekt), and VJOURNAL components for journal entries (not used). The iCalendar format uses property:value syntax with colon-separated names and values, semicolon-separated parameters, and folding for long lines, providing a human-readable yet machine-parseable format that CalDAV clients understand. The Sabre_VObject library handles iCalendar parsing and serialization, with PHProjekt models calling methods like add() to populate components.

The principal concept in CalDAV represents users or groups with calendar access, with principal URIs following the format "principals/username" identifying specific users. The principal properties include standard WebDAV properties like {DAV:}displayname for display names and custom properties like {http://sabredav.org/ns}email-address for email addresses, using namespace-qualified names to avoid property name collisions. The PrincipalBackend's getPrincipalByPath() returns these properties as associative arrays that SabreDAV uses for authentication and authorization decisions.

The calendar descriptor structure returned by getCalendarsForUser() includes id (user ID serving as calendar ID), uri (calendar URI like 'default'), principaluri (owner principal URI), display properties like {DAV:}displayname, client-specific properties like {http://apple.com/ns/ical/}calendar-color for Apple Calendar, and synchronization properties like getctag (change tracking tag). The use of current timestamp for getctag implements a simple but effective change tracking mechanism where the tag changes on every access, ensuring clients always check for updates. A production implementation might use database modification timestamps for more accurate change tracking.

The calendar object descriptor structure returned by getCalendarObjects() includes id (UID), uri (event URI), lastmodified (Unix timestamp), calendarid (owning calendar), and calendardata (serialized iCalendar string). The URI field serves as the identifier for event groups where recurring events share a URI but have different occurrences in the database. The calendardata contains the complete iCalendar VCALENDAR component with all VEVENT components for the event group, enabling clients to retrieve full event information including recurrence rules and exceptions in a single response.

## Configuration and Settings

The CalDAV library uses minimal explicit configuration, with most behavior determined by SabreDAV's defaults and PHProjekt's existing configuration. The base URI configuration in CaldavController through $server->setBaseUri() matches the controller's route, ensuring that SabreDAV generates correct URLs in responses. The hardcoded '/index.php/Calendar2/caldav/index' path reflects PHProjekt's routing structure where controllers are accessed through index.php with module/controller/action path segments. This configuration must be updated if PHProjekt's routing changes or if the CalDAV endpoint moves to a different URL.

The authentication configuration through HTTP Basic Authentication requires clients to send username and password with every request, with no session-based authentication or token caching. This stateless approach aligns with CalDAV's design for client-server communication where clients may issue requests infrequently and servers may scale horizontally without shared session state. The credential validation through Phprojekt_Auth::login() uses PHProjekt's configured authentication backend (database or LDAP), inheriting authentication policies including password complexity requirements and account lockout rules.

The calendar properties configuration includes hardcoded values like 'blue' for calendar color, 'default' for calendar name, and 0 for calendar order, implementing reasonable defaults for the one-calendar-per-user model. The supported-calendar-component-set restricting to VEVENT only indicates PHProjekt calendars contain events but not tasks (VTODO) or journal entries (VJOURNAL), simplifying both implementation and client expectations. A production implementation might make these properties configurable through user preferences, though the current approach's simplicity may be adequate for typical use cases.

The SabreDAV plugin configuration determines which CalDAV features are available, with Sabre_DAV_Auth_Plugin enabling authentication, Sabre_CalDAV_Plugin providing core CalDAV protocol support, Sabre_DAVACL_Plugin adding access control, and Sabre_DAV_Browser_Plugin adding HTML debugging interface. The plugin order matters as some plugins depend on others (e.g., authentication must be configured before other plugins can rely on authenticated user context), with the current ordering working correctly for PHProjekt's needs.

## Design Patterns and Principles

The Adapter pattern dominates the CalDAV library's architecture where PHProjekt-specific classes adapt PHProjekt's data models and systems to interfaces defined by SabreDAV, enabling integration without modifying either PHProjekt's core or the SabreDAV library. The PrincipalBackend adapts Phprojekt_User_User to Sabre_DAVACL_IPrincipalBackend, CalendarBackend adapts calendar models to Sabre_CalDAV_Backend_Abstract, and authentication helpers adapt Phprojekt_Auth to Sabre_DAV_Auth_IBackend. This pattern demonstrates the Open-Closed Principle where both PHProjekt and SabreDAV are closed to modification while integration occurs through adapters open to extension.

The Bridge pattern appears in the separation between SabreDAV's protocol implementation and PHProjekt's data access, with backend classes serving as bridges that decouple the protocol abstraction from the data implementation. SabreDAV calls abstract methods like getCalendarsForUser() without knowing how calendars are stored, while PHProjekt backends implement these methods by querying databases and constructing responses. This pattern enables independent evolution of protocol support and data storage, supporting scenarios like switching from database to file-based storage without changing protocol implementation.

The Delegation pattern appears throughout the implementation where PHProjekt delegates protocol handling to SabreDAV while SabreDAV delegates data access to PHProjekt backends, creating a mutual delegation where each component handles its core competency. The CaldavController's indexAction() exemplifies this by configuring SabreDAV then calling $server->exec() to delegate all request processing, with SabreDAV calling back to PHProjekt backends for data as needed. This pattern demonstrates separation of concerns where protocol complexity lives in SabreDAV while business logic lives in PHProjekt.

The Template Method pattern appears in SabreDAV's backend abstracts like Sabre_CalDAV_Backend_Abstract which define algorithm structure (how to handle PROPFIND, how to serve GET requests) while delegating specific steps (what calendars exist, what events to return) to subclass implementations. PHProjekt's CalendarBackend classes provide concrete implementations of abstract methods, filling in the template with PHProjekt-specific data access logic. This pattern demonstrates Hollywood Principle ("don't call us, we'll call you") where the framework calls application code rather than vice versa.

The Proxy pattern appears in how CalDAV backends proxy access to underlying domain models, with getCalendarObjects() querying Calendar2_Models_Calendar2 and calling methods like asVObject() to retrieve data. The backends serve as proxies that add CalDAV-specific concerns (iCalendar formatting, URI handling, grouping logic) while delegating domain logic to models. This pattern maintains separation where models focus on business logic while backends focus on protocol adaptation, supporting testability where each component can be tested independently.

The Strategy pattern appears implicitly in SabreDAV's plugin architecture where different plugins implement different aspects of CalDAV functionality, with the server composing capabilities by registering plugins. The authentication plugin, CalDAV plugin, ACL plugin, and browser plugin each implement a strategy for handling specific concerns, with the server coordinating across plugins. This pattern demonstrates composition over inheritance where functionality is assembled through plugin registration rather than class hierarchy.

The Incomplete Implementation pattern (intentional) appears in methods like getPrincipalsByPrefix() and createCalendar() that throw NotImplemented exceptions, signaling that certain CalDAV features are not supported by PHProjekt's implementation. This pattern represents pragmatic engineering where optional protocol features are omitted to reduce implementation complexity, with clear error messages enabling future implementation if requirements change. The pattern demonstrates YAGNI principle (You Aren't Gonna Need It) where features are implemented when needed rather than speculatively.
