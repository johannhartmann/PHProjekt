# Component: Search

## Overview

The Search library provides comprehensive full-text search capabilities for PHProjekt 6, implementing an inverted index architecture that enables efficient keyword searching across all modules and content types in the application. This library handles the complete search lifecycle including indexing of text content from database fields and uploaded files, maintaining word frequency statistics for relevance ranking, executing searches with both exact and partial matching strategies, and formatting results with appropriate display metadata for UI presentation. The search system operates transparently through lifecycle hooks that automatically index content when items are created or updated and remove indexed content when items are deleted, ensuring that the search index remains synchronized with the application's data without requiring manual index management or batch reindexing operations.

The library architecture follows a modular design with four specialized classes that each handle distinct aspects of the search functionality, coordinated by the main Phprojekt_Search facade class. The Phprojekt_Search_Words class manages the vocabulary of indexed terms, storing each unique word once with a reference count indicating how many items contain that word, enabling efficient storage and supporting future relevance ranking based on term frequency. The Phprojekt_Search_WordModule class implements the inverted index structure through a many-to-many relationship between words and items, enabling fast lookup of all items containing specific search terms without scanning all records. The Phprojekt_Search_Display class maintains denormalized display metadata for search results including item titles and descriptions extracted from configurable fields, eliminating the need to load full item objects for result presentation. The Phprojekt_Search_Files class extracts text content from uploaded files, extending search capabilities beyond database fields to include document content.

The search implementation uses a stopword filtering approach to improve relevance and reduce index size by excluding common words that appear in most documents and provide little discriminatory value for search queries. The system loads a configurable stopword list from a text file specified in configuration, filtering these words from both indexing and search operations to prevent index pollution and improve query performance. The word processing pipeline includes multiple filtering stages including string cleanup to normalize case and remove punctuation, length filtering to exclude very short words (likely acronyms or typos) and very long words (likely errors), stopword filtering to remove common terms, and deduplication to ensure each word is indexed only once per item even if it appears multiple times.

The search query interface supports two distinct search strategies based on whether the query contains multiple words or a single word, implementing different semantics appropriate to each case. Multi-word queries use exact matching with AND semantics, requiring that all search terms appear in matched items, supporting precise queries like "project management report" that find items containing all three words. Single-word queries use partial matching with LIKE operators and OR semantics when combined with relevance sorting, supporting exploratory queries where users know only part of a word or want to find related terms. The search results include access control enforcement that filters out items the current user lacks read permission for, ensuring that search does not leak information about restricted content. The result limiting includes both an overall result count limit and a per-module limit that prevents any single module from dominating results, ensuring diversity in search result sets.

The separation of concerns is clear with Words handling vocabulary management, WordModule managing the inverted index structure, Display handling result presentation, and Files handling document content extraction. This modular design enables testing and maintenance of each component independently while the facade ensures consistent behavior across all search operations.

## Key Classes and Files

### Phprojekt_Search (Search.php:21-251)

The Phprojekt_Search class serves as the main facade for search functionality, providing high-level methods that coordinate operations across the specialized search components. The class maintains protected properties for each component (_words, _wordModule, _files, _display), instantiating them in the constructor and ensuring fresh instances in the __clone() method to prevent shared state between cloned objects. This composition pattern enables the facade to delegate specific operations to appropriate components while maintaining a cohesive API that hides implementation details from calling code.

The indexObjectItem() method (Search.php:88-119) implements the complete indexing workflow for a single item, first determining the module and item IDs from the provided object, deleting any existing index entries to ensure a clean slate through _wordModule->deleteWords() and _words->decreaseWords() which maintains reference counts, extracting indexable text from the object's fields through _getObjectDataToIndex(), saving display metadata via _display->saveDisplay() for result presentation, handling uploaded files by extracting their content through _files->getWordsFromFile() when field type is 'upload', filtering out hidden fields to prevent indexing of internal data, concatenating all text values with spaces, tokenizing and indexing the text through _words->indexWords() which returns word IDs, and finally creating word-to-item associations through _wordModule->indexWords(). This comprehensive workflow ensures that all searchable content including text fields and file attachments is indexed in a single atomic operation, with proper cleanup of old index entries preventing stale data.

The deleteObjectItem() method (Search.php:128-134) and deleteObjectItemByIds() method (Search.php:136-141) implement index cleanup when items are deleted, following the same pattern as indexing by first retrieving word IDs associated with the item through _wordModule->deleteWords(), decrementing word reference counts through _words->decreaseWords() which removes words that are no longer referenced by any items, and removing display metadata through _display->deleteDisplay(). The reference counting approach ensures that the word vocabulary only contains words that actually appear in indexed items, preventing unbounded vocabulary growth and maintaining index compactness. The separation into two methods (one accepting an object, one accepting IDs directly) supports different calling patterns where sometimes the full object is available and sometimes only IDs are known.

The search() method (Search.php:156-192) implements the query execution logic with sophisticated handling of single-word versus multi-word queries, determining the search strategy by checking if the query contains spaces to distinguish between single and multiple words. For multi-word queries, the method uses exact matching (wordOperator = 'equal') with AND semantics (relationOperator = 'AND') to find items containing all search terms, supporting precise queries. For single-word queries, the method uses partial matching (wordOperator = 'like') with OR semantics (relationOperator = 'OR') to find items containing words that include the search term as a substring, supporting exploratory queries. The method then searches for matching words through _words->searchWords(), retrieves items containing those words through _wordModule->searchModuleByWordId() which enforces access control, and when a count limit is specified implements a per-module result limit of 3 items to ensure result diversity by preventing any single module from dominating results. Finally, the method enriches results with display metadata through _display->getDisplay() which adds titles, descriptions, and module information for UI presentation.

The _getObjectDataToIndex() method (Search.php:232-250) implements field filtering logic that determines which object properties should be indexed by examining the object's metadata to identify text-based database columns (varchar, text, tinytext, longtext) that contain natural language content suitable for full-text indexing. The method iterates over the _metadata property which contains database table schema information, filters for allowed data types to exclude numeric fields, dates, foreign keys, and other non-textual data, converts column names from SQL snake_case to PHP camelCase for property access through convertVarFromSql(), and extracts values from the object for each qualifying field. This metadata-driven approach enables the search system to work generically across all modules without hardcoding knowledge of specific model structures, automatically indexing new text fields when modules are extended with additional fields.

### Phprojekt_Search_Words (Search/Words.php:21-252)

The Phprojekt_Search_Words class manages the word vocabulary for the search index, extending Zend_Db_Table_Abstract to provide direct access to the search_words table which stores unique words with reference counts. The table structure consists of id (primary key), word (the unique term), and count (number of items containing this word), with the count supporting future relevance ranking based on inverse document frequency where rare words are more significant than common words. The class loads a stopword list during construction from a configurable file path, storing it in the _stopWords array for filtering during indexing and searching.

The indexWords() method (Words.php:66-72) provides the main entry point for adding words to the vocabulary, accepting a text string which is tokenized through _stringToArray() that applies the complete word processing pipeline, then persisting the words through _save() which handles both insertion of new words and reference count updates for existing words. The _stringToArray() method (Words.php:196-212) implements sophisticated text processing including cleaning through Phprojekt_Converter_String::cleanupString() which normalizes case and removes punctuation, splitting on spaces to create a word array, filtering for length through stripLengthWords() which removes very short and very long words that are likely noise, filtering stopwords through _stripStops() when a stopword list is configured, and deduplication through array_unique() to ensure each word is indexed only once per item even if it appears multiple times.

The _save() method (Words.php:116-149) implements efficient batch insertion and update operations that minimize database round trips by first querying for all words that already exist in the vocabulary using an IN clause with quoted word values, incrementing reference counts for found words through a single UPDATE with Zend_Db_Expr to execute SQL `count + 1` on the database side avoiding read-modify-write races, and inserting new words not found in the vocabulary with initial count of 1. This approach balances performance by batching operations while maintaining accuracy of reference counts through atomic increment operations. The method returns an array of word IDs for all processed words, enabling the calling code to create word-to-item associations in the inverted index.

The searchWords() method (Words.php:85-105) implements word vocabulary searching with support for both exact and partial matching strategies, tokenizing the search query through _stringToArray() which applies the same filtering as indexing to ensure consistency, constructing WHERE clauses based on the operator parameter with 'equal' using = comparisons for exact matching and 'like' using LIKE with wildcard patterns for substring matching, combining multiple word conditions with OR to find items containing any of the search terms, and ordering results by count descending to rank frequent words (which appear in many items) lower than rare words, supporting relevance ranking. The method returns an array of word records including IDs for subsequent item lookup, with optional count limiting to restrict result sets.

The decreaseWords() method (Words.php:160-187) implements reference count maintenance when items are deleted from the index, accepting an array of word IDs that were associated with the deleted item, querying current counts for those words, partitioning words into those with count = 1 (which should be deleted entirely) and count > 1 (which should be decremented), deleting words with count = 1 since they are no longer referenced by any items through batch DELETE, and decrementing counts for remaining words through UPDATE with Zend_Db_Expr executing SQL `count - 1`. This reference counting ensures that the vocabulary remains compact by automatically removing words that are no longer used, preventing unbounded vocabulary growth over time.

### Phprojekt_Search_WordModule (Search/WordModule.php:22-236)

The Phprojekt_Search_WordModule class implements the inverted index structure through the search_word_module table which establishes many-to-many relationships between words and items, enabling efficient lookup of all items containing specific words without scanning all records. The table structure consists of module_id, item_id, and word_id (composite primary key), with each record representing the appearance of a word in a specific item. This denormalized structure trades storage space for query performance by storing word-item associations explicitly rather than scanning item content during searches.

The indexWords() method (WordModule.php:54-59) creates inverted index entries by iterating over an array of word IDs and calling _save() for each to insert a record associating the word with the specified module and item. The _save() method (WordModule.php:229-235) performs straightforward inserts into the search_word_module table with module_id, item_id, and word_id values, creating the inverted index entries that enable fast word-to-item lookups. This simple insertion approach relies on the calling code (Phprojekt_Search) to handle de-duplication and ensure that stale entries are removed before new entries are created.

The deleteWords() method (WordModule.php:69-81) removes all inverted index entries for a specified module and item combination, querying search_word_module for matching records, collecting word IDs from the results for return to the caller (enabling reference count decrements), and deleting all matching records through batch DELETE. The return of word IDs enables the calling code to maintain proper reference counts in the search_words table, ensuring that the vocabulary remains consistent with the inverted index.

The searchModuleByWordId() method (WordModule.php:92-177) implements the core search query execution with sophisticated handling of AND versus OR search semantics and comprehensive access control enforcement. For AND searches (when multiple words must all match), the method constructs nested SELECT queries that progressively filter to items containing all search terms, building a query structure like `SELECT * FROM search_word_module WHERE word_id = N AND item_id IN (SELECT item_id FROM search_word_module WHERE word_id = M AND item_id IN (...))` through iterative query composition. For OR searches (when any word match suffices), the method uses a simple IN clause with all word IDs, querying search_word_module directly for efficiency. The method then enforces access control by loading each matched item through its model's find() method which respects permissions, filtering out items where find() returns empty indicating the user lacks access. This permission checking during result processing rather than query construction simplifies the query logic while ensuring security, though it may return fewer results than requested if many matched items are filtered out.

### Phprojekt_Search_Display (Search/Display.php:21-245)

The Phprojekt_Search_Display class manages denormalized display metadata for search results, extending Zend_Db_Table_Abstract to access the search_display table which stores presentation information for items including titles, descriptions, project associations, and module labels. This denormalization avoids the need to load full item objects during search result presentation, significantly improving performance by enabling result rendering from a single query rather than N queries for N results. The table structure consists of module_id, item_id (composite primary key), project_id (for filtering), first_display (primary title/identifier), and second_display (description or summary text).

The saveDisplay() method (Display.php:106-132) extracts display fields from objects during indexing, reading searchFirstDisplayField and searchSecondDisplayField properties from the item object which specify which fields should be displayed in results, falling back to "ID: {id}" for first_display if the specified field doesn't exist, truncating second_display to 100 characters with ellipsis to prevent extremely long descriptions from degrading UI performance, and either inserting new records or updating existing records through _exists() checking followed by _save() or _update() calls. This field extraction approach enables each module to define its own display field preferences through model properties, supporting heterogeneous item types with different appropriate display representations.

The getDisplay() method (Display.php:50-95) retrieves display metadata for search results, accepting a nested array structure mapping module IDs to arrays of item IDs, constructing batch queries for each module using IN clauses to retrieve multiple items efficiently, enriching results with module names and translated labels through Phprojekt_Module::getModuleName() and getModuleLabel(), and handling missing display records (which can occur if items are deleted after search indexing) by creating placeholder entries with empty display fields. The method returns a flat array of result records indexed by "moduleId-itemId" keys for O(1) access, with each record containing id, moduleId, moduleName, moduleLabel, firstDisplay, secondDisplay, and projectId fields ready for JSON serialization and UI consumption.

The deleteDisplay() method (Display.php:142-146) removes display metadata when items are deleted from the search index, using a simple WHERE clause with module_id and item_id to identify the record to delete. The _exists() method (Display.php:178-181), _save() method (Display.php:196-204), and _update() method (Display.php:235-244) provide internal helper methods for managing display records, with _exists() using find() to check for record presence by composite primary key, _save() using insert() for new records, and _update() using update() with WHERE clause for modifications. These helper methods follow the standard Zend_Db_Table patterns for CRUD operations, providing clean abstractions over SQL operations.

### Phprojekt_Search_Files (Search/Files.php:22-95)

The Phprojekt_Search_Files class extends search capabilities to uploaded file contents, enabling full-text search within documents attached to items rather than limiting search to database fields. The class provides text extraction from various file formats, though the current implementation has a minimal feature set supporting only basic text file reading. The getWordsFromFile() method (Files.php:32-50) accepts a file path, determines the file type through _getFileType() which extracts the extension, constructs the full file path relative to PHPR_CORE_PATH, checks readability to avoid errors on missing or inaccessible files, and uses a switch statement on file type to select appropriate extraction logic with the default case reading the entire file into an array of lines and joining with spaces.

The _getFileType() method (Files.php:89-94) implements simple extension extraction by splitting the filename on dots and returning the last segment in uppercase, supporting file type dispatching in getWordsFromFile(). The current implementation lacks specialized handling for common document formats like PDF, Microsoft Office documents, or HTML, falling back to the default text extraction for all file types. This limitation means that binary document formats are unlikely to produce useful search results as the binary content will be processed as text, generating noise in the search index. The switch statement structure suggests that the design anticipated adding format-specific extractors, though these were never implemented, representing an incomplete feature that would benefit from integration with document parsing libraries.

## Public API and Interfaces

The Search library exposes its functionality primarily through the Phprojekt_Search facade class, providing three main operations that handle the complete search lifecycle. The indexing API consists of indexObjectItem($object) which is typically called from model lifecycle hooks when items are saved, automatically updating the search index without requiring explicit calls from business logic. Application models that extend Phprojekt_Item_Abstract inherit a recordValidate() hook that calls the search indexing automatically, making the search system transparent to developers who simply save objects normally and have them automatically indexed. The typical usage pattern involves saving an object through `$item->save()` which triggers internal hooks that call `$search = new Phprojekt_Search(); $search->indexObjectItem($item)`, though the search instantiation happens within the framework rather than application code.

The deletion API mirrors the indexing API with deleteObjectItem($object) and deleteObjectItemByIds($moduleId, $itemId), providing two variants depending on whether the full object is available or only IDs are known at deletion time. The method is called from delete() hooks in model classes, ensuring that search index entries are removed when items are deleted, preventing stale results from pointing to non-existent items. The two-method approach supports different calling contexts including standard object deletion where the full object is available, and cascading deletion scenarios where only IDs may be known without loading full objects for performance reasons.

The search API provides the search($words, $count) method which accepts a query string with one or more space-separated words and an optional result count limit, returning an array of result structures ready for JSON serialization and UI display. The typical usage occurs in search controllers that accept user queries from GET/POST parameters and return results, such as `$search = new Phprojekt_Search(); $results = $search->search($_GET['query'], 25);` followed by JSON encoding and output. The method handles all aspects of query execution including word tokenization, stopword filtering, database querying, access control enforcement, result limiting, and display metadata enrichment, providing a single-call interface that hides the complexity of the multi-table search infrastructure.

## Dependencies and Integration

The Search library depends on Zend Framework's database abstraction layer through Zend_Db_Table_Abstract which all search component classes extend, providing SQL query construction via Zend_Db_Select, result hydration into arrays or objects, and transaction support for atomic operations. The dependency on Zend_Db_Expr enables SQL expressions like `count + 1` and `count - 1` to be executed on the database side for atomic reference count updates, avoiding race conditions that could occur with read-modify-write sequences. The use of Zend_Db_Table patterns including fetchAll(), insert(), update(), and delete() provides consistent CRUD operations across all search components while maintaining database portability.

Integration with the PHProjekt core infrastructure occurs through multiple touchpoints including the Phprojekt singleton which provides database adapter access via `Phprojekt::getInstance()->getDb()`, configuration access for the stopword list path through `getConfig()->searchStopwordList`, and the translation system through `translate()` for localizing module labels in search results. The Phprojekt_Module class provides module name and label lookups through static methods, enabling search results to display human-readable module names rather than numeric IDs. The Phprojekt_Loader::getModel() method enables dynamic model loading during access control checks, supporting search across heterogeneous item types without hardcoding module knowledge.

The integration with the ActiveRecord layer through Phprojekt_Item_Abstract enables transparent search indexing through model lifecycle hooks, with models extending the base class automatically participating in search without requiring explicit integration code. The Item_Abstract class likely includes hooks in its save() and delete() methods that instantiate Phprojekt_Search and call appropriate indexing/deletion methods, though the exact implementation would need to be verified in the Item_Abstract source code. The use of object metadata through the _metadata property enables generic field extraction without hardcoding knowledge of specific model structures, supporting extensibility as modules add new fields or new modules are installed.

The Phprojekt_Converter_String utility class provides text normalization functionality including cleanupString() for case normalization and punctuation removal, and stripLengthWords() for filtering words by length to exclude very short and very long words that are likely noise. These utilities enable consistent text processing across the application, ensuring that indexing and searching use the same normalization rules for predictable matching behavior. The Phprojekt_Converter_Text::convert() method extracts file paths from upload field values, enabling the Files component to locate and read uploaded document content.

The access control integration through Phprojekt_Item_Rights and model find() methods ensures that search results respect permissions by loading each matched item through its model which applies permission checks before returning objects. This integration occurs in the WordModule::searchModuleByWordId() method which loads models through Phprojekt_Loader::getModel(), calls find() to retrieve items, and filters out items where find() returns empty indicating lack of access. This approach provides security by ensuring that search cannot be used to discover information about restricted items, though it may result in fewer results than requested if many items are filtered out by permission checks.

## Data Models and Structures

The Search library manages four database tables that together implement the inverted index architecture with display metadata caching and reference counted vocabulary. The search_words table stores the unique word vocabulary with columns id (auto-increment primary key), word (varchar indexed for lookup), and count (integer tracking how many items contain this word). The count field enables future relevance ranking through inverse document frequency calculations where rare words (low count) are weighted more heavily than common words (high count). The indexed word column supports efficient word lookup during searching, enabling the system to quickly find word IDs for search terms before querying the inverted index.

The search_word_module table implements the inverted index structure through a three-column composite key consisting of module_id (integer identifying the module), item_id (integer identifying the specific item), and word_id (integer foreign key to search_words.id). This table represents a many-to-many relationship between words and items, with each record indicating that a word appears in a specific item. The composite key ensures uniqueness and enables efficient querying in both directions including finding all items containing a word (search queries) and finding all words in an item (index maintenance during updates). The inclusion of module_id in the key rather than having a separate module column enables more efficient querying when filtering results by module type.

The search_display table stores denormalized display metadata with a composite primary key of module_id and item_id, plus columns for project_id (integer indicating the owning project), first_display (text field for primary title or identifier), and second_display (text field for description or summary). This denormalization enables search result presentation without loading full item objects, significantly improving performance by allowing a single query to retrieve all necessary display information for a result set. The project_id column supports future filtering of search results by project, enabling project-scoped searches though the current implementation doesn't utilize this capability. The display fields are extracted from item objects during indexing based on searchFirstDisplayField and searchSecondDisplayField properties that each model defines.

The relationships between these tables form a three-layer architecture where search_words forms the vocabulary layer, search_word_module forms the inverted index layer, and search_display forms the presentation layer. The flow during indexing starts with extracting text from an item, tokenizing into words, adding words to search_words (or incrementing existing counts), creating search_word_module entries linking words to the item, and storing display metadata in search_display. The flow during searching starts with tokenizing the query, looking up word IDs in search_words, querying search_word_module for items containing those words, filtering items by access control, and enriching results with display metadata from search_display. This layered architecture separates concerns effectively with vocabulary management, index structure, and presentation being independently maintainable.

## Configuration and Settings

The Search library's primary configuration is the searchStopwordList setting in configuration.php which specifies the path to a text file containing stopwords that should be excluded from indexing and searching. The stopword file format consists of one word per line, with the Phprojekt_Search_Words constructor reading the file content and splitting it into an array for filtering operations. Common stopwords include articles (a, an, the), prepositions (of, in, on, at), conjunctions (and, or, but), and other frequently occurring words that provide little discriminatory value for search queries. The stopword filtering improves both relevance (by excluding words that appear in most documents) and performance (by reducing index size and query complexity).

The searchFirstDisplayField and searchSecondDisplayField properties on item models configure which fields should be extracted for search result display, enabling each module to specify appropriate display representations for its content. These properties default to common field names like 'title' and 'description', with the Display.saveDisplay() method falling back to "ID: {id}" if the specified first field doesn't exist, ensuring that all items have at least minimal display information. The second display field is truncated to 100 characters with ellipsis to prevent extremely long text from degrading UI performance, representing a hardcoded limit that could potentially be made configurable if different deployments require different description lengths.

The result limiting uses hardcoded values including the per-module limit of 3 items in the search() method which prevents any single module from dominating search results. This limit ensures result diversity by forcing the UI to show matches from multiple modules when available, supporting exploratory search where users might not know which module contains relevant content. The overall result count is provided by the calling code through the $count parameter, enabling different contexts to request different result set sizes such as quick search dropdowns requesting 10-20 results versus full search pages requesting 50-100 results.

The file path construction in Phprojekt_Search_Files uses PHPR_CORE_PATH constant to build absolute paths for uploaded file reading, assuming that uploaded files are stored relative to the core directory. This path handling would need to be updated if the upload storage location changes or if uploads are moved to external storage systems like S3, representing a coupling between the search system and the file storage implementation. The current file type handling uses a switch statement with only a default case, suggesting that format-specific configuration for PDF extractors, Office document parsers, or HTML cleaners was planned but never implemented.

## Design Patterns and Principles

The Facade pattern dominates the Search library's architecture through the Phprojekt_Search class which provides a simplified interface over the complex multi-table search infrastructure, coordinating operations across Words, WordModule, Display, and Files components while hiding implementation details from calling code. This pattern enables clients to perform indexing or searching through a single method call without understanding the underlying complexity of vocabulary management, inverted index updates, display metadata persistence, and file content extraction. The facade reduces coupling by serving as the single entry point for search operations, enabling internal refactoring of search components without affecting calling code that depends only on the facade interface.

The Inverted Index pattern forms the core search architecture through the search_word_module table which implements the classic information retrieval data structure where words map to documents (items) rather than documents mapping to words. This pattern enables efficient search queries that start with search terms and directly look up matching documents without scanning all documents, providing O(1) lookup time for each word followed by intersection or union operations on result sets. The pattern trades storage space (storing word-document relationships explicitly) for query performance (avoiding full table scans), a trade-off appropriate for systems with frequent searches and infrequent updates like collaborative project management applications.

The Reference Counting pattern appears in the word vocabulary management where the search_words.count field tracks how many items contain each word, enabling automatic garbage collection of unused words when counts reach zero. This pattern prevents unbounded vocabulary growth by removing words that are no longer indexed, maintaining system efficiency over long periods. The atomic increment and decrement operations using Zend_Db_Expr ensure that reference counts remain accurate even under concurrent updates, avoiding race conditions that could cause premature deletion of words that are still referenced. The pattern demonstrates attention to long-term system behavior and resource management rather than just initial functionality.

The Template Method pattern appears in the word processing pipeline implemented through _stringToArray() which defines the algorithm structure of cleanup, split, filter by length, filter stopwords, and deduplicate, with extension points through configurable stopword lists and filterable cleanup operations. This pattern enables consistent text processing across indexing and searching while allowing customization through configuration of stopwords and potential future customization of cleanup rules or length thresholds. The pattern supports the Open-Closed Principle where the overall algorithm is closed to modification but open to extension through configuration.

The Strategy pattern appears in the search query execution where different search strategies (exact matching with AND semantics for multi-word queries, partial matching with OR semantics for single-word queries) are selected based on query characteristics detected by checking for spaces in the query string. This pattern enables different search behaviors appropriate to different query types without requiring clients to explicitly specify strategy, implementing an intelligent default that matches user expectations. The pattern could be extended to support explicit strategy selection through query syntax like quotes for exact phrases or plus signs for required terms, though the current implementation uses automatic strategy selection.

The Lazy Loading pattern appears in the access control enforcement during search result processing where items are loaded through model find() methods only when needed for permission checking, avoiding the overhead of loading full objects for items that won't appear in results. This pattern defers expensive operations until necessary, improving performance when many items are filtered out by permission checks. The pattern is also implicit in the display metadata caching which avoids loading full objects for result presentation, though this is more accurately described as denormalization than lazy loading.

The Composite Key pattern appears in the search_word_module and search_display tables which use multi-column primary keys (module_id, item_id, word_id) and (module_id, item_id) respectively, enabling unique identification of relationships without artificial surrogate keys. This pattern improves query performance by enabling index seeks on natural key combinations and supports efficient querying patterns including finding all words in an item (key prefix on module_id and item_id) and finding all items containing a word (key prefix on word_id in the inverted index). The pattern reduces storage by avoiding surrogate key columns while maintaining referential integrity through natural key relationships.
