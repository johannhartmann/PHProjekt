# Component: Exception

## Overview

The Exception library provides a hierarchical exception taxonomy for the PHProjekt framework, establishing a structured approach to error handling and reporting throughout the application. This library defines a base exception class and specialized exception types that represent specific error conditions, from validation failures and authorization violations to missing configuration and I/O errors. The exception hierarchy enables precise error identification, appropriate HTTP status code mapping, and structured error information delivery to API clients, supporting both human-readable error messages and machine-parseable error metadata.

The Exception library serves as a critical component in PHProjekt's error handling architecture, bridging the gap between internal error conditions and external error reporting. By extending PHP's native Exception class with PHProjekt-specific exception types, the library enables application code to throw semantically meaningful exceptions that convey not just error messages but also error types, HTTP status codes, and additional contextual information. This structured approach facilitates consistent error handling across the application, allowing error controllers and exception handlers to differentiate between expected error conditions (like validation failures) and unexpected errors (like database connection failures).

A key architectural decision in the Exception library is the distinction between "published" and "unpublished" exceptions. The `Phprojekt_Exception_Published` base class represents exceptions that are safe to expose to API clients, with error messages that have been translated and sanitized for public consumption. These published exceptions include a `toArray()` method that serializes exception information into a structured format suitable for JSON responses, and they carry HTTP status codes that indicate the appropriate client response. In contrast, unpublished exceptions (those that extend `Phprojekt_Exception` directly but not `Phprojekt_Exception_Published`) represent internal errors whose details should not be exposed to clients for security reasons.

The Exception library integrates closely with the framework's error controller, which catches exceptions during request processing and transforms them into appropriate HTTP responses. When a published exception is caught, the error controller uses the exception's `getHttpCode()` method to set the HTTP response code and calls `toArray()` to obtain structured error data for the JSON response. This integration ensures that validation errors return 422 (Unprocessable Entity) responses, authorization failures return 403 (Forbidden) responses, and configuration errors return 500 (Internal Server Error) responses, allowing JavaScript clients to handle different error types appropriately.

## Component Structure

| Path | Purpose |
|------|---------|
| `library/Phprojekt/Exception.php` | Base exception class for all PHProjekt exceptions |
| `library/Phprojekt/Exception/Published.php` | Base class for exceptions that can be safely exposed to clients |
| `library/Phprojekt/Exception/Validation.php` | Exception thrown when model validation fails |
| `library/Phprojekt/Exception/InvalidParameter.php` | Exception thrown when invalid parameters are provided |
| `library/Phprojekt/Exception/NotAuthorized.php` | Exception thrown when users lack required permissions |
| `library/Phprojekt/Exception/IOException.php` | Exception thrown for file and network I/O errors |
| `library/Phprojekt/Exception/HolidayRegionNotSet.php` | Exception thrown when holiday region configuration is missing |
| `library/Phprojekt/Exception/ContractNotSet.php` | Exception thrown when user contract data is missing |

The Exception library follows a clear hierarchical organization with `Phprojekt_Exception` at the root, providing a common ancestor for all framework exceptions. Below this sits `Phprojekt_Exception_Published`, which adds capabilities for public error reporting, and below that are the specific exception types that represent particular error conditions. This three-tier hierarchy (base, published, specific) provides flexibility in error handling, allowing code to catch exceptions at the appropriate level of specificity based on how the error should be handled.

The organizational structure reflects a separation between infrastructure exceptions (like `IOException`) that extend the base `Exception` class directly, and application-level exceptions (like `Validation`, `InvalidParameter`, `NotAuthorized`) that extend `Phprojekt_Exception_Published` because they represent expected error conditions that should be communicated to users. This separation ensures that infrastructure failures are logged but not exposed in detail to clients, while application-level errors provide clear, actionable feedback to users and API consumers.

## Key Classes and Files

### Phprojekt_Exception

The base exception class `Phprojekt_Exception` located in `Exception.php` serves as the root of PHProjekt's exception hierarchy, extending PHP's native Exception class to provide a common ancestor for all framework exceptions. This class is intentionally minimal, containing no additional methods or properties beyond those inherited from the standard Exception class. Its primary purpose is to provide a type that can be used in catch blocks to distinguish PHProjekt exceptions from exceptions thrown by third-party libraries or the PHP runtime itself. By catching `Phprojekt_Exception`, error handlers can identify framework-specific errors and route them through PHProjekt's error handling mechanisms rather than treating them as unexpected system errors.

The minimalist design of `Phprojekt_Exception` reflects the principle that the base exception type should impose no constraints on its subclasses. Different exception types may need to carry different contextual information (validation errors need field names, authorization errors need resource identifiers, I/O errors need file paths), and the base class avoids prescribing any particular structure for this information. Subclasses are free to define whatever constructor parameters and instance variables they need to capture the relevant error context. This flexibility allows the exception hierarchy to grow organically as new error types are identified, without requiring modifications to the base class.

### Phprojekt_Exception_Published

The `Phprojekt_Exception_Published` class in `Exception/Published.php` extends `Phprojekt_Exception` and serves as the base class for all exceptions that can be safely exposed to API clients. This class introduces three critical capabilities: HTTP status code management through the `$_httpCode` property and `getHttpCode()` method, error type identification through the `$_type` property, and structured error serialization through the `toArray()` method. The constructor accepts a message parameter that is automatically translated using `Phprojekt::getInstance()->translate()`, ensuring that error messages are presented in the user's preferred language. Additionally, the constructor accepts an optional `$error` parameter that can carry machine-readable error codes or identifiers, separate from the human-readable message.

The `toArray()` method provides the serialization mechanism that enables published exceptions to be converted into JSON responses. This method returns an associative array containing the error type, the translated message, and the optional error code if present. Subclasses can override this method to add additional fields specific to their error context. The separation of the `$_type` property from the exception class name allows for stable error type identifiers in API responses even if exception class names change during refactoring, supporting API versioning and backward compatibility. The HTTP status code mechanism enables published exceptions to indicate the appropriate response code for their error condition, with validation errors defaulting to 422, authorization errors to 403, and configuration errors to 500.

The Published exception class also establishes a pattern for protected properties that subclasses can set to customize behavior. The `$_type` property defaults to "generic" but subclasses typically override this to provide specific type identifiers like "validation", "notAuthorized", or "contractNotSet". Similarly, the `$_httpCode` property defaults to 500 (Internal Server Error) but subclasses override it to provide more specific status codes. This use of protected properties rather than abstract methods allows subclasses to customize behavior through simple property assignments rather than requiring method implementations, reducing boilerplate code in the specific exception classes.

### Phprojekt_Exception_Validation

The validation exception in `Exception/Validation.php` represents the most commonly thrown application-level exception, occurring whenever a model fails validation during save operations. This exception extends `Phprojekt_Exception_Published` and is designed to carry detailed information about the validation failure, including the field name, field label, and validation error message. The constructor accepts an error array with keys 'field', 'label', 'message', and optionally 'error', and constructs an exception message in the format "fieldName: errorMessage". The exception stores the field and label in protected properties `$_field` and `$_label`, making them available for serialization.

The `toArray()` method override adds the field name and label to the error structure, enabling JavaScript clients to highlight the specific form field that failed validation and display an error message adjacent to that field. The HTTP status code for validation exceptions is 422 (Unprocessable Entity), which is the semantically correct status for requests that are syntactically valid but semantically invalid. This exception is typically thrown in REST controller post and put actions after calling `recordValidate()` on a model and detecting validation failures. The RestController catches validation exceptions and returns them directly to the client with the 422 status code and the structured error information, allowing the JavaScript UI to provide inline validation feedback.

The validation exception design reflects a pragmatic approach to error reporting where the exception carries enough information for the client to provide actionable feedback to users, but not so much information that it reveals internal implementation details. The field name corresponds to the database column or model property name, while the label provides the user-facing field name for display purposes. The message describes why validation failed (e.g., "This field is required" or "Invalid date format"), and the optional error code provides a machine-readable identifier that clients can use to implement custom error handling logic or localized error messages.

### Phprojekt_Exception_InvalidParameter

The `InvalidParameter` exception in `Exception/InvalidParameter.php` handles cases where controller actions receive parameters that don't match expected formats or constraints. This exception extends `Phprojekt_Exception_Published` and is designed to carry information about the specific parameter that was invalid, its actual value, and optionally a description of what format the value should match. The constructor accepts three parameters: the field name, the invalid value, and an optional `$shouldMatch` parameter describing the expected format. It constructs a descriptive error message like "Invalid value \"abc\" for dateField, it should match YYYY-MM-DD format".

The exception stores the field name, value, and expected format in protected properties and overrides the `toArray()` method to include these in the serialized error structure. Like validation exceptions, invalid parameter exceptions use the 422 HTTP status code, indicating that the request was understood but cannot be processed due to semantic errors. This exception is particularly useful in REST endpoints that accept URL parameters or query strings, where parameter validation happens before model instantiation. For example, an endpoint that accepts a date range might throw an `InvalidParameter` exception if the start date parameter doesn't match the expected date format, providing clear feedback about what went wrong and what format is expected.

The distinction between `Validation` and `InvalidParameter` exceptions reflects the difference between model-level validation (which occurs after model properties are set and evaluates business rules) and parameter-level validation (which occurs before model instantiation and evaluates parameter format and presence). Invalid parameter exceptions typically represent programmer errors or malicious requests rather than user input errors, as properly-designed clients should validate input before sending requests. However, by providing structured error information, these exceptions enable clients to handle edge cases gracefully and provide meaningful error messages even when unexpected parameter errors occur.

### Phprojekt_Exception_NotAuthorized

The authorization exception in `Exception/NotAuthorized.php` represents security violations where authenticated users attempt to access resources they lack permission to access. This exception extends `Phprojekt_Exception_Published` and uses the HTTP status code 403 (Forbidden), which indicates that the server understood the request but refuses to authorize it. The exception type identifier is "notAuthorized", allowing JavaScript clients to detect authorization failures and potentially redirect users to a login page or display an appropriate error message. Unlike validation exceptions, authorization exceptions typically don't need to carry additional context beyond the error message, as the mere fact of an authorization failure is sufficient information for clients to handle the error.

Authorization exceptions are thrown throughout the application when rights checks fail, such as when a user attempts to view a project they're not a member of, edit an item they don't have write access to, or delete a record they don't have delete permissions for. The `Phprojekt_Item_Abstract` class and its subclasses typically perform rights checks before allowing operations to proceed, throwing `NotAuthorized` exceptions when checks fail. The error controller catches these exceptions and returns them to the client with the 403 status code, allowing the JavaScript UI to distinguish authorization failures from other error types and handle them appropriately (e.g., by showing a login prompt if the session has expired, or by displaying a "You don't have permission" message if the user simply lacks the necessary rights).

The use of a dedicated exception type for authorization failures rather than a generic exception with an error message enables fine-grained error handling in both the error controller and in JavaScript clients. The error controller can log authorization failures differently from other errors, potentially tracking them for security monitoring purposes. JavaScript clients can implement retry logic for authorization failures that might be due to expired sessions, while treating other error types as permanent failures. This exception type represents one of the clearest examples of how PHProjekt's exception taxonomy enables semantic error handling that improves both security and user experience.

### Phprojekt_Exception_IOException

The I/O exception in `Exception/IOException.php` represents a different category of exception that extends PHP's base Exception class directly rather than extending `Phprojekt_Exception_Published`. This design decision reflects the fact that I/O errors are typically infrastructure failures (disk full, permissions issues, network timeouts) that should not be exposed to clients in detail for security reasons. The IOException is intentionally minimal, containing no additional methods or properties, serving simply as a type marker that allows application code to distinguish I/O failures from other error types in catch blocks.

I/O exceptions are thrown when file operations fail (reading configuration files, writing upload files, accessing log files) or when network operations fail (connecting to external APIs, fetching remote resources). These exceptions are typically caught at a high level in the application and logged with full details including stack traces, but only generic error messages are returned to clients to avoid revealing information about the server's file system structure or network configuration. The error controller's handling of unpublished exceptions demonstrates this pattern: when an IOException is caught, it logs the full exception details but returns only "Internal Server Error" to the client with a 500 status code.

The decision to extend the base Exception class rather than `Phprojekt_Exception` represents a pragmatic acknowledgment that I/O exceptions often wrap exceptions thrown by PHP's file system or stream functions, and maintaining a separate hierarchy allows for easier exception chaining and interoperability with third-party libraries. Application code that performs I/O operations can catch IOException specifically to handle I/O failures differently from application-level errors, while still allowing generic exception handlers higher in the call stack to catch all Exception instances as a fallback.

### Phprojekt_Exception_HolidayRegionNotSet and Phprojekt_Exception_ContractNotSet

The `HolidayRegionNotSet` and `ContractNotSet` exceptions in their respective files represent domain-specific configuration exceptions related to the Timecard module's requirements. These exceptions extend `Phprojekt_Exception_Published` and use 500 (Internal Server Error) status codes because they represent configuration problems that prevent normal operation rather than client errors. The `HolidayRegionNotSet` exception is thrown when the Timecard module attempts to calculate holidays for a user but the user's profile lacks the required holiday region setting. Similarly, the `ContractNotSet` exception is thrown when time tracking operations require contract information (like working hours or vacation days) but the user has no associated contract record.

The `ContractNotSet` exception includes a custom constructor that provides a fixed error message "You don't have an associated contract", demonstrating a pattern where domain-specific exceptions can encapsulate standard error messages rather than requiring callers to provide messages. This approach ensures consistent error messaging for specific error conditions and reduces duplication of error message strings throughout the codebase. The exception type identifiers ("holidayRegionNotSet" and "contractNotSet") enable JavaScript clients to detect these specific configuration errors and potentially guide users through configuration workflows to resolve them.

These domain-specific exceptions illustrate how the exception hierarchy can be extended to capture application-specific error conditions without modifying the core exception classes. As new modules are added to PHProjekt or new business rules are implemented, additional exception types can be created to represent the specific error conditions those modules need to communicate. The Published base class provides the infrastructure for HTTP status code mapping and error serialization, while the specific exception classes need only define their type identifiers and optionally provide custom constructors or override the `toArray()` method to include additional context.

## Public API and Interfaces

The Exception library presents a straightforward public API consisting primarily of exception constructors and the specialized methods on published exceptions. Application code interacts with the exception system mainly through throw statements that instantiate and raise appropriate exception types. The base `Phprojekt_Exception` uses the standard Exception constructor signature accepting a message, numeric code, and optional previous exception for exception chaining. The `Phprojekt_Exception_Published` constructor extends this signature with an additional `$error` parameter that can carry machine-readable error identifiers, and it automatically translates the message parameter through the framework's translation system.

Specialized exception constructors present interfaces tailored to their specific error conditions. The `Validation` exception constructor accepts an array with keys 'field', 'label', 'message', and optionally 'error', encapsulating all the information needed to report a field validation failure. The `InvalidParameter` constructor accepts the parameter name, invalid value, and optional expected format description, constructing a descriptive error message from these components. The `ContractNotSet` exception takes no parameters, using a fixed error message defined in the exception class. These varied constructor signatures reflect the principle that exception construction should be as simple as possible for the specific error condition being reported, with constructors handling message formatting and context assembly.

The `toArray()` method on published exceptions provides the primary interface for error serialization, returning associative arrays that can be converted to JSON for API responses. This method is called by the error controller when handling published exceptions, and its return value becomes the error object in the JSON response. The method's consistent interface (parameterless, returning an array) enables polymorphic handling of different exception types, with the error controller treating all published exceptions identically regardless of their specific type. The `getHttpCode()` method similarly provides a consistent interface for retrieving the appropriate HTTP status code for each exception type, enabling the error controller to set response codes appropriately without switch statements or type checking.

## Dependencies and Integration

The Exception library has minimal external dependencies, relying primarily on PHP's native Exception class as its foundation. The `Phprojekt_Exception_Published` class depends on the `Phprojekt` singleton class to access the translation system through `Phprojekt::getInstance()->translate()`, enabling automatic message translation when exceptions are constructed. This dependency on the translation system ensures that error messages are presented in the user's configured language, supporting PHProjekt's internationalization requirements. The translation integration also means that exception messages should be provided in English with translation keys that map to localized strings in the language files.

The primary integration point for the Exception library is the `ErrorController` in the Default module, which serves as the central exception handler for the application. The error controller receives exceptions through Zend Framework's error handling plugin, which catches exceptions during request processing and forwards them to the error controller's `errorAction()` method. The error controller examines the exception type and handles published and unpublished exceptions differently: published exceptions have their `toArray()` method called to generate structured error data for the response, while unpublished exceptions are logged with full details but only generic error information is returned to clients. This integration ensures consistent error handling across the application while maintaining security by not exposing internal error details.

The Exception library integrates extensively with the RestController base class, which throws various exception types during REST API request processing. The RestController throws `Zend_Controller_Action_Exception` instances for HTTP-level errors like missing parameters or incorrect HTTP methods, and throws `Phprojekt_Exception_Validation` instances when model validation fails during POST or PUT operations. The RestController also catches `Phprojekt_Exception_NotAuthorized` exceptions in its `getAction()` method and converts them to 404 (Not Found) responses to avoid revealing the existence of resources that users aren't authorized to access. This security-conscious exception handling demonstrates how the exception system supports both user experience (through structured error reporting) and security (through controlled information disclosure).

## Data Models and Structures

The Exception library defines several data structures through its exception classes' protected properties and `toArray()` return values. The base structure for published exceptions consists of a 'type' field identifying the error type, a 'message' field containing the translated human-readable error message, and an optional 'error' field containing a machine-readable error code or identifier. This base structure provides the minimum information needed for clients to display error messages to users and potentially implement type-specific error handling logic. The separation of type from message enables clients to identify specific error conditions even when message text changes due to translation or message improvements.

The validation exception extends this base structure with 'field' and 'label' properties that identify which model field failed validation. The field property contains the internal field name (typically matching the database column name), while the label property contains the user-facing field label suitable for display in error messages. This structure enables JavaScript clients to implement inline validation error display, highlighting the specific form field that failed validation and showing an error message adjacent to it. The combination of field name, label, and message provides all the information needed for rich validation feedback without requiring additional server round-trips.

The invalid parameter exception structure includes 'field', 'value', and 'shouldMatch' properties that describe parameter validation failures. The field property identifies which parameter was invalid, the value property shows what value was provided, and the shouldMatch property describes the expected format or constraint. This structure enables clients to log detailed error information for debugging purposes and potentially provide user guidance about correct parameter formats. The inclusion of the actual value in the error structure is designed for debugging scenarios rather than production use, as sensitive parameter values should be sanitized before being included in exception messages.

## Configuration and Settings

The Exception library requires minimal configuration, operating primarily through the protected properties defined in exception classes rather than through external configuration files. Each published exception subclass configures its behavior through the `$_type` and `$_httpCode` protected properties, which define the exception's type identifier and HTTP status code respectively. These properties are set at the class level through property initializers, making the configuration readily visible in the exception class definitions. This approach to configuration reflects the principle that exception behavior should be determined by exception type rather than by runtime configuration, ensuring consistent error handling regardless of deployment environment.

The translation of exception messages relies on configuration in the translation system, with exception messages serving as translation keys that map to localized strings in language files. Exception constructors should provide English error messages that serve as both the default message (if translation is unavailable) and the translation key. The translation system configuration determines which language is used for error messages based on the current user's language preference. This configuration integration ensures that exception messages are automatically localized without requiring exception classes to be aware of the user's language preference or the translation mechanism.

The error controller's behavior with exceptions can be customized through Zend Framework configuration that determines how the error handler plugin routes exceptions to the error controller. However, the Exception library itself imposes no requirements on this configuration, working with the default Zend Framework error handling mechanism. The only configuration consideration for the Exception library is ensuring that the error controller is correctly registered in the application's routing configuration so that exceptions can be caught and processed appropriately. The library's independence from configuration reflects its role as infrastructure that should work consistently across different deployments without requiring customization.

## Design Patterns and Principles

The Exception library extensively employs the Template Method pattern through its exception hierarchy, where the `Phprojekt_Exception_Published` base class defines the overall structure for error serialization (the `toArray()` method) while allowing subclasses to customize specific aspects by overriding the method and calling the parent implementation. This pattern is evident in the validation and invalid parameter exceptions, which call `parent::toArray()` to get the base error structure and then add their specific fields to it. The template method approach ensures consistent error structure across all exception types while allowing each type to include its specific contextual information.

The library demonstrates the Strategy pattern through its use of different exception types to represent different error handling strategies. Each exception type encapsulates a particular error handling strategy, including the appropriate HTTP status code, error type identifier, and additional context fields. Application code selects the appropriate strategy by choosing which exception type to throw based on the error condition encountered. The error controller then executes the strategy by calling the exception's methods to determine the HTTP status code and generate the error response. This pattern enables flexible error handling where new error types can be added without modifying the error controller or other exception types.

The design reflects the Open-Closed Principle, with the exception hierarchy open for extension (new exception types can be added by extending existing classes) but closed for modification (the base exception classes and error controller don't need to change when new exception types are added). The `toArray()` method provides a uniform interface that all published exceptions implement, enabling the error controller to treat all exception types polymorphically. New exception types need only extend `Phprojekt_Exception_Published`, set their type and HTTP code properties, and optionally override `toArray()` to add type-specific fields, without requiring any changes to exception handling code elsewhere in the application.

The Liskov Substitution Principle is maintained throughout the hierarchy, with all subclasses of `Phprojekt_Exception_Published` being usable wherever the parent class is expected. The error controller's exception handling code works with any published exception through the common interface provided by the base class, without needing to know about specific exception types. This substitutability is critical for enabling the error controller to handle exceptions polymorphically, treating validation errors, authorization errors, and configuration errors uniformly while still allowing each to provide its specific error information.

The Single Responsibility Principle is evident in the separation of exception types, with each exception class responsible for representing one specific error condition and encapsulating the information relevant to that condition. The validation exception is responsible only for validation error representation, the authorization exception only for authorization failure representation, and so on. This separation ensures that changes to how one error type is represented don't affect other error types, and that new error types can be added without impacting existing ones. The principle extends to the separation between exception definition (in the exception classes) and exception handling (in the error controller), with clear boundaries between error representation and error response generation.
