# Component: Cleaner

## Overview

The Cleaner library is a comprehensive input validation, sanitization, and escaping framework designed to protect PHProjekt 6 applications from injection attacks and data integrity issues by providing a layered defense mechanism for handling untrusted user input. This custom-built security library, developed by Mayflower GmbH and distributed under LGPL v3, serves as the first line of defense against common web vulnerabilities by systematically validating user input against expected data types, sanitizing malformed or potentially dangerous values into safe equivalents, and escaping output for safe rendering in various contexts such as HTML, SQL, and URLs. The library operates on the principle that all external input should be considered untrusted until explicitly validated, implementing a whitelist-based approach where values must conform to defined type specifications before being accepted into the application layer.

The Cleaner framework addresses the fundamental security challenge of input handling by wrapping PHP's global scope variables such as $_GET, $_POST, and $_REQUEST in protective abstractions that enforce validation and sanitization policies before application code can access parameter values. Rather than allowing direct access to potentially tainted input variables, the library introduces a Cage abstraction that encapsulates these scopes and provides controlled access through methods that automatically validate and sanitize values based on declared type expectations. This design pattern prevents developers from accidentally using unsanitized input by making validated access the path of least resistance, effectively building security into the development workflow rather than relying on developers to remember security best practices for every parameter access.

The library's architecture separates validation concerns from sanitization concerns, recognizing that these represent distinct security objectives with different risk profiles and recovery strategies. Validation determines whether input conforms to expected format and range constraints, returning boolean success indicators that allow application code to reject invalid submissions with appropriate error messages that guide users toward providing acceptable input. Sanitization attempts to transform potentially invalid or dangerous input into safe equivalents by stripping problematic characters, normalizing formats, and applying type coercion rules that preserve user intent while eliminating security risks. This dual-phase approach provides flexibility for different use cases where strict validation might reject legitimate user input that could be safely sanitized, or where business requirements dictate that invalid input should fail fast rather than being silently transformed.

The Cleaner library implements an extensible type system that covers common data types encountered in web applications including integers, floats, booleans, strings, dates, times, timestamps, IP addresses, alphanumeric strings, and specialized formats like HTML and filter query strings. Each type definition pairs a validator implementation that checks conformance with a sanitizer implementation that attempts to extract valid values from malformed input, allowing the framework to handle real-world user input patterns where formatting inconsistencies are common. The library also provides context-specific escaping functions that prepare validated values for safe use in different output contexts, recognizing that a value safe for display in HTML may require different escaping than the same value embedded in SQL queries or JavaScript code.

## Component Structure

| Directory/File | Purpose |
|----------------|---------|
| `Cage.php` | Scope wrapper class that encapsulates PHP superglobals ($_GET, $_POST, etc.) to provide controlled validated access to parameters |
| `Engine.php` | Singleton factory and orchestration class that manages component instances and provides static access to validation, sanitization, and escaping services |
| `Parameter.php` | Value object representing a processed parameter with metadata including original value, sanitized value, validation status, and error messages |
| `Validator.php` | Collection of validation methods that check whether values conform to specific type definitions using regular expressions and PHP type checking |
| `Sanitizer.php` | Collection of sanitization methods that transform values into conforming types by stripping invalid characters and applying normalization rules |
| `Escaper.php` | Context-specific output escaping methods for HTML, URL, and SQL contexts to prevent injection attacks when rendering validated data |
| `Messages.php` | Internationalized message container that accumulates validation and sanitization error messages with locale-specific translations |
| `Util.php` | Utility class providing helper functions like blank value detection used throughout the validation and sanitization pipeline |
| `Exception.php` | Base exception class for Cleaner-specific errors such as invalid type specifications or configuration problems |

The Cleaner component organization reflects a separation of concerns where the Cage class serves as the primary integration point for application code, Engine acts as the service locator and factory for obtaining component instances, and the specialized Validator, Sanitizer, and Escaper classes contain the actual data processing logic organized by responsibility. The Parameter class provides a rich return type that encapsulates all processing metadata, allowing calling code to introspect what transformations were applied and whether validation succeeded without needing to manage this state separately.

## Key Classes and Files

The **Cleaner_Cage** class serves as the protective wrapper around PHP superglobal arrays, providing the primary interface through which application code safely accesses request parameters, session data, and other external input sources. This class implements a facade pattern that intercepts parameter access and automatically routes values through validation and sanitization pipelines before returning them to calling code, effectively preventing direct contact with potentially malicious input. The `getInstance()` static factory method creates Cage instances by accepting a reference to a scope array and a descriptive key name, wrapping common sources like $_GET or $_POST to create typed access objects. The `getParameter()` method represents the core abstraction where applications specify the expected type, parameter name, whether empty values are acceptable, a default value for missing or invalid parameters, and whether to attempt sanitization when validation fails. This method returns a Cleaner_Parameter object that encapsulates the validation result, original value, sanitized value if applicable, and any messages generated during processing, providing rich metadata that allows sophisticated error handling without requiring catch blocks or out-of-band error signaling. The `validate()` and `sanitize()` convenience methods offer simpler interfaces for cases where applications only need validation results or sanitized values without the full parameter metadata, delegating to the Engine class for actual processing.

The **Cleaner_Engine** class implements the Singleton pattern to provide centralized configuration and factory services for obtaining Validator, Sanitizer, Escaper, and Messages instances throughout the application. This class acts as the service locator that decouples client code from concrete component implementations, allowing configuration of alternative validator or sanitizer implementations through the `setValidatorClass()`, `setSanitizerClass()`, `setEscaperClass()`, and `setMessagesClass()` methods which modify the class names used by factory methods. The static `getInstance()` method ensures only one Engine instance exists per request, maintaining consistent configuration across all validation and sanitization operations. The `validate()` static method provides application-level access to type validation by accepting a type identifier, value to validate, and optional messages container, then looking up the appropriate validator method through reflection on the Validator instance and invoking it with call_user_func_array for dynamic dispatch. Similarly, the `sanitize()` and `escape()` static methods provide centralized access to sanitization and escaping services, normalizing type identifiers to lowercase and mapping them through configuration arrays to specific method implementations. The factory methods `getValidator()`, `getSanitizer()`, `getEscaper()`, and `getMessages()` instantiate component objects based on configured class names, enabling dependency injection patterns where test code or specialized implementations can be substituted without modifying client code.

The **Cleaner_Parameter** class represents the result of parameter processing as an immutable value object that captures all relevant metadata about validation and sanitization operations performed on a single input value. This class stores the original value exactly as received from the source scope, the sanitized value if sanitization was attempted, the default value to use when the parameter is missing or invalid, and boolean flags indicating whether the value was valid according to type rules, whether sanitization was applied, and whether the returned value represents the default rather than user-provided input. The Messages object attached to each parameter captures any validation or sanitization errors encountered, providing detailed feedback that can be displayed to users or logged for debugging. The `getValue()` method implements the core value resolution logic by returning the original value when validation succeeded, the default value when the parameter was missing or blank, the sanitized value when sanitization was attempted and produced a result, or the original value when sanitization was disabled, creating a priority chain that prefers valid original values over sanitized approximations over defaults. The `__toString()` magic method delegates to `getValue()` to allow Parameter objects to be used directly in string contexts, promoting convenience while maintaining type safety through explicit accessor methods like `isValid()`, `isSanitized()`, and `isDefault()` that allow application code to make informed decisions about how to handle edge cases. The comprehensive metadata exposed by Parameter objects enables sophisticated error handling strategies where applications can distinguish between missing parameters, invalid format, sanitization failures, and successful validation to provide appropriate user feedback and fallback behaviors.

The **Cleaner_Validator** class implements validation logic for all supported data types through a collection of public methods that follow a consistent naming pattern of `validate` followed by the type name in camel case. The `$validators` array maps type identifiers like 'int', 'float', 'bool', 'date', 'time', 'timestamp', 'ipv4', 'alnum', 'alpha', 'string', 'numeric', and 'word' to their corresponding validation method names, allowing the Engine to dynamically dispatch validation requests based on type strings. The `validateInt()` method demonstrates the validation pattern by first checking if the value is already a PHP integer using `is_int()`, then falling back to numeric string checking by verifying `is_numeric()` returns true and the value remains unchanged when cast to integer, ensuring that strings like "42" validate successfully while "42.5" or "42abc" are rejected. The `validateBool()` method shows more sophisticated validation by recognizing both PHP boolean values and common string representations like 'true', 'false', 'yes', 'no', '1', '0', 'on', 'off', providing user-friendly acceptance of different boolean expression formats commonly encountered in web forms. The `validateIsoDate()`, `validateIsoTime()`, and `validateIsoTimestamp()` methods use regular expressions to enforce ISO 8601 format requirements while calling PHP's `checkdate()` function to verify that dates represent valid calendar dates rather than syntactically correct but semantically impossible values like February 30th. The `validateIpv4()` method leverages PHP's `ip2long()` function which performs full IP address validation including range checking, demonstrating how the Validator class wraps existing PHP validation functions with consistent error reporting through the Messages interface. Each validation method accepts a value and Messages object, returning boolean success status while populating the Messages container with error codes like 'INVALID_INT', 'INVALID_BOOL', or 'INVALID_ISODATE' that can be translated to user-facing error messages through the internationalization system.

The **Cleaner_Sanitizer** class implements type coercion and data cleansing logic through sanitization methods that attempt to extract valid values from malformed input by removing invalid characters, normalizing formats, and applying intelligent heuristics. The `$sanitizers` array maps type identifiers to sanitization method names similar to the Validator's structure, supporting an extended type set that includes specialized sanitization targets like 'html' for HTMLPurifier integration, 'xss' for aggressive cross-site scripting prevention, 'filter' for search query sanitization, and 'arrayofint' for comma-separated integer lists. The `sanitizeInt()` method demonstrates sophisticated sanitization logic by handling multiple input formats including numeric types that are cast directly, scientific notation strings like "1E5" that are double-cast to honor exponent representation, and arbitrary strings where all non-digit characters except the leading minus sign are stripped to extract embedded integers. The `sanitizeFloat()` method applies similar heuristics while preserving decimal points, handling multiple decimals by keeping only the first occurrence and stripping non-numeric characters to extract usable floating-point values from messy input. The `sanitizeHtml()` method integrates with HTMLPurifier to provide comprehensive XSS protection by configuring HTMLPurifier with restrictive settings that allow only safe attributes like style, size, href, alt, and src, permit limited CSS properties for formatting, and strip all potentially dangerous HTML constructs while preserving legitimate formatting tags. The `sanitizeBool()` method converts various string representations into PHP boolean values by checking against whitelist arrays of true and false equivalents, returning null when the input doesn't match recognized patterns to distinguish unknown values from explicit false. The `sanitizeIsoDate()`, `sanitizeIsoTime()`, and `sanitizeIsoTimestamp()` methods attempt to parse diverse date and time formats using PHP's `strtotime()` function, stripping timezone declarations and GMT offsets that might confuse parsing, then formatting the result according to ISO 8601 standards to normalize input into canonical representations. The `sanitizeArrayOfInt()` helper demonstrates compound sanitization by splitting comma-separated strings into arrays and casting each element to integer, providing safe handling of multi-value parameters common in checkbox and select-multiple form controls.

The **Cleaner_Escaper** class provides output encoding functions that prepare validated data for safe rendering in various contexts where special characters could be interpreted as code rather than data. The `$escapers` array organizes escaping methods by scope (html, css, javascript, sql) and sub-type, allowing context-specific escaping strategies that apply appropriate encoding rules based on where the value will be used. The `escapeHtmlValue()` method uses PHP's `htmlentities()` function with ENT_QUOTES flag to encode both single and double quotes along with other HTML special characters like less-than, greater-than, and ampersand, preventing values from breaking out of attribute contexts or introducing unauthorized tags when rendered in HTML templates. The `escapeHtmlUrl()` method applies `urlencode()` after UTF-8 encoding to prepare values for safe inclusion in URL query strings and path components, handling international characters and special symbols that would otherwise break URL parsing or introduce injection vulnerabilities. The `escapeSqlValue()` method uses `addslashes()` to escape SQL special characters, providing a basic SQL injection defense layer though applications should prefer prepared statements and parameter binding for database queries rather than relying on string escaping which can be bypassed under certain character encoding scenarios. The escaping methods represent a final defense layer applied at output time to complement the input validation and sanitization performed during parameter processing, recognizing that context-specific encoding requirements depend on where data will be rendered and cannot be predetermined during input processing.

The **Cleaner_Messages** class implements an internationalized error message container that accumulates validation and sanitization error codes and provides locale-specific translations for display to users. The class maintains a `$_messages` array that stores message keys like 'INVALID_INT', 'INVALID_REQUIRED', or 'SANITIZE_DEFAULT' added through the `add()` method during validation and sanitization operations. The static `$_translations` cache stores loaded locale message files to avoid repeated file system access, implementing a simple memoization pattern that improves performance when processing multiple parameters. The `get()` method loads translations for the specified locale by calling the protected `_load()` method which reads PHP files from a Locale directory that return associative arrays mapping message keys to translated strings, then maps accumulated message keys to their localized text before returning the result. The `isEmpty()` method allows quick checking whether any errors were recorded, enabling conditional error display without needing to retrieve full message text. The `has()` method checks whether a specific message key was added, supporting logic that needs to distinguish between different error types when determining appropriate responses. The `__toString()` method joins message keys with commas for simple debugging output, though production code should use `get()` with appropriate locale to obtain user-friendly translated messages. This internationalization support allows PHProjekt to serve multilingual user bases with validation errors displayed in each user's preferred language, improving usability across diverse deployment environments.

The **Cleaner_Util** class provides utility functions shared across the Cleaner framework, currently containing the single static method `isBlank()` that determines whether a value should be considered empty for validation purposes. This method implements a more nuanced empty check than PHP's built-in `empty()` function by returning false for non-string, non-null values regardless of their content, then trimming string values and checking if the result is an empty string. This approach treats whitespace-only strings as blank while allowing the integer zero, float zero, boolean false, and empty arrays to be considered non-blank, preventing validation logic from incorrectly rejecting legitimate zero values or false booleans that differ meaningfully from absent or whitespace parameters. The Cage class uses `isBlank()` when determining whether parameters are present in the wrapped scope, ensuring that whitespace-padded form submissions are handled consistently with truly missing parameters when the `$empty` flag indicates required parameters.

The **Cleaner_Exception** class extends PHP's base Exception class to provide Cleaner-specific exception types thrown when configuration errors or invalid operations are detected. The Engine class throws Cleaner_Exception when validation, sanitization, or escaping is requested for unregistered type identifiers, preventing silent failures when application code misspells type names or attempts to use unsupported validation rules. The Messages class throws exceptions when locale files cannot be found, surfacing internationalization configuration problems during development rather than allowing them to cause runtime failures in production. The exception-based error handling provides explicit failure modes for programming errors like invalid type specifications while keeping validation failures as expected conditions represented through return values and Messages objects rather than exceptions, maintaining a clear distinction between errors that indicate bugs versus normal validation rejection of user input.

## Public API and Interfaces

The primary public interface for consuming the Cleaner library begins with obtaining Cage instances that wrap input scopes, typically accomplished through the `Cleaner_Cage::getInstance()` static factory by passing references to $_GET, $_POST, or custom parameter arrays along with descriptive scope names for error reporting. Application code calls `getParameter()` on Cage instances to retrieve validated and optionally sanitized parameter values, specifying the expected type string like 'int' or 'date', the parameter name within the wrapped scope, whether empty values should be considered invalid, a default value for missing or invalid parameters, and whether failed validation should trigger automatic sanitization attempts. The method returns Cleaner_Parameter objects whose `getValue()` method provides the best available value based on validation and sanitization results, while `isValid()`, `isSanitized()`, and `isDefault()` methods expose processing metadata for sophisticated error handling. Alternatively, applications can call `validate()` or `sanitize()` directly on Cage instances for simplified boolean validation or sanitized value retrieval without the full Parameter wrapper.

The lower-level interface exposed by Cleaner_Engine provides static methods for validation, sanitization, and escaping that can be called directly without wrapping scopes in Cage objects, supporting use cases where input comes from sources other than HTTP request parameters. The `Cleaner_Engine::validate()` static method accepts type identifier, value, and optional Messages object, returning boolean validation results while populating messages with error codes. The `Cleaner_Engine::sanitize()` static method performs type coercion and returns the sanitized value or null if sanitization fails, accumulating messages during processing. The `Cleaner_Engine::escape()` static method requires scope and sub-type parameters like ('html', 'value') or ('sql', 'value') to apply context-appropriate output encoding. These static methods provide flexibility for validation scenarios like sanitizing configuration file input, validating API responses, or escaping values dynamically constructed during request processing rather than originating from HTTP parameters.

The configuration interface allows applications to customize validation, sanitization, escaping, and message handling by implementing custom classes that follow the same method naming conventions and registering them through `Cleaner_Engine::setValidatorClass()`, `Cleaner_Engine::setSanitizerClass()`, `Cleaner_Engine::setEscaperClass()`, and `Cleaner_Engine::setMessagesClass()`. Custom validators extend the type system with application-specific validation rules like credit card number checking or domain-specific identifier validation, while custom sanitizers can implement specialized cleansing logic for proprietary data formats. This extensibility allows PHProjekt to adapt the Cleaner framework to evolving security requirements without modifying the core library, supporting organizational security policies that mandate specific validation approaches or escaping strategies beyond the default implementations.

## Dependencies and Integration

The Cleaner library maintains minimal external dependencies, relying primarily on standard PHP functions for string manipulation, regular expression matching, type checking, and date handling available in all PHP 5.x installations. The library leverages PHP's ctype extension for character type checking in validators like `validateAlpha()` and `validateAlnum()`, providing efficient validation of character composition without requiring regex patterns. The date and time validators use PHP's `checkdate()` and `strtotime()` functions to validate and parse temporal values, depending on PHP's date handling capabilities for calendar correctness and format flexibility. The sanitizer integrates with HTMLPurifier for comprehensive HTML sanitization in the `sanitizeHtml()` method, dynamically loading the HTMLPurifier.standalone.php file from the library directory and configuring a permissive policy that allows formatting markup while stripping scripts and dangerous attributes.

Within the PHProjekt 6 architecture, the Cleaner library integrates at the controller layer where HTTP request handling begins, wrapping $_GET and $_POST arrays in Cage instances immediately after routing determines which controller will handle the request. Controllers access parameters exclusively through Cage methods rather than directly referencing superglobals, enforcing validation as a required step in the request handling workflow. The RestController and other PHProjekt base controllers instantiate Cages during initialization and provide them to action methods, promoting consistent parameter handling across all controllers and preventing accidental bypass of validation logic. Models that accept user input call Cleaner validation and sanitization methods on values before performing business logic or database persistence, creating defense in depth where multiple validation layers catch different classes of invalid input.

The data flow through Cleaner integration begins when a web request arrives at PHProjekt with query string parameters, form data, or JSON payloads that populate PHP superglobal arrays. The front controller or request dispatcher creates Cage instances wrapping relevant superglobals and passes them to routed controllers as method parameters or stores them in registry objects accessible throughout request processing. Controller action methods call `getParameter()` to retrieve individual values, triggering validation against declared types and optionally sanitization if validation fails. The Parameter objects returned from getParameter provide rich metadata that controllers use to distinguish between valid, sanitized, and default values when formulating responses or error messages. Controllers pass validated values to model layer methods that perform business logic, apply additional domain-specific validation rules, and persist data to databases using Zend_Db prepared statements that provide final SQL injection defense. View templates access only validated and sanitized data passed from controllers, with additional escaping applied by the Escaper class when rendering values in HTML, JavaScript, or URL contexts depending on template structure.

## Data Models and Structures

The Cleaner library's data model centers on the Parameter value object that encapsulates all metadata associated with processing a single input value through validation and optional sanitization. The Parameter structure includes fields for the original unmodified value exactly as received from the input source, the sanitized value produced by attempting to coerce invalid input into a conforming representation, the configured default value to return when the parameter is missing or processing fails, and three boolean flags indicating validation success, whether sanitization was attempted and produced results, and whether the returned value represents the default rather than user input. The attached Messages object stores an array of error code strings accumulated during validation and sanitization that can be translated to user-friendly text through locale-specific message files. This rich structure allows application code to implement sophisticated error handling logic that distinguishes between absent parameters where the default should be used, invalid parameters where sanitization produced usable values, and irrecoverably invalid parameters that require user correction.

The validator and sanitizer configuration arrays defined in Cleaner_Validator and Cleaner_Sanitizer classes represent type system metadata that maps user-facing type identifiers to internal method names implementing validation and sanitization logic. These arrays support both canonical type names like 'integer', 'float', and 'boolean' as well as abbreviated aliases like 'int', 'real', and 'bool' that map to the same validation methods, promoting API flexibility while maintaining implementation simplicity. The type system includes primitive types for integers, floats, booleans, and strings; formatted types for dates, times, and timestamps following ISO 8601 standards; network types like IPv4 addresses; character class restrictions like alphanumeric and alphabetic strings; and specialized types for HTML content, XSS-protected output, search filter strings, and integer arrays. This type vocabulary provides validation coverage for common web application input patterns while remaining extensible through custom validator implementations.

The Messages class implements a simple accumulator pattern where validation and sanitization methods add error code strings to an array during processing, then application code retrieves translated messages mapped to these codes through locale-specific lookup tables. The error codes follow naming conventions like 'INVALID_{TYPE}' for validation failures ('INVALID_INT', 'INVALID_BOOL', 'INVALID_ISODATE') and 'SANITIZE_DEFAULT' or 'INVALID_REQUIRED' for sanitization and required field failures, providing consistent error reporting vocabulary across all validators. The locale message files return associative arrays mapping these codes to translated strings in languages like English and German, supporting PHProjekt's internationalization requirements while keeping translation concerns separate from validation logic.

## Configuration and Settings

The Cleaner library's configuration system operates primarily through the Engine singleton which stores class name strings for Validator, Sanitizer, Escaper, and Messages implementations that factory methods instantiate when components are needed. The default configuration instantiates Cleaner_Validator, Cleaner_Sanitizer, Cleaner_Escaper, and Cleaner_Messages classes, but applications can substitute custom implementations by calling `Cleaner_Engine::setValidatorClass()`, `Cleaner_Engine::setSanitizerClass()`, `Cleaner_Engine::setEscaperClass()`, or `Cleaner_Engine::setMessagesClass()` with fully-qualified class names before first use of the Engine. This dependency injection pattern allows test code to substitute mock validators that always return specific results, applications to add custom validation types beyond the built-in set, or deployments to enforce organizational security policies through specialized sanitization logic without modifying library code.

The Cage class accepts configuration through its method parameters rather than stored settings, allowing fine-grained control over validation behavior on a per-parameter basis. The `$empty` parameter to `getParameter()` and `validate()` methods controls whether missing or blank parameters should be considered validation failures, supporting required field semantics where parameters must be present and non-empty. The `$default` parameter specifies fallback values when parameters are absent or invalid, enabling graceful degradation without requiring explicit null checking throughout application code. The `$sanitize` boolean flag to `getParameter()` determines whether validation failures should trigger automatic sanitization attempts or immediately return invalid status, allowing applications to enforce strict validation for critical parameters while accepting sanitized values for less sensitive input. These per-parameter configuration options provide flexibility for different validation requirements across the application without requiring separate Cage instances or global configuration state.

The HTMLPurifier integration in `Cleaner_Sanitizer::sanitizeHtml()` demonstrates configuration of a third-party sanitization component where HTMLPurifier_Config objects specify allowed HTML elements, permitted attributes, CSS properties, character encoding, XHTML compliance level, and caching paths for compiled configuration. The default configuration allows only safe attributes like href, src, alt, and style while restricting CSS properties to visual formatting like font-weight, text-align, and color, providing XSS protection while preserving basic formatting capabilities. Applications needing different HTML sanitization policies can extend Cleaner_Sanitizer to override `sanitizeHtml()` with alternative HTMLPurifier configurations or substitute different HTML filtering libraries entirely through the Engine's class substitution mechanism.

## Design Patterns and Principles

The Cleaner library demonstrates the Wrapper pattern through the Cage class which encapsulates PHP superglobal arrays to provide controlled access that enforces validation policies. This wrapping prevents direct access to potentially tainted input by interposing validation logic between application code and raw parameter values, effectively making validated access the default path while requiring explicit effort to bypass security checks. The wrapper abstraction also allows Cleaner to augment parameter access with metadata like validation status and error messages without modifying the underlying arrays, maintaining backward compatibility with PHP's parameter handling while improving security properties.

The Factory pattern appears in the Engine class which provides factory methods for creating Validator, Sanitizer, Escaper, and Messages instances based on configured class names. The `getValidator()`, `getSanitizer()`, `getEscaper()`, and `getMessages()` methods encapsulate instantiation logic, allowing the rest of the codebase to obtain component instances without knowing concrete class names or construction requirements. This factory centralization supports dependency injection where alternative implementations can be substituted globally by changing Engine configuration, enabling test doubles, specialized validators, and custom sanitization strategies without modifying client code. The factory also implements lazy instantiation where components are created only when first needed rather than during Engine construction, reducing initialization overhead for requests that don't use all Cleaner features.

The Singleton pattern implemented by Engine ensures a single configuration instance exists per request, maintaining consistent validator, sanitizer, and escaper class selections across all validation operations. The static `$_instance` field stores the singleton which `getInstance()` returns after creating it on first access, preventing configuration inconsistencies that could arise if multiple Engine instances used different component implementations. The singleton pattern supports global configuration changes through setter methods that modify the instance stored in the static field, allowing bootstrap code to configure custom validators before request processing begins with changes affecting all subsequent validation operations.

The Value Object pattern is exemplified by the Parameter class which represents validation results as an immutable data structure containing original value, sanitized value, default value, status flags, and messages. Parameter instances are constructed with all fields at creation time and provide only accessor methods without state-modifying operations, ensuring that validation results cannot be accidentally altered after processing completes. The value object abstraction allows Parameter instances to be safely passed through multiple application layers without risk of mutation, while the comprehensive metadata supports diverse error handling strategies at each layer. The `__toString()` magic method provides convenient string conversion for template rendering while explicit accessor methods maintain type safety for logic that needs to distinguish validation outcomes.

The Strategy pattern underlies the type system where validation and sanitization logic varies by data type, with each type implementing its own validation and sanitization strategy through dedicated methods. The Engine selects appropriate validation or sanitization strategy by looking up type identifiers in configuration arrays that map to method names, then invoking the selected strategy through reflection and `call_user_func_array()`. This dynamic dispatch allows the type system to remain extensible where new types can be added by implementing additional validation and sanitization methods and updating the configuration arrays, without requiring changes to the dispatch logic or client code that references types by string identifiers. The strategy pattern decouples type-specific validation and sanitization implementations from the framework that invokes them, promoting maintainability and extensibility as security requirements evolve.
