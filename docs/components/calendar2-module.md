# Component: Calendar2

## Overview

The Calendar2 module provides sophisticated scheduling and event management capabilities within PHProjekt, implementing a complete calendar system with support for recurring events, participant management, and standards-based calendar synchronization through the CalDAV protocol. This module represents the second generation of calendar functionality in PHProjekt (hence "Calendar2"), incorporating lessons learned from the original implementation while adding enterprise-grade features like RFC 5545-compliant recurrence rules, participant status tracking, and bidirectional synchronization with external calendar clients. The module enables users to schedule meetings, track appointments, manage availability, and coordinate schedules across teams, all within the project-context framework that characterizes PHProjekt's organizational model.

The architectural sophistication of Calendar2 extends beyond basic event CRUD operations to encompass complex temporal logic for expanding recurring events, iCalendar format serialization for CalDAV interoperability, and sophisticated participant management that tracks acceptance status for each invitee. The recurring event implementation uses RRULE syntax from RFC 5545, supporting patterns like "every second Tuesday" or "monthly on the last weekday" through a dedicated helper class that translates RRULE strings into concrete date sequences. The participant model tracks not just who is invited to events but also their response status (pending, accepted, rejected), creating a meeting coordination system rather than just a personal calendar. The visibility model enables both public events visible to all users with project access and private events visible only to the owner, supporting both organizational coordination and personal schedule management.

The Calendar2 module's integration with external calendar systems through CalDAV protocol support represents a significant architectural achievement, implementing the complex CalDAV specification through SabreDAV library integration. The CalDAV backend presents PHProjekt calendars as standard CalDAV resources that external clients like Microsoft Outlook, Apple Calendar, Mozilla Thunderbird, or mobile calendar applications can subscribe to and synchronize with. This bidirectional synchronization enables users to view and modify PHProjekt events through their preferred calendar client, with changes propagating back to PHProjekt through CalDAV protocol operations. The CalDAV implementation includes HTTP Basic Authentication for security, iCalendar format conversion for data exchange, and proper CalDAV property support for features like calendar colors and display names.

The technological foundation of Calendar2 includes PHP 5.3+ with extensive DateTime manipulation for temporal calculations, the SabreDAV library (version 1.6.2) for CalDAV protocol implementation, RFC 5545 RRULE parsing for recurrence pattern interpretation, and Active Record persistence through Phprojekt_Item_Abstract for database operations. The module stores event data in the calendar2 table with supporting tables for participant tracking and exception dates, with foreign key relationships to project and user tables ensuring referential integrity. The recurrence implementation uses PHP's DateInterval and DatePeriod classes for efficient date sequence generation, while the CalDAV backend implements Sabre_CalDAV_Backend_Abstract to integrate with SabreDAV's server infrastructure. The module's notification integration with Phprojekt_Notification enables email reminders before events, with the system calculating appropriate send times based on event start times and user timezone preferences.

The Controllers directory contains three specialized controllers that handle different access patterns—IndexController for the Dojo frontend, Calendar2Controller for REST APIs, and CaldavController for CalDAV protocol operations. This triple-controller architecture enables the same event data to be accessed through multiple protocols without duplicating business logic, with each controller providing an appropriate interface for its client type. The CaldavController's integration with SabreDAV happens through backend classes in the CalDAV directory, creating a clean separation between protocol handling and data access.

The Models directory contains the substantial Calendar2 model at 1,310 lines of code, reflecting the complexity of event management with recurrence patterns, participant tracking, and iCalendar format conversion. The CalendarInformation and InformationDecoratorReadonly models demonstrate the decorator pattern where different views of event metadata are provided depending on context—full editability for web-created events versus read-only for CalDAV-synchronized events. The Helper directory contains three focused utility classes that encapsulate complex algorithms for recurrence expansion, authentication integration, and timezone handling, preventing these cross-cutting concerns from cluttering the main model and controller classes. The CalDAV directory houses the backend implementation that bridges between SabreDAV's expectations and PHProjekt's data model, translating between iCalendar format and Active Record objects.

## Key Classes and Files

### Models/Calendar2.php

The Calendar2_Models_Calendar2 class implements the core event entity with sophisticated support for recurring events, participant management, and dual-format persistence (database Active Record and iCalendar serialization). This model extends Phprojekt_Item_Abstract to inherit permission integration, search indexing, and history tracking while adding calendar-specific capabilities that distinguish events from generic items. The class spans 1,310 lines of carefully structured code that balance between standard Active Record patterns and the temporal complexity inherent in calendar systems. The model defines constants for status values (pending, accepted, rejected) and visibility levels (public, private), providing type-safe enumerations that prevent invalid state assignments.

The participant management system maintains two parallel arrays: _participantData for the current in-memory state and _participantDataInDb for the original database state, enabling the model to calculate participant changes when saving. This dual-tracking approach allows the save operation to determine which participant statuses changed and trigger appropriate notifications only to affected users. The participant data structure maps user IDs to status values, creating a compact representation of the many-to-many relationship between events and participants with associated status information. The model's handling of participants demonstrates the Unit of Work pattern where changes accumulate in memory and are flushed to the database transactionally during save operations.

The recurrence functionality centers on the rrule field that stores RFC 5545-compliant recurrence rules like "FREQ=WEEKLY;BYDAY=TU,TH" for events occurring every Tuesday and Thursday. The model delegates recurrence expansion to Calendar2_Helper_Rrule which parses the rule and generates concrete date sequences, then creates virtual event instances for each occurrence. These virtual instances share most properties with the series master but have different start and end times, with the model maintaining _isFirst flag to distinguish the series master from generated occurrences. The _originalStart field tracks the database-stored start time, enabling the model to detect when event times change and invalidate cached recurrence expansions. This virtual instance approach avoids exploding recurring events into millions of database records while providing the illusion that each occurrence is a distinct entity from the frontend's perspective.

The getDataForCalDAV method demonstrates the model's dual-format capability by serializing event data into iCalendar format suitable for CalDAV protocol responses. This method constructs VEVENT components with proper DTSTART, DTEND, RRULE, EXDATE (exception dates), and ATTENDEE (participants) properties, implementing the subset of iCalendar specification relevant to PHProjekt's feature set. The conversion handles timezone complications by expressing all times in UTC for wire format while storing local times in the database, preventing timezone-related bugs that plague calendar applications. The method also generates UID values that uniquely identify events across systems, enabling external calendar clients to track and update the same events across multiple synchronization cycles.

The save method orchestrates complex persistence workflows including participant status updates, notification scheduling, recurrence validation, and search index updates. The method first validates that recurrence rules are well-formed and don't create logical impossibilities like weekly events with no selected days. For events with participants, the method compares _participantData against _participantDataInDb to determine status changes, queuing notifications for users whose status changed or who were newly added. The method handles exception dates (specific occurrences cancelled from a recurring series) by maintaining a separate exceptions array that gets serialized to the database. The parent class's save method handles standard Active Record persistence while Calendar2's override adds calendar-specific pre-save and post-save hooks that manage the temporal and relational complexity unique to event management.

### Helper/Rrule.php

The Calendar2_Helper_Rrule class implements RFC 5545 recurrence rule parsing and expansion, translating compact RRULE strings into sequences of DateTime objects representing event occurrences. This helper encapsulates the complex temporal mathematics required for patterns like "every second Tuesday" or "the last weekday of each month," preventing this complexity from contaminating the Calendar2 model. The class accepts a first occurrence DateTime, a duration DateInterval, an RRULE string, and optional exception dates during construction, storing these as instance variables for subsequent query operations. This constructor-based configuration follows the immutable value object pattern where instances are configured once and then queried multiple times without mutation.

The _parseRrule method dissects RRULE strings into structured data including FREQ (frequency like DAILY, WEEKLY, MONTHLY), INTERVAL (multiplier like "every 2 weeks"), BYDAY (days of week for weekly/monthly patterns), UNTIL (end date for bounded series), and COUNT (maximum occurrences). The parser implements a lenient interpretation that handles both strictly-conforming and loosely-formatted rules, providing interoperability with diverse CalDAV clients that may generate slightly non-standard rules. The parsed data structure stores DateInterval objects for frequencies rather than string constants, enabling direct use with PHP's DateTime arithmetic without repeated parsing. The parser also calculates FREQINTERVAL by multiplying the base frequency by the interval multiplier, creating a single DateInterval that represents the actual recurrence period.

The getOccurrences method generates concrete occurrence dates within a specified time range, handling both bounded series (with UNTIL or COUNT) and unbounded series (recurring indefinitely). The method uses PHP's DatePeriod class to generate candidate dates based on the frequency interval, then filters these candidates through BYDAY constraints if specified. For monthly patterns, additional logic determines whether occurrences should be absolute (e.g., "15th of month") or relative (e.g., "second Tuesday"), with the implementation supporting both through different code paths. The exception dates array is consulted during generation, skipping any occurrence that matches an exception. This multi-stage filtering approach (generate candidates, apply day-of-week filter, apply exception filter) creates a pipeline architecture that's easier to understand and maintain than monolithic date generation logic.

The class's integration with PHP's DateTime infrastructure demonstrates effective use of standard library capabilities rather than reimplementing date arithmetic from scratch. The use of DateInterval for duration representation enables timezone-aware calculations where "add one day" correctly handles daylight saving transitions by maintaining clock time rather than adding exactly 86,400 seconds. The DatePeriod usage for base frequency generation leverages PHP's built-in iterator protocol, enabling memory-efficient generation of potentially infinite sequences through lazy evaluation. This thoughtful integration with platform capabilities reduces bug surface area and improves performance compared to custom temporal logic implementations.

### CalDAV/CalendarBackend.php

The Calendar2_CalDAV_CalendarBackend class implements the Sabre_CalDAV_Backend_Abstract interface, providing the bridge between SabreDAV's CalDAV server infrastructure and PHProjekt's event data model. This backend translates CalDAV protocol operations (get calendars, create event, update event, delete event) into corresponding Active Record operations on Calendar2 models, enabling external calendar clients to interact with PHProjekt calendars through standard protocols. The class follows SabreDAV's backend architecture where backends are responsible for data persistence while the SabreDAV framework handles protocol details like HTTP headers, iCalendar parsing, and WebDAV property management.

The getCalendarsForUser method implements CalDAV's calendar discovery mechanism, returning calendar metadata for a specified user principal. The PHProjekt implementation simplifies this by providing exactly one calendar per user (the "default" calendar), avoiding the complexity of supporting multiple calendars per user. The method extracts the username from the principal URI through regular expression matching, loads the corresponding user record, and returns a hardcoded calendar descriptor with the user's ID as the calendar ID. This simplification trades flexibility for implementation simplicity, with the assumption that users who need multiple logical calendars can use visibility or project context for organization rather than separate physical calendars.

The getCalendarObjects method retrieves all events within a calendar (optionally filtered by date range), performing the inverse conversion from Calendar2 Active Record models to iCalendar format. This method queries the database for events belonging to the specified user and project context, then invokes each event's getDataForCalDAV method to obtain iCalendar representations. For recurring events, the backend must decide whether to return just the series master or to expand recurrences into individual occurrences, with the implementation returning series masters and relying on CalDAV clients to perform expansion. This approach reduces bandwidth and simplifies the backend at the cost of requiring clients that correctly handle recurrence rules.

The createCalendarObject, updateCalendarObject, and deleteCalendarObject methods implement event modification operations by parsing incoming iCalendar data, creating or updating Calendar2 models, and persisting changes to the database. The parsing converts iCalendar VEVENT components into model properties, handling complications like recurring rule conversion, attendee list parsing, and timezone normalization. The methods enforce PHProjekt's permission model by checking whether the authenticated user has write access to the target project before allowing modifications. Error handling throughout the backend translates between SabreDAV's exception types and PHProjekt's error handling patterns, ensuring that protocol violations, permission errors, and validation failures produce appropriate HTTP status codes and error messages for CalDAV clients.

### Controllers/CaldavController.php

The Calendar2_CaldavController serves as the HTTP endpoint for CalDAV protocol operations, integrating SabreDAV's server infrastructure with PHProjekt's MVC framework. This controller differs substantially from typical PHProjekt controllers in that it delegates nearly all logic to SabreDAV rather than implementing request handling directly. The preDispatch override disables view rendering since CalDAV responses are generated entirely by SabreDAV rather than through Zend view templates. The checkAuthentication override replaces PHProjekt's session-based authentication with HTTP Basic Authentication, extracting credentials from HTTP headers and validating them through Phprojekt_Auth::login before allowing SabreDAV processing to proceed.

The indexAction method instantiates and configures the SabreDAV server stack, including the authentication backend (Calendar2_Helper_Auth), principal backend (Phprojekt_CalDAV_PrincipalBackend), and calendar backend (Calendar2_CalDAV_CalendarBackend). These three backends provide SabreDAV with access to user identity management, principal (user) enumeration, and calendar data respectively. The method constructs a directory tree reflecting CalDAV's hierarchical resource structure where principals appear under /principals/username and calendars appear under /calendars/username/default. The SabreDAV server is then configured with authentication plugin (DAV\Auth\Plugin), CalDAV plugin (CalDAV\Plugin), and ACL plugin (DAVACL\Plugin), each adding protocol capabilities to the base WebDAV server.

The controller's minimal implementation demonstrates the power of framework integration where substantial functionality emerges from proper wiring of components without requiring extensive custom code. The entire CalDAV protocol implementation—including calendar discovery, event queries, event creation, event updates, event deletion, and synchronization—flows through this single indexAction method by delegating to SabreDAV's protocol handler. This delegation pattern creates a clean separation where protocol concerns (HTTP headers, iCalendar parsing, WebDAV properties) remain in SabreDAV while business logic (permission checking, event validation, recurrence expansion) remains in PHProjekt. The controller's role as a thin adapter between web framework and protocol library exemplifies the adapter pattern's value for integrating third-party libraries.

### Helper/Auth.php

The Calendar2_Helper_Auth class implements Sabre\DAV\Auth\Backend\AbstractBasic, providing the authentication backend that SabreDAV uses to validate CalDAV client credentials. This helper bridges between SabreDAV's authentication expectations and PHProjekt's authentication system (Phprojekt_Auth), translating HTTP Basic Authentication credentials into PHProjekt user sessions. The validateUserPass method receives username and password from SabreDAV (extracted from HTTP Authorization header), invokes Phprojekt_Auth::login to validate credentials against PHProjekt's user database, and returns true/false to indicate authentication success. This simple bridging creates CalDAV authentication that shares credentials with the web interface, enabling single-sign-on where users access calendars through CalDAV using the same credentials as web login.

The helper's implementation of HTTP Basic Authentication addresses security concerns through HTTPS requirement recommendations in deployment documentation, as Basic Authentication transmits credentials in base64-encoded form (essentially plaintext) rather than using challenge-response mechanisms. The integration with PHProjekt_Auth::login ensures that authentication policies like password hashing, account lockout, and LDAP delegation apply consistently across both web and CalDAV interfaces. The helper also handles the proxy authentication scenario where administrators can access calendars on behalf of other users, with special logic detecting admin status and adjusting the effective user context accordingly. This proxy support enables administrative calendar management without requiring administrators to know user passwords.

### Models/CalendarInformation.php and InformationDecoratorReadonly.php

The CalendarInformation model defines field metadata for calendar events including field names, types, validation rules, and display properties, enabling PHProjekt's dynamic form generation system to construct appropriate event editing interfaces. This metadata includes text fields for summary and location, datetime fields for start and end times, textarea for description, select fields for status and visibility, and specialized fields for recurrence rules and participant lists. The metadata drives validation by specifying required fields, maximum lengths, and allowed value ranges, ensuring data integrity through declarative constraints rather than procedural validation code scattered throughout controllers.

The InformationDecoratorReadonly class applies the decorator pattern to CalendarInformation, wrapping the base metadata with modifications that mark all fields as read-only. This decorator is used when displaying events that originated from CalDAV clients rather than the PHProjekt web interface, preventing web users from modifying events that should be edited through the originating client to avoid synchronization conflicts. The read-only decorator demonstrates how different views of the same data can be presented by decorating metadata rather than duplicating model classes. This approach maintains a single source of truth for field definitions while enabling context-dependent presentation through lightweight decorator objects that add or modify metadata properties.

## Public API and Interfaces

The Calendar2 module exposes three distinct API layers serving different client types and protocols. The traditional HTTP API through Calendar2_IndexController follows PHProjekt conventions where URLs like /calendar2/index/json-list accept date range parameters (startDate, endDate) and return JSON arrays of event objects with expanded recurrence instances. The jsonDetailAction accepts event IDs and returns complete event information including participant lists, recurrence rules, and exception dates, enabling the frontend to render full event forms. The jsonSaveAction accepts event data as POST parameters, validates against CalendarInformation metadata, persists changes through the Calendar2 model, and returns success status with the event ID. These traditional endpoints serve the Dojo frontend and follow the action-based URL patterns established by the Default module's IndexController base class.

The RESTful API through Calendar2_Calendar2Controller provides resource-oriented access following HTTP verb semantics where GET /calendar2/calendar2/{id} retrieves an event, POST /calendar2/calendar2 creates an event, PUT /calendar2/calendar2/{id} updates an event, and DELETE /calendar2/calendar2/{id} removes an event. This REST interface enables integration with HTTP clients and libraries that expect standard REST patterns, supporting scenarios like mobile applications or external system integrations that prefer RESTful conventions over action-based endpoints. Both traditional and REST interfaces delegate to the same Calendar2 model, ensuring behavioral consistency while accommodating different client preferences. The dual-interface approach demonstrates API design flexibility where multiple access patterns serve the same underlying business logic without implementation duplication.

The CalDAV API through Calendar2_CaldavController implements the CalDAV protocol (RFC 4791) enabling synchronization with standard calendar clients like Microsoft Outlook, Apple Calendar, Mozilla Thunderbird, and iOS/Android calendar apps. CalDAV clients discover calendars through PROPFIND requests to /calendar2/caldav/calendars/username/, retrieve events through REPORT requests with date range filters, create events through PUT requests with iCalendar payloads, update events through PUT requests to existing event URLs, and delete events through DELETE requests. The CalDAV interface requires HTTP Basic Authentication with each request rather than using session-based authentication, with credentials validated through Calendar2_Helper_Auth. This protocol-level API operates at a lower abstraction level than HTTP/REST, dealing with iCalendar format, WebDAV properties, and calendar-specific extensions that standard REST clients wouldn't understand.

## Dependencies and Integration

The Calendar2 module depends heavily on the SabreDAV library (version 1.6.2) which provides the CalDAV protocol implementation including HTTP request parsing, iCalendar format handling, and WebDAV property management. SabreDAV's architecture expects backends to implement specific interfaces (Sabre_CalDAV_Backend_Abstract, Sabre\DAV\Auth\Backend\AbstractBasic) which Calendar2 provides through CalendarBackend and Helper/Auth classes. This integration creates tight coupling to SabreDAV's interface contracts, with the benefit that protocol-level complexity remains encapsulated in the library while Calendar2 focuses on data access and business logic. The SabreDAV integration demonstrates the adapter pattern where PHProjekt's event model is adapted to SabreDAV's expectations through backend classes that translate between Active Record and iCalendar representations.

Integration with PHProjekt's notification system (Phprojekt_Notification) enables email reminders for upcoming events, with Calendar2 models scheduling notifications during save operations. The notification integration uses Phprojekt's job queue system where notification records are created with delivery times calculated based on event start times and user preferences (e.g., "remind me 30 minutes before"). The notification system queries the queue periodically, sending emails for notifications whose delivery time has passed. This asynchronous architecture decouples event creation from email delivery, ensuring that saving events remains fast even when email servers are slow or unavailable. The notification integration also handles participant status changes by sending notification emails when participants accept or reject event invitations, creating a meeting coordination workflow.

Data flows through Calendar2 follow temporal patterns where queries typically include date range filters to retrieve only relevant events rather than loading complete calendars. The IndexController's jsonListAction accepts startDate and endDate parameters, constructing SQL queries with WHERE clauses that filter by these boundaries. For recurring events, the controller invokes the Calendar2 model's expansion logic to generate occurrences within the date range, then flattens the result set to include both non-recurring events and expanded occurrences. This expansion-at-query-time approach avoids storing every occurrence in the database while providing the illusion that each occurrence exists as a distinct entity. The CalDAV backend follows similar patterns, with REPORT requests including time-range filters that Calendar2 translates to database queries plus recurrence expansion for matching series.

## Data Models and Structures

The Calendar2 module's data model centers on the calendar2 table which stores both non-recurring events and recurring event series masters. The table schema includes temporal fields (start, end) that define event time boundaries, descriptive fields (summary, location, description, notes) that provide event details, structural fields (project_id, owner_id) that establish organizational context, participation fields (participants stored as serialized arrays mapping user IDs to status values) that track invitations, recurrence fields (rrule storing RFC 5545 rule strings, recurrence_id for exception occurrences) that define repeating patterns, and visibility fields (visibility enum controlling public/private status) that implement privacy controls. This comprehensive schema enables the table to serve both as transactional event storage and as the source of truth for CalDAV synchronization.

The participants field's serialized array representation creates a denormalized storage pattern where the many-to-many relationship between events and participants is collapsed into a single database column. This design choice trades normalization for query simplicity, as retrieving participant lists requires no joins at the cost of making queries like "find all events where user X is a participant" more expensive. The serialization format (PHP's serialize or JSON depending on version) encodes both participant IDs and their status values, maintaining the association between who was invited and whether they accepted. The model's participant management logic handles serialization/deserialization transparently, presenting participant data as associative arrays to application code while persisting it as opaque strings to the database.

The recurrence_id field implements the exception instance pattern where specific occurrences of a recurring series can be modified independently of the series master. When a user changes a single occurrence (e.g., moving one Tuesday meeting to Wednesday), the system creates a new database record with recurrence_id pointing to the original start time of the modified occurrence. Queries for event lists include both series masters (recurrence_id is null) and exception instances (recurrence_id is not null), with the expansion logic checking exception instances against generated occurrences and substituting the exception data when matches occur. This approach enables "edit this occurrence" and "edit all future occurrences" workflows common in calendar applications while maintaining a reasonable database record count.

## Configuration and Settings

The Calendar2 module's configuration encompasses CalDAV endpoint settings, notification timing preferences, recurrence expansion limits, and timezone handling policies. The CalDAV endpoint configuration includes the base URL where CalDAV clients should connect (typically /calendar2/caldav/), authentication realm for HTTP Basic Authentication challenges, and SSL/TLS requirements for secure credential transmission. While PHProjekt doesn't enforce HTTPS at the application level, deployment documentation strongly recommends HTTPS for CalDAV endpoints given Basic Authentication's security characteristics. The endpoint configuration also specifies principal namespace conventions that determine how calendar URLs are structured (e.g., /calendars/username/default vs. /calendars/username/calendar-id).

Notification timing configuration determines when reminder emails are sent relative to event start times, with settings like "default reminder time" (e.g., 30 minutes before) and "maximum advance notification" (e.g., don't send reminders more than one week before events). These settings balance user preferences for advance notice against the risk of sending so many reminders that users ignore them. The notification configuration also controls whether participants receive status change notifications when other participants accept or reject invitations, enabling or disabling the meeting coordination workflow based on organizational preferences. The configuration system supports both system-wide defaults that apply to all users and user-specific overrides that respect individual preferences.

Recurrence expansion limits prevent pathological recurring patterns from overwhelming the system by capping the number of occurrences generated during expansion operations. Settings like "maximum occurrences per expansion" (e.g., 1000) and "maximum expansion range" (e.g., 5 years into the future) ensure that even unbounded recurring series (those without UNTIL or COUNT) can be queried without generating infinite sequences. These limits create trade-offs between supporting long-term planning and maintaining reasonable resource consumption, with the configuration values tuned based on deployment characteristics like typical calendar viewing ranges and database performance. The timezone configuration determines how event times are stored (UTC in database but displayed in user's local timezone) and how CalDAV clients' timezone specifications are interpreted during iCalendar parsing.

## Design Patterns and Principles

The Calendar2 module extensively applies the Strategy pattern for recurrence expansion where different expansion strategies apply based on recurrence rule characteristics. Weekly recurrences use a day-of-week filtering strategy that generates candidates from the base period then filters to specified days. Monthly recurrences use an absolute-date strategy for patterns like "15th of each month" or a relative-date strategy for patterns like "second Tuesday." The Rrule helper acts as the context that selects appropriate expansion strategies based on parsed rule components, executing the selected strategy to produce occurrence sequences. This pattern enables the recurrence system to handle diverse patterns through specialized algorithms rather than attempting one-size-fits-all generation logic that would struggle with edge cases.

The Adapter pattern appears throughout the CalDAV integration where PHProjekt's event model is adapted to SabreDAV's backend interface expectations. The CalendarBackend class adapts Calendar2 Active Record models to Sabre_CalDAV_Backend_Abstract by implementing required methods that translate between model operations and backend method calls. The Helper/Auth adapter bridges between SabreDAV's authentication interface and PHProjekt's authentication system, translating between different authentication mechanisms and session management approaches. These adapters create clean boundaries where protocol-specific code remains in adapter classes while business logic remains in models and controllers, enabling protocol evolution without forcing business logic changes.

The Decorator pattern manifests in InformationDecoratorReadonly which wraps CalendarInformation to modify field metadata, marking fields as read-only for CalDAV-originated events. This decorator demonstrates how presentation can be adapted through metadata modification rather than model duplication, with the decorator intercepting getFieldDefinition calls and modifying returned metadata before passing it to clients. The pattern enables different views of the same underlying data structure—fully editable for web-created events, read-only for sync-created events—without requiring separate model classes or duplicated validation logic. The decorator approach maintains single source of truth for field definitions while supporting context-dependent presentation through lightweight wrapper objects.

The Command pattern appears in the participant status tracking where each status change (user accepts invitation, user rejects invitation) is represented as a command that gets executed during save operations. The model accumulates status change commands in the _participantData array, compares against _participantDataInDb during save to determine which commands represent actual changes, then executes those commands by updating database records and queuing notification commands. This accumulate-then-execute approach enables optimistic UI updates where the frontend immediately reflects status changes while actual persistence and notification happen asynchronously during the next save operation. The pattern also enables transaction rollback where save failures leave the model in its pre-save state, preventing partial updates that would corrupt the participant status tracking.

The Separation of Concerns principle guides the distribution of responsibilities across specialized classes where Calendar2 model handles event entity logic, Rrule helper handles temporal mathematics, CalendarBackend handles protocol adaptation, and CalendarInformation handles metadata definition. This separation prevents the "god class" anti-pattern where a single class attempts to handle business logic, protocol concerns, temporal logic, and metadata simultaneously. The principle extends to the controller layer where IndexController handles web requests, Calendar2Controller handles REST requests, and CaldavController handles CalDAV protocol, with each controller focused on its specific protocol's requirements rather than attempting to serve all protocols through a single interface. This separation enables independent evolution where recurrence algorithms can be optimized, CalDAV protocol updated, or metadata extended without changes rippling across unrelated concerns.
