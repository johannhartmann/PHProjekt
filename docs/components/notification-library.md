# Component: Notification

## Overview

The Notification library provides comprehensive multi-channel notification delivery for PHProjekt 6, implementing a dual-delivery system that sends both email notifications to external email addresses and in-application frontend messages to logged-in users through a long-polling mechanism. This library handles the complete notification lifecycle including determining appropriate recipients based on permissions, extracting and formatting relevant data from model changes through integration with the history tracking system, generating localized content in each recipient's preferred language, delivering messages through appropriate channels based on user preferences, and managing the lifecycle of frontend messages including validity periods and delivery acknowledgment. The notification system operates transparently through lifecycle hooks in model save operations, automatically generating notifications when items are created, modified, or deleted without requiring explicit notification calls in business logic.

The library architecture follows a multi-tier design with the main Phprojekt_Notification class serving as a facade that coordinates email and frontend message generation, the Phprojekt_Notification_Mail class handling email composition and SMTP delivery, and the Phprojekt_Notification_FrontendMessage class managing persistent in-application messages with database storage and retrieval. The notification system integrates deeply with PHProjekt's history tracking infrastructure to identify what changed in a model save operation, enabling informative notifications that show both the current state and the specific changes made. The history integration prevents unnecessary notifications when save operations don't actually modify any fields, implementing an optimization that reduces notification noise when users click save without making changes.

The email notification system supports both plain text and HTML formats, generating messages from view templates that render field values and change lists with appropriate formatting for each mode. The system implements per-recipient language localization by grouping recipients by language preference and generating separate emails for each language group, ensuring that multilingual teams receive notifications in their preferred languages without requiring language-specific distribution lists. The email content includes a structured presentation of the modified item including a title identifying the module and item, a complete listing of all current field values for context, and for modifications a change log showing old and new values for each modified field. The email includes a clickable link to view the item in the application, constructing URLs with appropriate module and project context to enable direct navigation.

The frontend message system implements a notification center experience where users receive in-application messages that appear in a dedicated UI component without requiring email client interaction. The system uses a long-polling architecture where the client periodically requests new messages through an AJAX endpoint that blocks for up to 20 seconds (4 iterations of 5-second sleep) waiting for messages to appear, providing near-real-time notification delivery without the complexity of WebSocket or server-sent events. Frontend messages include validity periods that control when they're visible, enabling time-sensitive notifications like meeting reminders that appear a configurable number of minutes before an event. The system marks messages as delivered when retrieved by recipients, implementing a single-delivery semantic that ensures users don't see the same notification repeatedly.

## Component Structure

| File/Directory | Purpose |
|----------------|---------|
| `Notification.php` | Main notification facade coordinating email and frontend message generation with recipient determination and content formatting (802 lines) |
| `Notification/Mail.php` | Email notification implementation with SMTP delivery, template rendering, and format selection (HTML/text) (222 lines) |
| `Notification/FrontendMessage.php` | In-application message persistence with long-polling retrieval, validity management, and delivery tracking (364 lines) |

The Notification library follows a clear separation of concerns with the main Notification class handling business logic including recipient determination, content extraction, and format conversion, while the specialized delivery channel classes (Mail and FrontendMessage) handle transport-specific operations including message construction, delivery, and retrieval. The FrontendMessage class extends Phprojekt_ActiveRecord_Abstract to provide database persistence for in-application messages, while the Mail class extends Phprojekt_Mail (which itself extends Zend_Mail) to inherit email composition capabilities while adding PHProjekt-specific features like user lookup and template rendering. This layered architecture enables independent extension of each delivery channel without affecting the others, supporting future additions like SMS notifications or mobile push notifications through new classes that implement the same pattern.

## Key Classes and Files

### Phprojekt_Notification (Notification.php:19-802)

The Phprojekt_Notification class serves as the primary facade for notification operations, providing high-level methods that coordinate the process of generating and delivering notifications across multiple channels. The class defines action constants (LAST_ACTION_ADD, LAST_ACTION_EDIT, LAST_ACTION_DELETE, LAST_ACTION_LOGOUT, LAST_ACTION_LOGIN, LAST_ACTION_REMIND) that categorize notification types, and transport constants (TRANSPORT_MAIL_TEXT, TRANSPORT_MAIL_HTML) that specify email delivery formats. The class maintains protected properties including _lastHistory for caching history data retrieved from the history tracking system, _frontendMessage for the FrontendMessage instance, _controllProcess for explicitly set process types, _model for the domain object being notified about, and _recipients for custom recipient lists.

The send() method (Notification.php:121-184) implements the complete email notification workflow by first querying history to populate _lastHistory through Phprojekt_History::getLastHistoryData(), returning immediately if history is empty indicating no actual changes were made, determining adapter name and parameters based on transport type (text or HTML email), collecting sender information through getFrom(), recipient list through getTo(), subject through getSubject(), and body parameters through getBodyParams() and getBodyFields(), grouping recipients by language preference through Phprojekt_Setting to enable localized content, and iterating over language groups to generate and send one email per language with content translated appropriately. This sophisticated multi-language approach ensures that international teams receive notifications in their preferred languages without requiring manual segmentation.

The getTo() method (Notification.php:204-219) implements permission-aware recipient determination by calling _model->getUsersRights() to retrieve users with access to the item, filtering out the current user to avoid self-notification, filtering out users with 'none' permission who have no access, and returning the resulting array of user IDs. This integration with the permission system ensures that notifications respect access control by only notifying users who can actually view the item being modified, preventing information leakage through notification content. The method supports models that implement getUsersRights(), providing a contract that models must implement to participate in the notification system.

The getSubject() method (Notification.php:227-236) constructs email subjects by combining the module name, item ID in brackets, and the display field value from the model, creating subjects like "[Project #42] Q4 Marketing Campaign" that uniquely identify the item while providing context. The use of searchFirstDisplayField enables each module to define which field provides the best subject line content, supporting heterogeneous item types with different appropriate display representations. The trim and concatenation logic ensures clean formatting even when display fields are empty or contain whitespace.

The getBodyParams() method (Notification.php:244-271) extracts metadata for email body generation including action label ('created' or 'modified') based on the history action type, module table name for display in the email title, and URL for linking to the item constructed from module name, project ID (for normal save type modules), and item ID. The URL construction using hash fragment syntax supports single-page application navigation in PHProjekt's Dojo-based frontend, enabling clickable links in emails that open directly to the relevant item. The conditional inclusion of project ID based on Phprojekt_Module::saveTypeIsNormal() demonstrates awareness of different module types where some modules are project-scoped and others are global.

The getBodyFields() method (Notification.php:280-295) retrieves complete current state of the item by querying the model's field definition through getInformation()->getFieldDefinition(), iterating over all fields to build an array of field-label-value triples, translating labels through Phprojekt::getInstance()->translate() for the recipient's language, and converting values through _convert() which handles special field types like selectboxes and displays by translating integer IDs to their string representations. This comprehensive field listing provides context for notification recipients who can see the complete current state of the item rather than just what changed, supporting understanding of modifications in the broader context of the item.

The getBodyChanges() method (Notification.php:307-365) processes history records to extract change information by iterating over _lastHistory entries, looking up field definitions to determine field types and labels, translating labels for the recipient's language, converting selectbox/display/multipleselectbox field values from integer IDs to human-readable strings through range lookups, and applying _convert() for final value formatting. The method includes sophisticated logic for determining whether display fields should be converted based on whether their range is properly structured as arrays, demonstrating defensive programming that handles both well-formed and malformed metadata. The translation of both old and new values ensures that changes are comprehensible even when the values are foreign key references or enum values.

The saveFrontendMessage() method (Notification.php:414-451) orchestrates frontend message creation by querying history when a model is present to populate _lastHistory and enable change detection, extracting body changes when controllProcess is not explicitly set, returning early if no recipients exist to avoid unnecessary processing, collecting metadata through various getter methods (getProcess, getDescription, getModuleId, getProjectId, getItemId, getValidUntil, getValidFrom, getRecipients, getItemName), configuring the FrontendMessage instance through a series of setCustom* calls, and delegating to _frontendMessage->saveFrontendMessage() for persistence. This method demonstrates the Builder pattern where the notification object accumulates configuration through method calls before triggering the final save operation.

The getRecipients() method (Notification.php:639-673) implements comprehensive recipient determination by returning explicitly set recipients if present, falling back to querying the model's getUsersRights() when available and filtering by permission and exclusion of the current user, or as a final fallback retrieving all users when no model is present, and finally filtering the results through filterRecipientsToSettings() to respect user preferences for notification delivery. The three-tier fallback (explicit recipients → permission-based → all users) supports different notification scenarios including permission-aware item notifications, global announcements, and system notifications like login/logout messages.

The filterRecipientsToSettings() method (Notification.php:780-801) enforces user preferences by mapping the current process to a setting key through mapProcessToSettings(), querying each recipient's notification setting through getSetting(), and removing recipients who have explicitly disabled notifications for this category by setting the value to 0. The method's comment explains that users with no saved setting (NULL value) are included in notifications because the default is opt-in, requiring users to explicitly uncheck notifications to stop receiving them. This default-on approach ensures that new users receive notifications until they configure preferences, balancing discoverability with user control.

### Phprojekt_Notification_Mail (Notification/Mail.php:19-222)

The Phprojekt_Notification_Mail class extends Phprojekt_Mail (which extends Zend_Mail) to provide PHProjekt-specific email notification functionality including user lookup for sender and recipient information, template-based body generation with language localization, and SMTP delivery with error handling. The class defines constants for body modes (MODE_HTML, MODE_TEXT) and parameter array indices (PARAMS_CHARSET, PARAMS_BODYMODE) that structure the configuration passed to the constructor. The constructor extracts charset and body mode from the params array, calling the parent Phprojekt_Mail constructor with charset and storing body mode in the _bodyMode property for later use during body generation.

The setCustomFrom() method (Mail.php:64-79) implements sender information extraction by instantiating a Phprojekt_User_User, finding the user by ID, retrieving the email address from user settings through getSetting('email'), constructing a display name from firstname, lastname, and username with fallback to username alone when names are empty, and calling setFrom() inherited from Zend_Mail with the email and name. This method bridges PHProjekt's user ID abstraction to email's name/address requirements, enabling notifications to appear from the actual user who made the change rather than a generic system address.

The setTo() method (Mail.php:88-112) implements recipient information extraction by iterating over an array of user IDs, querying email addresses through Phprojekt_Setting, skipping recipients without configured email addresses to avoid delivery errors, finding user information through Phprojekt_User_User, constructing display names from name components with username fallback, and calling addTo() inherited from Zend_Mail for each valid recipient. The method handles the edge case of recipient ID 0 by falling back to the current user's ID, though the business logic significance of this special case is unclear. The skipping of recipients without email addresses implements defensive delivery that continues processing remaining recipients even when some have incomplete configuration.

The setCustomBody() method (Mail.php:136-175) implements template-based email body generation by retrieving the Phprojekt view instance, populating view variables including mainFields for complete current state, changes for modification details (when action is EDIT), translated title string, labels for sections and columns, copyright notice, and URL for viewing the item, loading view scripts through Phprojekt_Loader::loadViewScript(), rendering the appropriate template (mailHtml.phtml or mailText.phtml) based on _bodyMode, and calling either setBodyHtml() or setBodyText() inherited from Zend_Mail with the rendered content. The template rendering approach separates presentation from logic, enabling designers to modify email appearance without changing PHP code while supporting both HTML and text formats from the same underlying data.

The sendNotification() method (Mail.php:211-221) implements email delivery by calling setTransport() inherited from Phprojekt_Mail to create an SMTP transport object, calling send() inherited from Zend_Mail with the transport to deliver the email, and wrapping the send in try-catch to transform any exceptions into Zend_Controller_Action_Exception with a 422 status code indicating "Unprocessable Entity". This error handling transforms SMTP errors (connection failures, authentication failures, rejected recipients) into application-level exceptions that controllers can handle appropriately, preventing SMTP errors from propagating as generic exceptions that might not be handled consistently.

### Phprojekt_Notification_FrontendMessage (Notification/FrontendMessage.php:19-364)

The Phprojekt_Notification_FrontendMessage class extends Phprojekt_ActiveRecord_Abstract to provide database persistence for in-application messages, implementing the complete lifecycle of message creation, retrieval, delivery tracking, and expiration. The class maps to the frontend_message table which stores all message metadata including actor ID (who generated the message), recipient ID (who should receive it), module and item IDs identifying what the message relates to, project ID for context, process type and description for display, validity period (from and until timestamps) controlling when messages are visible, details blob for storing serialized change information, and delivered flag marking whether the message has been retrieved.

The getMessageData() method (FrontendMessage.php:29-65) implements message retrieval with automatic delivery marking by constructing a WHERE clause filtering for recipient_id matching the current user, valid_from and valid_until bracketing the current time, and delivered flag equal to 0 indicating undelivered messages, ordering by valid_from DESC to present newest messages first, fetching all matching records, deserializing the details field from serialized PHP to arrays, converting datetime and time fields from UTC storage to the user's timezone through Phprojekt_Converter_Time::utcToUser(), updating each retrieved message to set delivered = 1 marking it as delivered, and returning the processed message array. The automatic delivery marking implements exactly-once delivery semantics where messages disappear from the queue once retrieved, though the update-after-fetch approach has a race condition where concurrent requests might retrieve the same messages.

The getMessage() method (FrontendMessage.php:75-110) enriches raw message data with user-friendly values by calling getMessageData() to retrieve messages and mark them delivered, calling _deleteOutdatedMessages() to clean up expired messages, returning false if no messages are present, loading the actor user object to get display name, retrieving module name through Phprojekt_Module::getModuleName(), translating the description, retrieving project title through Project_Models_Project::find(), converting the validity timestamp to user timezone with an optional addTime offset for reminder messages, and packaging everything into an array with string values ready for JSON serialization and display. This transformation from database IDs to display strings enables the frontend to render messages without additional lookups.

The getFrontendMessage() method (FrontendMessage.php:125-140) implements the long-polling mechanism by executing a while loop that iterates up to 4 times, calling getMessage() to check for new messages, returning immediately when messages are found, sleeping for 5 seconds when no messages are present before checking again, and returning an empty array after all iterations complete without finding messages. This 20-second polling window (4 iterations × 5 seconds) provides near-real-time notification delivery without requiring WebSocket or EventSource infrastructure, trading some latency and server resources for implementation simplicity. The fixed iteration count prevents runaway polling that could exhaust server resources, though it requires clients to re-poll after the timeout expires.

The setCustom* methods (FrontendMessage.php:149-284) provide a builder pattern interface for configuring messages before save, including setCustomProjectId(), setCustomProcess(), setCustomRecipients(), setCustomModuleId(), setCustomItemId(), setCustomValidFrom(), setCustomValidUntil(), setCustomDescription(), setCustomDetails() which serializes an array, setCustomDisplayItem(), setCustomDisplayModule(), and setCustomItemName(). These methods enable fluent configuration like `$msg->setCustomProjectId(42)->setCustomProcess('add')->setCustomItemId(100)`, though the actual implementation doesn't return $this so true fluent chaining isn't supported. The use of "Custom" prefix in method names distinguishes these from potential inherited ActiveRecord methods with similar names.

The saveFrontendMessage() method (FrontendMessage.php:333-363) implements batch message creation by setting actorId to the current user, checking if recipientId is an array indicating multiple recipients, directly calling parent::save() for single-recipient messages, or for multiple recipients iterating over the recipient array to clone the message object, populate all fields from the original, set recipientId to the current iteration's recipient ID, and call save() on the clone. This approach creates separate database records for each recipient rather than using a junction table, simplifying retrieval queries at the cost of data duplication when the same message is sent to many recipients. The cloning ensures that each save creates a distinct ActiveRecord instance avoiding shared state corruption.

## Public API and Interfaces

The Notification library exposes its functionality primarily through the Phprojekt_Notification facade class, with typical usage involving instantiating a notification object, calling setModel() to associate a domain object with the notification, and calling either send() for email delivery or saveFrontendMessage() for in-application messages. The email workflow follows the pattern of `$notification = new Phprojekt_Notification(); $notification->setModel($item); $notification->send(Phprojekt_Notification::TRANSPORT_MAIL_HTML);` which automatically determines recipients based on permissions, extracts content from the model and history, generates localized emails for each recipient language, and delivers through SMTP. The frontend message workflow similarly uses `$notification->saveFrontendMessage();` which persists messages to the database for retrieval through the long-polling endpoint.

The frontend message retrieval API centers on the getFrontendMessage() method accessed through the FrontendMessage class, typically invoked from a controller endpoint that the frontend polls periodically. The typical usage involves `$frontendMessage = new Phprojekt_Notification_FrontendMessage(); $data = $frontendMessage->getFrontendMessage($userId);` which blocks for up to 20 seconds waiting for new messages and returns either message data or an empty array. The client-side polling logic repeatedly calls this endpoint, processes any returned messages by displaying them in the UI, and immediately re-polls to maintain the notification stream. This polling-based architecture requires no special server infrastructure beyond long-running PHP processes.

The customization API provides several extension points including setControllProcess() to override automatic process determination, custom recipient lists through the _recipients property setter (though no public setter method is provided for this), and custom validity periods for frontend messages through setCustomValidFrom() and setCustomValidUntil() before calling saveFrontendMessage(). These customization points support specialized notification scenarios like meeting reminders that need specific validity windows or system announcements that notify all users regardless of permissions. The getDescription() and mapProcessToSettings() methods demonstrate template method patterns where subclasses could override to provide custom descriptions or setting mappings, though the library doesn't explicitly document this extensibility.

## Dependencies and Integration

The Notification library depends extensively on PHProjekt's history tracking infrastructure through Phprojekt_History, calling getLastHistoryData() to retrieve changes made during model save operations. This integration enables informative notifications that show what actually changed rather than just indicating that a change occurred, with the history system tracking old and new values for each modified field along with action types (add, edit, delete). The notification system's check for empty history implements an important optimization that prevents notifications when save operations don't actually modify any fields, avoiding notification noise from users clicking save without making changes. The deep integration with history means that models must properly integrate with the history tracking system for notifications to contain meaningful content.

Integration with the permission system through model getUsersRights() methods ensures that notifications respect access control by only notifying users who can view the item being modified. The recipient determination logic filters users based on permission levels, excluding those with 'none' permission who have no access rights. This integration prevents information leakage where notification content could reveal the existence or details of restricted items to unauthorized users. The model contract requiring getUsersRights() implementation means that models must provide permission information for notification to work correctly, coupling the notification system to the access control infrastructure.

The Phprojekt_Setting integration enables multiple aspects of notification functionality including retrieving user email addresses through getSetting('email'), determining language preferences through getSetting('language') for localization, and checking notification preferences through settings in the Notification module. The language integration enables per-recipient localization where emails are generated in each recipient's preferred language, supporting multilingual teams without requiring language-specific distribution lists. The notification preference system uses settings like 'datarecords', 'loginlogout', and 'alerts' to control which notification types users receive, implementing user control over notification frequency.

The email delivery infrastructure integrates with Zend Framework's Zend_Mail and Zend_Mail_Transport components through the Phprojekt_Mail base class, leveraging the framework's email composition and SMTP delivery capabilities. The notification system uses Phprojekt_Mail's setTransport() method to configure SMTP settings from application configuration, enabling deployment-specific email server configuration. The template rendering integrates with Phprojekt's view system through Phprojekt::getInstance()->getView(), loading email templates from the view script path and rendering them with notification data. This view integration enables designers to customize email appearance without modifying PHP code.

The Phprojekt_Module integration provides module name lookups through getModuleName() and getId() methods, enabling notifications to display human-readable module names rather than numeric IDs. The module system also provides saveTypeIsNormal() checks that determine whether modules are project-scoped or global, affecting URL construction in notifications. The Phprojekt_Converter_Time integration handles timezone conversions through utcToUser() methods, ensuring that timestamps in notifications display in recipients' local timezones rather than UTC. The Phprojekt_Converter_Text integration handles value conversions for upload fields and other special types, enabling comprehensive display of field values regardless of type.

## Data Models and Structures

The Notification library manages the frontend_message database table which stores persistent in-application messages with a comprehensive schema supporting rich notification features. The table structure includes id (auto-increment primary key), actor_id (foreign key to user.id identifying who generated the message), recipient_id (foreign key to user.id identifying who should receive it), project_id (foreign key to project.id for context), module_id (foreign key to module.id identifying the module), item_id (integer identifying the specific item within the module), process (varchar storing action type like 'add', 'edit', 'delete'), description (text with translated description of the action), valid_from (datetime indicating when the message becomes visible), valid_until (datetime indicating when the message expires), details (text storing serialized PHP array with change information), item_name (varchar with display name for the item), and delivered (integer flag, 0 for undelivered, 1 for delivered).

The validity period fields (valid_from and valid_until) implement a time-windowing feature that controls when messages are visible to recipients, enabling both retroactive messages that appear starting from a past timestamp and future messages that don't appear until a specified time. The default valid_until calculation adds the configured validPeriod (in minutes) to the current time, implementing message expiration that prevents the notification center from accumulating unbounded messages. The special handling for reminder messages adjusts the valid_from timestamp by subtracting the configured remindBefore period, implementing "alert N minutes before event" functionality for calendar entries and other time-sensitive items.

The details field stores serialized PHP arrays containing change information extracted from the history system, implementing a flexible schema that can accommodate different field types and change structures without requiring schema changes. The serialization approach trades query flexibility (can't filter by specific detail fields) for schema flexibility (can store arbitrary change information), appropriate for the notification use case where queries always retrieve complete messages rather than filtering by content. The deserialization during retrieval converts integer IDs to human-readable strings where appropriate, though some value conversions are deferred to the recipient's language context.

The delivered flag implements single-delivery semantics where messages are marked as delivered when first retrieved and don't appear in subsequent queries, preventing users from seeing the same notification repeatedly. The update happens immediately after retrieval in getMessageData(), though this approach has a potential race condition where concurrent retrieval requests might both see delivered = 0 and both mark the same messages as delivered. A more robust implementation might use SELECT FOR UPDATE or unique constraints to prevent duplicates, though the current approach works adequately under typical usage patterns where polling requests are sequential rather than concurrent.

The separation of actor_id and recipient_id enables future audit capabilities where notification history shows who generated each message and who received it, supporting compliance requirements or debugging notification delivery issues. The current implementation stores separate records for each recipient when multiple users should receive the same message, implementing a per-recipient delivery model that simplifies retrieval queries at the cost of storage space and insert performance. An alternative design might use a junction table for many-to-many recipient relationships, though the current approach's simplicity likely outweighs its inefficiencies for typical notification volumes.

## Configuration and Settings

The Notification library's behavior is controlled through multiple configuration settings including the validPeriod configuration value (in minutes) that determines how long frontend messages remain visible before expiring, defaulting to a reasonable period like 60-120 minutes to prevent notification center clutter. The remindBefore configuration value (in minutes) controls how far in advance reminder notifications appear before scheduled events, enabling users to configure whether they want 5-minute, 15-minute, or longer advance warning for meetings and appointments. These configuration values provide system-wide defaults that can be applied consistently across all notifications without requiring per-notification configuration.

The notification preference system uses per-user settings stored in the Notification module including datarecords (controls notifications for item creation, modification, and deletion), loginlogout (controls notifications for user login and logout events), alerts (controls reminder notifications for time-sensitive events), and usergenerated (controls notifications for user-initiated actions). These settings default to enabled (NULL value is treated as enabled) to ensure new users receive notifications until they configure preferences, implementing an opt-out model that favors notification discoverability over minimizing unwanted messages. The setting values are integers where 0 indicates disabled and 1 indicates enabled, using simple boolean semantics suitable for checkbox UI controls.

The email configuration integrates with the broader Phprojekt configuration system including SMTP server settings (host, port, authentication credentials) used by the Zend_Mail transport layer, charset configuration (defaulting to UTF-8) for proper encoding of international characters, and language defaults used when recipients have no configured language preference. The email template paths are determined by the view script loading mechanism, enabling deployment-specific template customization by overriding view files without modifying library code. The copyright notice included in email footers comes from a Phprojekt::COPYRIGHT constant, centralizing copyright information that appears across multiple interfaces.

The language integration relies on per-user language preferences stored through Phprojekt_Setting, with the notification system querying these preferences to group recipients and generate separate localized emails for each language group. This per-recipient localization enables truly multilingual notification support where a single save operation generates English notifications for English-speaking team members and German notifications for German-speaking team members, all from a single send() call. The fallback to system default language when no user preference is configured ensures that notifications always have some language rather than failing when preferences are unconfigured.

## Design Patterns and Principles

The Facade pattern dominates the Notification library's design through the Phprojekt_Notification class which provides a simplified interface over complex notification operations, hiding the details of recipient determination, history querying, content extraction, localization, and multi-channel delivery behind simple methods like send() and saveFrontendMessage(). This pattern enables calling code to trigger notifications with minimal knowledge of the underlying complexity, supporting loose coupling where business logic doesn't need to understand notification mechanics. The facade coordinates multiple subsystems including history tracking, permissions, settings, email delivery, and database persistence while presenting a unified interface that matches the conceptual model of "send notification about this item".

The Strategy pattern appears in the transport selection where the send() method accepts a transport parameter that determines whether to send text or HTML email, with potential for future extension to SMS, mobile push, or other delivery mechanisms. The current implementation uses a switch statement to select between transport types, though a more formal strategy pattern implementation might use transport-specific adapter classes that implement a common interface. The TRANSPORT_* constants provide semantic names for transport types, enabling calling code to specify intent rather than numeric codes while maintaining type safety through integer values.

The Builder pattern appears in the frontend message configuration through the series of setCustom* methods that accumulate message properties before saveFrontendMessage() triggers persistence, implementing a fluent configuration style (though without returning $this for true chaining). This pattern separates construction from representation where the notification object accumulates configuration in memory before committing to storage, enabling validation, modification, or cancellation before persistence occurs. The builder approach also supports partial configuration where default values apply for any properties not explicitly set, as seen in getValidUntil() which calculates a default expiration when _validUntil is not set.

The Template Method pattern structures the notification generation workflow where high-level methods like send() define the algorithm skeleton (query history, determine recipients, extract content, group by language, send emails) while delegating specific steps to overridable methods like getFrom(), getTo(), getSubject(), getBodyParams(), getBodyFields(), and getBodyChanges(). This pattern enables customization through subclassing where specialized notification types could override specific content extraction methods while reusing the overall workflow. The pattern also appears in getDescription() which maps processes to description strings, providing an extension point for custom processes.

The Observer pattern appears implicitly in the notification system's integration with model lifecycle hooks, where model save operations trigger notification generation without explicit coupling between models and notification code. While the implementation doesn't use formal Observer interfaces, the pattern's intent is clear: models are subjects that notify observers (the notification system) of changes, with the notification system responding by generating and delivering notifications. This loose coupling enables adding or removing notification functionality without modifying model code, supporting the Open-Closed Principle where models are closed to modification but notification behavior is open to extension.

The Long Polling pattern implemented in getFrontendMessage() provides near-real-time notification delivery without WebSocket or server-sent events complexity, iterating multiple times with sleep intervals to wait for messages to appear before responding to the client. This pattern trades server resources (holding connections open) for implementation simplicity, enabling real-time notification experiences with minimal infrastructure requirements. The fixed iteration count prevents runaway resource consumption while the sleep intervals reduce CPU usage compared to busy-waiting, demonstrating performance optimization within the architectural constraints.

The Adapter pattern bridges PHProjekt's user ID abstraction to email's name/address requirements through methods like setCustomFrom() and setTo() that translate user IDs to email addresses and display names. This pattern enables the notification system to work with PHProjekt's user model while satisfying email protocols' requirements for sender and recipient information. The adapter also appears in field value conversion through _convert() which adapts between model property values (often integers or dates) and human-readable notification content (strings and formatted dates), translating between the domain model's representation and the notification's presentation needs.
