# Component: HTMLPurifier

## Overview

HTMLPurifier is a standards-compliant HTML filtering library that provides robust XSS protection and HTML sanitization capabilities for the PHProjekt 6 application. This third-party library, integrated at version 3.2.0, serves as the primary defense mechanism against malicious HTML injection by rigorously validating and filtering arbitrary HTML snippets before they are rendered in the user interface. The library achieves its security objectives through a sophisticated multi-stage pipeline that lexes HTML into tokens, applies various validation and transformation strategies to remove unsafe elements and attributes, ensures proper nesting and well-formedness, and finally regenerates clean HTML from the purified token stream.

The HTMLPurifier library is distributed under the GNU Lesser General Public License version 2.1 and was developed by Edward Z. Yang. Within the PHProjekt 6 architecture, HTMLPurifier acts as a critical security layer that processes all user-generated content before display, ensuring that even if malicious scripts or HTML are submitted through forms or APIs, they cannot compromise the security of other users viewing that content. The library's comprehensive approach to HTML filtering goes beyond simple blacklisting of dangerous tags, instead implementing a whitelist-based system that only permits known-safe HTML constructs while systematically validating all attributes against strict type definitions.

The integration pattern used in PHProjekt 6 involves bundling the entire HTMLPurifier library as a single standalone file that consolidates all necessary classes and dependencies into one monolithic PHP file. This standalone distribution approach simplifies deployment and reduces the overhead of managing multiple file includes at runtime, particularly beneficial when opcode caching is available. The library provides extensive configuration capabilities that allow PHProjekt to customize the HTML filtering behavior based on context, such as permitting more permissive HTML in certain administrative interfaces while applying stricter filtering to user-generated content in collaborative workspaces.

HTMLPurifier's architecture is based on a pipeline of transformations that separates concerns between lexical analysis, structural validation, semantic validation, and output generation. This separation allows the library to handle malformed HTML gracefully while ensuring that the output always conforms to standards, preventing browser parsing inconsistencies that could lead to security vulnerabilities. The library supports both HTML 4.01 and XHTML 1.0 standards and includes specialized facilities for processing inline CSS styles with the same rigorous validation approach applied to HTML structure.

The configuration schema subsystem demonstrates particular sophistication with its builder pattern implementation that processes text-based schema definition files into validated runtime configuration objects, allowing the library's extensive configuration options to be strictly type-checked and validated.

## Key Classes and Files

The **HTMLPurifier** class serves as the primary facade that coordinates all subsystems of the filtering pipeline and provides the main entry point for client code through its `purify()` method. This class maintains references to the strategy engine, HTML generator, and filter chain while managing the configuration and context objects that flow through the entire purification process. The class implements a singleton pattern through the `$instance` static property and supports both instance-level and invocation-level configuration, where configuration can be specified during object construction or passed to individual `purify()` calls with the latter taking precedence. The `purify()` method orchestrates the complete filtering workflow by first creating a lexer based on configuration settings, then establishing an execution context that holds state throughout the process, setting up the HTML generator for output production, registering error collectors and ID accumulators if configured, converting input to UTF-8 encoding, instantiating and executing pre-filters, tokenizing the HTML through the lexer, applying the core strategy transformations to the token stream, executing post-filters on the output, and finally converting the result back to the original character encoding if necessary.

The **HTMLPurifier_Filter_ExtractStyleBlocks** class implements a specialized filter that extracts inline `<style>` blocks from HTML content, processes them through the CSSTidy library for sanitization, and stores the cleaned CSS in the execution context for later reinjection. This filter addresses the security challenge of allowing users to include styling information without permitting arbitrary CSS that could be exploited for phishing attacks or UI redressing. The `preFilter()` method uses a regular expression to identify and extract style block contents into the `_styleMatches` array before passing them through the `cleanCSS()` method which removes HTML comment wrappers often used to hide CSS from old browsers, parses the CSS using CSSTidy, validates each CSS property against the CSS definition whitelist from the configuration, removes dangerous at-rules like `@import`, `@charset`, and `@namespace` that could load external resources, applies scope prefixes to selectors if configured to prevent CSS from affecting elements outside the designated scope, and escapes special characters that could break out of the style context. The filter collaborates with the CSSTidy third-party library which must be available at runtime for CSS parsing and normalization.

The **HTMLPurifier_Filter_YouTube** class demonstrates the filter extension mechanism by providing safe handling of YouTube video embeds through a two-phase transformation approach. The `preFilter()` method converts potentially unsafe `<object>` tags containing YouTube URLs into safe temporary `<span>` markers with the class `youtube-embed` that carry only the YouTube video identifier extracted from the original embed code. This intermediate representation prevents the object tag from being processed by the standard HTML filtering rules which might modify or remove it incorrectly. The `postFilter()` method then converts these marker spans back into properly structured `<object>` tags with validated YouTube URLs, complete with appropriate parameters for transparent windowless mode rendering and conditional comments for Internet Explorer compatibility using embedded ActiveX objects. This pattern of pre-conversion to safe markers followed by post-conversion to final markup allows complex third-party content to be supported without compromising the security guarantees of the main filtering pipeline.

The **HTMLPurifier_Printer** base class provides utility methods for generating HTML output used primarily by the debugging and configuration subsystems rather than the core filtering pipeline. This class serves as an abstract base that encapsulates HTML generation logic through methods like `start()` for opening tags, `end()` for closing tags, `element()` for complete elements with content, `elementEmpty()` for self-closing tags, and `row()` for creating table rows with key-value pairs. The `getClass()` method demonstrates sophisticated reflection capabilities by extracting class names while removing namespace prefixes and appending metadata about the class type, such as enumerating the valid values for enum-based validator classes or listing the component validators for composite CSS validators. The printer subsystem collaborates with the HTMLPurifier_Generator to create properly escaped and formatted HTML output that can be safely displayed in configuration interfaces.

The **HTMLPurifier_Printer_ConfigForm** class extends the printer base to generate complete HTML forms for configuring HTMLPurifier settings through a web interface, making the library's extensive configuration options accessible without requiring direct manipulation of configuration arrays. The `render()` method builds a complete HTML table with rows for each configuration directive, consulting the configuration definition to determine the appropriate form field type and rendering select dropdowns for directives with allowed value lists, textareas for multi-line text configuration like hash arrays and lookup tables, and text inputs for simple scalar values. The class implements a decorator pattern through HTMLPurifier_Printer_ConfigForm_NullDecorator that adds checkboxes to allow disabling individual directives by setting them to null, and specialized printer classes like HTMLPurifier_Printer_ConfigForm_bool that render appropriate UI elements for boolean configuration values as radio button pairs. This form generation capability allows PHProjekt administrators to adjust HTML filtering rules through a user-friendly interface rather than editing PHP configuration files.

The **HTMLPurifier_Lexer_PEARSax3** class provides an alternative HTML tokenization implementation based on the PEAR XML_HTMLSax3 package, demonstrating the library's pluggable lexer architecture. This SAX-based lexer operates by registering callback handlers with the underlying XML parser for open tags, close tags, text data, and escaped content like comments, then accumulating HTMLPurifier token objects in the `$tokens` array as the parser invokes these callbacks during HTML traversal. The `openHandler()` method creates either HTMLPurifier_Token_Start or HTMLPurifier_Token_Empty tokens depending on whether the tag is self-closing, while the `closeHandler()` detects and ignores spurious close tags that the SAX parser sometimes generates for empty elements. The `escapeHandler()` specifically identifies HTML comments by checking for the `--` prefix that distinguishes comments from CDATA sections. While this lexer is available as an alternative, the library documentation notes that it has entity-resolution limitations in attributes and generally exhibits lower performance than the default DOM-based lexer, making it primarily useful for environments where DOM extensions are unavailable.

The **HTMLPurifier_ConfigSchema_InterchangeBuilder** class manages the process of constructing configuration schema objects from declarative schema definition files stored as text-based key-value pairs. The `buildFromDirectory()` static method orchestrates schema loading by reading an `info.ini` file that provides schema metadata, scanning the schema directory for `.txt` definition files, sorting these files to ensure deterministic processing order, parsing each file using HTMLPurifier_StringHashParser to extract key-value pairs, and invoking the `build()` method to create either namespace or directive interchange objects based on whether the ID contains a dot separator. The `buildDirective()` method demonstrates comprehensive schema validation by processing required fields like TYPE and ID, parsing DEFAULT values through the variable parser with strict type checking, extracting DESCRIPTION text for documentation, parsing ALLOWED value whitelists for enum-like constraints, processing VALUE-ALIASES for backward compatibility, handling ALIASES for directive name changes, recording VERSION information for feature tracking, and setting DEPRECATED-USE and DEPRECATED-VERSION for migration planning. The `_findUnused()` method provides development-time validation by triggering warnings for unrecognized keys in schema files, helping maintain schema consistency as the configuration system evolves.

## Public API and Interfaces

The primary public interface for external code interacting with HTMLPurifier consists of instantiating the HTMLPurifier class and invoking its `purify()` method with HTML content to be filtered. Client code typically creates an HTMLPurifier instance by passing a configuration object or configuration array to the constructor, which establishes the default filtering rules for that instance, and then repeatedly calls `purify($html)` to filter different HTML snippets using those settings. The configuration object, an instance of HTMLPurifier_Config, allows fine-grained control over dozens of filtering parameters including which HTML elements and attributes are permitted, whether to allow specific features like URI schemes or image dimensions, how to handle encoding transformations, and whether to collect error information for debugging purposes.

The `purify()` method signature accepts the HTML string to be filtered as its first parameter and an optional configuration parameter that can override the instance configuration for that specific invocation. This design pattern allows code to create a single HTMLPurifier instance with common settings while occasionally applying stricter or more permissive filtering rules for specific content types by passing per-invocation configuration adjustments. The method returns a string containing the purified HTML where all disallowed elements have been removed, remaining elements have been validated for proper nesting and well-formedness, attributes have been validated against their type definitions, and the output is guaranteed to be safe for inclusion in web pages without XSS vulnerabilities.

The filter extension mechanism provides an advanced integration point where developers can create custom HTMLPurifier_Filter subclasses that implement `preFilter()` and `postFilter()` methods to manipulate HTML before and after the core purification process. Pre-filters receive the raw HTML string and can perform transformations like extracting style blocks or converting unsafe embed codes into safe markers, while post-filters receive the purified HTML and can reintroduce processed content or perform final transformations. Filters register themselves through the configuration system using the Filter namespace, allowing PHProjekt to enable or disable specific filters based on context requirements.

The configuration schema system exposes an API through HTMLPurifier_Config for setting and retrieving configuration values using namespace and directive names, such as `$config->set('Core', 'Encoding', 'UTF-8')` to specify character encoding or `$config->get('HTML', 'Allowed')` to retrieve the list of allowed HTML elements. The configuration system performs runtime type validation to ensure that values match their schema definitions, preventing configuration errors from causing unexpected filtering behavior. Additionally, the configuration form printer provides a web-based interface generation API through the `HTMLPurifier_Printer_ConfigForm` class which can generate complete HTML forms for configuration management in administrative interfaces.

## Dependencies and Integration

HTMLPurifier maintains minimal external dependencies as a largely self-contained library, requiring only standard PHP extensions for DOM manipulation and string processing that are available in virtually all PHP installations. The library's core functionality depends on PHP's DOM extension for the default lexer implementation which parses HTML into a DOM tree structure for reliable tokenization, although alternative lexers based on regular expressions or the PEAR XML_HTMLSax3 package are available if DOM is unavailable. The character encoding handling relies on PHP's mbstring extension or iconv extension for Unicode normalization and charset conversion, ensuring that HTML in various encodings can be safely processed and that encoding-related XSS attacks are prevented.

The optional CSSTidy dependency provides CSS sanitization capabilities for the ExtractStyleBlocks filter, and when available, enables HTMLPurifier to safely process inline styles and style blocks by parsing CSS syntax, validating property values, and removing dangerous CSS constructs. Without CSSTidy, the ExtractStyleBlocks filter is not functional, but this does not impair the core HTML filtering functionality. Similarly, the PEAR XML_HTMLSax3 package is an optional dependency for the PEARSax3 lexer implementation which some deployments may prefer in environments where SAX parsing is more efficient than DOM manipulation, though the default DOM-based lexer is recommended for most scenarios.

Within the PHProjekt 6 architecture, HTMLPurifier integrates at the presentation layer where user-generated content is prepared for display in the browser. Controllers that handle user input typically pass submitted HTML through HTMLPurifier before storing it in the database or before rendering it in views, ensuring that malicious scripts cannot be persisted or executed. The library is instantiated with configuration appropriate to the context, such as allowing more HTML features in rich text editing fields while applying more restrictive filtering to simple text fields that should not contain markup. The integration pattern typically involves creating a shared HTMLPurifier instance configured through PHProjekt's configuration files, then reusing that instance throughout request processing to avoid the overhead of repeatedly parsing configuration schemas and building validation structures.

The data flow through the HTMLPurifier integration begins when PHProjekt receives user input through forms or API endpoints, continues as the appropriate controller method retrieves the HTML content and invokes HTMLPurifier's purify method, progresses through the multi-stage filtering pipeline that tokenizes, validates, and transforms the HTML, and concludes with the purified HTML being returned to the controller for storage or immediate rendering. Error handling integrates with PHProjekt's exception system by catching any HTML Purifier exceptions that indicate configuration problems or resource constraints, logging appropriate error messages, and falling back to stricter filtering or rejecting the input entirely if purification fails.

## Data Models and Structures

HTMLPurifier's internal data model centers on token objects that represent the atomic units of HTML structure, with each token corresponding to either an opening tag, closing tag, empty self-closing tag, text content, or comment. The token stream produced by the lexer flows through the strategy pipeline as an array of these token objects, where transformation strategies can inspect, modify, remove, or insert tokens to enforce HTML rules while maintaining enough structural information to regenerate correct HTML. Token objects carry attributes, tag names, and other metadata needed for validation, with specialized token types like HTMLPurifier_Token_Start containing attribute arrays that map attribute names to values, all of which are validated against the HTML definition before being permitted in the output.

The configuration data model represents settings as a hierarchical namespace structure where each directive is identified by a namespace name and a directive name, allowing logical grouping of related settings like 'HTML.Allowed', 'CSS.MaxImgLength', and 'Core.Encoding'. Configuration values are strongly typed according to their schema definitions, supporting types including boolean, string, integer, text (multi-line string), array, hash (associative array), and lookup (array used as a set with keys being the significant values). The schema definition files describe each directive's type, default value, allowed values for constrained types, version information, and deprecation status, enabling the configuration system to validate settings at assignment time rather than discovering errors during filtering operations.

The HTML definition data model describes the complete set of permitted HTML elements and their attributes, structured as a collection of element definition objects that specify which attributes each element accepts, what content model it follows for child elements, and any special validation rules that apply. Attribute definitions include type information that determines whether an attribute accepts URIs, colors, lengths, enumerations from a fixed set, or free-form text, with each type having an associated validator that enforces the appropriate constraints. This metadata-driven approach allows HTMLPurifier's behavior to be configured by adjusting the HTML definition rather than modifying code, and supports creating custom definitions that permit only a specific subset of HTML for security-sensitive applications.

The CSS definition data model follows a similar pattern to HTML definitions, describing CSS properties as a collection of property definition objects that specify value syntax, default values, and validation rules. Each property definition references one or more CSS value definition objects that implement validation logic for specific CSS value types like colors, lengths, URIs, fonts, and composite values. The CSS definition supports scoping mechanisms that prefix all selectors with a configured scope selector, preventing CSS rules from affecting document elements outside the intended content area and defending against CSS-based attacks that manipulate page layout for phishing purposes.

## Configuration and Settings

HTMLPurifier exposes an extensive configuration system with over one hundred distinct configuration directives organized into namespaces including Core (fundamental settings), HTML (HTML-specific filtering rules), CSS (CSS property handling), URI (URL validation and transformation), and Filter (filter-specific parameters). The Core namespace includes essential settings like encoding specification through 'Core.Encoding' which determines how character encoding transformations are handled, 'Core.EscapeInvalidTags' which controls whether invalid tags are escaped or removed entirely, and 'Core.CollectErrors' which enables error collection for debugging filtered content. These core settings affect the fundamental behavior of the filtering pipeline and must be carefully configured to balance security requirements with usability concerns.

The HTML namespace configuration provides fine-grained control over permitted HTML elements and attributes through directives like 'HTML.Allowed' which accepts a whitelist string specifying permitted elements and their attributes using syntax like "p,b,a[href],img[src|alt]", 'HTML.ForbiddenElements' which blacklists specific elements even if they would otherwise be allowed, and 'HTML.ForbiddenAttributes' which removes specific attributes across all elements. Additional HTML configuration includes 'HTML.Doctype' for specifying the target HTML version, 'HTML.TidyLevel' for controlling how aggressively the library transforms HTML to conform to standards, and 'HTML.SafeObject' and 'HTML.SafeEmbed' for enabling limited support for object and embed tags with strict URL whitelisting to prevent embedding of malicious active content.

The Filter namespace configuration manages pre-filters and post-filters through directives like 'Filter.ExtractStyleBlocks' which enables the style block extraction filter, 'Filter.ExtractStyleBlocksScope' which sets the CSS selector prefix for scoping extracted styles, and 'Filter.ExtractStyleBlocksEscaping' which controls whether special HTML characters are escaped in CSS content. Filter configuration also includes 'Filter.YouTube' for enabling the YouTube embed filter and 'Filter.Custom' for registering custom filter instances that implement application-specific transformation logic. This filter configuration mechanism allows PHProjekt to enable specific filters based on the context where HTML is being processed, such as enabling style extraction only in content areas where rich formatting is appropriate.

The URI namespace configuration controls how URLs in attributes like href and src are validated and transformed through directives including 'URI.AllowedSchemes' which whitelists permitted URI schemes like http, https, and mailto while blocking dangerous schemes like javascript and data, 'URI.DisableExternal' which prevents linking to external resources, and 'URI.MakeAbsolute' which transforms relative URLs into absolute URLs using a specified base. These URI validation settings are critical for preventing XSS attacks that exploit URI parsing inconsistencies between HTML Purifier and browsers, and for enforcing content security policies that restrict which external resources can be referenced.

## Design Patterns and Principles

HTMLPurifier's architecture demonstrates the Strategy pattern through its core filtering engine where the HTMLPurifier_Strategy_Core class orchestrates a sequence of token transformation strategies that each apply specific validation and transformation rules. This strategy-based design allows the filtering logic to be decomposed into manageable, testable units where each strategy has a clearly defined responsibility such as removing non-whitelisted elements, fixing tag nesting problems, validating attributes, or handling entity encoding. The strategies operate on the common token stream representation, enabling the pipeline to be extended with additional strategies or reordered to accommodate different filtering requirements without modifying the core HTMLPurifier class or the lexer and generator subsystems.

The Facade pattern is embodied in the HTMLPurifier class itself, which presents a simplified interface to the complex subsystems of lexing, strategy execution, filtering, and HTML generation. Client code interacts exclusively with the HTMLPurifier facade through the straightforward `purify()` method, remaining insulated from the complexity of managing lexers, strategies, contexts, generators, and configuration schemas. This facade insulation allows the internal implementation to evolve without impacting client code, as demonstrated by the availability of multiple lexer implementations that can be substituted through configuration without requiring any changes to the code that invokes purification.

The Template Method pattern appears in the filter extension mechanism where the base HTMLPurifier_Filter class defines the overall structure of filter processing with `preFilter()` and `postFilter()` template methods, while concrete filter implementations like ExtractStyleBlocks and YouTube override these methods to provide specific transformation logic. This pattern enables consistent filter integration where all filters participate in the same pipeline phases regardless of their specific functionality, and ensures that filter implementations can focus on their transformation logic without concerning themselves with pipeline management or context handling.

The Builder pattern is demonstrated in the HTMLPurifier_ConfigSchema_InterchangeBuilder class which constructs complex configuration schema objects through a step-by-step assembly process that validates each schema element as it is added. The builder processes schema definition files that specify directives and namespaces through method calls like `buildNamespace()` and `buildDirective()`, accumulating these elements in an interchange object that represents the complete schema once all files have been processed. This pattern separates the representation of configuration schemas from their construction, allowing schema definitions to be loaded from files, generated programmatically, or even retrieved from a database without changing the rest of the configuration system.

The Printer classes implement the Decorator pattern where HTMLPurifier_Printer_ConfigForm_NullDecorator wraps other printer implementations to add null-value handling checkbox UI elements around the base printer's output. This decorator approach allows orthogonal concerns like null-ability to be layered onto printer implementations without requiring every printer to implement null handling logic, and enables runtime composition of printer behaviors based on configuration schema metadata that indicates which directives support null values. The separation of printing concerns into decoratable components promotes reusability and maintainability of the configuration form generation subsystem.
