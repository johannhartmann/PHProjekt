# Component: Timecard

## Overview

The Timecard module provides comprehensive time tracking and resource management capabilities within PHProjekt, enabling organizations to monitor work hours, manage vacation time, track project allocations, and analyze resource utilization patterns. This module transforms abstract labor concepts into concrete data structures where employees record hours worked against specific projects, managers track team capacity and allocation, and administrators analyze productivity trends across the organization. The module serves dual purposes as both an individual time logging tool where employees document their daily activities and as a management reporting platform where supervisors monitor resource consumption and project costs. The integration with project context ensures that time entries automatically associate with organizational hierarchies, creating visibility into how human resources are distributed across different initiatives.

The architectural sophistication of the Timecard module extends beyond simple time entry to encompass employment contract management, vacation balance calculation, working time regulations, and holiday awareness through regional calendar integration. The contract model represents employment agreements specifying weekly hours, salary periods, and vacation entitlements, providing the baseline against which actual time entries are compared to calculate utilization rates and overtime. The vacation tracking system maintains running balances of available vacation days, automatically deducting from entitlements as time off is taken while preventing negative balances through validation rules. The holiday integration leverages the Mayflower Holiday library to recognize regional and national holidays, automatically adjusting working day calculations to account for non-working days that vary by location and year.

The Timecard module's integration with external calendar systems through CalDAV protocol support enables bidirectional synchronization where vacation periods appear as calendar events in external clients like Microsoft Outlook, Apple Calendar, or mobile calendar applications. This CalDAV capability extends the module's reach beyond the PHProjekt web interface, allowing employees to view their time off schedules through their preferred calendar applications while maintaining PHProjekt as the authoritative source for time tracking data. The CalDAV backend presents vacation periods as all-day events with appropriate iCalendar properties, enabling external clients to display time off in calendar views alongside meetings and other events. The implementation reuses SabreDAV infrastructure from Calendar2 module, demonstrating architectural consistency across modules that expose calendar-like data.

The technological foundation of the Timecard module includes PHP 5.3+ with extensive DateTime manipulation for temporal calculations, Active Record persistence through Phprojekt_ActiveRecord_Abstract for database operations, the Mayflower Holiday library for holiday calculations across different regions, and SabreDAV library (version 1.6.2) for CalDAV protocol implementation. The module stores timecard entries in the timecard table with supporting tables for contracts (defining employment terms), vacation (tracking time off), and user-contract relationships (associating employees with employment agreements over time). The minutes-based calculation system stores durations as integer minutes rather than decimal hours, avoiding floating-point precision issues while enabling exact arithmetic for aggregations. The module's reporting capabilities provide both detailed entry-level data and aggregated summaries, supporting management queries like "total hours per project" and compliance queries like "overtime worked this period."

The Timecard module's structure follows PHProjekt's standard modular organization while emphasizing reporting capabilities through specialized controller actions that aggregate time data across multiple dimensions. The Controllers directory contains three specialized controllers reflecting different access patterns—IndexController with numerous custom reporting actions (recentProjects, bookedProjects, minutesBooked, workBalanceByDay, projectUserMinutes), TimecardController providing RESTful CRUD operations, and CaldavController exposing vacation data through CalDAV protocol. This reporting-heavy controller design distinguishes Timecard from simpler CRUD modules, as management needs for resource analysis drive substantial custom query logic beyond standard list/detail operations.

The Models directory contains five model classes that together implement the complete time tracking domain including transactional time entries (Timecard), template employment agreements (Contract), time off periods (Vacation), user preferences (Setting), and metadata definitions (Information). The separation of Contract from Timecard enables the system to track changing employment terms over time where an employee might move from part-time to full-time contract midway through employment, with historical timecard entries remaining associated with their original contract terms for accurate reporting. The VObjectReader model demonstrates the module's iCalendar format support, parsing CalDAV requests to extract vacation period data from external calendar clients. The CalDAV directory houses the backend that bridges between SabreDAV and PHProjekt's vacation model, implementing a pattern parallel to Calendar2's CalDAV integration but specialized for time off tracking.

## Key Classes and Files

### Models/Timecard.php

The Timecard_Models_Timecard class implements the core time entry entity representing a single work period logged by an employee against a specific project. This model extends Phprojekt_ActiveRecord_Abstract while implementing Phprojekt_Model_Interface, establishing it as a full participant in PHProjekt's permission system, search indexing, and history tracking. The class spans 694 lines of focused code that balance between standard Active Record patterns and the domain-specific complexity of time duration calculations, overlap detection, and utilization reporting. The model stores time entries with start datetime, end time (time-only, not full datetime), and calculated duration in minutes, creating a denormalized storage pattern where durations are persisted rather than calculated on query for performance optimization.

The save method orchestrates complex validation and calculation workflows including duration computation from start datetime and end time, automatic ownerId assignment for new entries, unique identifier generation for CalDAV compatibility, and permission verification through _checkSaveRights. The duration calculation converts start and end times to Unix timestamps, computes the difference in seconds, then converts to minutes through integer division, avoiding floating-point arithmetic that could accumulate precision errors. The method handles the edge case of empty endTime by setting minutes to null rather than zero, distinguishing between "no end time recorded yet" and "zero duration entry" which have different semantic meanings. The automatic ownerId assignment ensures that time entries always have clear ownership even when created through bulk import or administrative interfaces.

The model's validation logic implements business rules that prevent logical impossibilities like negative durations (end before start), future-dated entries (recording time before it happens), overlapping entries (same user logging multiple activities simultaneously), and excessive daily totals (working more than physically possible hours per day). The overlap detection queries the database for existing entries by the same user on the same date, comparing time ranges to identify conflicts. The excessive hours check sums existing entries for the day and validates that the new entry doesn't push the total beyond configured limits (typically 24 hours). These validation rules enforce data quality while preventing common data entry errors that would corrupt reporting accuracy.

The getModelInformation method returns Timecard_Models_Information which defines field metadata including field types, validation rules, required status, and display properties. This metadata drives the dynamic form generation system that renders appropriate input controls for each field type—text inputs for notes, datetime pickers for start times, time selects for end times, and project selectors for project associations. The information model also specifies field ordering and grouping, controlling how fields appear in forms and lists. The separation of metadata into a dedicated Information model maintains clean boundaries where Timecard handles business logic while Information handles presentation concerns, enabling presentation changes without modifying entity logic.

### Models/Contract.php

The Timecard_Models_Contract class represents employment agreements that define working hours, vacation entitlements, holiday regions, and salary structures. This model extends Phprojekt_ActiveRecord_Abstract to provide persistence capabilities while implementing domain-specific methods for contract queries and calculations. The contract model serves as a template that multiple employees can share, with the user_contract_relation junction table associating users with contracts during specific date ranges. This temporal association enables the system to track contract changes over time, such as promotions from part-time to full-time status or transfers to different employment terms, while maintaining accurate historical records for past time entries.

The fetchByUserAndPeriod static method implements sophisticated temporal queries that retrieve applicable contracts for a user within a specified date range, handling the complexity of overlapping contract periods and open-ended contracts (those without specified end dates). The method queries the user_contract_relation table to find contract associations where the specified period intersects with the contract's validity period, then fetches the actual contract records from the contract table. The returned data structure includes contract objects alongside their start and end dates from the junction table, enabling calling code to determine which contract applies at any given point in time. This temporal query capability supports reporting scenarios like "calculate expected working hours for the past year" where a user might have had multiple contracts with different terms during that period.

The contract model stores essential employment parameters including weekly hours (expected work time per week), vacation days per year (annual time off entitlement), holiday region (geographic location for holiday calculations), and employment type (full-time, part-time, contractor). These parameters feed into various calculations throughout the Timecard module including utilization rate computation (actual hours / expected hours), vacation balance tracking (available days - used days), and working day calculations (business days - holidays). The model's integration with Mayflower Holiday library happens through the holiday region field, which specifies which holiday calendar to use when determining non-working days. The library supports multiple regions enabling multi-national organizations to correctly calculate working time for employees in different countries or states.

### Models/Vacation.php

The Timecard_Models_Vacation class manages time off periods including scheduled vacations, sick leave, and other absence types. Unlike the Timecard model which represents work performed, Vacation represents work not performed due to planned absences. The model implements a simplified interface focused on querying rather than complex business logic, with the getByPeriod static method serving as the primary access point. This method retrieves vacation periods for the authenticated user within a specified date range, filtering by user_id automatically to enforce data isolation. The vacation records include start and end dates (both inclusive) plus absence type and approval status, creating a complete picture of time away from work.

The vacation model's integration with the CalDAV backend enables vacation periods to appear as all-day calendar events in external calendar clients, providing employees with unified visibility into their schedules. The CalDAV backend queries vacation records through getByPeriod, then converts them to VEVENT iCalendar components with all-day event properties. This integration creates bidirectional synchronization where vacation requests created in PHProjekt appear in external calendars, and vacation periods created in external calendars (if CalDAV supports write operations) flow back into PHProjekt. The vacation synchronization demonstrates the module's commitment to integration, ensuring that time off information reaches employees through their preferred tools rather than requiring them to check PHProjekt specifically.

The vacation balance calculation logic (implemented in controllers or helper classes) uses vacation records to determine remaining entitlement by subtracting used vacation days from annual allowances specified in employment contracts. The calculation handles partial years (new employees or mid-year contract changes) by prorating annual entitlements based on contract start dates. The system prevents negative balances through validation rules that reject vacation requests exceeding available days, ensuring that employees can't schedule more time off than their contracts allow. The approval workflow (tracked through status fields) enables manager review before vacation periods are officially granted, creating a request-approve pattern that maintains organizational control over time off distribution.

### Controllers/IndexController.php

The Timecard_IndexController extends the Default module's IndexController while adding substantial reporting functionality through specialized action methods that aggregate time data across various dimensions. The controller's init method configures context switching to support both JSON and CSV output formats for reporting actions, enabling users to view reports in the browser or export them for analysis in spreadsheet applications. The format configuration includes CSV-specific headers that trigger browser downloads with timestamped filenames, creating a convenient export mechanism for management reporting. The controller overrides setCurrentProjectId to always use the root project, reflecting Timecard's global scope where time entries span all projects rather than filtering by current project context.

The workedMinutesPerDay action demonstrates the controller's reporting pattern by accepting date range parameters, querying timecard records within that range grouped by date, summing minutes for each day, and returning structured data suitable for visualization. This action enables time tracking dashboards that show daily work patterns, helping employees and managers identify anomalies like missed entries or excessive overtime. The projectUserMinutes action implements multi-dimensional aggregation by grouping time entries by both project and user, providing management visibility into how team members allocate time across different initiatives. These aggregation queries leverage SQL's GROUP BY capabilities through Active Record abstractions, maintaining database-agnostic query logic that could support multiple database backends.

The recentProjects and bookedProjects actions implement smart defaults that reduce data entry friction by suggesting recently used or frequently booked projects when users create new time entries. The recentProjects action queries the current user's time entries ordered by entry date, extracting unique project IDs to present as shortcuts. The bookedProjects action returns projects where the user has logged any time during a specified period, providing contextual project lists rather than showing all projects in the system. These user experience optimizations demonstrate the controller's focus on reducing time entry overhead, as employees are more likely to consistently track time when the system minimizes repetitive data entry through intelligent defaults.

The workBalanceByDay action implements more sophisticated calculations that combine actual worked time from timecard entries with expected working time from employment contracts, computing daily balances that show whether users are ahead or behind their expected hours. This action integrates data from multiple models including Timecard for actual hours, Contract for expected hours, and Vacation for scheduled time off, combining them into a unified balance calculation. The resulting data structure shows cumulative balance over time, enabling trend analysis that identifies chronic overwork or underwork patterns. This reporting capability supports both employee work-life balance monitoring and management resource utilization analysis.

### CalDAV/CalendarBackend.php

The Timecard_CalDAV_CalendarBackend class implements Sabre_CalDAV_Backend_Abstract to provide CalDAV protocol support for vacation synchronization, following the same architectural pattern as Calendar2's CalDAV backend but specialized for time off data. The backend presents each user's vacation periods as a single CalDAV calendar containing all-day events, enabling external calendar clients to subscribe and synchronize. The getCalendarsForUser method returns a hardcoded calendar descriptor labeled "default" with the user's ID as the calendar identifier, simplifying implementation by avoiding multiple calendar support while providing the essential synchronization capability.

The getCalendarObjects method retrieves vacation periods for the specified user and date range, converting each vacation record into an iCalendar VEVENT component with all-day event properties. The conversion sets DTSTART and DTEND as DATE (not DATETIME) values spanning the vacation period, SUMMARY describing the absence type, and UID providing stable identifiers for synchronization. The all-day event format ensures that vacation periods block entire days in calendar views rather than appearing as specific time slots, accurately representing time off semantics. The backend returns vacation events alongside any other calendar events (if integrated with Calendar2), creating unified calendar views in external clients.

The createCalendarObject, updateCalendarObject, and deleteCalendarObject methods implement vacation management through CalDAV protocol, parsing incoming iCalendar data to extract vacation period details, creating or updating Vacation models, and persisting changes to the database. The parsing extracts DTSTART and DTEND to determine vacation period boundaries, SUMMARY to capture absence reason, and other relevant properties to populate vacation record fields. The methods enforce permission checks to ensure users can only create vacation periods for themselves (or for their reports if managers), maintaining security boundaries even when accessed through CalDAV protocol. Error handling translates validation failures and permission errors into appropriate HTTP status codes and iCalendar-compatible error responses.

The settings integration demonstrates PHProjekt's consistency where similar concerns (user preferences) are handled through similar mechanisms across different modules.

## Public API and Interfaces

The Timecard module exposes three distinct API layers serving different client types and usage patterns. The traditional HTTP API through Timecard_IndexController provides specialized reporting endpoints where URLs like /timecard/index/worked-minutes-per-day accept date range parameters (start, end) and return JSON arrays with daily work summaries. The reporting actions follow a consistent pattern where parameters specify the analysis period and dimension (per day, per project, per user), the controller queries timecard and contract data, aggregates results appropriately, and returns structured JSON suitable for charting or tabular display. These reporting endpoints serve the PHProjekt web interface's dashboard and reporting widgets, enabling managers to analyze resource allocation and utilization patterns through visual interfaces.

The RESTful API through Timecard_TimecardController provides resource-oriented access to individual timecard entries following HTTP verb semantics where GET /timecard/timecard/{id} retrieves an entry, POST /timecard/timecard creates an entry, PUT /timecard/timecard/{id} updates an entry, and DELETE /timecard/timecard/{id} removes an entry. This REST interface enables integration with time tracking tools, mobile applications, or external systems that need to record or query work hours. The REST controller delegates to the same Timecard model used by the traditional controller, ensuring behavioral consistency across different access patterns. Both traditional and REST interfaces enforce permission rules where users can only access their own time entries unless they possess administrative privileges, maintaining data privacy boundaries.

The CalDAV API through Timecard_CaldavController implements a subset of CalDAV protocol focused on vacation synchronization rather than full event management. CalDAV clients discover the vacation calendar through PROPFIND requests to /timecard/caldav/calendars/username/, retrieve vacation periods through REPORT requests with date range filters, and potentially create vacation requests through PUT requests with iCalendar payloads. The CalDAV interface requires HTTP Basic Authentication with each request, validating credentials through the same authentication system used for web access. This protocol-level API operates at a lower abstraction than HTTP/REST, dealing with iCalendar format, WebDAV properties, and calendar-specific extensions that provide interoperability with standard calendar clients.

## Dependencies and Integration

The Timecard module depends on several external libraries and PHProjekt infrastructure components including the Mayflower Holiday library for holiday calculations, SabreDAV library (version 1.6.2) for CalDAV protocol implementation, and Phprojekt_ActiveRecord_Abstract for database persistence. The Mayflower Holiday integration provides holiday awareness where the system queries the library to determine whether specific dates are holidays based on configured regions, enabling accurate working day calculations that account for national, regional, and religious holidays. This holiday awareness permeates vacation balance calculations, overtime computation, and expected working hour determination, ensuring that the system's understanding of "working days" matches organizational reality.

Integration with the Project module happens through the projectId foreign key on timecard entries, associating each time log with a specific project in the organizational hierarchy. This association enables project-level time reporting where managers query total hours logged against specific projects or project hierarchies, supporting project cost tracking and resource allocation analysis. The integration respects project permissions where users can only create timecard entries for projects they have access to, maintaining security boundaries even though Timecard operates in global context. The project association also drives the recent projects and booked projects features where the system suggests contextually relevant projects based on the user's time logging patterns within their accessible project scope.

Data flows through the Timecard module follow temporal aggregation patterns where raw time entries are summed across various dimensions (day, week, month, project, user) to produce management reports. The IndexController's reporting actions accept date range parameters, query timecard entries within those ranges, group by the relevant dimension (date for daily reports, project_id for project reports, owner_id for user reports), sum the minutes column, and return aggregated results. For balance calculations, the flow combines timecard data with contract data and vacation data, computing expected work time based on contract hours and working days, subtracting vacation periods, comparing against actual logged time, and returning the balance. This multi-model integration demonstrates the module's analytical sophistication where simple time entry data transforms into actionable management insights through sophisticated querying and calculation.

## Data Models and Structures

The Timecard module's data model centers on three primary tables that together implement the complete time tracking domain. The timecard table stores individual work periods with columns for id (primary key), owner_id (employee who logged the time), project_id (project the work was performed for), start_datetime (when work began), end_time (when work ended, time-only), minutes (calculated duration), notes (description of work performed), and uid/uri (CalDAV identifiers). The storage pattern for start_datetime and end_time creates an interesting hybrid where starts include both date and time while ends include only time, with the assumption that most time entries occur within a single day. This storage optimization reduces data redundancy while supporting the multi-day entry case through the minutes field that can exceed 1440 (24 hours × 60 minutes).

The contract table defines employment agreements with columns for id, name (contract description), weekly_hours (expected work per week), vacation_days (annual time off entitlement), holiday_region (geographic location for holiday calendars), and employment_type (full-time, part-time, contractor). The user_contract_relation junction table creates temporal associations between users and contracts with columns for user_id, contract_id, start (date contract became effective), and end (date contract ended, nullable for ongoing contracts). This temporal association pattern enables accurate historical queries where the system determines which contract was in effect at any given date, supporting scenarios like retroactive salary calculations or historical utilization reports that need to account for changing employment terms.

The vacation table tracks time off periods with columns for id, user_id (employee taking time off), start (first day of absence), end (last day of absence, inclusive), type (vacation, sick, personal), status (requested, approved, rejected), and created (when request was submitted). The inclusive date range representation (both start and end are days off) differs from typical programming conventions where end dates are exclusive, requiring careful handling in date arithmetic to avoid off-by-one errors. The vacation data integrates with both timecard reporting (reducing expected work time) and CalDAV synchronization (appearing as calendar events), demonstrating the table's dual role in both internal calculations and external integrations.

| Table | Primary Purpose | Key Fields | Key Relationships |
|-------|----------------|------------|-------------------|

## Configuration and Settings

The Timecard module's configuration encompasses working time policies, validation thresholds, holiday regions, and CalDAV endpoint settings. The working time configuration includes parameters like maximum daily hours (typically 24), minimum entry duration (e.g., 15 minutes to prevent tiny fractional entries), and rounding rules (whether to round to nearest 15 minutes or allow exact minute tracking). These policies balance between realistic work tracking and preventing data quality issues from impossible entries. The configuration also specifies whether to enforce strict non-overlap validation (preventing any temporal overlap between entries) or lenient validation (allowing overlaps with warnings), with organizations choosing based on their trust model and data quality priorities.

Validation threshold configuration determines when the system warns versus blocks time entries including excessive daily hours thresholds (e.g., warn above 10 hours, block above 16 hours), future entry prevention (how far in advance entries can be created), and backdating limits (how far in the past entries can be recorded). These thresholds implement organizational policies around time tracking discipline, with some organizations allowing flexible backdating for correcting errors while others enforce strict daily entry requirements. The configuration system supports both system-wide policies and project-specific overrides, enabling different projects to have different time tracking requirements based on client contracts or compliance needs.

Holiday region configuration specifies which geographic holiday calendars to use when calculating working days and expected work time, with the Mayflower Holiday library supporting multiple regions including Germany, United States, United Kingdom, and various other countries and subdivisions. The configuration maps contract records to holiday regions, enabling multi-national organizations to correctly calculate working time for employees in different locations. The holiday configuration also specifies how to handle flexible holidays (those that can be taken on different days) and religious holidays (those that only apply to specific populations), creating accurate working time calculations that respect cultural and legal requirements across diverse workforces.

## Design Patterns and Principles

The Timecard module extensively applies the Value Object pattern through its duration representation where time periods are immutable values calculated from start and end times rather than mutable entities. The minutes field stores duration as an integer value that gets recalculated during save operations, ensuring that stored durations always reflect current start and end times without requiring complex synchronization logic. This value object approach enables duration comparisons and aggregations through simple integer arithmetic rather than complex temporal calculations, improving both code clarity and performance. The pattern extends to date range values where vacation periods and contract validity periods are represented as immutable start-end pairs rather than mutable time spans.

The Template Method pattern appears in the save override where Timecard_Models_Timecard defines the overall save workflow (calculate minutes, set defaults, validate permissions, persist) while allowing specific validation steps to be customized through hook methods. The _checkSaveRights template method enables subclasses or decorators to inject custom authorization logic while inheriting the standard save orchestration. This pattern maintains the DRY principle where common save logic appears once in the base implementation while variation points support customization without duplicating the overall workflow. The pattern also enables testing where mock implementations can override template methods to test specific aspects without executing complete database operations.

The Strategy pattern manifests in the reporting system where different aggregation strategies apply based on the requested report type. Daily aggregation strategies group by date and sum minutes per day. Project aggregation strategies group by project_id and sum minutes per project. User aggregation strategies group by owner_id and sum minutes per user. The controller acts as the strategy context that selects appropriate aggregation logic based on the requested report type, then executes the selected strategy to produce results. This pattern enables new report types to be added through new strategy implementations without modifying existing report logic, supporting extensibility through the Open-Closed Principle where the system is open to report extensions but closed to modifications of existing reports.

The Separation of Concerns principle guides the distribution of responsibilities where Timecard model handles time entry business logic, Contract model handles employment agreement logic, Vacation model handles time off logic, and various controller actions handle different reporting concerns. This separation prevents the god object anti-pattern where a single class attempts to handle all time tracking concerns, instead creating focused classes with clear responsibilities and minimal overlap. The principle extends to the CalDAV integration where CalendarBackend handles protocol adaptation while Vacation model handles domain logic, maintaining clean boundaries between protocol concerns and business logic. This separation enables independent evolution where vacation policies can change without affecting CalDAV protocol handling, and protocol updates can occur without modifying vacation business rules.

The Command pattern appears in the batch operations where multiple time entries can be created or modified together through a single request, with each entry represented as a command that gets validated and executed independently. The controller accumulates commands from the request, validates each command against business rules, executes successful commands while collecting failures, and returns results indicating which commands succeeded and which failed. This pattern enables partial success scenarios where some time entries save successfully while others fail validation, providing better user experience than all-or-nothing transactions that would reject entire batches for single invalid entries. The command accumulation also enables optimizations where database connections are reused across multiple entry saves rather than establishing new connections per entry.
