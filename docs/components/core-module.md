# Component: Core

## Overview

The Core module serves as the administrative backbone of the PHProjekt application, providing centralized management capabilities for users, roles, modules, system configuration, and operational history. This module implements the control plane through which system administrators govern all aspects of the platform, from defining organizational roles and permissions to configuring system-wide settings and managing the lifecycle of functional modules. The Core module enforces strict authorization requirements, with most operations restricted to users holding administrative privileges, ensuring that sensitive system configuration cannot be modified by unauthorized personnel. The module integrates deeply with the framework's authentication and authorization infrastructure, acting as the primary interface through which security policies are defined and enforced throughout the application.

The architectural role of the Core module extends beyond simple CRUD operations on administrative entities. It provides the foundational data structures that other modules depend upon, including the user registry, role hierarchy, module catalog, and configuration repository. Through its Controllers and Models, the Core module exposes both web-based administrative interfaces and programmatic APIs that other components consume to make runtime decisions about permissions, localization, and feature availability. The module's design embodies the principle of separation of concerns by isolating administrative functionality from business domain logic, allowing the Project, Calendar2, Timecard, and other domain modules to focus on their specific responsibilities while delegating cross-cutting administrative concerns to Core.

The Core module leverages standard PHProjekt patterns including the Model-View-Controller architecture, Active Record persistence, and JSON-based API responses. Controllers extend Core_IndexController, which itself inherits from the framework's base IndexController, adding administrative authorization checks in the preDispatch lifecycle method. Models utilize Phprojekt_ModelInformation_Default to define field metadata, enabling dynamic form generation in the Dojo-based frontend. The module includes comprehensive database schema definitions in JSON format, specifying table structures for users, roles, modules, settings, history tracking, and search indexing. This declarative schema approach enables the database migration system to create and maintain Core module tables consistently across different deployment environments.

The technological foundation of the Core module includes standard PHP 5.3+ with Zend Framework 1.10.7 for MVC structure, Phprojekt's Active Record library for data persistence, and Dojo Toolkit for the administrative user interface. The module stores data across multiple MySQL tables including user, role, module, configuration, setting, history, and various junction tables that establish relationships between these entities. Integration with the Phprojekt_Auth component ensures that administrative operations are performed within authenticated sessions, while the Phprojekt_Configuration library provides key-value storage for both system-wide and user-specific settings. The module's design anticipates multi-language deployments through language file support for English, German, and Spanish, with all user-facing text externalized for translation.

The Core module's structure follows PHProjekt's standard modular organization where Controllers, Models, Views, Languages, and Sql directories each serve distinct purposes in the MVC architecture. The Controllers directory contains ten specialized controller classes, each focused on a specific administrative domain such as users, roles, or modules, promoting single responsibility and maintainability. Models are organized into subdirectories by functional area, with User, Notification, and General subdirectories grouping related setting metadata classes. The Views hierarchy separates server-side view scripts from client-side Dojo components, with the latter organized into Administration and Setting subdirectories that mirror the controller organization. Language files use PHP include syntax with associative arrays mapping translation keys to localized strings, enabling runtime language selection based on user preferences.

The Sql/Db.json file represents a critical component of the module's infrastructure, containing a comprehensive database schema definition expressed in declarative JSON format. This schema specification includes CREATE statements for fifteen tables (configuration, database_manager, frontend_message, history, item_rights, module, module_tab_relation, project, project_module_permissions, project_role_user_permissions, role, role_module_permissions, search_display, search_words, search_word_module, setting, tab, tags, user, user_proxy), initial data INSERT statements for bootstrapping a new installation with default users and roles, and relationship definitions that maintain referential integrity. The migration system processes this JSON specification to generate database-specific SQL statements, with support for versioned schema evolution through numbered sections (6.0.0) that enable incremental upgrades from earlier releases.

## Key Classes and Files

### Controllers/IndexController.php

The Core_IndexController class serves as the authorization gatekeeper for all Core module operations, extending the framework's base IndexController with administrative access control enforcement. The preDispatch method intercepts every request directed to the Core module, invoking Phprojekt_Auth::isAdminUser() to determine whether the authenticated user possesses administrative privileges. For non-administrative users, the method examines a whitelist of controller-action combinations that represent public operations accessible to regular users, such as viewing history for items they have access to, retrieving the list of global modules for navigation, fetching user lists for selection widgets, or managing their personal settings. Requests that do not appear on this whitelist trigger an HTTP 401 Authorization Required response, terminating request processing before reaching the action method. This security-by-default approach ensures that sensitive administrative functions cannot be accidentally exposed through configuration errors or oversight.

The getModelObject method provides a convention-based mechanism for action methods to obtain appropriate model instances without hardcoding class names. By examining the controller name from the current request, the method dynamically constructs a model class name following the Phprojekt_{Controller}_{Controller} naming pattern, then instantiates and returns an object of that class. This convention enables standard CRUD action methods inherited from the base IndexController to operate generically across different administrative entities, with the specific model determined at runtime based on the request URL. The pattern demonstrates dependency inversion where high-level controller logic depends on abstractions (the model interface) rather than concrete implementations, enabling code reuse across multiple administrative entity types.

### Controllers/UserController.php

The Core_UserController manages the complete lifecycle of user accounts including creation, modification, deletion, and querying of user information. The jsonGetUsersAction method returns a filtered list of active users formatted as JSON with id and display fields, which the frontend uses to populate selection widgets in forms throughout the application. This method exemplifies the query pattern where controllers expose specialized endpoints optimized for specific UI needs rather than forcing the frontend to retrieve and filter complete entity representations. The jsonDetailAction retrieves comprehensive information about a single user including profile fields, role assignments, and setting values, returning both the data and metadata that describes field types, validation rules, and display properties. This metadata-driven approach enables the Dojo frontend to dynamically generate appropriate form controls without hardcoding knowledge of user entity structure.

The controller implements save operations through inherited jsonSaveAction from the base IndexController, which creates new users or updates existing ones based on the presence of an id parameter. Password handling receives special treatment with hash generation before persistence, ensuring that plaintext passwords never reach the database. Email address validation enforces proper format requirements, while username uniqueness is verified through database constraints that trigger validation errors if conflicts occur. The controller coordinates with the Phprojekt_User_User model to perform actual persistence operations, with the model's Active Record capabilities handling SQL generation and execution. Deletion operations cascade to related tables including settings, role assignments, and permission grants, with the database migration system having established appropriate foreign key relationships to maintain referential integrity.

### Controllers/RoleController.php

The Core_RoleController specializes in managing organizational roles and their associated module permissions, providing the interface through which administrators define templates for user access patterns. The jsonGetModulesAccessAction method returns a comprehensive matrix of module-permission pairs for a specified role, with each module represented as an object containing permission flags for none, read, write, access, create, copy, delete, download, and admin privileges. This fine-grained permission model enables administrators to craft precise access control policies that restrict users to exactly the operations they require for their organizational responsibilities. The method delegates to Phprojekt_Role_RoleModulePermissions model which queries the role_module_permissions junction table and enriches the results with module metadata from the module table, returning a complete picture of what a role holder can accomplish within each module.

Save operations on roles involve two-phase commits where the role entity itself is persisted first, followed by updates to the role_module_permissions junction table that establishes the many-to-many relationship between roles and modules. The controller handles the complexity of synchronizing this junction table by deleting existing permission grants for the role and inserting new records based on the submitted permission matrix, ensuring that the database state accurately reflects administrator intent even when permissions are revoked. The parent attribute on roles enables hierarchical role definitions where child roles can inherit and extend permissions from parent roles, though the current implementation treats roles as independent entities with the hierarchy structure available for future enhancement.

### Controllers/ModuleController.php

The Core_ModuleController manages the system's module catalog, providing operations for activating, deactivating, configuring, and removing functional modules from the PHProjekt installation. The jsonGetGlobalModulesAction returns modules with save_type values of 1 or 2, indicating global modules that appear in the main navigation versus project-specific modules that only display within project contexts. This distinction enables the frontend to render appropriate navigation structures based on module types, with global modules appearing in the top-level menu and project modules appearing in project-specific menus. The metadata returned alongside module data includes the current user's admin status, enabling the frontend to conditionally display administrative functions like module configuration or deactivation based on permissions.

Deletion operations through jsonDeleteAction exemplify defensive programming patterns where the controller validates that target modules are not system modules before proceeding with removal. The CAN_NOT_DELETE_SYSTEM_MODULE constant defines the error message returned when administrators attempt to delete protected modules like Project, Calendar2, or Core itself, preventing system instability that would result from removing foundational components. For custom modules created through the Module Designer, deletion cascades across multiple tables including the module registry entry, database_manager field definitions, project_module_permissions grants, and role_module_permissions associations. The controller coordinates with DatabaseManager to drop the custom module's data table, completing the removal process and freeing database resources.

### Controllers/ModuleDesignerController.php

The Core_ModuleDesignerController implements meta-programming capabilities that allow administrators to create entirely new modules through web-based forms without writing code, dramatically extending PHProjekt's adaptability to organization-specific workflows. The controller processes field definitions submitted through the administrative interface, translating them into database_manager entries that describe table structure, form layout, validation rules, and grid display configuration. These metadata entries drive the Default module's generic CRUD operations, enabling newly created modules to inherit standard create, read, update, and delete functionality automatically. The designer's output includes SQL table creation statements executed through DatabaseManager, controller class generation that extends appropriate base controllers, and model class generation that extends Phprojekt_Item_Abstract with proper relationship definitions.

The module creation workflow orchestrates multiple subsystems including schema management for table creation, file generation for controller and model classes, module registry updates to make the new module discoverable, and permission initialization to grant appropriate access to default roles. The controller validates module names for uniqueness and conformance to naming conventions, ensuring that generated class names do not conflict with existing classes and follow PHP identifier rules. Field type selection determines both database column types and frontend widget types, with the controller maintaining mappings between abstract field types like "text," "date," "select," and "rating" and their corresponding database types and Dojo widgets. This abstraction layer shields administrators from technical implementation details while maintaining the flexibility to support diverse data types and user interface patterns.

### Controllers/SettingController.php

The Core_SettingController manages hierarchical configuration through three levels: system-wide defaults defined in the General configuration, module-specific defaults that override system settings for particular modules, and user-specific overrides that take precedence over both system and module settings. The jsonListAction retrieves effective settings for the current user by querying the setting table with filters for user_id and module_id, then merging these results with defaults from configuration tables to produce a complete configuration view. This three-tier approach balances flexibility with manageability, enabling administrators to establish organizational standards through system defaults while permitting users to customize aspects like language, timezone, and notification preferences according to their individual needs.

Setting persistence involves validation against metadata definitions from Core_Models_User_Setting and Core_Models_General_Configuration, ensuring that values conform to expected types and ranges before database storage. Password settings receive special handling with salted hash generation, while email addresses are validated against RFC-compliant patterns. The controller supports batch setting updates through jsonSaveAction, which processes multiple setting key-value pairs in a single transaction to maintain consistency when interdependent settings are modified together. Integration with Phprojekt_Configuration library provides a programmatic interface for other modules to retrieve setting values, with automatic fallback from user-specific to module-specific to system-wide defaults ensuring that configuration queries always return meaningful values.

### Controllers/HistoryController.php

The Core_HistoryController provides query access to the comprehensive audit trail maintained by the history subsystem, enabling administrators and users to understand how data has evolved over time. The jsonListAction accepts item_id and module_id parameters to retrieve all recorded changes for a specific entity, returning results ordered chronologically with user attribution, field names, old values, new values, action types (add, edit, delete), and timestamps. This audit capability supports compliance requirements in regulated industries where organizations must demonstrate data lineage and change accountability. The history table captures changes automatically through hooks in the Active Record save and delete methods, requiring no explicit instrumentation in business logic code.

The controller implements permission filtering to ensure users only view history for items they have authorization to access, delegating to the item_rights table to determine whether the current user possesses read access for the specified item. Query optimization addresses performance concerns in installations with extensive history data by supporting date range filters and pagination parameters that limit result set sizes. The controller can generate history exports in CSV format for offline analysis, with column formatting that makes old and new values human-readable by referencing field metadata to resolve foreign key identifiers to display names. This history capability has proven valuable during troubleshooting sessions where understanding the sequence of changes leading to an issue enables faster root cause identification.

### Models/User/Setting.php

The Core_Models_User_Setting class defines metadata for user-specific configuration fields including password, confirm password, email, language, time zone, and notification preferences. This class extends Phprojekt_ModelInformation_Default rather than Phprojekt_ActiveRecord_Abstract because it describes field definitions and validation rules rather than representing persisted entities directly. The setFields method invokes fillField for each configurable attribute, specifying field labels, types, tab assignments, positions, and constraints like maximum length and requirement status. Language selection draws from Phprojekt_LanguageAdapter::getLanguageList() to populate a dropdown with available translation options, while timezone selection leverages Phprojekt_Converter_Time::getTimeZones() to provide appropriate timezone offsets.

Password fields are marked as type "password" which signals the frontend to render masked input controls and triggers automatic hashing before persistence. The confirmValue field implements client-side validation that ensures password changes require matching entries in both password and confirm password fields, preventing typos that would lock users out of their accounts. Email validation applies regular expression patterns that verify RFC compliance, rejecting malformed addresses at the presentation layer before they reach the persistence layer. This metadata-driven approach to field definition enables the Core module to maintain consistent validation logic across web forms, API endpoints, and batch import operations, as all entry points consult the same metadata definitions when validating user settings.

### Models/General/Configuration.php

The Core_Models_General_Configuration class defines system-wide configuration fields that establish organizational defaults, beginning with companyName which represents the organization operating the PHProjekt installation. This company name serves multiple purposes including display in the application header, naming the root project node in the project hierarchy, and personalization of notification email templates. The setFields method marks companyName as required with maximum length of 255 characters, enforcing that every installation maintains this fundamental organizational identity. Additional system configuration fields can be added through subclassing or modification of this metadata definition, enabling organizations to track installation-specific values like default project priorities, standard working hours, or approval workflow preferences.

The validateConfigurations method implements business rule validation beyond simple field-level checks, ensuring that configuration changes maintain system invariants. The companyName validation specifically prevents empty values that would leave the organization unnamed, returning translated error messages through Phprojekt::getInstance()->translate() to respect user language preferences. The setConfigurations method persists configuration values to the configuration table with module_id set to 0 to indicate system-wide scope, and implements special handling for companyName by synchronizing it with the root project's title field. This synchronization ensures consistency between the system configuration and the project hierarchy, with the root project serving as the top-level organizational container. Configuration persistence uses Phprojekt_Configuration class which provides key-value storage with support for hierarchical overrides at module and user levels.

## Public API and Interfaces

The Core module exposes its functionality primarily through JSON-based HTTP endpoints that follow REST-like conventions, with each controller providing actions that accept parameters via URL query strings or POST bodies and return JSON-encoded response objects. External code interacts with the Core module through these HTTP APIs when operating in the context of the Dojo frontend, with AJAX requests dispatched to URLs following the pattern /Core/{controller}/{action}. The UserController's jsonGetUsers action exemplifies the query pattern, accepting no required parameters and returning an array of user objects with id and display properties suitable for populating selection widgets. The jsonDetail action accepts an optional id parameter defaulting to 0 for new entity creation, returning both data and metadata that enables dynamic form generation. These dual-purpose endpoints reduce API surface area by consolidating create and edit operations behind a single interface that adapts based on parameter presence.

Programmatic integration occurs through direct instantiation of Core module models by other PHP components within the application, with common patterns including Phprojekt_User_User instantiation for user lookups, Phprojekt_Role_Role queries for permission resolution, and Phprojekt_Module_Module fetches for module catalog access. The authentication subsystem exemplifies this integration pattern by creating Phprojekt_User_User instances during login processing to validate credentials and load user profiles. The Phprojekt_Configuration class provides a programmatic interface to configuration and setting values, with methods like getConfiguration($key) and getSetting($key, $userId) that abstract the hierarchical fallback logic across system, module, and user levels. These programmatic interfaces follow dependency inversion principles where consumers depend on abstract interfaces rather than concrete implementations, enabling test doubles during unit testing and maintaining loose coupling between modules.

The Core module defines several extension points where other modules can integrate with administrative functionality without modifying Core module code. The setting system provides one such extension point where modules register their own setting definitions by creating Classes extending Phprojekt_ModelInformation_Default in their Models directories, with the setting system automatically discovering and incorporating these definitions into the user settings interface. The module catalog registration mechanism provides another extension point where modules create entries in the module table during installation, causing their navigation links to appear in appropriate locations without Core module awareness of specific module implementations. The role-module permission system enables new modules to participate in role-based access control by defining module_id values that appear in permission grant tables, with the Role management interface dynamically generating permission matrices that include both built-in and custom modules.

## Dependencies and Integration

The Core module depends heavily on framework components provided by Zend Framework and the Phprojekt library, establishing itself as a higher-level module that builds upon foundational infrastructure. The Zend_Controller_Action base class provides MVC controller infrastructure including request/response objects, view rendering, and action method dispatch, with all Core controllers extending this hierarchy through the intermediate IndexController. The Zend_Db component supplies database abstraction through PDO with support for parameterized queries, result set objects, and transaction management that Core controllers and models utilize for all persistence operations. Authentication integration relies on Phprojekt_Auth which wraps Zend_Auth to provide session-based identity management with PHProjekt-specific extensions like admin user checking and proxy authentication support.

Data flow within the Core module follows standard PHProjekt patterns where HTTP requests enter through controller action methods, which instantiate model objects to perform business logic and persistence operations, then serialize results to JSON for transmission back to the Dojo frontend. The UserController's save operation exemplifies this flow: the jsonSaveAction inherits from IndexController, which calls getModelObject() to instantiate Phprojekt_User_User, populates the model's properties from POST parameters, invokes the model's save() method to persist changes, and returns success/failure status as JSON. During model save operations, the Active Record infrastructure generates SQL statements, executes them through Zend_Db, and fires post-save hooks that trigger history recording and search index updates. This layered architecture maintains clear separation between HTTP concerns handled by controllers, business logic implemented in models, and infrastructure provided by the framework.

Integration with other PHProjekt modules occurs primarily through shared infrastructure components rather than direct module-to-module communication. The Project module reads user information from tables managed by Core, queries role definitions to resolve permissions, and checks module_id values to determine which modules are active in particular project contexts. The Calendar2 module retrieves user lists for participant selection, validates user permissions before creating events, and records changes in the history table managed by Core. The Timecard module loads user profiles to associate time entries with employees, enforces module-level permissions defined through Core's role system, and synchronizes timezone settings from user configurations. This integration pattern maintains module autonomy where each module can function independently while leveraging shared services, avoiding tight coupling that would complicate testing and evolution of individual modules.

## Data Models and Structures

The Core module manages a comprehensive data model spanning fifteen database tables that represent users, roles, modules, permissions, settings, history, and search infrastructure. The user table serves as the central identity registry with columns for username (unique identifier for authentication), firstname and lastname (display name components), status (active/inactive flag), and admin (boolean indicating administrative privileges). Foreign key relationships connect users to the setting table through user_id, establishing the one-to-many relationship where each user has multiple setting key-value pairs. The role table defines organizational roles with name and parent columns, where parent implements hierarchical role relationships though current code treats roles independently. Junction table user_role (implicit through project_role_user_permissions) establishes the many-to-many relationship between users and roles, with project context determining which roles a user holds in different areas.

The module table catalogs installed modules with columns for name (internal identifier), label (display name), save_type (global/project scope indicator), version (migration tracking), and active (enabled/disabled status). The role_module_permissions junction table implements fine-grained access control by associating roles with modules and specifying access levels as bit flags where values like 1 indicate read access, 2 indicate write access, and combinations like 139 grant multiple permission types simultaneously. The project_module_permissions table determines which modules are available within specific projects, enabling per-project feature customization where some projects may have calendar functionality while others do not. The item_rights table provides item-level permissions with a composite primary key of module_id, item_id, and user_id, storing an access integer that encodes permission flags for the specific user-item combination.

The configuration and setting tables implement hierarchical key-value storage with configuration holding system and module-level defaults while setting stores user-specific overrides. Both tables share similar structure with module_id indicating scope (0 for system-wide, positive integers for specific modules), key_value naming the setting, and value storing the setting content as text. The setting table adds user_id to scope settings per user and identifier to namespace settings by functional area. The history table maintains a comprehensive audit trail with columns for module_id and item_id (identifying the changed entity), user_id (who made the change), field (which field changed), old_value and new_value (before and after states), action (add/edit/delete), and datetime (when the change occurred). This audit structure enables time-travel queries reconstructing entity state at historical points and compliance reporting demonstrating change accountability.

The search infrastructure spans three tables: search_words stores unique words with occurrence counts, search_word_module implements a junction table connecting words to specific module items, and search_display stores cached display strings for search results. This inverted index structure enables fast full-text search across all modules without requiring database-specific full-text search extensions, trading storage space for query performance. The tags table provides a simpler word registry for user-generated tags, while module_tab_relation and tab tables support form organization by grouping related fields into tabs. The database_manager table merits special mention as it implements the meta-programming foundation for the Module Designer, storing field definitions that drive dynamic form generation, validation, and CRUD operations for custom modules.

## Configuration and Settings

The Core module implements a sophisticated three-tier configuration system where system-wide defaults establish organizational standards, module-specific settings override system defaults for particular functional areas, and user-specific settings take ultimate precedence for individualized preferences. System-wide configuration resides in the configuration table with module_id set to 0, storing values like companyName that apply across the entire installation unless explicitly overridden. Module-specific configuration uses positive module_id values corresponding to entries in the module table, enabling modules like Calendar2 or Timecard to define default behaviors that differ from system-wide settings. User-specific settings in the setting table include user_id to scope configuration per user, with the SettingController implementing fallback logic that checks user-specific settings first, then module-specific, finally falling back to system-wide defaults.

Critical configuration options managed through the Core module include language selection (en, de, es) that determines which translation files are loaded for the user interface, timezone settings that control how datetime values are displayed and stored, notification preferences governing which events trigger email alerts, and theme selection for interface customization. The password setting receives special treatment with MD5 hashing applied before storage (though modern deployments should migrate to bcrypt or better), ensuring that plaintext credentials never appear in the database. Email configuration supports both individual user email addresses stored in settings and SMTP server configuration for outbound notification delivery. The configuration system supports arbitrary key-value pairs, enabling modules to define their own configuration needs without requiring Core module modifications, though well-behaved modules should define metadata classes that document their configuration options and validation rules.

## Design Patterns and Principles

The Core module demonstrates extensive application of the Model-View-Controller pattern where controllers handle HTTP request processing and coordinate between models and views, models encapsulate business logic and data persistence, and views render user interfaces. Controllers follow the Single Responsibility Principle by specializing in specific administrative domains—UserController manages users exclusively, RoleController handles roles exclusively, and so forth—avoiding the "god controller" anti-pattern where a single controller attempts to manage all administrative functions. This specialization improves maintainability by creating clear ownership boundaries where modifications to user management logic remain isolated in UserController without risk of inadvertently affecting role or module management.

The Template Method pattern appears in Core_IndexController where preDispatch defines the administrative authorization algorithm while allowing subclass controllers to customize specific aspects through inheritance. The algorithm consistently checks admin status, examines controller and action names, consults a whitelist of public operations, and either permits or denies access based on the decision tree. Subclass controllers inherit this security enforcement automatically without implementing it repeatedly, demonstrating Don't Repeat Yourself principles. The Factory Method pattern manifests in getModelObject where the controller base class provides the model instantiation algorithm while allowing the specific model class to be determined at runtime based on controller name, enabling generic CRUD action implementations that adapt to different entity types.

The Strategy pattern underlies the configuration hierarchy where different resolution strategies apply based on context—user-specific settings for personalization, module-specific settings for functional area customization, system-wide settings for organizational defaults. The SettingController acts as the context that selects appropriate strategies based on query parameters, with each strategy encapsulating its data source and fallback rules. This pattern enables the system to support complex configuration scenarios like "user Alice prefers German but module Calendar2 defaults to showing 24-hour time format across all users" by composing multiple strategies. The Facade pattern appears in how Core module controllers present simplified interfaces to complex subsystems, with UserController's jsonGetUsers hiding the complexity of database queries, Active Record operations, permission filtering, and JSON serialization behind a single method call that returns exactly the data needed for user selection widgets.

The Open-Closed Principle emerges in the module registration system where the Core module's module table and role_module_permissions system remain stable while new modules extend functionality by adding entries to these tables. The Module Designer exemplifies this extensibility by generating modules that participate in existing infrastructure (navigation, permissions, settings) without requiring Core module code changes. The Dependency Inversion Principle appears in how controllers depend on abstract model interfaces (Phprojekt_Model_Interface) rather than concrete implementations, enabling mock objects during testing and supporting the possibility of alternative persistence mechanisms. These design patterns and principles work synergistically to create an administrative module that balances flexibility with consistency, enabling PHProjekt to adapt to diverse organizational needs while maintaining architectural coherence and code quality.
