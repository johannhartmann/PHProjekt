# Component: Project

## Overview

The Project module serves as the organizational backbone of PHProjekt, implementing hierarchical project structures that provide context and access control for all other business functionality within the system. This module transforms the abstract concept of projects into a concrete tree-based data structure where projects can contain subprojects to arbitrary depths, mirroring organizational hierarchies, program structures, or work breakdown schemes. Every piece of work tracked in PHProjekt—whether calendar events, timecard entries, or module-specific items—exists within the context of a project, making the Project module the foundational organizational mechanism upon which the entire application is built. The module's sophisticated permission model enables fine-grained access control where different users hold different roles within different projects, creating flexible security boundaries that adapt to complex organizational structures.

The architectural significance of the Project module extends beyond simple data modeling to encompass the implementation of tree manipulation algorithms, permission inheritance schemes, and module activation policies. The tree structure is not merely a conceptual hierarchy but a physically realized nested set model where each project maintains a path field encoding its complete ancestry, enabling efficient subtree queries without recursive database operations. Permission inheritance flows down the tree, with child projects automatically inheriting access grants from parents unless explicitly overridden, reducing administrative overhead while maintaining security granularity. The module activation mechanism allows different projects to enable different functional modules, so a software development project might activate the Gantt chart module while a consulting project might disable it, creating project-specific feature sets without requiring separate application instances.

The Project module integrates deeply with PHProjekt's core infrastructure including the tree abstraction layer (Phprojekt_Tree_Node_Database) for hierarchical operations, the item rights system for permission grants, and the role-based access control framework for permission templates. Projects serve as the primary dimension for data filtering throughout the application, with the "current project" context determining which items appear in lists, which modules appear in navigation, and which users appear in selection widgets. This pervasive integration means that project selection is not merely a filter but a fundamental shift in application state that reconfigures the entire user experience to show only project-relevant information. The module's controllers handle both traditional CRUD operations through Project_IndexController and RESTful API access through Project_ProjectController, maintaining dual interfaces that serve both the Dojo frontend and potential external integrations.

The technological foundation of the Project module includes standard PHP 5.3+ with Active Record persistence through Phprojekt_Item_Abstract, tree operations through Phprojekt_Tree_Node_Database providing nested set manipulation, and extensive use of junction tables (project_module_permissions, project_role_user_permissions) for many-to-many relationships. The module stores data primarily in the project table with supporting tables for module activation and role assignments, with foreign key relationships ensuring referential integrity. The tree path field uses slash-delimited format (/1/2/5/) enabling efficient SQL LIKE queries for subtree operations while maintaining human-readable encoding. Integration with Zend_Session_Namespace provides caching for frequently accessed permission queries, reducing database load during permission-intensive operations like list filtering where every item requires authorization checking.

The Project module's structure follows PHProjekt's standard modular organization while emphasizing the dual nature of projects as both data entities and organizational containers. The Controllers directory contains two controllers reflecting the dual interface pattern where IndexController extends the Default module's base controller to inherit standard CRUD operations while overriding save and delete to handle tree semantics, while ProjectController extends Phprojekt_RestController to provide a RESTful alternative using HTTP verbs. This dual-controller approach enables the same business logic to be accessed through either traditional action-based URLs or REST-style resource URLs, supporting both the Dojo frontend's preferences and external API consumers' expectations.

The Models directory contains three specialized classes that together implement the complete project permission model. The Project model handles the project entity itself along with tree validation rules that prevent cycles and ensure structural integrity. The ProjectModulePermissions model manages the many-to-many relationship between projects and modules, determining which functional modules are active within specific projects. The ProjectRoleUserPermissions model implements the complex three-way relationship between projects, users, and roles, enabling administrators to assign users to different roles within different projects. This separation of concerns across three models maintains clear responsibilities where Project focuses on entity attributes and tree operations, ProjectModulePermissions focuses on feature activation, and ProjectRoleUserPermissions focuses on access control policies.

## Key Classes and Files

### Models/Project.php

The Project_Models_Project class implements the core project entity with sophisticated tree validation and module management capabilities, extending Phprojekt_Item_Abstract to inherit Active Record persistence, permission integration, and search indexing. The model defines a hasMany relationship to ProjectModulePermissions, establishing the one-to-many association where each project can have multiple module activation records. The class contains approximately 233 lines of carefully crafted code that balance between framework inheritance and project-specific business logic, implementing validation rules that enforce tree integrity constraints not expressible through database constraints alone.

The validateProjectId method implements cycle detection to prevent projects from being saved under themselves or any of their descendants, which would create logical impossibilities in the tree structure. This validation works by instantiating a Phprojekt_Tree_Node_Database wrapper around the current project, then checking if the proposed parent is either the project itself or appears anywhere in its subtree through the recursive _isInTheProject helper method. This algorithmic validation complements database-level constraints, catching errors at the application layer where meaningful error messages can be generated rather than allowing cryptic database errors to propagate. The validation exemplifies defensive programming where data integrity is enforced at multiple layers, creating redundant protections that catch errors even if one layer fails.

The saveModules method orchestrates module activation changes by first deleting all existing project-module associations for the project, then creating new associations based on the submitted module ID array. This delete-then-recreate pattern simplifies the logic compared to calculating diffs between existing and desired states, though at the cost of generating more database operations. The method iterates over the hasMany relationship's collection, invoking delete on each related ProjectModulePermissions instance, then creates new instances through the collection's create method and saves them with appropriate module_id and project_id values. The addModule method provides a complementary operation for adding individual modules without touching existing associations, used primarily when new modules are installed system-wide and need to be added to the root project.

The parentSave method provides a tree-aware save operation that invalidates cached tree structures after successful persistence, ensuring that subsequent tree queries reflect the modified structure. This cache invalidation is critical because the tree widget caches the complete project hierarchy for performance, and stale caches would show users outdated project structures that don't match database reality. The method demonstrates the Active Record pattern's extensibility where domain models can override lifecycle methods to inject custom behavior while inheriting standard persistence mechanics. The tree validation, module management, and cache invalidation together create a comprehensive project model that maintains both data integrity and system consistency across all layers of the architecture.

### Models/ProjectModulePermissions.php

The Project_Models_ProjectModulePermissions class manages the many-to-many relationship between projects and modules, determining which functional modules are active and accessible within specific project contexts. This model extends Phprojekt_ActiveRecord_Abstract to gain standard persistence capabilities while implementing specialized query methods that return module activation status for specific projects. The model's primary responsibility is maintaining the project_module_permissions junction table that contains foreign keys to both project and module tables, creating the links that enable per-project feature customization without requiring module-level modifications.

The getProjectModulePermissionsById method returns a comprehensive view of module activation status by querying the module catalog to retrieve all active modules, then augmenting each module record with an inProject boolean indicating whether that module is activated for the specified project. This data structure enables the frontend to render checkboxes or toggles showing which modules are active, with the complete module list ensuring that administrators can activate additional modules rather than being limited to deactivating existing ones. The method uses a SQL JOIN to efficiently determine activation status, with the query structure (right outer join between permissions and modules) ensuring that all modules appear in results even if they have no permission records for the project.

The deleteModuleRelation method handles cleanup when modules are uninstalled, removing all project-module associations for the specified module ID. This cascade deletion prevents orphaned permission records that would reference non-existent modules, maintaining referential integrity even though explicit foreign key constraints may not be defined. The method exemplifies the active record pattern's expressiveness where deletion logic is implemented through object iteration rather than direct SQL DELETE statements, maintaining object-oriented abstractions even for batch operations. The module activation model's integration with the Project model through the hasMany relationship enables projects to manage their module list through the familiar collection interface rather than requiring direct manipulation of the junction table.

### Models/ProjectRoleUserPermissions.php

The Project_Models_ProjectRoleUserPermissions class implements the most complex data model in the Project module, managing the three-way relationship between projects, users, and roles that enables per-project role assignments. This model determines which users have which roles within which projects, creating the foundation for the permission system's flexibility where a single user might be an administrator in one project, a contributor in another, and have no access to a third. The model contains approximately 149 lines of intricate logic that balance between performance optimization through aggressive caching and flexibility through recursive permission inheritance.

The getProjectRoleUserPermissions method returns the complete role assignment matrix for a project, structured as a nested data structure where each role contains an array of assigned users with their display names. This method executes a complex SQL query joining the project_role_user_permissions table with the user table to retrieve user details, then iterates over results to populate the nested structure. The use of Phprojekt_User_User::getDisplay and applyDisplay demonstrates integration with the user display name configuration system, ensuring that user names appear in the administrator-configured format (e.g., "lastname, firstname" or "firstname lastname") rather than hardcoding a specific format. This query serves the administrative interface where role assignments are displayed and modified.

The saveRelation method orchestrates role assignment changes through a delete-then-recreate pattern similar to module activation, first removing all existing role assignments for the project, then creating new assignments based on submitted data. The method includes sophisticated filtering through getAllowedUsers to ensure that role assignments only apply to users who have system-level access, preventing permission grants to disabled or deleted user accounts. The session-based cache invalidation with namespace pattern ensures that changes to role assignments immediately affect permission calculations, with the method explicitly unsetting session variables that cached previous role lookups. This explicit cache management addresses the challenge of distributed state where both database and session contain permission-relevant data that must remain synchronized.

The fetchUserRole method implements permission inheritance through recursive tree traversal, determining which role a user holds in a project by first checking for explicit assignments, then recursively checking parent projects if no explicit assignment exists. This inheritance model reduces administrative overhead where project hierarchies naturally reflect organizational hierarchies—granting a user admin role on a program project automatically extends that role to all subprojects without requiring individual grants. The aggressive session caching with namespaced session variables optimizes this potentially expensive recursive operation, with cache keys incorporating both project_id and user_id to ensure isolation between different queries. The fallback to role ID 1 (typically "Admin in All") for the root project ensures that permission calculations always return meaningful results even for projects with no explicit assignments.

### Controllers/IndexController.php

The Project_IndexController specializes the Default module's generic IndexController for project-specific operations, particularly the tree-aware save operation that maintains hierarchical integrity. The jsonSaveAction method overrides the base implementation to wrap projects in Phprojekt_Tree_Node_Database objects before invoking Default_Helpers_Save::save, enabling the save helper to apply tree-specific persistence logic including path calculation and parent reference updates. This override demonstrates the Template Method pattern where the overall save workflow (parameter extraction, validation, response formatting) is inherited while the specific model preparation step is customized for tree structures.

The method's handling of the return value from tree save operations addresses a subtle difference between insert and update operations where tree inserts may return wrapper objects rather than IDs directly. The conditional logic that sets showId based on whether the operation is creating or updating ensures that the returned JSON response contains the correct ID for the frontend to use in subsequent operations. This attention to edge cases prevents subtle bugs where new projects would have incorrect IDs in the frontend cache, leading to failed subsequent operations. The controller's coordination with Default_Helpers_Save demonstrates the separation of concerns where controllers handle HTTP concerns (parameter extraction, response formatting) while helpers handle business logic (validation, persistence, relationship management).

The controller inherits numerous action methods from the base IndexController including jsonListAction for retrieving project lists, jsonDetailAction for fetching individual project details, jsonDeleteAction for removing projects, and csvListAction for exporting project data. This inheritance reduces the Project module's code footprint while ensuring consistent behavior across all modules, with the tree-specific overrides applied only where necessary. The controller's integration with setCurrentProjectId ensures that project operations execute within appropriate project context, affecting permission calculations and default value assignments. The dual-interface pattern with both traditional and REST controllers enables the same project business logic to be accessed through different API styles, supporting diverse client needs without duplicating implementation.

### Controllers/ProjectController.php

The Project_ProjectController provides a RESTful API interface to project operations through inheritance from Phprojekt_RestController, implementing standard HTTP verb mappings where GET retrieves projects, POST creates projects, PUT updates projects, and DELETE removes projects. The class contains no custom methods, relying entirely on the behavior inherited from Phprojekt_RestController which delegates to the same Project_Models_Project model used by the traditional controller. This minimal implementation demonstrates the power of framework abstractions where substantial functionality emerges from proper inheritance relationships without requiring module-specific code.

The REST controller's integration with the tree structure happens transparently through the model layer, with the RestController base class invoking the same model methods as the traditional controller. This design ensures consistency where project operations produce identical results regardless of which controller interface clients use, preventing subtle behavioral differences that would complicate client implementations. The REST controller supports content negotiation through HTTP Accept headers, returning JSON or XML based on client preferences, enabling integration with diverse client technologies. The controller exemplifies the Open-Closed Principle where new API styles (REST) can be added through inheritance without modifying existing code (IndexController), supporting evolution without disruption.

### Extension.php and Migration.php

The Project_Extension class provides the hook through which PHProjekt's extension system discovers and loads the Project module's migration capabilities. The extension returns version information through getVersion (currently '6.1.0') and provides access to migration logic through getMigration which instantiates Project_Migration. This extension mechanism enables the module system to query module versions, compare them against database schema versions, and execute appropriate migrations to bring the database into alignment with code expectations. The extension pattern separates module metadata from module implementation, enabling the framework to query module capabilities without loading complete module code.

The Migration class (not shown but referenced) contains the actual schema evolution logic that creates or modifies database tables when the Project module is installed or upgraded. Migrations typically include CREATE TABLE statements for initial installation, ALTER TABLE statements for adding fields in later versions, and data migration logic for transforming data when schema changes require it. The migration system's integration with version tracking ensures that migrations execute exactly once per installation, preventing double-execution errors while enabling reliable upgrades from any previous version. This automated schema management reduces deployment complexity compared to requiring manual SQL script execution, supporting automated deployments and reducing human error in schema evolution.

## Public API and Interfaces

The Project module exposes its functionality through multiple interface layers including traditional action-based HTTP endpoints, RESTful resource URLs, and direct PHP model instantiation for internal integrations. The traditional interface through Project_IndexController follows PHProjekt conventions where URLs like /project/index/json-save accept parameters via POST and return JSON-encoded responses with type, message, and id fields. The jsonListAction accepts filtering parameters including parent project ID for retrieving only direct children, search terms for textual filtering, and date ranges for temporal filtering. The jsonDetailAction accepts an id parameter and returns complete project information including all field values, permission grants, and module activation status, enabling the frontend to render full project forms from a single request.

The RESTful interface through Project_ProjectController maps HTTP methods to operations following REST conventions where GET /project/project/{id} retrieves a project, POST /project/project creates a project, PUT /project/project/{id} updates a project, and DELETE /project/project/{id} removes a project. This REST interface enables integration with REST clients and libraries that understand HTTP semantics, supporting scenarios like mobile applications or external system integrations that prefer standardized REST patterns over action-based endpoints. Both interfaces delegate to the same model layer, ensuring behavioral consistency while accommodating different client preferences. The dual-interface approach demonstrates API design flexibility where the same business logic serves multiple access patterns without duplicating implementation.

Internal integration occurs through direct model instantiation where other PHProjekt modules create Project_Models_Project instances to query project information, check module activation, or determine user roles. The Project model's integration with the tree infrastructure through Phprojekt_Tree_Node_Database enables modules to perform tree operations like finding ancestors, retrieving subtrees, or calculating paths without understanding tree implementation details. The ProjectRoleUserPermissions model's fetchUserRole method is particularly critical for permission calculations, invoked throughout the application whenever code needs to determine what role a user holds in a project. This internal API serves as the foundation for the application-wide project context mechanism where the "current project" ID flows through request processing, affecting filtering, validation, and permission checks across all modules.

## Dependencies and Integration

The Project module depends heavily on the Phprojekt tree infrastructure (Phprojekt_Tree_Node_Database) which implements the nested set model for hierarchical data storage and retrieval. This tree abstraction handles path calculation, subtree queries, ancestor retrieval, and tree validation through a clean API that shields the Project module from tree implementation details. The integration runs deep, with project save operations wrapping Project models in tree node objects, tree node objects delegating persistence to the underlying Active Record model, and tree node caches requiring invalidation after structural changes. This bidirectional relationship creates tight coupling between the Project module and tree infrastructure, though the coupling is managed through well-defined interfaces rather than direct implementation dependencies.

Integration with the permission system occurs through multiple channels including the item_rights table for item-level permissions, the role_module_permissions table for role-based access templates, and the project-specific permission tables (project_module_permissions, project_role_user_permissions) for project-context authorization. The Project module reads from role_module_permissions to determine which permissions roles grant, reads from project_role_user_permissions to determine which roles users hold in projects, and writes to item_rights when projects are created or ownership changes. This multi-table permission model enables fine-grained access control where authorization decisions consider both the item being accessed, the user attempting access, the project providing context, and the role the user holds within that project.

Data flows through the Project module follow tree-aware patterns where operations that modify the tree structure trigger cascading updates to related data. Creating a new project involves not just inserting a project record but also calculating its path based on its parent, granting initial permissions to the creator, inheriting module activations from the parent, and invalidating tree caches to ensure consistency. Deleting a project requires checking whether it has children (some installations prevent deleting non-empty projects, others cascade deletion), removing permission grants, deleting module activations, and removing role assignments. The tree structure's prevalence throughout PHProjekt means that project changes ripple across the entire application, with other modules' data filtered by project context and navigation menus reconstructed based on project hierarchy.

## Data Models and Structures

The Project module's data model centers on the project table which implements a modified nested set pattern through the path field while maintaining adjacency list properties through the project_id parent reference. The table schema includes structural fields (id, project_id, path) that define tree topology, descriptive fields (title, notes) that capture project information, temporal fields (start_date, end_date) that bound project timelines, managerial fields (owner_id, priority, current_status) that track project metadata, and financial fields (complete_percent, budget, hourly_wage_rate) that support project accounting. This comprehensive schema enables the project table to serve as both organizational structure and project management record, though installations focused purely on access control might leave many fields empty.

The path field's slash-delimited format (/1/2/5/) encodes the complete path from root to the current project, enabling efficient subtree queries through SQL LIKE operations like "WHERE path LIKE '/1/2/%'" that retrieve all descendants of project 2. This denormalization trades update complexity for query efficiency, with path values requiring recalculation whenever project parentage changes but enabling subtree retrieval through single queries without recursive CTEs. The project_id field maintains the immediate parent relationship, providing the adjacency list property that simplifies parent access and enables tree traversal algorithms. This dual encoding (nested set via path, adjacency list via project_id) combines the strengths of both approaches while accepting the increased storage and maintenance overhead.

The project_module_permissions table implements a straightforward many-to-many junction with columns for id (primary key), project_id (foreign key to project), and module_id (foreign key to module). This simple structure enables efficient queries for "which modules are active in this project" and "which projects have this module activated" through standard SQL joins. The project_role_user_permissions table implements a more complex three-way relationship with columns for id, project_id, user_id, and role_id, creating associations that specify which role a user holds within a project. The absence of a composite primary key across project_id, user_id, and role_id allows users to potentially hold multiple roles within a project, though application logic typically enforces single-role assignments per user per project.

| Table | Primary Purpose | Key Fields | Relationships |
|-------|----------------|------------|---------------|
| project | Core project entity with tree structure | id, project_id (parent), path, title, owner_id | Parent: self-referential FK; Children: one-to-many |
| project_module_permissions | Module activation per project | id, project_id, module_id | Project: many-to-one; Module: many-to-one |
| project_role_user_permissions | Role assignments per project | id, project_id, user_id, role_id | Project: many-to-one; User: many-to-one; Role: many-to-one |

## Configuration and Settings

The Project module's configuration options primarily concern tree behavior, permission inheritance, and display preferences rather than functional feature flags. The tree configuration includes settings for maximum tree depth to prevent excessively deep hierarchies that would complicate navigation, root project configuration that specifies which project serves as the organizational root, and cycle prevention policies that determine whether validation happens at save time or is enforced through database constraints. While these settings don't appear in dedicated configuration files, they manifest as constants, database constraints, and validation logic distributed throughout the module code.

Permission inheritance configuration determines how role assignments propagate down the project tree, with the fetchUserRole method's recursive logic implementing the inheritance policy. The current implementation automatically inherits roles from parent projects when no explicit assignment exists, reducing administrative overhead in deeply nested project hierarchies. Alternative policies might require explicit assignment at every level or might inherit only specific role types, with the policy encoded in the fetchUserRole method's logic. Module activation inheritance follows similar patterns where new subprojects could automatically inherit parent module activations or could start with clean slates, with the choice affecting how much configuration administrators must perform when creating project structures.

## Design Patterns and Principles

The Project module extensively applies the Composite pattern through its tree structure where projects can contain other projects to arbitrary depths, with each project offering the same interface regardless of whether it has children. This pattern enables uniform treatment where operations on projects work identically whether applied to leaf projects (no children) or branch projects (containing subprojects), simplifying client code that doesn't need to distinguish between cases. The tree traversal operations inherit Composite pattern benefits where operations like "delete project" can recursively apply to entire subtrees through the same interface used for individual projects. The Phprojekt_Tree_Node_Database wrapper reinforces this pattern by providing tree-specific methods (getChildren, getParent, hasChildren) that operate uniformly across the tree structure.

The Strategy pattern appears in permission resolution where different strategies apply based on context—explicit role assignments for projects with direct grants, inherited roles for projects where the user has no direct grant, and default roles for the root project. The fetchUserRole method acts as the context that selects appropriate strategies, with the strategy determined by whether a database record exists for the project-user combination. This pattern enables flexible permission policies where inheritance rules can be modified by changing the strategy selection logic without affecting other components that call fetchUserRole. The session-based caching demonstrates the Proxy pattern where the cached role acts as a proxy for the database-backed role, with the proxy answering queries without database access when possible and deferring to the real subject only when caches miss.

The Facade pattern manifests in how the Project model presents simplified interfaces to complex operations, with methods like saveModules hiding the complexity of delete-then-recreate logic behind a single method call. Callers simply pass an array of module IDs without needing to understand that implementation involves deleting existing associations and creating new ones through the hasMany relationship collection. The validateProjectId facade similarly hides cycle detection complexity behind a simple validation interface that returns either null (valid) or an error message (invalid), abstracting the recursive tree traversal required for cycle detection. These facades reduce coupling between the Project module's public interfaces and its internal implementation strategies, enabling implementation changes without forcing client modifications.

The Separation of Concerns principle guides the distribution of responsibilities across three models where Project handles entity attributes and tree operations, ProjectModulePermissions handles feature activation, and ProjectRoleUserPermissions handles access control. This separation prevents the "god object" anti-pattern where a single class attempts to handle all project-related concerns, instead creating focused classes with clear boundaries and minimal overlap. The principle extends to the controller layer where IndexController handles traditional HTTP interactions while ProjectController handles REST interactions, with both delegating business logic to the same models. This separation enables independent evolution of different concerns—tree algorithms can be optimized without affecting permission logic, permission caching can be modified without changing module activation, and API interfaces can evolve without altering business logic.
