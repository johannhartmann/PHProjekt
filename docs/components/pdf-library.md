# Component: Pdf

## Overview

The Pdf library provides a specialized abstraction layer for generating PDF documents programmatically within the PHProjekt application. This library extends Zend Framework's PDF generation capabilities with PHProjekt-specific functionality designed to simplify common document generation tasks such as creating tabular reports, multiline text blocks, and structured layouts. The library addresses the complexity of PDF coordinate systems, text wrapping, page overflow handling, and formatting through a high-level API that enables developers to describe document content declaratively rather than imperatively managing low-level drawing operations.

The Pdf library serves as the primary mechanism for generating exportable reports and printable documents from PHProjekt data. While the application's primary user interface is web-based, many business workflows require physical or archival documents in standardized formats. The Pdf library enables these workflows by transforming model data, grid views, and form layouts into professionally formatted PDF documents suitable for printing, archiving, or distribution. The library's design emphasizes ease of use over comprehensive functionality, providing simplified interfaces for common document structures (tables, text blocks, information boxes) rather than exposing the full complexity of PDF rendering primitives.

The library is built on top of Zend_Pdf, a comprehensive PDF generation library included in the Zend Framework. Rather than replacing Zend_Pdf, the Phprojekt Pdf library extends it with convenience methods and abstractions that handle common challenges in PDF generation. The library manages text wrapping and reflow, automatic page breaks when content exceeds page boundaries, consistent spacing and padding, table rendering with automatic column width calculations, and proper handling of UTF-8 encoded text including multibyte characters. These abstractions enable developers to generate PDFs without deep knowledge of PDF coordinate systems, font metrics, or page geometry calculations.

A critical architectural aspect of the Pdf library is its use of a prototype-based template system. Rather than requiring procedural code that calls drawing methods sequentially, the library enables document structure to be described as nested data structures (arrays) that specify content type, positioning, dimensions, and formatting. The parseTemplate method interprets these prototype structures, orchestrating the rendering of multiple content elements (tables, text blocks, information boxes) across potentially multiple pages. This declarative approach separates document structure definition from rendering logic, enabling document templates to be defined in configuration files or database records and reused across different contexts without code changes.

## Component Structure

| Path | Purpose |
|------|---------|
| `library/Phprojekt/Pdf/Page.php` | Extended PDF page class with drawing and layout methods |
| `library/Phprojekt/Pdf/Table.php` | Table rendering manager handling multi-page tables |
| `library/Phprojekt/Pdf/Table/Row.php` | Table row representation with column collection |
| `library/Phprojekt/Pdf/Table/Column.php` | Table cell with text, width, alignment, and rendering |

The Pdf library follows a hierarchical structure reflecting the composition pattern inherent in document layouts. At the top level sits the Page class, which extends Zend_Pdf_Page and serves as the canvas on which all content is drawn. Below that, the Table class manages collections of rows and handles pagination when table content spans multiple pages. The Row class contains collections of columns and manages row-level styling like header formatting. At the bottom of the hierarchy, the Column class represents individual table cells with their text content, dimensions, and alignment properties.

This organizational structure mirrors the conceptual model of PDF documents where pages contain tables, tables contain rows, and rows contain cells. The structure enables natural composition where complex documents are built by assembling simpler components, and it facilitates code reuse where common rendering logic (like text wrapping or border drawing) is implemented once in the appropriate class and inherited or delegated to from higher levels. The separation of concerns across classes makes the codebase easier to understand and modify, with each class having clear responsibilities aligned with the document element it represents.

## Key Classes and Files

### Phprojekt_Pdf_Page

The Page class in `Pdf/Page.php` serves as the central component of the Pdf library, extending Zend_Pdf_Page with PHProjekt-specific functionality for document layout and content rendering. This class maintains state about the current drawing position (`freeLineX` and `freeLineY`), page margins (borderTop, borderRight, borderBottom, borderLeft), and formatting parameters (lineHeight, tablePadding, paragraphPadding). These state variables enable the class to track where the next element should be drawn, automatically advancing the position as elements are added and managing the transition to new pages when content exceeds page boundaries.

The class defines several constants that standardize measurements and formatting across the library. The `PT_PER_CM` constant (28.346456692913385826771653543307) provides the conversion factor between points (the PDF coordinate unit) and centimeters, enabling measurements to be specified in more intuitive units. The `DEFAULT_FONT_SIZE` constant (10) establishes a baseline font size for document text. The `HEADER_GRAY_LEVEL` constant (0.9) defines the gray fill color used for table headers, ensuring consistent styling across all tables. These constants centralize formatting decisions and make it easy to adjust styling across the entire library.

The `setBorder()` method establishes page margins that define the usable content area within the physical page boundaries. This method accepts one to four parameters following CSS-style margin specification: a single parameter sets all margins equally, two parameters set top/bottom and left/right, three parameters set top, left/right, and bottom, and four parameters set all margins individually. The method automatically initializes the free line position to the top-left corner of the content area, positioning the cursor for subsequent drawing operations. This automatic positioning simplifies content addition by eliminating the need for callers to manually calculate initial positions.

The `addTable()` method provides high-level table rendering functionality, accepting a tableInfo array that specifies table structure including rows, columns, text content, widths, and formatting. The method creates a Phprojekt_Pdf_Table instance, populates it with rows and columns based on the array structure, and calls the table's render method which handles the actual drawing and pagination. The method returns an array of pages that contain the rendered table, enabling callers to add the pages to their PDF document. This array-based API design enables table structure to be defined declaratively as data rather than imperatively through method calls, supporting template-based document generation.

The `addFreetext()` method handles multiline text rendering with automatic word wrapping, accepting a freetextInfo array specifying the text lines, position, font size, and width. The method uses the internal `drawMultilineText()` method which breaks text into lines that fit within the specified width, handling word boundaries and explicit line breaks (newlines in the input text). The method updates the freeLineY position to reflect the space consumed by the text, enabling subsequent content to be positioned correctly below the text block. This automatic position management is a key convenience feature that simplifies sequential content addition.

The `parseTemplate()` method implements the declarative template system, accepting a prototype array that describes a complete document structure. The prototype includes font specification, default font size, and an array of elements where each element specifies a type ('table', 'freetext', 'infoBox') and type-specific parameters. The method iterates through elements, dispatching to appropriate rendering methods based on type, and collects all generated pages into a return array. This template-based approach enables document structures to be defined in configuration files or database records, supporting dynamic document generation where document structure varies based on user preferences or data characteristics.

The `drawMultilineText()` method implements sophisticated text layout, breaking input text into lines that fit within specified width constraints while respecting word boundaries. The method calculates character widths using font metrics, accumulating word widths until the next word would exceed the line width, then starting a new line. Special handling for newline characters in the input enables explicit line breaks, and paragraph padding is added between input lines to create visual separation. The method updates the freeLineY position to account for the rendered text height, maintaining accurate position tracking for subsequent content.

The `getVariableText()` method performs text layout calculations without actually drawing, returning information about how text would be rendered including the number of lines, dimensions, and the specific word groupings for each line. This calculation-only method enables the "test render" pattern used throughout the library where dimensions are calculated before actual rendering, enabling layout decisions like page breaks to be made intelligently. The method handles complex scenarios like words containing explicit newlines (splitting the word across multiple lines) and tracks paragraph counts to calculate appropriate spacing.

The `drawVariableText()` method combines `getVariableText()` with actual rendering, drawing text with specified alignment (left, right, or center). The method calculates text position based on alignment: left-aligned text is positioned at the left edge plus padding, right-aligned text is positioned such that its right edge aligns with the column right edge minus padding, and center-aligned text is positioned at the horizontal center of the available width. This alignment handling is essential for professional table rendering where numeric columns are typically right-aligned and text columns are left-aligned.

### Phprojekt_Pdf_Table

The Table class in `Pdf/Table.php` manages the rendering of tabular data across potentially multiple pages, handling the complex logic required for automatic pagination when table rows exceed page boundaries. The class maintains references to the current page, the table's starting position, and a collection of rows to be rendered. The table's design follows the composite pattern where the table aggregates rows, rows aggregate columns, and each level manages its own rendering while delegating to the next level.

The `addRow()` method accumulates rows into the table's internal collection, building up the table structure before rendering occurs. This accumulation pattern separates table construction from table rendering, enabling the table structure to be defined completely before any drawing occurs. The separation is important because optimal layout decisions (like page breaks) require knowledge of the complete table structure rather than just the rows seen so far. The method's simple signature (accepting a Row object) reflects the composite pattern where the table doesn't need to know the internal structure of rows—it simply holds them for later rendering.

The `render()` method orchestrates table drawing, iterating through rows and rendering each one while checking if the row fits on the current page. Before rendering each row, the method calls the row's `testRender()` method to calculate how much vertical space the row will consume. If rendering the row would exceed the bottom page margin, the method creates a new page (using the Phprojekt_Pdf_Page copy constructor that preserves formatting settings), adds it to the pages collection, and continues rendering on the new page. This automatic pagination ensures tables can span multiple pages without requiring caller intervention.

The render method's handling of new pages demonstrates careful attention to state management. When creating a new page, the method preserves the current font and font size by calling `getFont()` and `getFontSize()` before creating the page, then calling `setFont()` on the new page with the preserved values. This ensures formatting consistency across page boundaries—text on page 2 of a table uses the same font and size as text on page 1. The method resets the Y coordinate to the top margin of the new page, positioning subsequent rows appropriately. The return value (an array of additional pages) enables callers to incorporate the new pages into their document.

After rendering all rows, the render method updates the last page's freeLineY position to reflect the space consumed by the table. This position update enables content added after the table to be positioned correctly below the table rather than overlapping it. The calculation accounts for row height based on font size and line height, ensuring accurate spacing. This automatic position management is a key benefit of the high-level API—callers don't need to manually calculate positions based on table dimensions.

### Phprojekt_Pdf_Table_Row

The Row class in `Pdf/Table/Row.php` represents a single row within a table, containing a collection of columns and managing row-level formatting such as header styling. The class follows the composite pattern, aggregating Column objects and coordinating their rendering while managing row-specific concerns like height calculation and border drawing. The distinction between regular rows and header rows is maintained through the `$_isHeader` boolean property, which controls formatting in subordinate columns.

The `addColumn()` method accumulates columns into the row's internal collection, mirroring the `addRow()` pattern in the Table class. This accumulation enables row structure to be defined before rendering, supporting the calculation-before-rendering pattern that enables intelligent layout decisions. The method's signature (accepting a Column object) maintains the composite pattern's encapsulation where rows don't need to know column internals—they simply aggregate and coordinate them.

The `render()` method orchestrates column rendering, iterating through columns and calling each column's render method while tracking the maximum column height. Since columns in a row may have different heights (due to text wrapping differently based on column width and content), the row must determine its height as the maximum of its column heights rather than assuming uniform height. The method first calls `renderBorder()` to draw row borders, then renders column content, ensuring borders are drawn before content so content appears on top.

The `testRender()` method calculates row height without actual rendering, calling `testRender()` on each column and returning the maximum height. This calculation-only method is crucial for pagination logic—the Table's render method needs to know how tall a row will be before deciding whether it fits on the current page. The separation of calculation from rendering enables this "look-ahead" capability without the cost of rendering content that might need to be discarded and re-rendered on a different page.

The `renderBorder()` method delegates border rendering to columns, iterating through columns and calling each column's `renderBorder()` method with appropriate parameters including the calculated row height and header status. This delegation pattern keeps border-drawing logic in the Column class (which knows its own width and needs to draw its portion of the row border) while the Row coordinates the overall border appearance and passes down row-level information like header status.

The `setHeader()` method marks the row as a header row by setting the `$_isHeader` property to true. This simple method has significant rendering implications—columns check their containing row's header status and apply special formatting (gray background) to header cells. This approach maintains the single responsibility principle where the Row class knows whether it's a header while the Column class knows how to render header formatting, with the Row passing its header status down to columns during rendering.

### Phprojekt_Pdf_Table_Column

The Column class in `Pdf/Table/Column.php` represents an individual cell within a table row, encapsulating the cell's text content, dimensions, alignment, and rendering logic. This class is the most granular component in the table hierarchy and handles the details of text layout, wrapping, and border rendering. The class maintains protected properties for height, width, text content, character encoding, and alignment, exposing these through accessor methods that support method chaining.

The `setText()` method sets the column's text content and encoding, accepting a string and optional encoding specification (defaulting to UTF-8). The method returns `$this` to enable method chaining, supporting the fluent interface pattern where column configuration can be expressed as a chain of method calls: `$column->setText('Content')->setWidth(100)->setAlignment('right')`. This pattern is used extensively in the table construction code where columns are configured through chained calls before being added to rows.

The `setWidth()` method establishes the column's width in points, determining how much horizontal space the column occupies and how text wrapping should occur. The width is a critical parameter that affects text layout—narrow columns require more aggressive wrapping with more lines, while wide columns enable text to flow more naturally. The method uses the fluent interface pattern, returning `$this` to support chaining. The width is set externally (typically from table definition arrays) rather than calculated automatically, giving callers control over column proportions.

The `setAlignment()` method configures horizontal text alignment within the column, accepting 'left', 'right', or 'center' as values. This alignment is applied during rendering when calling the page's `drawVariableText()` method. The method checks for null before updating the alignment property, enabling the alignment to remain at its default ('left') when not explicitly specified. This null-safe pattern allows optional parameters in table definition arrays where omitting alignment means using the default.

The `render()` method performs actual column rendering by calling the page's `drawVariableText()` method with the column's text, dimensions, and alignment. The method receives the calculated text height from `drawVariableText()` and stores it plus padding in the `$_height` property, making the actual rendered height available to the containing row for height calculation. This height feedback is essential for row border rendering which needs to match the actual rendered content height rather than an estimate.

The `testRender()` method calculates column dimensions without rendering, calling the page's `getVariableText()` method to determine how text would lay out given the column's width and content. This calculation method is used by row and table pagination logic to determine whether content fits on the current page. The method sets the column's height property based on calculated dimensions, making the "test rendered" height available for pagination decisions. The separation of calculation from rendering is a key architectural pattern that enables intelligent layout.

The `renderBorder()` method draws the column's border, creating a rectangle around the column's bounds. For header columns, the method fills the rectangle with a gray background before drawing the border stroke, creating the visual distinction for header rows. The method uses Zend_Pdf_Color_GrayScale objects to specify fill and stroke colors, and uses the page's `drawRectangle()` method with appropriate draw modes (SHAPE_DRAW_FILL for filled rectangles, SHAPE_DRAW_STROKE for outlined rectangles). The careful attention to drawing order (fill before stroke) ensures correct visual appearance.

## Public API and Interfaces

The Pdf library exposes its public API primarily through the Page class's high-level methods and the prototype-based template system. The typical usage pattern begins with creating a Phprojekt_Pdf_Page instance (or using Zend_Pdf to create a complete PDF document with pages), then calling methods like `addTable()` or `addFreetext()` to add content. The Page class's fluent interface and automatic position management enable sequential content addition without complex coordinate calculations. The setBorder method establishes margins, and subsequent content additions automatically flow within the bordered region with automatic position tracking.

The template-based API accessed through `parseTemplate()` provides a higher-level abstraction where entire document structures are described as arrays. The prototype array format includes a 'font' specification (e.g., Zend_Pdf_Font::FONT_HELVETICA), a 'fontSize' specification, and numbered entries for each content element. Each element has a 'type' field ('table', 'freetext', or 'infoBox') and type-specific parameters. This declarative API enables document structures to be stored as data rather than code, supporting scenarios where documents are configured by end users or generated from database-stored templates. The API returns arrays of pages, which can be added to Zend_Pdf documents using standard Zend_Pdf methods.

The table rendering API uses nested array structures to describe table content. A table definition array includes optional 'startX' and 'startY' coordinates (defaulting to margins), optional 'fontSize' and 'lineWidth' specifications, and a 'rows' array containing row definitions. Each row is an array of cell definitions plus an optional 'isHeader' boolean. Each cell definition includes 'text' (the cell content), 'width' (in points), and optional 'align' (left, right, or center). This array-based API separates data from presentation, enabling table content to come from model arrays or database queries without transformation.

The method chaining pattern appears in the Column class where setText, setWidth, and setAlignment return `$this`, enabling fluent configuration: `$column->setText('Value')->setWidth(100)->setAlignment('right')`. This pattern reduces boilerplate in table construction code where columns are configured and immediately added to rows. The pattern is particularly valuable when constructing tables programmatically from loops, as it enables concise single-expression column creation and configuration.

## Dependencies and Integration

The Pdf library has a fundamental dependency on Zend_Pdf, the PDF generation library included in the Zend Framework. The Phprojekt_Pdf_Page class extends Zend_Pdf_Page, inheriting all the low-level drawing capabilities (drawText, drawRectangle, drawLine, setFont, setFillColor) while adding higher-level convenience methods. This inheritance relationship means the Pdf library requires Zend_Pdf to be available and compatible with the version of Zend Framework used by PHProjekt. The library uses Zend_Pdf classes such as Zend_Pdf_Font for font management and Zend_Pdf_Color_GrayScale for color specification.

The library integrates with PHProjekt's character encoding handling through consistent use of UTF-8 as the default encoding and support for encoding parameters in all text-handling methods. The library uses PHP's iconv function to convert text from specified encodings to UTF-16BE (the encoding used internally by PDF fonts) before calculating character widths and rendering glyphs. This encoding support ensures that documents containing international characters, accented letters, or non-Latin scripts render correctly in generated PDFs. The library's default encoding parameter of 'UTF-8' aligns with PHProjekt's application-wide use of UTF-8 for text storage and processing.

The Pdf library integrates with controller code through direct instantiation and method calls. Controllers that need to generate PDF reports create Zend_Pdf documents, create Phprojekt_Pdf_Page instances, add content through the page methods, and send the resulting PDF to clients through appropriate HTTP headers. The integration pattern typically involves calling `parseTemplate()` with a document structure array built from model data, receiving back an array of pages, adding those pages to a Zend_Pdf document, and outputting the document with headers specifying content type 'application/pdf' and content disposition 'attachment'.

The library has minimal dependencies on other PHProjekt components, operating primarily through the Zend Framework. This independence makes the Pdf library relatively portable and testable—it doesn't require database connections, session management, authentication, or other application infrastructure. The library's focused scope (PDF generation) and reliance on a stable external dependency (Zend_Pdf) contribute to its maintainability and longevity, as changes in other PHProjekt subsystems are unlikely to necessitate changes to the Pdf library.

## Data Models and Structures

The Pdf library defines several data structures through its prototype and table definition arrays. The prototype structure is an associative array with keys 'font' (a Zend_Pdf_Font constant like Zend_Pdf_Font::FONT_HELVETICA), 'fontSize' (an integer point size), and numbered keys (0, 1, 2...) containing element definitions. Each element definition includes a 'type' key ('table', 'freetext', or 'infoBox') and type-specific keys. This structure enables complete document specifications to be represented as serializable data that can be stored in databases, configuration files, or generated dynamically from application state.

The table definition structure includes keys 'type' ('table'), optional 'startX' and 'startY' positioning (in points), optional 'fontSize' (integer), optional 'lineWidth' (float), and required 'rows' (array of row definitions). Each row definition is an array where cells are represented as associative arrays with keys 'text' (string), 'width' (integer or float in points), and optional 'align' (string: 'left', 'right', or 'center'). Header rows include an additional 'isHeader' key set to true. This nested structure naturally represents the table hierarchy (table contains rows, rows contain cells) while remaining simple enough to construct programmatically from model data.

The freetext definition structure includes keys 'type' ('freetext'), optional 'startX' and 'startY' positioning, optional 'fontSize', optional 'width' (defaulting to full content width between margins), and required 'lines' (array of strings where each element represents a line of text to render). Multiple lines in the array are rendered with paragraph spacing between them, enabling structured text content like lists or multi-paragraph blocks. The structure's simplicity reflects freetext's straightforward nature—it's essentially text rendering with automatic wrapping.

The text layout structure returned by `getVariableText()` includes keys 'width' (the effective width used for layout), 'height' (the total height including all lines and paragraph spacing), and 'lines' (an array of line information where each element is an array containing the words for that line, the X coordinate, and the Y coordinate). This structure encapsulates all the information needed to render the text, and its separation from actual rendering enables the "test render" pattern where layout calculations happen independently of drawing operations. The structure demonstrates the library's separation of layout calculation from rendering execution.

## Configuration and Settings

The Pdf library uses class constants and public properties for configuration rather than external configuration files or database settings. The Phprojekt_Pdf_Page class defines constants for common values: PT_PER_CM for unit conversion, DEFAULT_FONT_SIZE for base font sizing, and HEADER_GRAY_LEVEL for header cell background color. These constants can be referenced when configuring pages but cannot be changed without modifying the class, reflecting the design decision that these are implementation defaults rather than deployment-specific settings.

The Page class exposes several public properties that control layout behavior: borderLeft, borderRight, borderTop, borderBottom define page margins in points, freeLineX and freeLineY track the current drawing position, textWidth specifies the default width for freetext, lineHeight controls line spacing as a multiple of font size (default 1.4), tablePadding specifies padding within table cells in points (default 5), and paragraphPadding specifies vertical spacing between paragraphs in points (default 5). These properties are publicly accessible, enabling callers to customize layout behavior per-page or even mid-page by assigning new values.

The configuration approach through public properties provides flexibility while maintaining simplicity. Callers can adjust layout parameters as needed without complex configuration objects or builder patterns, simply assigning to page properties: `$page->tablePadding = 10;` to increase cell padding, or `$page->lineHeight = 1.2;` to tighten line spacing. This direct property access reduces abstraction overhead and makes the effects of configuration changes immediately apparent in the code. The defaults (defined in property initializers) are suitable for typical documents, so many uses of the library require no configuration at all.

The template-based approach enables additional configuration through the prototype array structure. Each element in a template can specify local font size, positioning, and formatting that overrides defaults. This element-specific configuration enables mixed formatting within documents, like larger fonts for headings or adjusted positioning for sidebars, without requiring code to manually manage font changes and position calculations. The configuration is data-driven, enabling document formatting to be controlled by users or administrators through UI-configured templates.

## Design Patterns and Principles

The Pdf library extensively employs the Composite pattern through its table-row-column hierarchy. The Table class aggregates Rows, Rows aggregate Columns, and each level can be treated uniformly through methods like `render()` and `testRender()` that cascade down the hierarchy. This pattern enables complex table structures to be represented as trees of objects that can be manipulated and rendered recursively. The pattern also supports future extensibility—new cell types could be added by creating Column subclasses, and new table types could be added by creating Table subclasses, without requiring changes to existing code.

The Template Method pattern appears in the relationship between test rendering and actual rendering. Both Table and Column classes implement `testRender()` methods that calculate layout without drawing, and `render()` methods that perform actual drawing. The overall structure (calculate layout, check if it fits, position it) is the template that remains constant, while the specific calculations and drawing operations vary between classes. This pattern enables the pagination logic to follow a consistent approach across different content types while allowing each type to implement its specific layout and rendering algorithms.

The Fluent Interface pattern appears in the Column class's setter methods which return `$this` to enable method chaining. This pattern makes column configuration code more readable and concise, especially when constructing tables programmatically: `$column->setText('Value')->setWidth(100)->setAlignment('right')` expresses configuration as a single logical operation rather than multiple disconnected statements. The pattern is particularly valuable in contexts where objects are configured and immediately used, reducing the need for intermediate variables and improving code flow.

The Decorator pattern is implicit in how Phprojekt_Pdf_Page extends Zend_Pdf_Page, adding functionality (automatic position tracking, text wrapping, table rendering) without modifying the base class. The Page class decorates Zend_Pdf_Page with higher-level operations while preserving access to all the low-level drawing primitives. This decoration enables the library to provide both high-level convenience (through methods like addTable) and low-level control (through inherited methods like drawLine) in a single interface, allowing callers to mix abstraction levels as needed.

The Library pattern is evident in the overall design where the Pdf library provides reusable functionality (PDF generation) as a self-contained package with minimal dependencies on the application. The library can be understood and used without deep knowledge of the rest of PHProjekt, and it could theoretically be extracted and used in other PHP applications with minimal modifications. This separation of concerns improves maintainability by isolating PDF generation logic from application logic, and it improves testability by enabling the library to be tested independently of the full application stack.

The Separation of Concerns principle is reflected in the division of responsibilities across classes: Page handles layout and positioning, Table handles pagination, Row handles height calculation and border coordination, Column handles text wrapping and cell rendering. Each class has a focused responsibility aligned with the document element it represents, avoiding the god object antipattern where one class tries to handle all aspects of PDF generation. This separation makes the codebase easier to understand, test, and modify, as changes to cell rendering don't require understanding pagination logic, and vice versa.
