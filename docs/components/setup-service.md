# Component: Setup

## Overview

The Setup service provides a comprehensive installation and configuration wizard for initializing new PHProjekt 6 installations and migrating data from legacy PHProjekt 5.x systems. This standalone service operates independently of the main application, running before the application's configuration file exists and guiding administrators through the multi-step process of database configuration, user account creation, directory setup, schema installation, optional data migration, and final system initialization. The Setup service embodies a progressive disclosure approach where each installation step builds upon the previous one, validating configuration at each stage before proceeding to ensure that errors are caught early and that the installation process can be safely restarted from any point.

The Setup service architecture separates presentation logic (controllers and views) from business logic (models), enabling the complex installation workflow to be tested independently of the web interface. The service operates through a series of JSON-based API endpoints that return both status information and HTML fragments for rendering, supporting a single-page application interface where users progress through installation steps without full page reloads. This AJAX-based approach provides immediate feedback on configuration errors and enables the interface to remain responsive during long-running operations like database schema creation or data migration from PHProjekt 5.x installations.

A distinctive characteristic of the Setup service is its stateful operation through Zend_Session namespaces, accumulating configuration choices across multiple HTTP requests until the final installation step when all settings are written to the configuration file and database. This session-based state management enables validation at each step without premature commitment of settings, allows users to navigate backward through setup steps to correct errors, and ensures that incomplete installations don't leave the system in an inconsistent state. The service maintains separate session namespaces for database credentials, user passwords, private folder paths, and migration state, isolating different aspects of configuration to prevent cross-contamination of settings.

The Setup service includes sophisticated migration capabilities that transform PHProjekt 5.x installations into PHProjekt 6 format, handling schema differences, data model changes, permission model evolution, and feature deprecation. The migration system processes users, groups, projects, permissions, timecard entries, contracts, and vacation records through a series of transformation steps that map old identifiers to new ones, convert serialized permission structures to the new rights system, and preserve data relationships across the version boundary. The migration architecture uses batch processing with configurable chunk sizes to handle large datasets without exhausting memory, and maintains progress state in sessions to enable incremental migration of different modules.

## Component Structure

| Path | Purpose |
|------|---------|
| `htdocs/Setup/Controllers/IndexController.php` | Controller handling setup wizard HTTP requests and orchestration |
| `htdocs/Setup/Models/Setup.php` | Core setup business logic for validation and installation |
| `htdocs/Setup/Models/Migration.php` | PHProjekt 5.x to 6.0 data migration engine |
| `htdocs/Setup/Models/Config.php` | Configuration file generation and formatting |
| `htdocs/Setup/views/` | PHTML templates for setup wizard UI screens |

The Setup service follows a Model-View-Controller architecture where the controller acts as a thin orchestration layer that delegates actual work to model classes. The IndexController handles HTTP request routing, parameter sanitization, session management, and response formatting, while the Setup model encapsulates server validation, database connection testing, directory permissions checking, and installation execution. The Migration model implements an entirely separate concern (migrating from PHProjekt 5.x) with its own complex state management and transformation logic, demonstrating proper separation of concerns where unrelated functionality is isolated in distinct classes.

The organizational structure reflects a deliberate isolation of setup functionality from the main application, with Setup residing in its own directory under htdocs rather than being integrated into the main application structure. This isolation enables the Setup service to function when the application itself cannot run (such as when configuration.php doesn't exist), and it simplifies security considerations by allowing the entire Setup directory to be removed or protected after installation completes. The view templates use simple PHTML format rather than sophisticated templating engines, keeping dependencies minimal and ensuring the setup wizard can render even if Zend Framework components fail to initialize fully.

## Key Classes and Files

### IndexController

The IndexController in `Controllers/IndexController.php` orchestrates the multi-step installation wizard, providing JSON API endpoints for each installation phase. The controller implements actions for displaying forms (jsonDatabaseFormAction, jsonUsersFormAction, jsonFoldersFormAction, jsonTablesFormAction, jsonMigrationFormAction) and processing submitted data (jsonDatabaseSetupAction, jsonUsersSetupAction, jsonFoldersSetupAction, jsonTablesSetupAction, jsonMigrateSetupAction, jsonFinishAction). Each action follows a consistent pattern: sanitize request parameters using the Cleaner library, delegate validation and processing to the Setup or Migration model, capture success or error status, render an appropriate template fragment, and return JSON containing the status, message, and template HTML through the returnContent helper method.

The controller's init method performs essential preprocessing for all actions, disabling view rendering through the viewRenderer helper, initializing view variables for messages and errors, retrieving the list of modules available for migration through Migration::getModulesToMigrate(), and instantiating the Setup model while capturing any initialization errors. This centralized initialization ensures consistent setup across all actions and provides early error detection for environmental problems. The controller defines default values as class constants (DEFAULT_DBHOST, DEFAULT_DBUSER, DEFAULT_DBNAME, DEFAULT_PORT, DEFAULT_USE_EXTRA_DATA, DEFAULT_DIFF_TO_UTC) that pre-populate form fields with sensible defaults, reducing the configuration burden for typical installations.

The indexAction implements the entry point for the setup wizard, destroying any existing session through Zend_Session::destroy() to ensure a clean slate, calling the Setup model's checkServer method to validate PHP version and extensions, and rendering the initial server validation screen. This action uniquely among setup actions uses the standard view rendering mechanism rather than AJAX, establishing the HTML page structure that subsequent AJAX requests will populate. The returnContent method formats responses in a specific JSON structure prefixed with "{}&&(" to prevent JSON hijacking attacks where third-party sites might attempt to read sensitive setup data by including the setup script as a script tag.

### Setup Model

The Setup model in `Models/Setup.php` implements core installation business logic including server validation, database configuration, user management, directory setup, and schema installation. The checkServer method performs comprehensive validation of the server environment by calling Phprojekt::checkExtensionsAndSettings to verify PHP version meets minimum requirements, required extensions (pdo_mysql, session, pcre, etc.) are loaded, and PHP configuration settings (magic_quotes_gpc off, safe_mode off, etc.) are correctly configured. The method throws exceptions when critical requirements aren't met, provides warning messages for recommended but non-critical settings, and performs additional checks like detecting whether the installation is running in a subdirectory rather than a virtual host.

The database validation and storage methods (validateDatabase, saveDatabase) test database connectivity by attempting to establish a Zend_Db connection with provided credentials, catching connection exceptions and converting them to user-friendly error messages. The validation method performs preliminary checks that required parameters aren't empty before attempting connection, providing fast feedback on incomplete forms. The saveDatabase method stores validated credentials in a Zend_Session_Namespace for later retrieval during installation, demonstrating the session-based state accumulation pattern that enables multi-step configuration without requiring configuration file commits at each step.

The user management methods (validateUsers, saveUsers) validate password requirements for admin and test accounts, ensuring passwords aren't empty, passwords match their confirmations, and admin and test passwords are different. These validations enforce security requirements while enabling administrators to establish known credentials during installation. The folder validation and creation methods (validatePrivateFolder, writeFolders) implement sophisticated logic for establishing the private data directory, proposing a default location outside the document root through getProposedPrivateFolderPath, warning administrators when they choose locations inside the document root through a confirmation workflow, and creating required subdirectories (logs, upload, tmp, webdav, application) with appropriate permissions.

The install method orchestrates schema creation and initial data loading by instantiating a Phprojekt_DbParser with the database connection and options indicating whether to include example data, calling parseData with the application directory to discover and execute SQL scripts and CSV data files, updating the admin and test user passwords in the database with MD5 hashes, and returning the parser's messages indicating what was created. The method uses output buffering to suppress parser debug output, ensuring clean JSON responses. The finish method completes installation by checking directory permissions through _checkPrivateDirRights and cleaning up session data and cookies through _deleteSessionAndCookies, preparing the system for first use.

### Migration Model

The Migration model in `Models/Migration.php` implements a sophisticated data migration engine for converting PHProjekt 5.x installations to version 6.0 format. The constructor accepts a config.inc.php file path from the PHProjekt 5.x installation, validates the file contains PHProjekt 5.x configuration, establishes connections to both the old database (for reading) and new database (for writing), and initializes mapping arrays that track identifier conversions between versions. The class maintains extensive state through properties like $_users mapping old user IDs to new IDs, $_projects mapping old project IDs to new IDs, $_groups mapping old group IDs to new project IDs, $_userKurz mapping user shortnames to IDs, and $_groupsUsers mapping groups to member lists.

The migrateSystem method orchestrates core data migration through a sequence of method calls: _migrateUsers converts user accounts while handling the special cases of root becoming admin and generating usernames based on the PHPR_LOGIN_SHORT configuration, _migrateGroups transforms PHProjekt 5.x groups into root-level projects in the hierarchical project structure, _migrateGroupsUserRelations establishes user access to group projects, _migrateProjects migrates the project hierarchy while handling parent dependencies through iterative processing, and _executeItemRightsInsert writes accumulated permission data in batch for performance. The migration accumulates item rights in memory (_dbItemRightValues array) until reaching a threshold (200,000 entries) then executes batch inserts, balancing memory usage against insert performance.

The migrateTimecard method implements complex timecard migration logic that combines PHProjekt 5.x's separate timecard (clock in/out) and timeproj (project booking) tables into PHProjekt 6.0's unified timecard structure. The migration processes each user's data by loading all timecard clock entries and timeproj bookings, organizing them by date, calculating actual worked minutes from clock times, distributing worked time across project bookings using a greedy algorithm, handling gaps by allocating unbilled time to the root project, and generating PHProjekt 6.0 timecard entries with start/end times and project associations. This transformation is necessary because PHProjekt 6.0 requires explicit project associations for all time entries whereas PHProjekt 5.x allowed unbilled time.

The migration system uses Zend_Session_Namespace extensively to persist identifier mappings and migration progress across HTTP requests, enabling incremental migration where different modules (System, Timecard) are migrated separately through multiple AJAX calls. The getModulesToMigrate static method returns the list of modules supporting migration, and the controller invokes migrateSystem, migrateTimecard, or other migration methods based on user selection. This modular approach prevents timeouts during large migrations, provides granular progress feedback, and enables selective migration where administrators might choose to migrate only certain modules.

### Config Model

The Config model in `Models/Config.php` generates the configuration.php file content programmatically, formatting configuration directives in INI format with extensive comments explaining each setting. The getDefaultProduction method constructs a complete configuration file by calling helper methods that generate sections for language (_getLanguage), paths (_getPaths), database (_getDatabase), logging (_getLogs), modules (_getModules), mail (_getMail), miscellaneous settings (_getMisc), front-end options (_getFront), frontend messages (_getFrontendMessage), and authentication (_getAuthentication). Each helper method returns a formatted string with INI directives and explanatory comments, and the main method concatenates these into a complete file.

The model adapts configuration format to the operating system through _setOs which detects Windows versus Unix and sets the appropriate end-of-line sequence ($this->_eol) to "\r\n" for Windows or "\n" for Unix, ensuring that generated configuration files use native line endings for the platform. The model retrieves the private folder path from the session namespace established during directory setup, and uses this path to construct uploadPath, tmpPath, applicationPath, and webdavPath directives. The model's _getDatabase method carefully escapes database credentials using addcslashes to prevent INI parsing issues with special characters in passwords.

The configuration file generation includes sophisticated commenting that explains not just what each setting does but also provides examples, recommended values, and references to documentation. The _getIntroduction method adds a PHP die() statement at the beginning of the file to prevent the configuration from being displayed if accessed directly through a web request, an important security measure. The _getAuthentication method uses a heredoc for the LDAP configuration section, preserving formatting for the extensive commented examples showing how to configure LDAP authentication with Zend_Auth.

## Public API and Interfaces

The Setup service exposes a JSON-based API accessed through HTTP POST requests to the IndexController's action methods. The API follows a consistent request-response pattern where clients send form data (database credentials, passwords, directory paths) as POST parameters, and receive JSON responses containing a type field (error, success, confirm, notice), a message field (user-facing feedback), and a template field (HTML fragment to display). The API's progressive disclosure model requires completing steps sequentially: database setup must complete before user setup, user setup before folder setup, folder setup before table creation, table creation before migration (optional), and migration before finalization.

The database setup API (jsonDatabaseSetupAction) accepts serverType (database adapter), dbHost, dbUser, dbPass, dbPort, and dbName parameters, validates connectivity, and stores credentials in session on success. The users setup API (jsonUsersSetupAction) accepts adminPass, adminPassConfirm, testPass, and testPassConfirm parameters, validates password requirements, and stores hashed passwords in session. The folders setup API (jsonFoldersSetupAction) accepts privateDir and confirmationCheck parameters, validates directory writability, warns if the directory is inside document root unless confirmationCheck is true, creates required subdirectories, writes .htaccess protection, writes the configuration.php file, and returns success or error status.

The tables setup API (jsonTablesSetupAction) accepts useExtraData parameter indicating whether to install example data, retrieves database credentials from session, instantiates Phprojekt_DbParser to parse and execute SQL and CSV files, updates admin and test passwords in the created tables, and returns installation messages. The migration API (jsonMigrateSetupAction) accepts migrationConfigFile (path to PHProjekt 5.x config), diffToUtc (timezone offset), and module (System, Timecard, etc.) parameters, validates the config file, instantiates the Migration model, calls the appropriate migration method, captures output, and returns success or error with migration messages. The finish API (jsonFinishAction) performs final cleanup including permission checks and session destruction.

## Dependencies and Integration

The Setup service depends heavily on Zend Framework components including Zend_Controller_Action for MVC structure, Zend_Db for database abstraction, Zend_Session for state management, Zend_Json for response formatting, and Zend_Http for request processing. The service uses PHProjekt's Cleaner library for input sanitization, Phprojekt::checkExtensionsAndSettings for environment validation, Phprojekt_DbParser for schema installation, Phprojekt_Table for table manipulation, and Phprojekt_Acl for permission constants. The Setup service must function with minimal dependencies since it runs when the application itself cannot, constraining the service to use only libraries that can initialize without a configuration file.

The service integrates with the main application at specific touch points including writing the configuration.php file in the application root, creating database schema matching the application's model definitions, initializing user accounts that the application's authentication system will recognize, and establishing directory permissions that the application will require. The Setup service's writeConfigFile method creates a configuration file compatible with Zend_Config_Ini, using semicolons for comments and following INI syntax precisely so the application can parse it. The install method's use of Phprojekt_DbParser ensures that schema matches what the application expects, as the parser reads the same SQL definitions the application's migration system uses.

The Migration component integrates with both PHProjekt 5.x and PHProjekt 6.0 data models, reading from PHProjekt 5.x tables like users, gruppen, projekte, timecard, timeproj while writing to PHProjekt 6.0 tables like user, project, timecard, item_rights, search_words. The migration must understand both schemas completely to perform accurate transformations, and it uses Phprojekt_Table for safe database manipulation with parameter binding. The migration system's session-based state management enables integration with the HTTP request-response cycle, allowing long migrations to be broken into manageable chunks presented through multiple AJAX requests rather than requiring a single long-running request that might timeout.

## Data Models and Structures

The Setup service works with several data structures that bridge user input, session storage, and database persistence. The database configuration structure stored in session includes keys serverType (PDO adapter name), dbHost (hostname or IP), dbUser (username), dbPass (password), dbPort (port number), and dbName (database name). The users configuration structure includes adminPass and testPass (plaintext passwords stored temporarily in session). The private folder structure contains a single path string representing the directory location. These session structures are temporary and discarded after installation completes.

The Migration model defines extensive mapping structures that relate old identifiers to new ones. The $_users array maps PHProjekt 5.x user IDs to PHProjekt 6.0 user IDs, the $_projects array maps old project IDs to new project IDs, the $_groups array maps old group IDs to new project IDs (since groups became projects), the $_userKurz array maps user shortnames to user IDs enabling permission migration where permissions referenced users by shortname, and the $_groupsUsers array maps group IDs to arrays of user IDs representing group membership. These mappings enable the migration system to preserve data relationships when identifiers change between versions.

The permission migration uses a complex accumulation structure where $_dbItemRightValues accumulates arrays of [moduleId, itemId, userId, accessBitmask] representing permissions to be inserted into the item_rights table. The migration processes permissions from PHProjekt 5.x's acc and acc_write fields (which store serialized arrays, user shortnames, group indicators, or the string "private") into PHProjekt 6.0's bitmask-based permission system where each user's access to each item is represented by a bitmask with bits for READ, WRITE, CREATE, DELETE, ADMIN, etc. The $_dbProjectItemRightValues array specifically tracks project permissions to enable validation that users have access to parent projects before granting access to child projects.

The search indexing structures include $_searchWord array mapping words to [count, pair] structures where count tracks word frequency and pair contains arrays of [itemId, moduleId] tuples, and $_searchDisplay array containing [moduleId, itemId, projectId, firstDisplay, secondDisplay] tuples for search result presentation. The migration populates these structures from PHProjekt 5.x content using Phprojekt_Converter_String::cleanupString for text normalization and Phprojekt_Converter_String::stripLengthWords for stop word filtering, then writes them to the search_words, search_word_module, and search_display tables in batch operations.

## Configuration and Settings

The Setup service configuration is minimal since the service exists to create configuration rather than consume it. The IndexController defines several class constants that provide default values: DEFAULT_DBHOST ('localhost'), DEFAULT_DBUSER ('phprojekt'), DEFAULT_DBNAME ('phprojekt'), DEFAULT_PORT (3306), DEFAULT_USE_EXTRA_DATA (1), and DEFAULT_DIFF_TO_UTC (0). These defaults pre-populate forms with values appropriate for typical local development installations, and administrators override them as needed for production deployments. The constants are referenced in the form display actions where they initialize view variables.

The Migration model defines constants for PHProjekt 6.0 fixed identifiers: USER_ADMIN (1), USER_TEST (2), and PROJECT_ROOT (1). These constants represent the admin user, test user, and root project that PHProjekt 6.0 creates during installation and which serve as anchors for the migration. The ROWS_PER_QUERY constant (5000) controls batch sizes for query operations, balancing memory usage against database round-trip overhead. The getModulesToMigrate static method effectively serves as configuration, defining the list of modules the migration supports (currently System and Timecard).

The Config model includes default values for various settings passed as parameters to its generation methods: DEFAULT_LANGUAGE ('en'), DEFAULT_USER_DISPLAY_FORMAT (0), DEFAULT_ITEMS_PER_PAGE (3), DEFAULT_MAIL_END_OF_LINE (0), and DEFAULT_COMPRESSED_DOJO ('true'). These defaults are embedded in the method signatures with default parameter values, and the generation methods use them when callers don't provide explicit values. The model's getProposedPrivateFolderPath static method implements intelligent defaulting for the private directory by proposing dirname($_SERVER['DOCUMENT_ROOT'])/phprojekt_private, placing the private directory outside the document root by default for security.

## Design Patterns and Principles

The Setup service demonstrates the Wizard pattern where a complex configuration task is decomposed into discrete sequential steps with validation at each stage. The wizard maintains state across steps through session storage, prevents skipping steps through controller logic that renders forms only after prerequisites complete, and provides clear progression indicators showing users where they are in the process. This pattern reduces cognitive load by focusing attention on one configuration aspect at a time, enables validation before commitment preventing configuration errors, and supports resumption after interruption by maintaining progress state.

The Command pattern appears in how controller actions delegate to model methods, where each action invokes a command-like method (validateDatabase, install, migrate) that encapsulates a complete operation. The commands are parameterized with request data, they return success/failure status, they accumulate errors in model properties for retrieval after execution, and they can be extended or replaced without modifying the controller. This pattern enables testing of business logic independently of HTTP concerns, supports alternative interfaces (CLI installer) without duplicating logic, and maintains the single responsibility principle where controllers handle HTTP while models handle business logic.

The Builder pattern manifests in the Config model's generation of configuration files, where the getDefaultProduction method acts as a director invoking builder methods (_getDatabase, _getPaths, _getLogs, etc.) that construct portions of the configuration. Each builder method returns a formatted string segment, the director concatenates segments with appropriate separators, and the result is a complete configuration file. This pattern enables configuration sections to be tested independently, supports alternative configuration formats by implementing different builders, and makes configuration generation logic readable by organizing related settings together.

The Template Method pattern appears in the Migration model's migration methods which follow a consistent pattern: query source data from PHProjekt 5.x tables, transform data including identifier mapping and format conversion, accumulate transformed data in arrays until thresholds are reached, execute batch inserts to PHProjekt 6.0 tables, and save mapping state to session. While not implemented through abstract base classes, this consistent algorithm structure across _migrateUsers, _migrateProjects, _migrateTimecard enables understanding and modification by establishing clear expectations about migration method structure.

The Memento pattern is implicit in how the Setup service uses Zend_Session_Namespace to capture and restore configuration state. Each setup step saves its results to session namespaces (databaseData, usersData, privateFolder), later steps retrieve this saved state, and the final installation step writes accumulated state to the configuration file. This pattern enables multi-request workflows, supports cancellation and restart without data loss, and allows later steps to access decisions from earlier steps. The Migration model extends this pattern by saving complex migration state (user mappings, project mappings, permission mappings) to session between HTTP requests, enabling incremental migration of large datasets.

The Strategy pattern appears in how different migration methods implement different strategies for transforming specific modules or data types. The migrateTimecard strategy differs fundamentally from migrateSystem because timecard data requires algorithmic distribution of worked time across projects while system data requires mostly structural transformation. The pattern enables each migration strategy to be developed independently, allows selective migration where only certain modules are transformed, and provides clear extension points for adding migration support for additional modules.
