# Component: Tree

## Overview

The Tree library provides hierarchical data structure management for PHProjekt 6, implementing a path-based tree representation that enables efficient querying of entire subtrees, flexible node manipulation including moving and deleting branches, and seamless integration with ActiveRecord models for persisting tree data. This library serves as the foundation for the project hierarchy in PHProjekt, where projects are organized in nested parent-child relationships that determine inheritance of permissions, settings, and organizational structure. The path-based approach stores the complete ancestry of each node as a slash-separated string in the database, enabling powerful SQL queries that retrieve entire subtrees through simple LIKE operations on the path field, avoiding the performance problems of recursive queries or complex traversal algorithms required by alternative tree representations like adjacency lists or nested sets.

The library architecture centers on the Phprojekt_Tree_Node_Database class which represents individual nodes in the tree while providing collection-like operations for working with subtrees. Each node wraps an ActiveRecord model object (typically Project_Models_Project) that contains the actual data fields including the tree structure fields (id, projectId for parent reference, and path for efficient subtree queries). The design implements a hybrid structure where the root node of any loaded subtree maintains an index of all nodes for O(1) lookup by ID, enabling fast random access without scanning the tree, while also maintaining parent-child references for natural tree traversal patterns. This dual-access approach balances different usage patterns including hierarchical traversal through parent and children references, flat access through the index for direct ID-based lookup, and iterator-based access through PHP's foreach construct for convenient enumeration.

The path-based tree representation uses a format where each node stores its complete ancestry as a string like "/1/5/12/" indicating that the node's path includes the root (1), an intermediate node (5), and its direct parent (12). This representation provides several advantages over alternative approaches including efficient subtree queries through SQL LIKE operations matching "path LIKE '/1/5/12/%'", clear depth calculation by counting slashes in the path, simple ancestor checking by testing if one path is a prefix of another, and straightforward move operations that update paths for the moved subtree. The NODE_SEPARATOR constant ('/' by default) defines the delimiter used in paths, with the implementation warning against changing this value for existing trees as no migration is provided, highlighting the importance of initial configuration decisions in database schema design.

The library implements comprehensive access control integration through the applyRights() method that filters tree nodes based on the current user's permissions, removing projects the user cannot read while preserving the tree structure and hierarchy. This filtering occurs after tree loading from the database, implementing a security layer that ensures users only see projects they have access to regardless of how they access the tree structure. The permission inheritance model uses the current permission at each level as the default for child nodes, implementing a cascading permission scheme where access granted at higher levels flows down to children unless explicitly overridden, matching organizational security patterns where department-level access implicitly grants access to team-level projects within that department.

This three-class structure demonstrates focused design where each class has a clear single responsibility including node management, error signaling, and iteration.

## Key Classes and Files

### Phprojekt_Tree_Node_Database (Tree/Node/Database.php:21-704)

The Phprojekt_Tree_Node_Database class serves as the comprehensive implementation of tree nodes with database persistence, implementing IteratorAggregate to enable foreach iteration over subtrees while providing rich APIs for tree manipulation, querying, and access control. The class uses composition to wrap an ActiveRecord model (stored in _activeRecord property) that contains the actual data including tree structure fields, maintaining separation between tree operations and domain data while enabling the tree node to proxy most property access and method calls through to the underlying model. The design implements several critical properties including _parentNode for upward traversal, _children array for downward traversal, _requestedId to remember which node was initially requested during setup, and _index array (maintained only by the root node) for O(1) node lookup by ID.

The constructor (Database.php:79-88) accepts an ActiveRecord object or stdclass and an optional node ID, storing the ActiveRecord reference and determining the requested ID either from the parameter or from the ActiveRecord's id property. This flexible initialization supports both creating empty nodes that will be populated during setup() and creating nodes with pre-loaded data. The __clone() method (Database.php:69-75) reinitializes all component instances to ensure that cloned tree nodes have fresh child arrays, parent references, indexes, and ActiveRecord objects, preventing shared state between clones that could cause subtle bugs when trees are copied.

The setup() method (Database.php:128-185) implements the critical operation of loading a subtree from the database, first validating that a requested ID was provided through the constructor, returning early for the special case of ID 0, constructing a complex self-join SQL query that retrieves the requested node and all its descendants through a LIKE condition on the path field, applying optional filters to narrow the subtree, converting column names from SQL snake_case to PHP camelCase for property access, iterating over results to construct the tree structure by setting the first matching record as the current node and creating child nodes when their parent exists in the index, and finally applying access control through applyRights() to filter unauthorized nodes. The self-join query demonstrates sophisticated SQL where the first table alias (t) represents the requested node and the second alias (tt) represents all descendants, with the join condition using string concatenation to match paths that start with the requested node's path.

The getRecordsFor() method (Database.php:198-214) provides a powerful capability to query for records of any model type that belong to projects within the current subtree, extracting project IDs from the tree's index, appending a project_id IN clause to any provided WHERE conditions, and delegating to the model's fetchAll() with appropriate limiting and sorting. This method enables efficient queries like "find all Todo items in this project and its subprojects" without requiring application code to understand the tree structure or build complex queries, demonstrating how the tree abstraction can simplify common operations. The companion getRecordsCount() method (Database.php:222-234) provides the same filtering for count queries, supporting pagination scenarios where count and data retrieval need separate operations.

The applyRights() method (Database.php:243-266) implements comprehensive access control by immediately returning for admin users who see all projects, extracting project IDs from the tree index, querying the permission system through Phprojekt_Right::getRightsForItems() to retrieve permission bitmasks for all projects, iterating over the tree to check READ permission for each node using inherited permission from parent when no explicit permission exists, collecting IDs of unauthorized nodes, and calling deleteNodes() to remove unauthorized nodes from the tree structure. The method uses the real user ID rather than effective user ID (as noted in the comment), preventing proxy authentication from bypassing permission checks and ensuring that delegation doesn't accidentally grant access to restricted projects. The permission inheritance model where currentRight maintains the last known permission and is used as default for children implements cascading security that matches organizational hierarchies.

The deleteNodes() method (Database.php:277-298) implements tree pruning by recursively traversing children to find and remove specified node IDs, removing nodes from both the _children array and the _index map, and using pass-by-reference for the IDs array to enable early termination when all target nodes are removed. This method supports the access control filtering but is kept private to prevent external code from arbitrarily removing nodes, maintaining tree integrity by ensuring that only authorized removal operations occur. The implementation demonstrates careful handling of iterator invalidation by checking if nodes exist before attempting removal, addressing the comment's note that deletion cannot update iterator references.

The appendNode() method (Database.php:342-356) implements the primary operation for adding nodes to the tree, checking if the node has an ActiveRecord object to contain actual data, determining if the node is new (id === null or id == 0) and if so setting its projectId to the parent's ID and computing its path by concatenating the parent's path, parent's ID, and the NODE_SEPARATOR, calling save() to persist the new node, setting the parent reference, and adding the node to the parent's children array indexed by the node's ID. This method handles both creating new nodes in the database and connecting existing nodes into the tree structure, supporting both initial tree construction and incremental growth scenarios.

The delete() method (Database.php:384-402) implements cascading deletion of entire subtrees, validating that the node has been persisted (id !== null), preventing deletion of the invisible root node (id 1) to protect the tree structure, constructing a WHERE clause that matches all records with paths starting with the current node's path (using LIKE for prefix matching), executing a batch DELETE to remove all matching records from the database, recursively clearing the in-memory child structures, and calling _initialize() to reset the node's internal state. This implementation demonstrates efficient batch deletion through the path-based structure where a single DELETE removes entire subtrees, avoiding the N queries required by traversal-based deletion while maintaining referential integrity.

The setParentNode() method (Database.php:414-426) implements node moving operations by checking if the new parent differs from the current parent (by comparing node IDs with projectId), updating the projectId to the new parent when a move is needed, calling _rebuildPaths() to recursively update path fields for the entire subtree being moved, saving the updated node, and setting the internal parent reference. The _rebuildPaths() method (Database.php:436-450) recursively traverses the subtree updating path fields by checking if the current path differs from the new path computed from the base path, updating the node's path when needed, recursively processing children with their new base path, updating the root node's index to maintain consistency, and calling parentSave() (likely a method that saves without triggering hooks) to persist path changes. This move operation maintains tree integrity by ensuring all paths remain consistent after relocation.

The __get(), __set(), __isset(), and __call() magic methods (Database.php:459-523) implement transparent property and method proxying to the underlying ActiveRecord, enabling code to treat tree nodes as if they were the wrapped model objects. The __get() method returns the parent node for the special 'parentNode' key and delegates all other property access to the ActiveRecord, __set() prevents modification of tree-critical fields (id and path) while allowing other properties to be set, __isset() checks both the node's own properties and the ActiveRecord's properties, and __call() attempts to proxy method calls to the ActiveRecord. This proxying pattern enables natural syntax like `$node->title = 'Project Name'` and `$node->customMethod()` without requiring explicit method forwarding for every ActiveRecord method.

The getNodeById() method (Database.php:532-535) provides O(1) node lookup by delegating to the root node's _getFromIndex() method, which maintains a flat index of all nodes for efficient access. The isRootNodeForCurrentTree() method (Database.php:563-566) checks if the node is the root of the loaded subtree by testing if parentNode is null, distinguishing between the root of a subtree query and the absolute root node of the entire tree. The getDepth() method (Database.php:608-614) calculates node depth by counting NODE_SEPARATOR occurrences in the path and subtracting the root's path depth, providing relative depth within the loaded subtree rather than absolute depth in the full tree. The getIterator() method (Database.php:584-590) implements IteratorAggregate by wrapping the node in a Phprojekt_Tree_Node_Iterator and RecursiveIteratorIterator to enable depth-first traversal through foreach.

### Phprojekt_Tree_Node_Exception (Tree/Node/Exception.php:37-39)

The Phprojekt_Tree_Node_Exception class extends PHP's standard Exception class to provide specialized error handling for tree-specific operations, enabling calling code to catch tree errors separately from other exception types. The class is defined as a simple marker type without additional methods, following the pattern where exception type alone provides sufficient information for error handling logic. The library throws this exception for various error conditions including attempting to setup a tree without providing a requested ID in the constructor, attempting to delete a node that hasn't been persisted to the database, and attempting to delete the invisible root node (ID 1) which would corrupt the tree structure. This exception type enables clean error boundaries where tree manipulation code can distinguish between expected tree constraint violations (handle gracefully) and unexpected system errors (log and fail).

### Phprojekt_Tree_Node_Iterator (Tree/Node/Iterator.php:25-151)

The Phprojekt_Tree_Node_Iterator class implements PHP's RecursiveIterator interface to enable natural foreach syntax for tree traversal, providing depth-first iteration over tree nodes through the RecursiveIteratorIterator wrapper used by tree nodes. The class wraps either an array of children or a single node (normalized to array in the constructor), implementing the standard Iterator methods including current() to return the current child node, key() to return the current node's ID, next() to advance the internal array pointer, rewind() to reset to the first element, and valid() to check if the current position is valid. The recursive iteration capabilities come from implementing hasChildren() which delegates to the current node's hasChildren() method, and getChildren() which returns a new iterator wrapping the current node's children array, enabling the RecursiveIteratorIterator to automatically traverse the entire tree structure.

The iterator design demonstrates the power of PHP's SPL (Standard PHP Library) interfaces where implementing RecursiveIterator with simple array pointer manipulation enables sophisticated tree traversal through the RecursiveIteratorIterator wrapper. The SELF_FIRST mode specified in the tree node's getIterator() implementation indicates that parent nodes are yielded before their children in the iteration order, supporting common tree processing patterns where parents must be processed before their descendants. The iterator implementation is stateless except for the array pointer, enabling multiple simultaneous iterations over the same tree without interference, though the underlying tree structure should not be modified during iteration to avoid undefined behavior.

## Public API and Interfaces

The Tree library exposes its functionality primarily through the Phprojekt_Tree_Node_Database class which provides both tree construction APIs and tree query APIs. The construction workflow typically involves instantiating a node with an ActiveRecord and optional ID through `new Phprojekt_Tree_Node_Database($project, $projectId)`, calling setup() to load the subtree from the database with `$node->setup()`, and then accessing the tree structure through various traversal methods. The setup process accepts optional filter objects that implement Phprojekt_Filter_Interface, enabling customization of which nodes are loaded, such as filtering by date ranges, status values, or other criteria. The returned tree includes all descendants of the requested node with access control already applied, providing a security-filtered view ready for display or processing.

The node manipulation API provides operations for modifying tree structure including appendNode() to add children, setParentNode() to move nodes within the tree, and delete() to remove entire subtrees. These operations maintain tree integrity by automatically updating path fields, parent references, and indexes as needed, with persistence to the database occurring through the wrapped ActiveRecord's save() method. The manipulation operations throw Phprojekt_Tree_Node_Exception for constraint violations including attempting to delete unpersisted nodes, deleting the root node, or setting up trees without specifying an ID. Application code typically wraps manipulation operations in try-catch blocks to handle these expected exceptions gracefully with user-friendly error messages.

The query API provides multiple access patterns for working with tree data including getNodeById() for direct access to nodes by ID, getChildren() and hasChildren() for immediate child access, getParentNode() and getRootNode() for upward traversal, getDepth() for level calculation, and getIterator() for foreach enumeration. The getRecordsFor() and getRecordsCount() methods extend the query capabilities beyond the tree itself to find records of arbitrary types that belong to projects within the subtree, implementing powerful cross-cutting queries like "all Todo items in my department's projects" through simple method calls. These query methods return either node objects, arrays of nodes, or ActiveRecord collections depending on the operation, with consistent null returns for missing nodes rather than throwing exceptions.

The property access API uses magic methods to provide transparent access to the wrapped ActiveRecord's properties, enabling code to read and write domain fields like title, status, and custom attributes directly on tree nodes. The special parentNode property provides read access to the parent node, while the protected tree structure fields (id and path) cannot be modified to prevent accidental corruption. Method calls similarly proxy through to the ActiveRecord, enabling application-specific methods to be called on tree nodes without explicit forwarding. This transparent proxying makes tree nodes feel like enhanced versions of the domain objects they wrap rather than wrapper objects with complex access patterns.

## Dependencies and Integration

The Tree library depends fundamentally on the ActiveRecord ORM infrastructure through its composition relationship with Phprojekt_ActiveRecord_Abstract, storing a reference to an ActiveRecord model that provides data persistence operations, table metadata, and database adapter access. The tree node acts as a decorator around ActiveRecord models, adding tree-specific operations while delegating data access to the wrapped model. This composition approach enables the tree library to work with any ActiveRecord-based model that includes the required tree structure fields (id, projectId, path), providing flexibility in what entity types can be organized hierarchically, though PHProjekt primarily uses it for Project models.

Integration with Zend Framework's database layer occurs through the ActiveRecord's Zend_Db_Adapter access, with the tree operations constructing SQL queries through Zend_Db_Select for complex operations like subtree loading. The setup() method builds a self-join query using Zend_Db_Select that demonstrates sophisticated use of joins, string concatenation in conditions, and programmatic query construction. The direct SQL operations in delete() bypass ActiveRecord for performance, using batch DELETE through the adapter's delete() method to efficiently remove entire subtrees. This mixed approach of using ORM for individual operations and direct SQL for bulk operations demonstrates pragmatic optimization where abstraction is sacrificed for performance in hot paths.

The Phprojekt_Filter_Interface integration enables customization of subtree loading by allowing filters to modify the SQL query before execution, supporting scenarios like loading only active projects or projects modified within a date range. The filter's filter() method receives the Zend_Db_Select and table alias, enabling it to add WHERE clauses, joins, or other query modifications. This filter pattern implements the Chain of Responsibility pattern where multiple filters could potentially be chained (though the current API accepts only one filter), enabling composition of query constraints without coupling the tree library to specific filtering logic.

The access control integration through Phprojekt_Right::getRightsForItems() and Phprojekt_Acl demonstrates tight coupling with the permission system, implementing security filtering as a first-class tree operation rather than an afterthought. The applyRights() method queries permissions for all nodes in the loaded subtree in a single batch operation, then filters the tree structure based on READ permissions. The use of Phprojekt_Auth::getUserId() rather than Phprojekt_Auth_Proxy::getEffectiveUserId() (as noted in the comment) ensures that proxied users don't bypass permission checks, implementing defense-in-depth security where impersonation doesn't grant additional access to restricted projects.

The Project_Models_Project integration occurs through the hardcoded fallback in getActiveRecord() which instantiates Project_Models_Project when no ActiveRecord is present, demonstrating the library's primary use case of managing project hierarchies. This coupling suggests that while the tree library is designed to be generic, it's strongly oriented toward project management and would require modification to support other entity types as trees. The convertVarFromSql() call during setup() demonstrates integration with the ActiveRecord naming conventions, translating database column names to PHP property names for consistent access patterns.

## Data Models and Structures

The Tree library relies on a database table structure that includes three critical fields for tree management: id (primary key), projectId (foreign key to parent node's id, NULL for root), and path (varchar storing the slash-separated ancestry). The path field forms the core of the tree representation, storing values like "/" for the root, "/1/" for direct children of root, "/1/5/" for grandchildren, and so on. This path-based structure enables the powerful SQL query pattern "SELECT * FROM table WHERE path LIKE '/1/5/%'" to retrieve entire subtrees in a single query, avoiding the recursive queries or multiple roundtrips required by traditional adjacency list representations. The path length grows with tree depth, requiring appropriately sized varchar fields (typically 255 or more) to support deep hierarchies.

The projectId field implements a traditional parent pointer that provides an alternative access path for single-level parent lookups and supports data integrity checks, though the primary tree operations rely on the path field rather than following parent pointers. This redundancy between projectId and path (since the path implicitly encodes all ancestors including the immediate parent) trades storage space for operational flexibility, enabling both efficient subtree queries through path and simple parent lookups through projectId. The dual representation also provides validation opportunities where the system can verify that projectId matches the last ID in the path, detecting corruption that might occur from manual database modifications or application bugs.

The in-memory tree structure maintained by the Tree library consists of a network of Phprojekt_Tree_Node_Database objects connected through _parentNode references upward and _children arrays downward, forming a doubly-linked tree. The root node of any loaded subtree maintains the _index array, a flat map from node IDs to node objects that enables O(1) lookup by ID without tree traversal. This hybrid structure of hierarchical links plus flat index balances different access patterns including tree traversal through parent/child references (natural for hierarchical operations), random access through the index (efficient for direct ID-based lookups), and sequential access through the iterator (convenient for processing all nodes). The memory footprint scales linearly with the number of loaded nodes, with each node storing references to its parent, children array, and ActiveRecord data.

The relationship between database and memory structures demonstrates a lazy-loading pattern where only the nodes specified in the setup() query are loaded into memory, with the loaded subtree becoming a connected component that can be traversed and manipulated. Modifications to the tree structure (adding, moving, deleting nodes) update both the memory structures and the database through ActiveRecord save() calls, maintaining synchronization between the in-memory and persistent representations. The setup() method's self-join query ensures that loaded subtrees are complete and contiguous, preventing disconnected nodes or missing intermediate levels that would violate tree structure invariants.

## Configuration and Settings

The Tree library uses minimal configuration, with the primary configurable element being the NODE_SEPARATOR constant defined as '/' for path field delimiter. This constant determines the character used to separate node IDs in the path field, with forward slash chosen for its readability and consistency with filesystem path conventions. The implementation includes a warning comment that this constant should not be changed for existing trees as no migration is provided, highlighting the importance of this configuration decision at system initialization. Alternative separators like pipe (|) or dot (.) could be used for new systems, though the slash convention is widely adopted and intuitive.

The invisible root node uses hardcoded ID value of 1, implementing a special node that serves as the parent of all top-level projects and cannot be deleted. This hardcoded special case appears in the delete() method which explicitly prevents deletion of ID 1, and in the applyRights() filtering which presumably ensures all users can see the root. The choice of ID 1 for the root couples the tree library to initial data seeding that creates this root node during installation, requiring that installations maintain this invariant. Alternative approaches might use ID 0 or negative IDs for the root, though the current choice of 1 aligns with human-friendly numbering where IDs start at 1.

The path format uses a specific convention where paths always start and end with slashes, storing values like "/1/5/12/" rather than "1/5/12" or "1-5-12". This format ensures that substring matching through LIKE operations works correctly, with leading slash preventing "/1" from matching "/10", "/11", etc., and trailing slash ensuring that the path clearly indicates ancestry rather than the node itself. The double-slash convention ("/") for the root node path provides a natural base case that concatenates cleanly with child IDs. This formatting convention is baked into the string manipulation logic in appendNode() and _rebuildPaths(), requiring careful attention when extending the library to prevent path format inconsistencies.

The access control integration uses the actual user ID rather than effective user ID (from proxy authentication), as noted in the applyRights() comment. This configuration choice implements a security policy where impersonation doesn't grant access to restricted projects, preventing administrative assistants from accessing confidential projects when acting on behalf of executives. This policy could be made configurable if different organizations have different security requirements around proxy access and delegation, though the current hardcoded approach implements defense-in-depth security that favors restriction over convenience.

## Design Patterns and Principles

The Composite pattern dominates the Tree library's design through the uniform treatment of individual nodes and subtrees, where both leaf nodes and internal nodes implement the same interface including getChildren(), hasChildren(), and iterator support. This pattern enables recursive algorithms to work uniformly across the tree without special-casing leaves versus branches, supporting operations like applyRights() that traverse trees applying the same permission logic to each node regardless of whether it has children. The pattern also supports treating any subtree as an independent tree, enabling modular operations where code operating on a subtree doesn't need to know its position in the larger tree.

The Decorator pattern appears in how tree nodes wrap ActiveRecord objects, adding tree-specific operations like appendNode(), delete(), and getDepth() while delegating data access and domain operations to the wrapped model. The magic methods __get(), __set(), __isset(), and __call() implement transparent proxying that makes the decoration nearly invisible to client code, enabling tree nodes to be used anywhere the underlying ActiveRecord would be accepted. This pattern maintains separation of concerns where ActiveRecord handles data persistence and validation while tree nodes handle hierarchical structure and traversal, avoiding the complexity of multi-inheritance or trait-based mixins.

The Iterator pattern implemented through Phprojekt_Tree_Node_Iterator and PHP's RecursiveIterator interface enables natural foreach syntax for tree traversal, abstracting the complexity of depth-first traversal behind a simple iteration interface. The use of RecursiveIteratorIterator demonstrates delegation where the tree node provides basic iteration over immediate children while the iterator wrapper handles recursion into subtrees. This pattern demonstrates the power of standard interfaces where implementing a few methods (current, key, next, rewind, valid, hasChildren, getChildren) unlocks rich functionality through framework-provided iterators like RecursiveIteratorIterator that implement various traversal strategies.

The Template Method pattern appears in the permission inheritance logic where applyRights() implements the algorithm template of "iterate over nodes, check permissions, delete unauthorized nodes" while the specific permission checking varies by context through the permission system. The currentRight variable that carries forward the last known permission implements the inheritance policy where children inherit parent permissions by default, a strategy that could be varied by changing the permission lookup logic without altering the overall filtering algorithm.

The Index pattern appears in the _index array maintained by root nodes, implementing a lookup table that provides O(1) access to nodes by ID without traversal. This pattern trades memory (storing pointers to all nodes in the flat index) for speed (avoiding tree traversal for each lookup), appropriate for the tree library's use case where random access by ID is common for operations like "show details for project 42". The pattern demonstrates performance optimization where the natural tree structure (optimized for hierarchical traversal) is augmented with an auxiliary data structure (optimized for random access) to support diverse access patterns efficiently.

The Path Enumeration pattern forms the core of the database representation, storing the complete ancestry of each node as an explicit path string rather than implicitly through parent pointers. This pattern trades storage space (paths grow with depth and contain redundant information) for query performance (subtree queries become simple string prefix matches). The pattern also enables simple operations like depth calculation (count separators), ancestor checking (test for prefix match), and level queries (all nodes at depth N have path with N separators), demonstrating how data structure choice fundamentally shapes operation complexity and performance characteristics.

The Lazy Initialization pattern appears in getActiveRecord() which loads the ActiveRecord from the database only when accessed if not already present, avoiding unnecessary database queries when tree structure operations don't require domain data. This pattern also appears implicitly in the tree loading process where setup() loads only the specified subtree rather than the entire tree, implementing lazy loading at the subtree granularity. The pattern balances memory efficiency with access latency, loading data on demand rather than eagerly loading everything upfront.
