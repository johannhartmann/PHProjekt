# Component: Model

## Overview

The Model library provides the foundational abstraction layer for representing and manipulating domain entities within the PHProjekt application. This library defines the contracts and utilities that enable consistent interaction with data objects across the application, regardless of their underlying storage mechanism or specific implementation details. At its core, the Model library establishes a uniform interface (`Phprojekt_Model_Interface`) that all domain models must implement, ensuring that controllers, converters, validators, and other system components can work with models polymorphically without requiring knowledge of their specific types or internal structures.

The Model library serves as the architectural keystone that enables separation of concerns between the application's business logic layer and its data access layer. By defining a clear interface contract, the library allows the application to treat all domain objects uniformly, whether they represent users, projects, tasks, time entries, or any other business entity. This abstraction enables powerful generic functionality such as the converter system (which can serialize any model to JSON or CSV), the validation system (which can validate any model's data against its metadata), and the filter system (which can construct WHERE clauses for any model). The interface-based design reflects the principle of programming to abstractions rather than concrete implementations, facilitating testability, maintainability, and extensibility throughout the application.

A critical aspect of the Model library is its integration with the ModelInformation subsystem, which provides rich metadata about model fields including their types, labels, validation rules, default values, and display properties. Every model exposes its metadata through the `getInformation()` method, which returns an object implementing `Phprojekt_ModelInformation_Interface`. This metadata-driven architecture enables the application to adapt dynamically to model definitions without hard-coding field-specific logic throughout the codebase. For example, the validation system can validate integer fields as integers and date fields as dates purely by examining metadata, and the converter system can apply appropriate type conversions when transforming models for JSON serialization.

The Model library includes three primary components working in concert to support model operations. The `Phprojekt_Model_Interface` defines the contract that all models must fulfill, specifying methods for finding, fetching, saving, validating, and iterating over model data. The `Phprojekt_Model_Validate` class provides comprehensive validation capabilities, checking required fields, validating data types, enforcing length constraints, and validating range constraints for select box and rating fields. The `Phprojekt_Model_Converter` class provides serialization capabilities, converting model objects and collections into associative arrays suitable for JSON encoding and transmission to API clients. Together, these components form a cohesive framework that simplifies model manipulation while ensuring data integrity and consistency across the application.

## Component Structure

| Path | Purpose |
|------|---------|
| `library/Phprojekt/Model/Interface.php` | Core interface defining the model contract |
| `library/Phprojekt/Model/Validate.php` | Validation engine for model data integrity |
| `library/Phprojekt/Model/Converter.php` | Serialization utility for model-to-array conversion |

The Model library follows a minimal organizational structure with just three files in the Model subdirectory, reflecting its focused role as an abstraction layer rather than a comprehensive ORM implementation. The interface file establishes the contract that all models must implement, defining the essential operations that any model must support. The validation and converter classes provide supporting infrastructure that operates on models through this interface, demonstrating how the abstraction enables building generic functionality that works with any model implementation.

This lean structure reflects the design philosophy that the Model library should define "what" models must do (through the interface) and provide essential supporting utilities (validation and conversion), while leaving the "how" of model implementation to concrete classes elsewhere in the codebase. The primary implementations of `Phprojekt_Model_Interface` reside in the ActiveRecord hierarchy (`Phprojekt_ActiveRecord_Abstract` and `Phprojekt_Item_Abstract`), which provide database-backed model functionality. This separation between interface definition and implementation enables the creation of alternative model implementations (such as models backed by web services, file systems, or in-memory data structures) that can integrate seamlessly with the existing application infrastructure.

## Key Classes and Files

### Phprojekt_Model_Interface

The Model Interface in `Model/Interface.php` establishes the fundamental contract that all PHProjekt domain models must fulfill, defining seven essential methods plus the Iterator interface. This interface extends PHP's Iterator interface, requiring that models support foreach iteration over their fields, enabling generic code to enumerate a model's properties without knowing them in advance. The interface design reflects careful consideration of the minimal set of operations that generic application code needs to perform on models, balancing comprehensiveness against simplicity.

The `getInformation()` method serves as the gateway to a model's metadata, returning an object implementing `Phprojekt_ModelInformation_Interface`. This method is called extensively throughout the application by converters, validators, filters, and other systems that need to understand field types, labels, and constraints. The metadata-driven approach enabled by this method eliminates the need for hard-coded field knowledge in generic components, allowing them to adapt automatically to model changes. The method signature's return type of `Phprojekt_ModelInformation_Interface` enables different models to provide different metadata implementations while maintaining a uniform interface for accessing that metadata.

The `find()` and `fetchAll()` methods define the basic retrieval operations that models must support. The find method locates a single record (typically by ID) and populates the current model instance with its data, following the Active Record pattern where model instances represent database rows. The fetchAll method retrieves multiple records, typically returning an array of model instances. The interface allows implementations flexibility in how they accept parameters (the interface methods take no parameters, but implementations can define parameters for WHERE clauses, ordering, limits, etc.), reflecting the pragmatic recognition that different storage mechanisms have different query capabilities.

The `save()` method provides the persistence operation, writing the current model's state to the backend storage. The method's boolean return type indicates success or failure, enabling calling code to detect persistence errors and respond appropriately. The interface doesn't prescribe whether save should perform INSERT or UPDATE operations—implementations typically inspect whether the model has an ID to make this determination. This abstraction allows the interface to accommodate various persistence strategies while providing a uniform save operation to application code.

The `hasField()` method enables runtime inspection of model structure, allowing code to check whether a model has a particular field before attempting to access it. This capability is essential for generic code that works with multiple model types, each with different field sets. For example, filter construction code uses this method to validate that requested filter fields exist in the target model, preventing runtime errors from invalid field references. The method's string parameter accepts field names in camelCase (the application convention), with implementations typically converting to snake_case for database column lookups.

The `recordValidate()` and `getError()` methods establish the validation contract. Models must validate their current state against business rules and metadata constraints when recordValidate is called, returning a boolean indicating validity. If validation fails, subsequent calls to getError must return an array of error structures describing what validation rules were violated. This two-method approach separates the validation decision (boolean result) from error detail retrieval, allowing calling code to first check if validation passed and only retrieve detailed error information when needed. The interface doesn't specify the error array structure, but the conventional format includes 'field', 'label', and 'message' keys for each error.

### Phprojekt_Model_Validate

The Validate class in `Model/Validate.php` provides a comprehensive validation engine that examines model data against metadata-defined constraints and custom validation rules. This class serves as the standard validation implementation used by `Phprojekt_Item_Abstract` and its subclasses, centralizing validation logic that would otherwise be duplicated across model classes. The validator maintains an error object (`Phprojekt_Error` instance) that accumulates validation failures, enabling a single validation pass to collect all errors rather than failing at the first error and requiring users to fix errors one at a time.

The `recordValidate()` method orchestrates the validation process, accepting an ActiveRecord instance, a data array, and a field definitions array. The method iterates through each data field, looking up its definition in the field definitions array to determine validation constraints. For each field, the method performs multiple validation checks in sequence: required field validation (checking that required fields have values), length validation (ensuring string values don't exceed maximum lengths), range validation (verifying that select box and rating values fall within allowed ranges), type validation (confirming that values match field data types), and custom validation (calling model-specific validator methods if they exist).

The required field validation is handled by the `validateIsRequired()` method, which checks if a value is empty (using PHP's empty() function) and returns an error message if so. This method is straightforward but critical, as required field violations are among the most common validation errors. The validator only checks required constraints for fields explicitly marked as required in their metadata (fields with `'required' => true`), allowing optional fields to be omitted or left empty. The error message returned ("Is a required field") is passed through the translation system, ensuring validation errors appear in the user's preferred language.

The length validation checks field values against the 'length' property in field metadata, comparing the string length to the maximum allowed length. This validation prevents database errors that would occur if overly long values were inserted into fixed-length database columns. The validator uses PHP's strlen() function rather than mb_strlen(), which means length is measured in bytes rather than characters for multibyte encodings. This is appropriate for database column length constraints which typically specify byte lengths, but may be unexpected for users entering multibyte text who may see length limits enforced at different character counts than expected.

The range validation handles two distinct field types with different range semantics. For selectbox and multipleselectbox fields, the validator checks that the field value matches one of the ID values in the field's range array, ensuring users haven't submitted invalid select box values (either through client-side tampering or outdated cached form data). For rating fields, the validator checks that the value falls within the numeric range from 1 to the maximum rating value specified in the field's range property. These validations prevent data integrity violations where foreign key relationships might be broken or numeric values might fall outside meaningful ranges.

The type validation is delegated to the `validateValue()` method, which examines the field's database data type from metadata and applies appropriate type-specific validation through the Cleaner validation library. Integer fields are validated with `Cleaner::validate('integer')`, float fields with `Cleaner::validate('float')`, date fields with `Cleaner::validate('date')`, and timestamp/datetime fields with `Cleaner::validate('timestamp')`. Time fields are conspicuously commented out in the validation logic, suggesting either a known issue with time validation or intentionally relaxed constraints for time fields. The method returns false if validation fails, signaling to the calling code that an "Invalid Format" error should be added.

The custom validation mechanism enables models to define field-specific validation rules by implementing methods named "validate{FieldName}" (e.g., validateEmail for an email field). After performing standard validations, the validator checks if the model class has a method matching this naming pattern, and if so, calls it with the field value. The custom validator method can perform any model-specific business rule validation (such as checking that email addresses are unique, or that end dates fall after start dates) and returns either an error message string or null. This extension mechanism allows models to augment standard validation with business-specific rules without modifying the core validator. The special case check preventing validateIsRequired from being called as a custom validator (since it's already called explicitly for required fields) demonstrates attention to avoiding duplicate validation logic.

The `validateDateRange()` method provides a specialized validation for date range fields, checking that end dates don't precede start dates. This method is designed to be called explicitly by models that have start date and end date fields, rather than being invoked automatically by the validation framework. The method adds a special "Period" error to the error collection if the date range is invalid, using a generic field name since the error applies to the relationship between two fields rather than to a single field. This cross-field validation capability demonstrates that the validator can handle validations that span multiple fields, not just single-field constraints.

### Phprojekt_Model_Converter

The Converter class in `Model/Converter.php` provides static methods for transforming model objects into associative arrays suitable for JSON serialization and transmission to API clients. This class serves as a bridge between the rich object-oriented model representation used internally and the flat array representation required for JSON encoding. The converter is intentionally simple and focused, performing straightforward field-by-field copying from model objects to arrays based on field definitions, without complex transformation logic or business rules.

The `convertModel()` static method accepts a single model instance and returns an associative array representing that model. The method first retrieves the model's field definition by calling `getInformation()->getFieldDefinition()`, which returns an array of field metadata structures. It then calls the private `_convertModel()` method with the model and field definitions to perform the actual conversion. This two-step design (public method that retrieves field definitions, private method that performs conversion) enables the related `convertModels()` method to optimize bulk conversions by retrieving field definitions once and reusing them for multiple models.

The `convertModels()` static method accepts an array of model instances (assumed to all be of the same type) and returns an array of associative arrays representing those models. The method optimizes the conversion process by retrieving field definitions from the first model only, then reusing those definitions for all subsequent models. This optimization is valid because models of the same type share the same field definitions, so retrieving definitions repeatedly would be wasteful. The method handles the empty array edge case by returning an empty array immediately, avoiding null pointer errors that would occur if it tried to access field definitions from a non-existent first element.

The private `_convertModel()` method performs the core conversion work, iterating through the field definitions and extracting each field's value from the model. The method constructs an associative array where keys are field names and values are the corresponding field values from the model. After copying all defined fields, the method explicitly adds the 'id' field to the result array. This explicit ID addition ensures that the model's identifier is always included in the serialized representation even if it's not listed in the field definitions (which may exclude it if it's configured as a hidden or system field). The method accesses model field values using dynamic property access (`$model->$key`), relying on models to implement appropriate __get magic methods for property access.

The Converter class's simplicity reflects a deliberate design decision to keep model-to-array conversion straightforward and predictable. The class doesn't perform type conversions, filtering, or transformations—it simply copies field values as-is from model to array. This design pushes type conversion responsibilities to other layers: the Converter_Json class handles type-specific conversions when constructing JSON responses, while the model's __get method (which typically calls Phprojekt_Converter_Value::get()) handles converting stored values to display formats. This separation of concerns keeps the Model_Converter focused solely on structural transformation (object to array) rather than semantic transformation (value conversion), improving maintainability and clarity.

## Public API and Interfaces

The Model library exposes its public API primarily through the `Phprojekt_Model_Interface` contract that all models implement, enabling application code to interact with models through a well-defined set of operations. Controllers typically work with models by calling find or fetchAll to retrieve data, accessing properties to read values, setting properties to modify values, calling recordValidate to check validity, and calling save to persist changes. This interaction pattern—retrieve, manipulate, validate, save—represents the standard CRUD workflow that the model interface is designed to support. The interface's Iterator implementation enables controllers to enumerate model fields using foreach, which is particularly useful in generic code that doesn't know a model's specific field set.

The validation API is accessed through two interface methods: recordValidate and getError. Application code calls recordValidate after setting model properties but before calling save, checking the boolean return value to determine if the model is valid. If validation fails, application code calls getError to retrieve detailed error information for presentation to users. This two-step API enables efficient validation checking (just examining the boolean) followed by detailed error retrieval only when needed. The error array structure follows a convention of including 'field', 'label', and 'message' keys, enabling generic error display code to present errors consistently regardless of which model or field generated them.

The conversion API is exposed through static methods on `Phprojekt_Model_Converter`, designed for use in controllers that need to serialize models for JSON responses. Controllers call `Phprojekt_Model_Converter::convertModel($model)` to convert a single model instance, or `Phprojekt_Model_Converter::convertModels($models)` to convert an array of models. These methods return associative arrays that can be passed to `Zend_Json_Encoder::encode()` for JSON serialization. The static method design makes the converter API simple to use without requiring object instantiation, and the method names clearly indicate whether they operate on single models or model collections.

The metadata API, while not directly part of the Model library, is essential to understanding how code interacts with models. Application code calls `$model->getInformation()` to obtain the model's ModelInformation object, then calls methods like `getFieldDefinition()` to retrieve field metadata. This metadata drives many model operations: converters use it to know which fields to include in output, validators use it to know what constraints to enforce, filters use it to know what data types to expect. The metadata API's separation from the model API proper reflects the distinction between model data (the values stored in model instances) and model metadata (the structure and constraints that apply to all instances).

## Dependencies and Integration

The Model library has relatively few direct dependencies, primarily relying on the ModelInformation and Error subsystems. The model interface requires implementations to return objects implementing `Phprojekt_ModelInformation_Interface` from their getInformation method, creating a dependency on the ModelInformation subsystem for metadata representation. The Validate class depends on `Phprojekt_Error` for error accumulation and the Cleaner library for type-specific validation. The Converter class has minimal dependencies, requiring only that models implement the model interface and provide field definitions through their metadata system.

The primary integration point for the Model library is through concrete model implementations, particularly the `Phprojekt_Item_Abstract` class which serves as the standard base for database-backed models. This class implements Phprojekt_Model_Interface and uses Phprojekt_Model_Validate internally in its recordValidate implementation, demonstrating the intended integration pattern. The Item_Abstract class also integrates with the Converter subsystem by implementing __get and __set methods that perform type conversions, and with the DatabaseManager for metadata provision. This integration demonstrates how the Model library's abstractions enable rich functionality in concrete implementations while keeping the interface contract minimal.

The Model library integrates extensively with the Converter library, particularly through Phprojekt_Converter_Json which calls Phprojekt_Model_Converter to serialize models before JSON encoding. This integration enables controllers to simply call `Phprojekt_Converter_Json::echoConvert($models)` to send JSON responses, with the model conversion happening transparently. The integration between Model_Converter and Converter_Json demonstrates proper layering: Model_Converter handles structural conversion (object to array) while Converter_Json handles format-specific conversion (array to JSON with type-specific value transformations).

The validation system integrates with exception handling through the Phprojekt_Exception_Validation exception type. When validation fails in REST controllers, they typically throw a Validation exception with the first error from the validator's error array. This integration between the validation system and exception system enables consistent error reporting across API endpoints, with validation failures always producing 422 status codes and structured error information. The integration demonstrates how the Model library's abstractions support higher-level application patterns while remaining independent of those patterns.

## Data Models and Structures

The Model library defines several key data structures that standardize how model information flows through the application. The field definition structure, returned by `getFieldDefinition()` on ModelInformation objects, is an array of associative arrays where each element represents one field. A field definition includes keys such as 'key' (the field name), 'label' (the user-facing label), 'type' (the UI control type like 'text' or 'selectbox'), 'required' (boolean indicating if the field is mandatory), 'length' (maximum string length), and 'range' (for select boxes, the array of valid options). This structure serves as the single source of truth about field properties, consulted by validators, converters, and other systems.

The error structure produced by the validation system follows a consistent format with three keys: 'field' containing the field name that failed validation, 'label' containing the user-facing field label for error messages, and 'message' containing the translated error message describing the validation failure. This structure is accumulated by the Phprojekt_Error object and returned as an array of such structures from the getError method. The consistent error structure enables generic error display code to present validation errors uniformly regardless of their source, and supports internationalization through the translated message field.

The converted model structure produced by Phprojekt_Model_Converter is an associative array where keys are field names (in camelCase as used in the application) and values are the field values from the model. The structure always includes an 'id' key with the model's identifier, even if not listed in the field definitions. This structure is designed for JSON serialization, with field names matching the JSON property names expected by JavaScript clients. The structure's flat nature (no nested objects) reflects the flat structure of database tables, with relationships represented by ID fields rather than nested objects.

The metadata structure from ModelInformation objects includes an 'info' array with keys like 'metadata' (containing database column information), 'cols' (containing column names), and 'name' (containing the table name). The metadata['columnName'] structure includes keys such as 'DATA_TYPE' (database type like 'int' or 'varchar'), 'LENGTH' (column length), 'NULLABLE' (whether nulls are allowed), and others derived from database schema information. This rich metadata structure enables the model system to adapt to database schemas without hard-coded field knowledge, supporting dynamic model behavior based on actual database structure.

## Configuration and Settings

The Model library requires minimal direct configuration, operating primarily through the metadata provided by model implementations rather than through external configuration files or settings. The library relies on model implementations to provide accurate metadata through their getInformation methods, with that metadata serving as the configuration that drives validation rules, conversion behavior, and other model operations. This metadata-driven approach means that changes to model structure (adding fields, changing constraints, modifying types) are automatically reflected in model behavior without requiring updates to configuration files.

The validation system uses field metadata as its configuration, examining properties like 'required', 'length', and 'range' to determine what constraints to enforce. These metadata properties are typically derived from database schemas (for database-backed models) or defined programmatically (for non-database models), ensuring validation rules stay synchronized with actual data structure. The validator's use of the Cleaner library for type validation means that type-specific validation rules are configured within the Cleaner library rather than in the Model library, following a principle of delegating specialized concerns to specialized components.

The converter configuration is implicit in the field definitions retrieved from models. The fields to include in converted output are determined by which fields appear in the field definitions array, allowing models to control their own serialization by configuring which fields their getInformation method returns. Models can implement different field orderings for different purposes (form display vs. list display vs. API output) through the ORDERING constants in ModelInformation_Default, enabling context-sensitive conversion without modifying the converter code. This flexibility in field definition allows models to tailor their external representation while using the same conversion infrastructure.

## Design Patterns and Principles

The Model library extensively employs the Interface Segregation Principle, defining a minimal interface that requires only essential operations rather than forcing implementations to provide comprehensive functionality. The interface includes only seven methods plus Iterator support, avoiding the bloat that often accompanies ORM frameworks which can have dozens of required methods. This minimalism makes it feasible for diverse implementations to conform to the interface while keeping the interface useful for generic application code. The principle is further reflected in the separation between Phprojekt_Model_Interface and Phprojekt_ModelInformation_Interface, avoiding coupling model operations to metadata operations.

The Strategy pattern appears in the validation system's support for custom validators. Models can provide field-specific validation strategies by implementing validate{FieldName} methods, and the validator will discover and use these strategies automatically. This pattern enables models to customize validation behavior without modifying the validator class, supporting the Open-Closed Principle where the validator is open for extension (through custom validator methods) but closed for modification. The pattern also appears in the separation between validation logic (in Model_Validate) and error reporting logic (in Phprojekt_Error), where different error reporting strategies could be plugged in.

The Template Method pattern is implicit in the model interface's design, where the interface defines the overall structure of model operations (find, fetchAll, save, validate) while leaving the implementation details to subclasses. The recordValidate method in particular follows this pattern: the interface defines that validation must happen and return a boolean, but implementations are free to customize what validations occur and how they're performed. The Phprojekt_Item_Abstract class provides a template implementation that uses Phprojekt_Model_Validate, but alternative implementations could use entirely different validation strategies.

The Dependency Inversion Principle is fundamental to the Model library's architecture. High-level application code (controllers, converters, validators) depends on the Phprojekt_Model_Interface abstraction rather than on concrete model classes. This inversion enables polymorphic model usage where application code works with any model type through the common interface, and enables testing through the use of mock model implementations. The principle extends to the metadata system where code depends on Phprojekt_ModelInformation_Interface rather than specific metadata providers, enabling alternative metadata sources without affecting model-using code.

The Single Responsibility Principle is reflected in the clear separation of concerns across the library's classes. Phprojekt_Model_Interface is responsible solely for defining the model contract. Phprojekt_Model_Validate is responsible solely for validating model data against constraints. Phprojekt_Model_Converter is responsible solely for transforming models into arrays. Each class has one reason to change: Interface changes if the model contract needs extension, Validate changes if validation rules change, Converter changes if serialization requirements change. This separation ensures that changes in one aspect of model handling don't cascade to unrelated aspects, improving maintainability and reducing coupling between model concerns.

The Law of Demeter is respected in the converter's design, which accesses only the immediate model properties rather than reaching through model relationships to access properties of related models. The converter extracts only the fields defined in the model's own field definitions, representing relationships through ID fields rather than navigating those relationships and including nested converted objects. This approach prevents the converter from having deep knowledge of model relationships and keeps converted structures flat and predictable. If nested representations are needed, they would be constructed at a higher level (such as in specific controller actions) rather than in the generic converter.
